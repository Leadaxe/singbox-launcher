## 1. Два движка ядра

Лаунчер умеет управлять ядром двумя способами. Выбор движка не виден ничему выше
шва: UI, трей, горячие клавиши и Debug API ходят к ядру только через активный
движок (`CoreBackend`).

| | **Classic** | **Daemon (lxd)** |
|---|---|---|
| Платформы | Windows, macOS, Linux | **только macOS** (Windows x64/arm64 — SPEC 141, с ядром v1.14.2-lx.2) |
| По умолчанию | да | нет, включается вручную |
| Как живёт ядро | дочерний процесс `sing-box run` | внутри долгоживущей системной службы `sing-box lxd` |
| Управление | Clash HTTP API | gRPC (`daemon.StartedService`) + admin REST |
| Смена конфига | kill + рестарт процесса | подмена ядра на месте, без рестарта службы |
| Привилегии | macOS: пароль на первый старт TUN за сессию лаунчера; root запускает только root-owned копию ядра (§2.2) | один раз при установке службы, дальше без пароля |
| Выход из лаунчера | гасит VPN | по умолчанию **оставляет VPN работать** |
| Требования к ядру | обычная сборка форка | сборка с сабкомандой `lxd` (`with_lx_command`) |

Реализация: `LegacyBackend` — классический spawn, `DaemonBackend` — lxd. Операции
с группами прокси абстрагированы швом `ProxyTransport` (Clash HTTP для classic,
gRPC для daemon), поэтому список серверов одинаков в обоих режимах.

Build-теги (SPEC 141). Код движка — `DaemonBackend` со стримами DNS, трафика и
tailscale, проба цепочки, классификатор службы и его гейт версий, вердикты
гейта привилегированного старта classic, сопряжение, подготовка конфига,
сборка команд, разводка Debug API — общий для *daemon-платформ*:
`//go:build darwin || (windows && !386)`. Платформенное лежит рядом:
`*_darwin.go` — launchd, plist, цепочка владения по uid (`Stat_t`), ключ кэша
хэшей по dev/inode, рендер sudo, Terminal, тексты диалогов; `*_windows.go` —
заглушки точек расширения, пока нет слоя службы Windows, и до тех пор движок
там закрыт (`daemonEngineAvailable`), лаунчер остаётся на classic. Linux и Win7
(`windows/386`, Go 1.20, `go.win7.mod`) собирают заглушки с тегом
`!darwin && (!windows || 386)`; `tools/win7guard` daemon-файлов не видит.
gRPC-клиент (`internal/lxdclient`, `internal/daemonpb`) и код удалённых машин
(`core/services/lxd_remote_*.go`) тегов не несут и собираются везде.

### 1.1 Где переключается

**Local → ⚙ (настройки подключения) → вкладка LOCAL** — радио Process / Daemon.
Радио выражает *намерение*: выбор Daemon показывает панель с командами ещё до
сопряжения, а фактический движок включается, когда сопряжение готово (это видно
в статусе секции). Переключать движок можно только при остановленном VPN.

Вкладка **REMOTE** того же окна — это прежний remote-override Clash API
(SPEC 064), отдельная от daemon-режима вещь.

## 2. Установка службы: sudo только в вашем терминале

Лаунчер **никогда не выполняет привилегированные операции сам**. Он готовит
готовую sudo-команду и даёт её скопировать или открыть в Терминале; вывод вы
видите целиком, sudo спрашивает вас.

| Операция | Команда |
|---|---|
| Установить или обновить службу | `sudo <ядро-лаунчера> lxd --service=install` |
| Удаление службы | `sudo <ядро-службы> lxd --service=uninstall --keep-copy` |
| Удаление вместе с данными демона | то же `+ --purge` |
| Удаление в **Remove all data…** | `sudo <ядро-службы> lxd --service=uninstall --purge` |
| Выпустить новое приглашение | `sudo <ядро-службы> lxd client add --name singbox-launcher` |

`<ядро-лаунчера>` — ядро, которым пользуется лаунчер (Settings → Storage → Core).
`<ядро-службы>` — root-owned копия службы (§2.1), если служба на ней, иначе ядро
лаунчера. `--keep-copy` (ядро lx.12+) снимает plist и задание launchd, а
копию и её `.install.json` оставляет — её запускает старт TUN в classic (§2.2).
**Remove all data…** предлагает полный uninstall без него: копия уходит вместе с
данными.

`--service=install` не требует параметров: он сам выбирает свободный loopback-порт
(19091+, либо сохраняет адрес уже существующей установки), сам генерирует секрет,
принудительно включает mTLS и печатает в конце **одноразовое приглашение**.

После установки запуск/остановка VPN и применение конфига пароля не требуют.

### 2.1 Служба запускает root-owned копию ядра (SPEC 136)

launchd запускает службу от root. Прежние ядра записывали в
`/Library/LaunchDaemons/com.leadaxe.sing-box-lxd.plist` путь к тому бинарю, которым
вызвали установку, — ядру в бандле или в папке данных. Оба файла принадлежат вашей
учётной записи, так что любая программа, работающая от вашего имени, могла подменить
файл и получить root на ближайшем старте службы.

С ядра **lx.12** команда установки копирует ядро в место, принадлежащее root,
и переписывает plist на копию:

| Что | Где |
|---|---|
| Копия ядра | плоский файл `/Library/PrivilegedHelperTools/sing-box-lxd` (`root:wheel 0755`, ядро lx.12+); каталога службы нет; процесс под root зовётся `sing-box-lxd` |
| Запись установки | `/Library/PrivilegedHelperTools/sing-box-lxd.install.json` (`root:wheel 0644`): источник, sha256, версия, время, plist, метка |

Одна команда на все случаи — первая установка, старый plist на ваши файлы,
обновление ядра: `sudo <ядро-лаунчера> lxd --service=install`. Она идемпотентна
(то же ядро копию не трогает), сохраняет `daemon.json`, секрет и сопряжённых
клиентов и перезапускает службу. После скачивания нового ядра лаунчер показывает
эту команду, а не простой перезапуск: перезапуск поднял бы старую копию.

Лаунчер проверяет службу без sudo и показывает результат на вкладке Status в
настройках подключения LOCAL:

| Состояние | Что значит | Как показано |
|---|---|---|
| не установлена | plist нет | ничего |
| небезопасна | plist не на копию, либо копия, `/Library/PrivilegedHelperTools` или `/Library` — симлинк, не root, или пишутся группой/остальными; plist на раскладку dev-сборок lx.11 (`/Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd/` или плоский `/Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd`) — «legacy layout: install, затем удалить: `sudo rm -rf /Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd /Library/PrivilegedHelperTools/com.leadaxe.sing-box-lxd.install.json`» | красным, с командой; диалог раз на версию лаунчера; WARN в логе перед каждым apply |
| устарела | копия отличается от ядра лаунчера (sha256) или её нет | жёлтым, с командой |
| не запущена | файлы в порядке (plist на безопасную копию, sha256 совпал), но launchd службу не держит: не загружена или `state` ≠ `running` (`launchctl print`, без sudo) | жёлтым, с командой `sudo launchctl bootstrap system /Library/LaunchDaemons/com.leadaxe.sing-box-lxd.plist` — загрузка, а не переустановка |
| процесс устарел | файлы совпали, но работающий демон сообщает другой бинарь (`executable_sha256` из `/admin/info`; у старого ядра — другую версию) | жёлтым, с командой |
| в порядке | служба запускает актуальную root-owned копию | ничего |

Небезопасная служба — громкое предупреждение, но не блокировка: VPN работает, пока
вы не выполните команду. `<ядро-лаунчера> lxd --service=status` (sudo не нужен)
печатает ту же проверку со стороны ядра и сверяет копию с бинарём, который её
запустил: exit 0 — в порядке, 2 — расхождение или небезопасна, 3 — не установлена,
4 — только копия (копия без службы, SPEC 137), 5 — не запущена (состояние у launchd),
1 — ошибка. Установка может занять до ~20 с: ядро ждёт выгрузки старой службы до
10 с и повторяет `bootstrap`. Копия лежит
вне папки данных лаунчера, поэтому **Remove all data…** службу не трогает и
предлагает команду удаления через копию.

### 2.2 Старт TUN в classic запускает ту же копию (SPEC 137)

В classic-движке на macOS конфиг с TUN поднимает ядро от root через системный
запрос пароля (раз за сессию лаунчера). Root запускает только root-owned копию из
§2.1 и системные утилиты по абсолютным путям — никогда файл из папки данных,
бандла или `PATH`:

| Действие | Что запускает root |
|---|---|
| Старт с TUN | `/usr/bin/env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin /bin/sh -c '<постоянное тело>' start-singbox-privileged <data>/bin <копия> config.json /Library/Logs/sing-box-lxd 0 <ваш uid> 2097152` |
| Stop / рестарт | `/bin/kill -TERM <pid шелла> <pid ядра>` |
| Kill в «Sing-Box already running» и в Diagnostics | `/usr/bin/pkill -TERM -f 'sing-box run\|start-singbox-privileged'` |
| Снятие TUN в визарде | ничего — остатки лаунчер удаляет сам |

Тело шелла — константа в бинаре лаунчера, пути приходят аргументами, а `env -i` не
пускает к root-шеллу окружение лаунчера (его `PATH`, экспортированные функции bash).
Скрипт `bin/start-singbox-privileged.sh` прежних версий больше не пишется и
удаляется при следующем старте.

Root ничего не пишет в ваши папки. Вывод ядра идёт в
`/Library/Logs/sing-box-lxd/classic.log` — каталог root (`root:wheel 0755`), а файл
ваш, `0600` (прошлый запуск — `classic.log.old`, тот же владелец): другие локальные
учётные записи его не читают, а подменить его ссылкой нельзя — каталог принадлежит
root. Тело проверяет ваш uid (цифры, не меньше 501, учётная запись существует),
создаёт каталог, не трогает ни каталог, ни файл, если на их месте симлинк, другой тип
или другой владелец (причина отказа попадает в ошибку старта), и ротирует файл
больше 2 МиБ. Лаунчер его только читает:
**Logs → Core** и профайлер трафика следуют за логом последнего старта (старт без
TUN по-прежнему пишет `<logs>/sing-box.log` сам). Снятие TUN удаляет root-owned кэш и
старые логи ядра в папках данных и логов правами самого лаунчера — право удаления
даёт каталог, а не владелец файла, — пароль не спрашивается. **Remove all data…** `/Library/Logs/sing-box-lxd` не удаляет (нужен root):
`sudo rm -rf /Library/Logs/sing-box-lxd`.

До запроса пароля лаунчер без sudo проверяет копию — цепочку владения как в §2.1 и
sha256 копии против ядра лаунчера. Нет копии, она не защищена или устарела
(например, после обновления ядра) — ядро не стартует, диалог показывает одну
команду с кнопками **Copy the command**, **Run in Terminal** и **Retry**:

| Случай | Команда |
|---|---|
| службы демона нет | `sudo <ядро-лаунчера> lxd --service=copy` — ядро lx.12+: только копия и её `.install.json`, без plist и launchd |
| служба демона установлена | `sudo <ядро-лаунчера> lxd --service=install` — команда из §2; обновит ту же копию и перезапустит службу |

После скачивания ядра в логе — WARN с обоими sha256, а ближайший старт с TUN
покажет диалог. При копии без службы `<ядро-лаунчера> lxd --service=status`
выходит с кодом 4 (только копия).

## 3. Сопряжение (mTLS)

Канал к демону — взаимно аутентифицированный TLS. Мандат клиента — его
собственный сертификат; пин серверного сертификата обязателен всегда.

**Приглашение** — одна строка формата:

```
адрес#отпечаток#код
```

Её печатает команда установки (лаунчер извлекает приглашение из вывода
привилегированного вызова, а в свой лог пишет его вырезанным) либо
`lxd client add` — для повторного сопряжения и для удалённых демонов. Приглашение
вставляется в поле сопряжения руками.

**Владение секретами.** Дом демона — его собственный state-каталог: `daemon.json`
с адресом прослушивания и admin-секретом лежит там и отдаётся по
`GET /admin/info`. Лаунчер хранит только свою клиентскую пару. У каждой машины —
**своя** пара: сертификат = полный мандат, и общий ключ на все устройства означал
бы, что отзыв доступа на одном роутере отзывает его везде.

> Из этого следует практическое правило: **удаление машины из списка в лаунчере
> не отзывает доступ**. Отзывать нужно на самой машине — лаунчер об этом
> предупреждает при удалении.

## 4. Удалённые машины

Удалённая машина — роутер, VPS или другой Mac, на котором ядро работает под
`sing-box lxd`, а лаунчер выступает его mTLS-клиентом.

### 4.1 Вкладка Remote

`Local` и `Remote` устроены одинаково — слева список прокси, справа управление.
Разница в том, чем управляем: своим ядром или списком чужих машин. В строке
машины видно имя, платформу, адрес и состояние ядра; там же — **Настроить**
(визард на её профиле), Start/Stop, **Restart ↻** (Stop + Start одним
действием, с подтверждением — VPN у клиентов машины на время рестарта
моргнёт), **Deploy**, правка, удаление и блок «Ещё» (профайлер трафика,
телеметрия хоста, ресурсы, диагностика).

Список узлов машины лечит себя сам. Сразу после Start демон уже отвечает
«started», но ядро внутри ещё поднимается и групп не отдаёт — поэтому группы
опрашиваются в фоне с ретраями, а тик автообновления перечитывает их, если
выбор группы пуст. Пустой список после Stop/Start — переходное состояние на
секунды, а не повод для Disconnect/Connect.

Ключевое свойство: **выбор машины и выбор «для кого собираем» — это один и тот
же выбор**. «Настроить» открывает визард, корневой на профиле этой машины, а
Deploy в той же строке отправляет её собственный конфиг. Промах «собрал для
одной, задеплоил на другую» невозможен по конструкции, а не по проверке.

### 4.2 Запись в реестре

Реестр машин — `bin/remote-daemons.json`. Запись (`services.RemoteDaemon`) несёт:

| Поле | Смысл |
|---|---|
| `id` | стабильный идентификатор (slug имени); он же — имя папки с клиентской парой и с профилем |
| `name` | человекочитаемое имя |
| `addr` | `host:port` управляющего канала |
| `server_fingerprint` | SHA-256 пин серверного сертификата; пусто = plain h2c (dev-демон на loopback) |
| `secret` | Bearer-секрет; нужен только plain-h2c демону — при mTLS мандатом служит клиентский сертификат |
| `goos` / `goarch` | платформа и архитектура **машины** |

`goos`/`goarch` живут именно здесь, а не в состоянии визарда: это свойство
машины, а не одной из её настроек. Строка списка их показывает, визард читает,
генерация собирает из них `TargetSpec` — один источник правды, иначе остаётся
способ собрать конфиг под архитектуру, отличную от показанной в списке.

### 4.3 Профиль на машину — layout на диске

```
bin/
├── wizard_states/
│   ├── state.json                  — состояние визарда ЭТОЙ машины (исторический layout)
│   ├── <name>.json                 — именованные снапшоты local
│   └── remote/
│       └── <machine-id>/           — всё, что принадлежит одной машине
│           ├── state.json          — её состояние визарда
│           ├── config.json         — её собранный конфиг
│           ├── srs/*.srs           — её rule-set'ы
│           └── subscriptions/*.raw — её тела подписок
├── subscriptions/<id>.raw          — raw-кеш подписок local
└── rule-sets/*.srs                 — SRS local
```

До SPEC 098 профиль был один на всех (`wizard_states/remote/state.json` и
`bin/remote-config.json`): настройка второй машины молча затирала первую.
Существующие установки мигрируют автоматически, если сопряжена **ровно одна**
машина; если их несколько — старые файлы остаются нетронутыми с предупреждением
в логе, потому что определить владельца невозможно.

### 4.4 Deploy

Deploy отправляет не только JSON. Перед отправкой собираются ресурсы, на которые
конфиг ссылается — локальные rule-set'ы (`route.rule_set` с `type: local`) и тела
подписок, — и уезжают в ресурсное хранилище машины вместе с конфигом
(`services.CollectDeployResources`).

Конфиг перед отправкой адаптируется под демон: относительные пути, которые ядро
пишет само (`cache_file`), абсолютизируются в каталог демона (демон стартует с
`cwd=/`), а `experimental.clash_api` удаляется — у конфига машины Clash API нет
by design.

Доставка — admin REST `POST /admin/apply`: демон валидирует конфиг **сабпроцессом**
до того, как тронуть работающий инстанс, и автоматически откатывается на последний
рабочий конфиг, если новый не стартовал. Start/Stop — через `/admin`.

Вся цепочка «ресурсы строго раньше конфига» — одна функция
`services.RemoteRegistry.Deploy`: её зовут и кнопка Deploy, и Debug API
(SPEC 100), поэтому «через API деплоится не так, как кнопкой» невозможно по
построению.

### 4.5 Наблюдаемость машины

| Инструмент | Источник | Что показывает |
|---|---|---|
| Список прокси | gRPC (`ProxyTransport`) | группы, выбор узла, задержки, пул балансировщика |
| Профайлер трафика | gRPC-стримы (`SubscribeConnections`, `SubscribeDNSQueries`, `SubscribeStatus`) | соединения и домены **ядра** машины; вместо разбивки по процессам — по клиентам сети |
| Телеметрия хоста | admin REST | CPU, память, хранилище, сеть **самой машины** |
| Ресурсы | admin REST | ресурсное хранилище машины (rule-set'ы, тела подписок) |

Профайлер и окно телеметрии — **по экземпляру на машину**: две машины должны
открываться рядом, ради сравнения такие вещи и смотрят. Повторное открытие
фокусирует существующее окно, а не поднимает второй стрим; экземпляр гаснет
вместе с каналом (при Disconnect и при удалении машины).

gRPC-подписки переживают Deploy/Start/Stop. Пересоздание инстанса ядра на
машине рвёт server-side стримы — транспорт это считает штатным событием:
сбрасывает состояние, ждёт пару секунд и переподписывается, пока подписку не
отменят (`runResilientStream`). Профайлер и статус продолжают показывать
живые данные без ритуала Disconnect/Connect.

Разбивки по процессам у машины нет и не может быть: `find_process` в конфиге
роутера выключен, потому что трафик идёт от устройств сети, а не от процессов
этого компьютера.

## 5. Remote в Debug API (SPEC 100)

Весь remote/daemon-функционал доступен и без UI — через тот же Debug API
лаунчера (loopback + bearer). Полный справочник с примерами — в
[API.md](API.md); здесь — принципы.

- **Stateless-адресация.** Каждый вызов явно называет машину —
  `/remote/machines/{id}/…`: реестр и сопряжение, health, Start/Stop/rollback
  ядра, deploy, зеркала state-ручек визарда, наблюдаемость, ресурсы.
  UI-понятие «активной машины» (Connect на вкладке Remote) на рабочие вызовы
  не влияет; сам override управляется отдельными ручками `/remote/ui*` и
  меняет только то, на что смотрит вкладка Servers.
- **Паритет с кнопкой.** Деплой через API и кнопкой Deploy — одна и та же
  цепочка `services.RemoteRegistry.Deploy` (§4.4).
- **Стримы — снапшотами.** `connections`, `dns/queries`, `logs` отдают окно
  (`?duration=…&max=…`), не вечный стрим; SSE-подписки сознательно отложены.
- **Raw passthrough.** Произвольный admin-REST-вызов (`…/raw/rest`) и
  произвольный gRPC-вызов (`…/raw/grpc`, discovery — `GET /grpc/methods`)
  уходят **только** на управляющий канал сопряжённой машины, с её
  mTLS-ключами и пином из реестра. Запросов на произвольные адреса нет.
- **`/daemon/*` (darwin).** Статус, сопряжение и движок локального демона,
  плюс готовые строки привилегированных команд (`/daemon/commands`) — API их
  никогда не исполняет: «sudo только в вашем терминале» действует и здесь.
- **Манифест `capabilities`.** `GET /` сообщает, какие группы есть на этой
  сборке: Win7 — без remote, вне darwin — без `/daemon/*`.

## 6. Границы и требования

- **Classic не меняется.** Тот же spawn, тот же Clash API, то же поведение.
- **Daemon — пока только macOS.** Код движка общий для daemon-платформ
  (`darwin || (windows && !386)`, §1); на Windows он закрыт до слоя службы
  SPEC 141 и ядра v1.14.2-lx.2; Linux и Win7 собирают заглушки.
- **Ядро должно уметь `lxd`** (`with_lx_command`). Пин `constants.RequiredCoreVersion`
  (актуальный пин — в `internal/constants/constants.go`) эту сборку включает. Проверять границу фичи следует
  запуском бинаря (`sing-box lxd --help`), а не по номеру релиза.
- **Root-owned копии нужно ядро lx.12+.** С ядром лаунчера ниже lx.12 (или
  неизвестной версии) лаунчер не даёт команд install и copy вовсе — такое ядро
  вернуло бы plist на собственный файл лаунчера (lx.11 — на раннюю раскладку) — и
  вместо них просит сначала обновить ядро: вкладка «Локально» →
  «Скачать/Переустановить» (`service_state` `core_too_old`).
- **Clash API у remote-конфига нет** by design — отсюда и gRPC-источники для
  списка узлов и профайлера.
