# Служебные файлы поверх Taildrop

Нормативно. Константы — `registry/service_files.json`; в тексте они названы
именами ключей (`name_prefix`, `max_bytes`, `ttl_seconds`, `kinds`). Контракт
1.1.148 (ключ разрешения — 1.1.149, чувствительный клип — 1.1.153), TASKS_LXBOX §144, §145. Заменяет `CLIPBOARD.md` (`lxclip-*`, 1.1.146): тот
протокол не реализовала ни одна сторона, миграции нет.

## 1. Что это

LxBox и лаунчер передают друг другу команды — «положи текст в буфер», «открой
ссылку» — обычным файлом Taildrop. Получатель-наш-продукт разбирает файл,
выполняет разрешённые команды и удаляет файл; во входящие служебный файл не
попадает. Официальный клиент Tailscale видит обычный файл `.json`.

Транспорт — Taildrop ядра sing-box-lx (gRPC `StartedService`:
`SubscribeTaildropInbox`, `SendTaildropFiles`, `DownloadTaildropFile`,
`DeleteTaildropFile`). Своего канала, порта и подписи нет: спаривания и
подписи нет по решению владельца 02.11.2026; доверие — tailnet (по умолчанию
Taildrop ходит между устройствами одного пользователя) плюс разрешения
получателя (§5).

## 2. Имя

`lx-<время>-<метка>.json`, например `lx-20261102T143005Z-k3x9p.json`:

- время — UTC отправителя, `name_time_format`;
- метка — `name_label_length` случайных символов `[a-z0-9]`; имя должно быть
  уникальным: одинаковое имя с одинаковым содержимым ядро склеивает с уже
  лежащим файлом, и новой отметки приёма не появляется;
- хеша содержимого нет.

Получатель опознаёт **кандидата** по `name_prefix` и `name_suffix`, а не по
точному виду: при совпадении имён ядро может переименовать файл. Время из имени
для возраста не используется (§6) — только для порядка при равном времени
приёма.

## 3. Тело

JSON в UTF-8 без BOM, не больше `max_bytes` байт:

```json
{"lx": 1, "commands": [
  {"kind": "clipboard", "text": "…"},
  {"kind": "open_url", "url": "https://…"}
]}
```

- `lx` — версия формата, из `versions`.
- `commands` — непустой список, выполняется по порядку.
- Команда — объект с `kind` и полями вида (`kinds.<kind>.fields`).

## 4. Кандидат или обычный файл

Кандидат остаётся **обычным файлом входящих** (не трогается, видим человеку),
если: тело больше `max_bytes`; не валидный UTF-8 / JSON; `lx` нет или он не из
`versions`; `commands` нет или это не список. Иначе файл — **служебный**.

## 5. Разрешения

У получателя на каждое устройство и каждый вид команды: «Clipboard from
<устройство>», «Links from <устройство>». По умолчанию выключены, в бэкап не
входят. Ключ разрешения — `senderID` записи `TaildropFile` (stable node ID
пира, тот же, что у `TaildropReceivingFile.senderID`; ядро с SPEC 149 §4,
контракт 1.1.149); если он пуст (ядро старше) — `senderName` (`ComputedName`
пира). Разрешение, выданное по имени, при появлении `senderID` к нему не
привязывается само: имя меняется, а устройство с тем же именем — другое.
Оба поля ядро держит в памяти: после перезапуска ядра у лежащих файлов они
пусты, и разрешение не находится.

## 6. Обработка служебного файла

По кадру входящих (`TaildropInbox`), до автосохранения и до уведомления
«принят»:

1. **Возраст** = часы получателя минус `modifiedAt` (mtime файла на диске
   получателя после приёма, секунды). Старше `ttl_seconds` — команды не
   выполняются.
2. **Команды** — по порядку. Неизвестный `kind` пропускается, остальные
   выполняются. Команда без разрешения (§5) пропускается.
   - `clipboard` — `text` не пустой; один ведущий U+FEFF снимается; переводы
     строк как есть. Если в пачке служебных файлов несколько `clipboard`,
     в буфер идёт последний по `modifiedAt` (при равенстве — по времени в
     имени).
   - `open_url` — схема из `kinds.open_url.schemes`, иначе пропускается. Как
     открыть (сразу или через уведомление) — решение стороны.
3. **Удаление** (`DeleteTaildropFile`) — ВСЕГДА после разбора, даже если ни
   одна команда не выполнена (нет разрешения, просрочен, все `kind`
   неизвестны).

Если приложение получателя не подключено к ядру, файлы лежат во входящих
ядра; при подключении обработка идёт по тем же пунктам, и п.1 отсекает
залежавшееся.

## 7. Отправитель

1. Цель — пир с `CanReceiveFiles`; выбирает человек.
2. Не отправляет и называет причину: пустой `text`; тело больше `max_bytes`;
   не UTF-8.
3. Чувствительный клип (на Android — `ClipDescription.EXTRA_IS_SENSITIVE`)
   не отправляется без показа человеку. Сторона, которая показывает текст
   перед отправкой и шлёт его только по действию человека, может его
   отправить (решение владельца 03.11.2026, контракт 1.1.153).
4. Отправка — только действием человека. Выполненная команда никогда не
   отправляется дальше автоматически: петли нет.

## 8. Что не входит

Не-текстовые клипы, история буфера, подпись и спаривание, подтверждение
доставки, команды кроме `kinds`.
