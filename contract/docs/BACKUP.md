# BACKUP — семантика LX Backup (контракт 0.12.0)

Нормативно. Схема — `schema/backup.schema.json`. **Идеи и инварианты — в
[`BACKUP_PRINCIPLES.md`](BACKUP_PRINCIPLES.md) (П1–П7); при конфликте с этим
документом побеждает он.** Здесь — «как»: поля, их поддержка сторонами и
процедуры импорта.

## 1. Что такое файл бэкапа

Файл — **сериализация состояния экспортирующего приложения** в общей схеме
(П1). Ничего сверх состояния в нём нет: ни блобов «на провоз», ни теневых
карманов. Следствия, которыми меряется реализация:

- экспорт — чистая функция состояния: два неотличимых состояния дают
  байт-идентичные файлы;
- состояние после импорта неотличимо от настроенного руками;
- `import(export(x))` в том же приложении = `x`.

**Непонятое отбрасывается с предупреждением** (П3): импортёр читает то, что
понимает, остальное называет пользователю warning'ом и в состояние не кладёт.
**Legacy-путей чтения нет** (П4): схема одна — текущая; старый файл
разбирается тем же общим правилом.

Колонка «Поддержка»: **обе** — поле означает одно и то же у launcher и LxBox;
**launcher** / **LxBox** — поле есть только у одной стороны, вторая обязана
отбросить его с warning, а не провозить.

### `subscriptions[].identity`

Чем подписка представляется провайдеру при запросе тела. Вложенный объект, а
не плоские ключи записи: это ОДНА настройка из нескольких частей, и
вложенность не даёт им расползтись по корню подписки, где они смешались бы с
полями самого источника.

| Ключ | Тип | Поддержка | Смысл |
|---|---|---|---|
| `user_agent` | string | обе | User-Agent ИМЕННО этой подписки; пусто — дефолт приложения |
| `send_hwid` | bool | обе | отправлять ли заголовки идентификатора устройства |
| `hwid` | string | обе | идентификатор устройства для этой подписки; пусто — глобальный |
| `device_os` | string | lxbox | имя ОС в заголовках |
| `ver_os` | string | lxbox | версия ОС в заголовках |
| `device_model` | string | lxbox | модель устройства в заголовках |
| `hash_device_model` | bool | обе | хэшировать ли модель устройства |

Все ключи необязательны, и **отсутствие ключа значит «как в системе», а не
«выключено»**: пустой `user_agent` — это «слать дефолт приложения», и
принимающая сторона, применив пустую строку как значение, затёрла бы свой
дефолт. У булевых ключей то же самое: нет ключа — «как в системе», `false` —
«явно не отправлять».

Настройка не косметическая: провайдеры **ветвят выдачу по UA**, и та же
ссылка на новой машине отдаст другой набор узлов.

Ключи, которых принимающая сторона не применяет (чужие `device_*` и всё
незнакомое), отбрасываются **одним** предупреждением
`backup_source_identity_dropped` на подписку с перечнем ключей: потеря у
пользователя одна, а не по строке на ключ. Пустой объект `identity`
предупреждений не даёт — предупреждают о том, что не доехало, а не о факте
наличия поля.

### Папки

Папка — контейнер **одиночных серверов**, общий для обеих сторон. Отдельной
секции у неё нет намеренно: собственных данных, кроме имени, она не несёт, а
вторая секция потребовала бы держать два места в согласии. Вместо этого
запись `servers[]` носит поле `folder` — имя папки, и обе стороны собирают
контейнер **по этому имени**.

Нормативны две вещи:

- **порядок членов** — порядок записей в файле: пользователь раскладывал узлы
  сам, и перетасованный после переноса состав это расхождение;
- **одно имя = одна папка**: второй встреченный `folder: "Proton"` дополняет
  уже собранную, а не заводит тёзку. Пустое имя (или отсутствие ключа) — это
  корень списка, а не безымянная папка.

В файл НЕ едут настройки самой папки (политика тегов, свёртка, общий detour) и
её члены, которых `servers[]` выразить не может — цепочки и неразобранные
записи. Это граница формы, а не забывчивость: потеря объявляется на экспорте
кодом `backup_local_only_dropped`, одним предупреждением на папку с перечнем.
Подписки и цепочки в папку не кладутся — поля `folder` у них нет.

### `directions[]`

Каноническая форма `direction.schema.json` — не внутренняя структура
приложения: у сторон они разные, а переносится модель. Та же таблица
действует для локальных Направлений источника `subscriptions[].outbounds[]`:
форма у них одна.

| Поле | Тип | Поддержка | Смысл |
|---|---|---|---|
| `tag` | string | обе | единственное имя Направления и цель правил (обязательное) |
| `enabled` | bool (`true`) | обе | выключенное не материализуется и не предлагается целью |
| `filter` | string | обе | ТЕЛО регулярки по итоговому тегу узла, без обёртки и флагов |
| `invert` | bool | обе | оставить узлы, НЕ совпавшие с `filter` |
| `default` | string | обе | ТЕЛО регулярки; первый совпавший узел становится умолчанием |
| `include_direct` | bool | обе | предложить прямое соединение опцией внутри Направления |
| `include_block` | bool | обе | предложить блокировку опцией внутри Направления |
| `include` | array строк | обе | прочие теги, добавляемые в Направление списком |
| `interrupt_exist_connections` | bool | обе | рвать существующие соединения при смене выбора |
| `auto` | `{mode, url, interval, tolerance, idle_timeout, interrupt_exist_connections, pool, pool_tolerance, sticky_hash}` | обе | параметры парной urltest-группы `<tag>-auto`; отсутствие ключа = автовыбора нет |

**Канонизация — с потерями.** Внутренняя запись Направления богаче канона, и
поля, которых в каноне нет, в файл не едут — ни в `directions[]`, ни в
`subscriptions[].outbounds[]`. Полный перечень цены — §10.

### `rules[]`, `dns`, `vars`, `route`, `warp[]`

| Поле | Поддержка | Смысл |
|---|---|---|
| `rules[].kind` | обе | `inline\|srs\|preset\|json`; чужой `kind` пропускается с warning |
| `rules[].num` | обе | общая ось порядка; импортёр перенумеровывает, сохраняя относительный порядок |
| `rules[].outbound`, `ref`, `name`, `vars`, `match`, `enabled` | обе | |
| `rules[].dns`, `rules[].resolve` | LxBox | лаунчер отбрасывает с warning |
| `dns.servers[]`, `dns.rules[]`, `dns.final`, `dns.strategy` | обе | тела переносятся только у `kind=user` |
| `vars` | обе | только `portable=true` из реестра |
| `route.final` | обе | символическая ссылка (§3) |
| `warp[]` | обе | `type: wg\|masque` + snake_case поля регистрации |

**Финальные конфиговые теги в файл не пишутся никогда** (П5) — они
вычисляются каждой сборкой на принимающей стороне.

## 3. Символические ссылки на outbound-цели

`rules[].outbound` и `route.final` переносятся как есть.

Цели едут вместе с правилами: `directions[]` содержит Направления в
канонической форме (`schema/direction.schema.json`). На импорте они
разбираются ПЕРВЫМИ и пополняют список известных целей, поэтому правило, чья
цель приехала в том же файле, приходит **рабочим**, а не выключенным.

Имя Направления ровно одно — `tag` (контракт 0.9.0). Ключ `label` в записи
Направления схемой не предусмотрен: приехавший — неизвестное поле, которое
импортёр отбрасывает с warning (П3), а не подставляет куда-нибудь.

Отбор узлов переносится ТЕЛОМ регулярного выражения без обёртки и флагов:
язык паттернов у сторон различается (`/re/i` в лаунчере, `RegExp` в LxBox),
а тело одинаково. Регистр не учитывается на обеих сторонах.

Если тег Направления на принимающей стороне уже занят, приехавшее **не
применяется** (warning `backup_direction_exists`): у пользователя там свои
настройки под этим именем. Правила при этом находят цель — тег совпадает.

Если целевой тег не существует и не приехал в файле (неизвестный preset id
вне `registry/presets.json`, ссылка на удалённое Направление):

- правило импортируется **выключенным** с warning;
- `route.final` **не применяется** с warning.

Причина именно такая: включённое правило с мёртвой целью заставляет ядро
отвергнуть весь конфиг, то есть одно потерянное правило лишило бы
пользователя VPN целиком.

## 4. Цепочки хопов

Запись `chains[]` — это `tag`, канон цепочки в поле `chain`
(`schema/source_chain.schema.json`) и необязательная обвязка из таблицы §2.

*Идентичность и merge — по `tag`* (П5). Занятый тег не перезаписывается: у
пользователя там свои настройки, и своя одноимённая цепочка сильнее
приехавшей. Пропуск предъявляется warning'ом `backup_chain_exists`
**всегда** — молчаливое «своя победила» скрыло бы случай тёзок. Тег
применённой цепочки пополняет список известных целей: правило, метящее в
цепочку из того же файла, приходит рабочим.

*Тег — не стабильный идентификатор, и это осознанная цена.* Он меняется
переименованием и уникализируется на сборке при коллизии. Следствия:

- цепочка, переименованная на другой стороне, приедет ВТОРОЙ записью рядом
  со своей — теги разошлись, и распознать их как одну и ту же нечем;
- две несвязанные цепочки, случайно названные одинаково на разных
  устройствах, при merge считаются одной: приехавшая не применяется.

Поле `id` в записи есть (ссылки `detour_node_source_id` должны находить
цепочку после переноса), но идентичностью при merge оно не является: сущности
адресуются тегом (П5), и заводить второй ключ, расходящийся с первым, значило
бы иметь две несогласуемые модели merge в одном формате.

*Порядок записей нормативен* и не сортируется ни на экспорте, ни на импорте:
вложенная цепочка вправе стоять позицией только у цепочки, объявленной НИЖЕ
её по списку, — этим исключены циклы. Импорт разбирает `chains[]` ПОСЛЕ
`directions[]` (позиция может ссылаться на Направление) и ДО `rules[]`
(правило может метить в цепочку как в цель).

*Достижимость позиций `hops` на импорте не проверяется:* хоп — чаще всего
узел подписки, который материализуется только после её обновления, и честной
проверки в момент импорта не существует. Цепочка ввозится как есть; рубеж у
обеих сторон один — сборка конфига, где цепочка с недостающей позицией
деградирует целиком с внятной причиной (`chain_hop_missing`), не роняя
остальной конфиг. Изобретать импортное «выключить на всякий случай» сторонам
запрещено — поведение разъедется.

## 5. Disabled-отметки

Перенос **по идентичности узла** (`IDENTITY.md` §1 — тег в рамках источника,
SPEC 112); значения — unix seconds, импортёр конвертирует в свой нативный
формат (Go int64 / Dart ISO-8601). Для формата обмена ключ непрозрачен: он
копируется как есть.

Ключи формы **64 lowercase hex** — legacy-хеши, снятые до SPEC 112: они
переживают перенос как есть и мигрируют на приёмнике при первом разборе
источника (`IDENTITY.md` §5.1). Импортёр их не отбрасывает и не пытается
трактовать.

Честные ограничения: отметки нод, патченных mobile import-rules, и нод,
схлопнутых по SNI, на другой стороне не совпадут — истекают по штатному TTL.
Отметка узла, переименованного провайдером между снятием и импортом, не
сопоставится (имя и есть идентичность).

## 6. Ссылка detour на узел

Ссылка едет ОБЪЕКТОМ (`docs/IDENTITY.md` §2.1): `detour_node_source_id` — id
источника-цели, `detour_node_tag` — identity-тег узла внутри него,
`detour_node_label` — подпись для UI.

Финальный конфиговый тег наружу не выезжает намеренно (П5): на приёмнике у
источника-цели свои `tag_prefix`/`tag_mask`, и хранимый тег приехал бы
мёртвым. Id источников roundtrip переживают — они пишутся полем `id` записи,
так что ссылка на своей же машине восстанавливается тождественно.

Упразднённый `detour_node_hash` (релизы v1.5.x) в схему **не входит**. Старый
файл с ним читается общим правилом П3: остальные поля применяются, ключ
отбрасывается с warning, ссылка по хешу теряется — задокументированная цена
разрыва (П4), а не баг.

## 7. Секреты

Открытым текстом — by design (граница доверия — локальная машина, как в
state.json / lxbox_settings.json). Шифрование архива — вне scope;
предупреждение при экспорте обязательно.

## 8. Версионирование

`lx_backup: 1` — мажор формата. Импортёр отклоняет бо́льшую мажорную версию
с понятной ошибкой («обновите приложение»), меньшую — читает.

## 9. Режимы импорта

Импорт работает в одном режиме — **replace**: разделы источников и правил
замещаются приехавшими целиком, DNS и warp следуют тому же правилу. Прежний
режим merge (дописывание к существующему) удалён: он не был достижим ни из
одного UI и потому не проверялся ничем, кроме собственных тестов, а
перенумерация оси порядка в нём переписывала номера уже стоявших правил,
включая якорные зоны шаблона. Возвращать его следует не флагом, а вместе с
инвариантом «файл = ось» из SPEC 113-C: перенумеровывать только
пользовательскую зону, якоря не трогать.

Дедуп внутри одного файла при этом никуда не делся: занятый тег Направления
или цепочки пропускается с warning (§3, §4) — это защита от тёзок внутри
приезжающего файла и от совпадения с тем, что уже создано более ранними
секциями того же импорта.

**Факт сторон на 02.09.2026 — ЖДЁТ РЕШЕНИЯ владельца (не норма).** Лаунчер:
replace раздела целиком, как записано выше. LxBox сегодня: **слияние по URL
подписки** — локальные источники, которых нет в файле, остаются; совпавшая по
URL подписка получает настройки файла (identity, имя, префикс, интервал),
отметки disabled объединяются; правила и DNS замещаются. Как записан §9
(«режим один — replace») это расхождение. Владелец решает: переписать §9 как
«replace у лаунчера, слияние у LxBox — `extension: mobile`» либо перевести
LxBox на replace. До решения норма §9 не меняется (см. D-089).

## 10. Что изменилось против 0.10.x

**Механизм `extensions` упразднён целиком** (П3). Его больше нет ни в схеме,
ни в экспорте, ни в импорте — ни на корне, ни внутри записей.

| Было (0.10.x) | Стало (0.11.0) |
|---|---|
| `extensions.launcher.{id, skip, outbounds, node_tag, fold, exclude_from_global, expose_group_tags_to_global, detour_tag, detour_node_*}` | те же имена — НЕОБЯЗАТЕЛЬНЫЕ поля самих записей (§2) |
| `extensions.lxbox` провозится нетронутым до следующего экспорта | не провозится: непонятое отбрасывается с warning |
| непонятые поля записи хранились в состоянии и возвращались при re-export | не хранятся: состояние после импорта неотличимо от настроенного руками |
| `subscriptions[].skip` — boolean (LxBox) | `skip` — список фильтров отсева (launcher); булев `skip` отбрасывается с warning `backup_field_type_mismatch`, остальные поля записи и весь остальной файл применяются. Это ЕДИНСТВЕННАЯ коллизия типов между версиями, и разбор обязан быть к ней терпим: уронить файл целиком из-за одного поля значило бы потерять всё прочее молча, вопреки П6 |
| `subscriptions[].detour` / `servers[].detour` — объект (LxBox) | `detour_tag` + `detour_node_*` (launcher); объектный `detour` отбрасывается с warning |
| `extensions.launcher.detour_node_hash` | в схему не входит; отбрасывается с warning |
| цепочки могли читаться из блоба `extensions.launcher.chains` (релизы v1.5.0–v1.5.1) | единственный путь — секция `chains[]`; блоб отбрасывается с warning |
| `additionalProperties: false` на большинстве уровней | `true` везде: схема не валит чужой файл, отбрасывает импортёр (П3) |

**Цена разрыва.** Файл, снятый версией 0.10.x, читается — общие поля
применяются, — но всё, что лежало в `extensions`, теряется:

- у файла, снятого ЛАУНЧЕРОМ: `id` источников, `skip`, локальные `outbounds`,
  `node_tag` серверов, `fold`, `exclude_from_global`,
  `expose_group_tags_to_global`, `detour_tag`, ссылки detour-на-узел и
  legacy-цепочки из блоба. Практически: после восстановления такого файла эти
  настройки нужно проставить руками; ссылки detour, потерявшие `id`
  источника-цели, придётся выбрать заново;
- у файла, снятого LXBOX: его mobile-only содержимое (папки, import-rules,
  identity-override) не применяется и не провозится обратно.

Обо всём этом импортёр обязан сказать: `extensions` любой глубины даёт **один
warning на файл** с перечнем затронутых записей, прочие неизвестные ключи —
warning с именем ключа и сущности (П6). Молчаливых потерь нет.

### Цена канонизации источников

Второй ряд потерь, у другой границы: не «канон беднее записи», а «в схеме нет
дома». Все они названы предупреждениями — молчаливых потерь нет (П6).

**Не едут в файл вовсе** (предупреждение на ЭКСПОРТЕ,
`backup_local_only_dropped`):

| Внутреннее поле | Что теряется |
|---|---|
| `relays_in_directions` (подписка) | предлагать ли служебные узлы подписки (релеи BYPASS) в выборе Направлений. На маршрут не влияет (релей материализуется всегда), но список целей после restore будет другим. У LxBox такой развилки нет вовсе |
| `tag_policy`, `replace`, `detour` (папка) | настройки САМОЙ папки: в схеме у неё есть ровно имя, потому что собственных данных, кроме него, она не несёт (§«Папки») |
| члены папки не-server | цепочка внутри папки и неразобранная запись: секция `servers[]` их не выражает, а положить цепочку в `chains[]` значило бы вынуть её из папки молча. Перечисляются видом и тегом: `Работа: chain hop-1` |

Предупреждение перечисляет **только заданные** поля, одной строкой на
сущность: `Liberty: relays_in_directions`, `Работа: tag_policy, replace`.
Односторонне заводить эти ключи в схеме нельзя — это вернуло бы ровно тот
тайный груз, ради сноса которого убран механизм `extensions` (П1/П3).
Настройки восстанавливают руками.

UA и HWID-семейство подписки сюда больше НЕ входят: с контрактом 0.12 они
едут объектом `identity` (§«`subscriptions[].identity`»), и код
`backup_source_identity_dropped` остался за ключами этого объекта —
«поле есть, но здесь не применяется». Два разных разговора с пользователем:
«такого поля в общем формате нет» и «формат его знает, а эта сторона нет».

**Едут в файле, но не применяются на импорте** (предупреждение на ИМПОРТЕ):

| Поле контракта | Код | Что происходит |
|---|---|---|
| `exclude_from_global`, `expose_group_tags_to_global` | `backup_source_flag_dropped` | класс флагов упразднён (SPEC 118); узлы источника остаются в общем пуле кандидатов. Прежнее поведение даёт свёртка источника в группу |
| `label` у `servers[]` / `chains[]` | `backup_label_dropped` | **LEGACY-ВХОД**: с контрактом 0.12 поля в схеме нет, оно читается для файлов 0.11 и раньше. У канона v7 имени, кроме тега, нет: узел зовут его тегом (SPEC 112). Подпись, разошедшаяся с тегом, отбрасывается; у сервера без `node_tag` она ещё может стать тегом — тогда потери нет и предупреждения тоже. Экспорт `label` в этих секциях не пишет вовсе. На `label` ПОДПИСКИ правило не распространяется: это имя источника, ссылочного тега в паре с ним нет |
| ключи `identity`, которых сторона не знает | `backup_source_identity_dropped` | mobile-only `device_os`/`ver_os`/`device_model` и всё незнакомое: один warning на подписку с перечнем |

Флаги и `label` объявлены в типах контракта, поэтому общий разбор неизвестных
ключей их не ловит — предупреждение ставится отдельно, иначе они пропадали бы
совсем молча. Внутрь `identity` общий обход тоже не спускается намеренно:
иначе одна потеря давала бы два предупреждения разными кодами.

Полный словарь кодов бэкапа с указанием стороны эмиссии — в
`registry/backup_warnings.json`.

### Цена канонизации Направлений

Отдельное ограничение, не связанное с разрывом 0.10.x → 0.11.0: оно
существовало для `directions[]` и раньше и действует на обе секции, где
Направление встречается (`directions[]` и `subscriptions[].outbounds[]`).

Переносится каноническая модель `direction.schema.json`, а внутренняя запись
Направления богаче. При экспорте **не переносятся**:

| Внутреннее поле | Что теряется |
|---|---|
| `ref` + `updates` | привязка к пресету/шаблону и стек патчей. Ссылочная запись экспортируется MERGED-телом: у принимающей стороны нет ни нашего шаблона, ни наших пресетов, и тонкая ссылка приехала бы туда пустой оболочкой. После импорта Направление — обычное, «прямое»; связь с пресетом восстанавливается только вручную |
| `comment` | заметка пользователя |
| `options`, кроме `interrupt_exist_connections` | прочие опции селектора |
| ключи `filters`, кроме `tag` | отбор узлов по чему-либо, кроме итогового тега |
| `type` | импорт всегда ставит `selector`: тип не объявлен в каноне, и других значений в переносимой модели нет |
| `invert` у `preferredDefault` | `default` едет ТЕЛОМ регулярки; инверсия умолчания не переносится (у `filter` — переносится, ключом `invert`) |

**Переносятся**, вопреки первому впечатлению, `addOutbounds` и
`preferredDefault`: первое — признаками `include_direct` / `include_block` и
списком `include` (тег блокировки и прямого соединения у сторон свой, и
переносить его буквально значило бы сослаться на чужое имя), второе — телом
регулярки в `default`.

Значение `tolerance` / `pool_tolerance`, заданное ссылкой на переменную
шаблона (`@urltest_tolerance`), в файл не едет: у принимающей стороны свой
шаблон, где это имя может не значить ничего. В файле оказывается `0` —
«не задано», и приёмник берёт собственное умолчание.

Практически: восстановленное из бэкапа Направление ведёт трафик так же, но
теряет связь с пресетом, заметку и нестандартные фильтры. Заново их ставят
руками.

Правильный путь переноса на 0.11.0 — снять бэкап **новой** версией
приложения: она пишет всё то же самое общими полями схемы, и roundtrip снова
тождественен.
