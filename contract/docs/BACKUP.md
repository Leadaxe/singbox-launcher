# BACKUP — семантика LX Backup (контракт 1.0.0)

Статус: **норма контракта 1.0.0** (D-109, D-110). Схема действующего формата —
`schema/backup.schema.json` (`lx_backup: 2`); схема предыдущего —
`schema/backup-0.12.schema.json` (`lx_backup: 1`), заморожена для
legacy-чтения. **Идеи и инварианты — в
[`BACKUP_PRINCIPLES.md`](BACKUP_PRINCIPLES.md) (П1–П7); при конфликте с этим
документом побеждает он.** Здесь — «как»: поля, их поддержка сторонами и
процедуры импорта.

## 1. Что такое файл бэкапа

Файл — **сериализация состояния экспортирующего приложения** в общей схеме
(П1). С контрактом 1.0 это стало буквальным: записи файла — ТЕ ЖЕ записи, что
лежат в состоянии, с теми же именами полей. Маппера между «формой файла» и
«формой состояния» больше нет, и потому поле не может забыться в конверторе:
добавленное в состояние едет в файл само.

Ничего сверх состояния в файле нет: ни блобов «на провоз», ни теневых
карманов. Следствия, которыми меряется реализация:

- экспорт — чистая функция состояния: два неотличимых состояния дают
  байт-идентичные файлы;
- состояние после импорта неотличимо от настроенного руками;
- `import(export(x))` в том же приложении = `x`.

**Тонкий слой** остался ровно там, где у контракта уже было своё имя или где
поле по смыслу не едет. Перечень закрыт и зафиксирован обеими сторонами
14.09.2026: `directions[]` (форма `direction.schema.json` — в ней живут поля
LxBox, которых в модели лаунчера нет), `fold` (форма
`source_fold.schema.json` — в состоянии свёртка зовётся иначе, и двух имён в
одном файле быть не должно), `disabled{}` (форма 0.12 — у LxBox по ней живёт
TTL-очистка отметок), `vars` (только переносимые имена), `route{final}`,
`warp[]` (сырой JSON). Всё остальное — имена полей состояния без
переименований.

**Непонятое отбрасывается с предупреждением** (П3): импортёр читает то, что
понимает, остальное называет пользователю warning'ом и в состояние не кладёт.

**Запись — только 1.0, чтение — оба мажора** (D-110). С синхронных релизов
(лаунчер 1.6.0, LxBox 2.23.3) обе стороны пишут только `lx_backup: 2`; выбора
формата на экспорте нет ни у одной. `lx_backup: 1` (0.x) читается обеими
сторонами **всегда** — это legacy-вход для файлов, которые уже у
пользователей на руках, а не срок (П4). Схема 0.12
(`schema/backup-0.12.schema.json`) заморожена для legacy-чтения: её не правят
и по ней не пишут. Окно «два писателя, дефолт 0.12», которое держали стороны
до синхронных релизов, отменено тем же решением.

**Чужое объявленное игнорируется МОЛЧА.** Поле объявлено в схеме; каждая
сторона применяет то, что умеет, а остальное игнорирует без предупреждения и
по возможности провозит сырым JSON до следующего экспорта. Это не «непонятое»
(П3), а чужое объявленное — предупреждение давало бы шум на каждом импорте;
провоз допустим, но не обязателен. Кто что применяет — колонка **«Поддержка»**
в таблицах §2 (`лаунчер` / `LxBox` / `обе`). Правило действует только на поля,
которые схема называет прямо: незнакомый ключ, которого в схеме нет,
по-прежнему даёт warning (П3/П6).

## 2. Таблица полей

Колонка «Поддержка»: **обе** — поле означает одно и то же у launcher и LxBox;
**launcher** / **LxBox** — поле применяет только названная сторона. Вторая
сторона поступает с ним по правилу §1: объявленное в схеме игнорирует молча и
по возможности провозит; отбрасывать с warning обязана только незнакомый
ключ, которого в схеме нет.

Таблицы ниже описывают **формат 1.0** (`lx_backup: 2`). Поля формата 0.12
здесь не повторяются: соответствие ключей старого и нового формата — §11,
схема старого — `schema/backup-0.12.schema.json`.

### `sources[]` — общая часть узла

Эти поля несёт любая корневая запись вида `server` и `chain`, а также узлы
внутри папки (`sources[].nodes[]` — та же форма).

**Корневых видов узла два, внутри папки — четыре.** `auto` (провайдерская
группа) и `unsupported` (неразобранная запись тела) бывают только членами
папки. Корневая провайдерская группа в состоянии законна, но `sources[]` её
не выражает: писатель такую запись не пишет и говорит об этом
`backup_source_kind_unsupported` (вид и число узлов — отдельными полями),
читатель отвергает приехавшую тем же кодом. Схема их и не объявляет —
`$defs/sourceServer` знает `server\|chain`, `$defs/node` — все четыре.

| Поле | Тип | Поддержка | Смысл |
|---|---|---|---|
| `kind` | корень `server\|chain`; в папке ещё `auto\|unsupported` | обе | вид записи. В корне `sources[]` бывают ещё `folder` и `subscription` (свои таблицы ниже). `unsupported` — запись тела, которую разобрать не удалось: она не исчезает, а занимает своё место с `origin.raw` и `reason` |
| `tag` | string | обе | СЫРОЙ тег узла — его единственное имя и идентичность (SPEC 112). В корне он же финальный; внутри контейнера финальный получается наложением `tag_policy` |
| `enabled` | bool | обе | участвует ли узел в сборке; пишется всегда, в том числе `false` |
| `origin` | `{kind, raw, sub_url?}` | обе | чем узел был до разбора: `kind` ∈ `uri\|wg_ini\|json`, `raw` байт в байт. Отсутствие = создан руками с нуля |
| `body` | object | обе | тело записи в форме sing-box как есть. `server` — outbound целиком БЕЗ ключей `tag` и `detour` (они поля записи); `chain` — настройки маршрута без позиций. Контракт тело не типизирует намеренно: состав ключей задаёт ядро |
| `detour` | `{folder_id?, tag}` | launcher | через кого дозваниваться (§6) |
| `hops[]` | array `{folder_id?, tag}` | обе | `chain` only: позиции в порядке пакета, ближний хоп первым (§4) |
| `group` | `{group_type, default?, members[], strategy?}` | обе | `auto` only: провайдерская группа `selector\|urltest` со своим составом |
| `service` | bool | launcher | узел приехал служебной частью чужой записи (релей BYPASS внутри конфига другого узла), а не отдельной позицией списка |
| `reason` | string | обе | `unsupported` only: почему запись не разобралась, текстом парсера |
| `sections` | object | обе (launcher применяет, LxBox — по ## 13) | фрагмент конфига, который узел носит с собой; форма и норма — `NODE_SECTIONS.md`, см. ниже |

**`id` у члена папки нет.** Он поле КОРНЕВОЙ записи, а не узла: схема
объявляет его в `$defs/sourceServer` (и у контейнеров), но не в `$defs/node`,
и в состоянии он живёт на `state.Source`, а не на `state.Node`. У корневых
`server`/`chain` он есть и означает следующее.

| Поле | Тип | Поддержка | Смысл |
|---|---|---|---|
| `id` | string | обе | ULID КОРНЕВОЙ записи (у членов папки его нет). Ссылкой у узловых видов не является — ссылки идут по тегу, — но переживает перенос, чтобы повторный импорт того же файла не заводил дубль |

**Состав подписки в файл не едет.** `nodes[]` у неё нет: это кэш выдачи
провайдера, он пересоберётся первым обновлением. Вместе с ним не едут
метаданные выдачи и история обновлений — рантайм конкретной машины. Это не
потеря и предупреждения не даёт: переносится подписка, а не её слепок.

### `fold` и `fold_tag`

Объект `fold` — форма контракта (`source_fold.schema.json`), и своего тега он
не несёт: в 0.11 имя группы было **позиционным деривативом** «префикс тегов, а
при пустом — `<номер>:`» (D-081), потому что свёрнутая секция была одна —
`subscriptions[]`.

В 1.0 дериватив не работает дважды. Во-первых, номер считается среди подписок,
а свёртка есть и у папки: папка и первая свёрнутая подписка получали ОДИН и
тот же `1:select`, то есть двух владельцев одного outbound-тега. Во-вторых,
явное имя (`Proton-select`) дериватив подменял молча, и правило того же файла
метило в цель, которой на приёмнике уже нет.

Поэтому 1.0 везёт имя ЯВНО — ключом `fold_tag` рядом с `fold`, а не внутри
него: форму контракта 0.11 трогать не за что. Читатель: `fold_tag` главнее,
дериватив остаётся запасным ходом для файла, где `fold_tag`'а нет (чужая
сторона, пишущая только `fold`).

### `sources[].identity`

Чем подписка представляется провайдеру при запросе тела. Вложенный объект, а
не плоские ключи записи: это ОДНА настройка из нескольких частей, и
вложенность не даёт им расползтись по корню подписки, где они смешались бы с
полями самого источника. В состоянии v8 она хранится тем же объектом — файл и
здесь повторяет состояние.

| Ключ | Тип | Поддержка | Смысл |
|---|---|---|---|
| `user_agent` | string | обе | User-Agent ИМЕННО этой подписки; пусто — дефолт приложения |
| `send_hwid` | bool | обе | отправлять ли заголовки идентификатора устройства |
| `hwid` | string | обе | идентификатор устройства для этой подписки; пусто — глобальный |
| `device_os` | string | LxBox | имя ОС в заголовках |
| `ver_os` | string | LxBox | версия ОС в заголовках |
| `device_model` | string | LxBox | модель устройства в заголовках |
| `hash_device_model` | bool | обе | хэшировать ли модель устройства |

Все ключи необязательны, и **отсутствие ключа значит «как в системе», а не
«выключено»**: пустой `user_agent` — это «слать дефолт приложения», и
принимающая сторона, применив пустую строку как значение, затёрла бы свой
дефолт. У булевых ключей то же самое: нет ключа — «как в системе», `false` —
«явно не отправлять».

Настройка не косметическая: провайдеры **ветвят выдачу по UA**, и та же
ссылка на новой машине отдаст другой набор узлов.

Ключи, которых принимающая сторона не применяет (чужие `device_*` и всё
незнакомое), отбрасываются **одним** предупреждением
`backup_source_identity_dropped` на подписку с перечнем ключей: потеря у
пользователя одна, а не по строке на ключ. Пустой объект `identity`
предупреждений не даёт — предупреждают о том, что не доехало, а не о факте
наличия поля. Правило одинаково для обоих входов: файл 1.0 с mobile-only
ключами разбирается так же, как файл 0.x.

### `sources[].sections`

Фрагмент конфига, который узел носит с собой (SPEC 121/122, D-101/D-102):
route-правила и DNS-записи, живущие и умирающие вместе с ним. Норма —
[`NODE_SECTIONS.md`](NODE_SECTIONS.md); здесь только то, что касается файла.

| Поле | Тип | Поддержка | Смысл |
|---|---|---|---|
| `rules[]` | array правил | обе | route-правила узла в КОРНЕВОЙ форме (`rules[]` ниже); `kind` только `inline\|srs` |
| `dns.servers[]` | array DNS-серверов | обе | DNS-серверы узла в корневой форме; `kind` только `user` |
| `dns.rules[]` | array DNS-правил | обе | DNS-правила узла в корневой форме; `kind` только `user` |

Форма записей — **та же, что в корне файла**: узловое правило отличается от
корневого только тем, где оно лежит. Это и есть «одно пространство имён»;
второй набор ключей у тех же сущностей был бы возвратом к маппингу.

`@self` целой строкой и `@{self}` внутри строки = финальный тег ЭТОГО узла;
хранится как есть, подставляет сборка. В корневых `rules[]` и `dns` этих
записей нет — их дом здесь, и общая у них только ось порядка (`num`).

Секции есть только у узлов `kind: server`. Поле `sections` у записи, которой
оно не положено (подписка, цепочка, группа, `unsupported`), отбрасывается с
`backup_section_record_dropped`; тем же кодом отбрасывается запись чужого вида
внутри секций. Секции подписочных узлов не сохраняются вовсе — сторона
сообщает об этом уровнем info, без кода контракта (`NODE_SECTIONS.md` §5, E1).

**В формате 0.12 секций нет**: писатели 0.12 их не писали (потерю называл
код `backup_local_only_dropped` с полем `sections`), а с D-110 формат 0.12 не
пишет ни одна сторона. Поле в схеме 0.12 объявлено ради чтения файлов,
которые успели написать dev-сборки; подробности — §11.

### `directions[]`

Каноническая форма `direction.schema.json` — не внутренняя структура
приложения: у сторон они разные, а переносится модель. Форма не менялась при
переходе на 1.0: это одно из исключений тонкого слоя (§1).

| Поле | Тип | Поддержка | Смысл |
|---|---|---|---|
| `tag` | string | обе | имя Направления и цель правил (обязательное) |
| `label` | string | LxBox | отображаемая подпись Направления. Лаунчер игнорирует молча (имя у него — тег) и на экспорте не пишет; целью правил не является — ссылки идут на `tag` |
| `ping_url` | string | LxBox | URL замера доступности узлов Направления **в приложении** (бюджет пинга/URLTest клиента, D-096). Лаунчер игнорирует молча и провозит. Не путать с `auto.url` — параметром urltest-группы ядра |
| `ping_timeout_ms` | integer > 0 | LxBox | таймаут одного замера узла Направления в приложении, мс (D-096). Лаунчер игнорирует молча и провозит. Не путать с `auto.idle_timeout` |
| `enabled` | bool (`true`) | обе | выключенное не материализуется и не предлагается целью |
| `filter` | string | обе | ТЕЛО регулярки по итоговому тегу узла, без обёртки и флагов |
| `invert` | bool | обе | оставить узлы, НЕ совпавшие с `filter` |
| `default` | string | обе | ТЕЛО регулярки; первый совпавший узел становится умолчанием |
| `include_direct` | bool | обе | предложить прямое соединение опцией внутри Направления |

| `include` | array строк | обе | прочие теги, добавляемые в Направление списком |
| `interrupt_exist_connections` | bool | обе | рвать существующие соединения при смене выбора |
| `auto` | `{mode, url, interval, tolerance, idle_timeout, interrupt_exist_connections, pool, pool_tolerance, sticky_hash}` | обе | параметры парной urltest-группы `<tag>-auto`; отсутствие ключа = автовыбора нет |

**Канонизация — с потерями.** Внутренняя запись Направления богаче канона, и
поля, которых в каноне нет, в файл не едут. Полный перечень цены — §10.

Локальных Направлений источника (`subscriptions[].outbounds[]` формата 0.12) в
1.0 нет: класс упразднён SPEC 118, и дома у них в новой форме не появилось.

### `rules[]`

Правило маршрута в форме состояния. Главное отличие от 0.12: матчеры и **цель**
живут одним куском в `body` — ровно так, как их понимает ядро; разобранной
пары `match` + `outbound` больше нет.

принимающей стороной (лаунчером) они **игнорируются молча** — см. правило §1.

Таблица говорит, КАКИЕ поля едут и кто их применяет; ЧТО импорт делает с уже
стоящей записью — предмет §9 (`rules[]` замещаются целиком, `dns` и `warp[]`
сливаются «своё сильнее», `vars` и `route.final` — по своим правилам).

**Финальные конфиговые теги в файл не пишутся никогда** (П5) — они
вычисляются каждой сборкой на принимающей стороне.

## 3. Символические ссылки на outbound-цели

Цель правила (ключ `outbound` **внутри** `body`, см. §2) и `route.final`
переносятся как есть.

Цели едут вместе с правилами: `directions[]` содержит Направления в
канонической форме (`schema/direction.schema.json`). На импорте они
разбираются ПЕРВЫМИ и пополняют список известных целей, поэтому правило, чья
цель приехала в том же файле, приходит **рабочим**, а не выключенным.

Целью правил Направление зовут ровно одним именем — `tag` (контракт 0.9.0).
Необязательный ключ `label` — отображаемая подпись, **Поддержка: LxBox**
(контракт 0.12.4, D-094): LxBox его пишет и читает, лаунчер игнорирует молча
(имя у него — тег) и на экспорте не пишет. Неизвестным полем `label` больше не
считается — он объявлен в схеме, — и warning не даёт ни у одной стороны. `tag`
он не подменяет: ссылки правил идут на `tag`.

Отбор узлов переносится ТЕЛОМ регулярного выражения без обёртки и флагов:
язык паттернов у сторон различается (`/re/i` в лаунчере, `RegExp` в LxBox),
а тело одинаково. Регистр не учитывается на обеих сторонах.

Если тег Направления на принимающей стороне уже занят, приехавшее **не
применяется** (warning `backup_direction_exists`): у пользователя там свои
настройки под этим именем. Правила при этом находят цель — тег совпадает.

Если целевой тег не существует и не приехал в файле (неизвестный preset id
вне `registry/presets.json`, ссылка на удалённое Направление):

- правило импортируется **выключенным** с warning;
- `route.final` **не применяется** с warning.

Причина именно такая: включённое правило с мёртвой целью заставляет ядро
отвергнуть весь конфиг, то есть одно потерянное правило лишило бы
пользователя VPN целиком.

## 4. Цепочки хопов

Цепочка — запись `sources[]` вида `kind: chain`. Настройки маршрута лежат в
`body` (состав `source_chain.schema.json` минус позиции), позиции — отдельным
полем `hops[]`: они ссылки, а не значения, и в теле им делать нечего.

**`hops[]` — массив ссылок формы `{folder_id?, tag}`** (та же форма, что у
`detour`, §6). `folder_id` пуст или отсутствует → адресуется КОРНЕВОЕ
пространство финальных тегов; заполнен → ULID контейнера машины-экспортёра, и
импортёр переписывает его по карте id (§6). Поле необязательно: LxBox
адресует хоп тегом и пустой `folder_id` читает как корень — это законная
запись, а не потеря.

*Идентичность и merge — по `tag`* (П5). Занятый тег не перезаписывается: у
пользователя там свои настройки, и своя одноимённая цепочка сильнее
приехавшей. Пропуск предъявляется warning'ом `backup_chain_exists`
**всегда** — молчаливое «своя победила» скрыло бы случай тёзок. Тег
применённой цепочки пополняет список известных целей: правило, метящее в
цепочку из того же файла, приходит рабочим.

*Тег — не стабильный идентификатор, и это осознанная цена.* Он меняется
переименованием и уникализируется на сборке при коллизии. Следствия:

- цепочка, переименованная на другой стороне, приедет ВТОРОЙ записью рядом
  со своей — теги разошлись, и распознать их как одну и ту же нечем;
- две несвязанные цепочки, случайно названные одинаково на разных
  устройствах, при merge считаются одной: приехавшая не применяется.

Поле `id` в записи есть, но идентичностью при merge оно не является: ссылочные
сущности адресуются тегом (П5), и заводить второй ключ, расходящийся с первым,
значило бы иметь две несогласуемые модели merge в одном формате. (У папки —
наоборот: там `id` первичен, потому что на него ссылаются, а имён-тёзок
пользователь вправе завести сколько угодно, §9 п. 3.)

*Порядок записей нормативен* и не сортируется ни на экспорте, ни на импорте:
вложенная цепочка вправе стоять позицией только у цепочки, объявленной НИЖЕ
её по списку, — этим исключены циклы. Импорт разбирает цепочки ПОСЛЕ `directions[]`
(позиция может ссылаться на Направление) и ДО `rules[]` (правило может метить
в цепочку как в цель).

*Достижимость позиций `hops` на импорте не проверяется:* хоп — чаще всего
узел подписки, который материализуется только после её обновления, и честной
проверки в момент импорта не существует. Цепочка ввозится как есть; рубеж у
обеих сторон один — сборка конфига, где цепочка с недостающей позицией
деградирует целиком с внятной причиной (`chain_hop_missing`), не роняя
остальной конфиг. Изобретать импортное «выключить на всякий случай» сторонам
запрещено — поведение разъедется.

## 5. Disabled-отметки

Перенос **по идентичности узла** (`IDENTITY.md` §1 — тег в рамках источника,
SPEC 112); значения — unix seconds, импортёр конвертирует в свой нативный
формат (Go int64 / Dart ISO-8601). Для формата обмена ключ непрозрачен: он
копируется как есть.

Ключи формы **64 lowercase hex** — legacy-хеши, снятые до SPEC 112: они
переживают перенос как есть и мигрируют на приёмнике при первом разборе
источника (`IDENTITY.md` §5.1). Импортёр их не отбрасывает и не пытается
трактовать.

Честные ограничения: отметки нод, патченных mobile import-rules, и нод,
схлопнутых по SNI, на другой стороне не совпадут — истекают по штатному TTL.
Отметка узла, переименованного провайдером между снятием и импортом, не
сопоставится (имя и есть идентичность).

## 6. Ссылка detour на узел

Ссылка едет ОБЪЕКТОМ `detour: {folder_id?, tag}` — той же формы, что позиция
цепочки `hops[]` (§4). `folder_id` пуст или отсутствует → адресуется КОРНЕВОЕ
пространство финальных тегов; заполнен → ULID папки или подписки, внутри
которой живёт узел с сырым тегом `tag`.

Финальный конфиговый тег наружу не выезжает намеренно (П5): на приёмнике у
контейнера-цели своя `tag_policy`, и хранимый финальный тег приехал бы
мёртвым. Адресуется сырой тег — идентичность узла в рамках источника
(SPEC 112).

**`folder_id` — ULID машины-экспортёра, и импорт его переписывает.** Карта
строится на разборе `sources[]`: контейнер файла, совпавший с локальным,
отдаёт локальный `id`; заведённый заново — берёт `id` из файла. Все
`detour.folder_id` и `hops[].folder_id` проходят через эту карту, поэтому
ссылка переживает перенос на чужую машину, где ULID'ы другие. На своей же
машине она восстанавливается тождественно — `id` контейнеров roundtrip
переживают.

Ссылка, чей контейнер в файле не нашёлся, **ввозится как есть**: импорт её не
снимает и предупреждения не даёт — по тому же правилу, что позиция цепочки
`hops[]` (§4, «цепочка ввозится как есть»).

Так сделано намеренно, и обе стороны обязаны поступать одинаково. Импорт не
знает, чем ссылка станет: папка с таким `id` может приехать следующим файлом
или уже лежать на машине под другим именем. А снять `detour` значило бы тихо
пустить узел НАПРЯМУЮ — то есть подменить решение пользователя об
анонимности, не сказав ни слова. Недостижимая цель — вопрос СБОРКИ, и там она
разбирается fail-closed (`detour` — единая строгость, SPEC 077 упразднён; хоп
— `chain_hop_missing`), где видно и настоящую топологию, и то, что узел
выключен целиком, а не молча выпрямлен. Изобретать импортное «снять на всякий
случай» сторонам запрещено — поведение разъедется.

Упразднённый `detour_node_hash` (релизы v1.5.x) в схему **не входит**. Старый
файл с ним читается общим правилом П3: остальные поля применяются, ключ
отбрасывается с warning, ссылка по хешу теряется — задокументированная цена
разрыва (П4), а не баг. Плоская тройня 0.12 (`detour_tag`,
`detour_node_source_id`, `detour_node_tag`) читается legacy-входом и
превращается в тот же объект — §11.

## 7. Секреты

Открытым текстом — by design (граница доверия — локальная машина, как в
state.json / lxbox_settings.json). Шифрование архива — вне scope;
предупреждение при экспорте обязательно.

## 8. Версионирование

`lx_backup` — мажор формата, целое число: **`1`** — семейство 0.x,
**`2`** — контракт 1.0. Различаются форматы ровно им, одним сравнением ещё до
разбора тела; строковой версии в корне нет намеренно — два способа сказать
«какой это формат» разошлись бы.

Импортёр **отклоняет бо́льшую мажорную версию** с понятной ошибкой («обновите
приложение») и никогда не разбирает её частично: файл 1.0, прочитанный
читателем, который знает только `1`, потерял бы всё, что не совпало по именам,
и сделал бы это молча. Меньшую версию читает всегда — это legacy-вход (§1).
Пишется только `2` (D-110).

Значение вне `{1, 2}` — отказ: файл либо не наш, либо из будущего.

## 9. Импорт — слияние по идентичности

Режима «заменить всё» **нет** и флага режима нет (D-095). **Источники всегда
сливаются по идентичности**; полной замене подлежит ровно одна секция —
`rules[]`. Норма одна на обе стороны.

**Слияние одно на оба формата.** Файл 1.0 и файл 0.x различаются только
разбором: каждый вход превращает записи файла в записи состояния, а дальше
работает ОДИН код слияния по правилам ниже. Второй набор правил для старого
формата означал бы две расходящиеся модели импорта в одном приложении.

Почему у источников слияние, а у правил замена: у каждой записи источника
есть собственная идентичность, по которой две стороны узнают одно и то же
(адрес подписки, тело сервера, тег ссылочной сущности). У правил такой
идентичности нет — есть общая **ось порядка** с абсолютными номерами, у
каждой стороны своими, и «долить» чужие правила означало бы перенумеровать
уже стоявшие, включая якорные зоны шаблона (SPEC 113-C, «файл = ось»).

### Норма слияния

**1. Подписки — по `url`.** Ключ — `url` **байт в байт**, без всякой
нормализации: строку не трогают ни `TrimSpace`, ни приведение регистра
хоста, ни выравнивание слэша и порядка query. Любая нормализация обязана
совпасть у двух реализаций посимвольно, иначе одна сторона сольёт записи, а
вторая заведёт вторую подписку на тот же адрес; ввод и экспорт у обеих
сторон и так хранят адрес подрезанным.

Совпала → локальная запись **остаётся**: её `id`, состав узлов со всеми
отметками, история обновлений и диагностика. Из файла применяются её
**настройки** — каждая сторона те, что умеет: имя (**только непустое**:
отсутствие поля значит «эта сторона имени не носит», а не «сотри своё»),
`enabled`, `tag_policy`, `update.*`, `max_nodes`, `skip`, свёртка
(`fold` + `fold_tag`), `detour`, `relays_in_directions`, `identity`.

Набор применяемых настроек **зависит от формата файла**, и это не
непоследовательность, а следствие П7. В 1.0 у подписки есть дом у всех
перечисленных полей, и совпавшая запись берёт их из файла целиком. В 0.12
части из них (`relays_in_directions`, настройки папки) в записи нет вовсе, и
применить их «ноль» значило бы стереть локальную настройку импортом старого
файла — поэтому вход 0.x эти поля не трогает.

`identity` применяется **слепком целиком**: отсутствие объекта `identity` =
сброс на «как в системе» (пустой UA, пустой HWID, `send_hwid` и
`hash_device_model` — «не задано»). Оставить прежний UA при отсутствующем
объекте значило бы сохранить настройку, которую пользователь на той машине
снял.

Отметки `disabled` — **объединение**: свои не перетираются, приехавшие
доливаются. Отметка «этот узел мне не нужен» — решение, принятое на
конкретной машине, и файл с другой её не отменяет. Тег, который есть среди
уже загруженных узлов, применяется сразу; остальные ждут первого
достоверного fetch (вердикт O2).

Не совпала → добавляется. Локальные подписки, которых в файле нет, остаются.

**2. Корневые серверы — по ТЕЛУ.** Дедуп против существующих **корневых**
серверов (в 0.12 это записи `servers[]` без поля `folder`, в 1.0 — записи
`sources[]` вида `server`). Тело берётся из **исходника записи** — `origin.raw`
(в 0.12 это `uri` либо `config_json`), а не из материализованного `body`.
Порядок обязателен: у живущей на машине записи материализованное тело уже есть
(его дала сборка или обновление), а у только что приехавшего URI-сервера его
ещё нет, и сравнение «материализованного с исходником» никогда не совпадёт —
один и тот же сервер удваивался бы на каждом импорте. Материализованное `body`
— ключ только у записи, у которой исходника нет вовсе (узел, созданный руками
с нуля).

Тело — это:

- `origin.kind: uri`: `origin.raw` после `TrimSpace` и **без фрагмента
  `#имя`** (отрезается всё от первого `#`, затем `TrimSpace`). Фрагмент у
  share-URI — это имя узла, а не часть тела: тот же сервер с другим `#` — та
  же запись;
- `origin.kind: json` (и `body` у записи без исходника): **канонический JSON**
  — верхнеуровневые `tag` и `detour` сняты, ключи объектов отсортированы
  рекурсивно, пробелов нет, текст — сырой UTF-8 без HTML- и
  юникод-экранирования. Это ровно нормальная форма identity-хэша (D-007).
  Снятие `tag`/`detour` симметрично отрезанному у URI фрагменту: имя узла и
  путь дозвона к нему телом сервера не являются;
- `origin.kind: wg_ini` сравнивается **текстом как есть**: разбирать INI ради
  ключа нечем, а `#` там начинает комментарий строки и отрезать по нему
  нельзя.

**Тег в сравнении не участвует** ни в одном из двух случаев: у одиночного
узла тег — локальное имя, и тот же сервер, переименованный на другой
машине, обязан узнаться, иначе каждый импорт плодил бы его копию.

Совпало → **пропуск без warning**: это не потеря, а «у тебя уже есть».
Иначе запись добавляется, а её тег уникализируется против занятых имён
корневого пространства (теги корневых узлов + теги Направлений + теги замен
папок/подписок) суффиксом `-2` — той же формой, что у ручного добавления.

**Исключение — `sections`.** Совпавшее тело означает «тот же узел», но
секции (SPEC 121) телом не являются, и пропустить их значило бы потерять
ровно ту связку, ради которой бэкап и делали. Поэтому: поле `sections` в
файле **есть** → оно **замещает** локальные секции этого узла целиком
(настройки файла сильнее локальных, как у подписки); поля **нет** →
локальные секции остаются нетронутыми. Поштучного слияния записей нет:
у них не существует ключа, по которому их можно было бы сопоставить.
Полная замена `rules[]` (п. 7) правил узла не касается — они лежат внутри
`sources[].sections` со своими позициями на оси и приезжают вместе со своим
узлом; перенумерация оси при этом общая (п. 7).

**3. Папки — сперва по `id`, затем по имени; члены — по телу.**

В 1.0 у папки есть собственная запись и в ней `id`, поэтому ключ слияния
двухступенчатый: сначала ищется папка с тем же `id` (это та же папка, как бы
её ни переименовали), и только если такой нет — папка с тем же именем (это
та же папка, приехавшая с ЧУЖОЙ машины, где ULID'ы другие). Имя сравнивается
**как есть**: без подрезки и с учётом регистра («DE» и «de » — две разные
папки).

По имени матчатся **только папки, существовавшие до импорта**. Папка,
заведённая этим же импортом из файла, по имени больше не находится: иначе
вторая папка-тёзка ФАЙЛА дописалась бы в первую, и состав двух разных папок
слился бы в одну. UI обеих сторон допускает тёзок, и «одно имя = одна папка»
как единственное правило было нормой формата 0.12, где `id` у папки нет.

В 0.12 папка выражена полем `folder` записи `servers[]`, `id` у неё нет, и
там действует прежнее правило «одно имя = одна папка» без ступени по `id`.

Настройки самой папки (`tag_policy`, `fold`/`fold_tag`, общий `detour`) у
совпавшей записи берутся **из файла** — как у подписки, и с той же оговоркой
про формат: у 0.12 этих полей нет, и вход 0.x их не трогает.

Члены дедупятся по телу (правило 2) **в пределах этой папки** — один и тот же
сервер в двух разных папках законен, и схлопывать такую раскладку импорт не
вправе. Ссылочные члены без тела (`chain`, `auto`) ключуются **тегом**, как в
корне: тела у них нет, и сравнивать нечего. Существующие члены остаются на
местах, новые дописываются **в конец** в порядке файла, тег уникализируется
внутри папки.

**4. Цепочки и Направления — по тегу.** Совпадение **точное, с учётом
регистра** (теги ядра регистрозависимы); пространство тегов общее с
Направлениями и тегами замен. Занятый тег → приехавшая запись **не
применяется**: цепочка с `backup_chain_exists`, Направление с
`backup_direction_exists` (§3, §4). Это ссылочные сущности — на их имя метят
правила, и второго владельца у имени быть не может; перезапись стёрла бы
настройки, сделанные на этой машине. Warning ставится ВСЕГДА, даже когда
«своя победила»: молчание скрыло бы случайных тёзок.

**5. DNS — слияние «своё сильнее»; `vars` и `route.final` — как были.**

- **DNS-серверы** сливаются по ключу `kind`+`tag`, а у `kind: preset` — по
  `kind`+`ref`: тега у ссылочной записи нет вовсе, её идентичность это `ref`.
  Ключ `kind`+`tag` без учёта `ref` схлопывал бы ВСЕ preset-серверы в один, и
  все, кроме первого, пропадали бы молча как «своё сильнее». **DNS-правила** —
  по `kind`+`ref`+телу (своего имени у правила нет, и различить два правила
  можно только тем, что они делают). Совпавшая запись остаётся **локальной**,
  несовпавшая дописывается **в конец** в порядке файла. Не замена, потому
  что список резолверов собран под сеть пользователя, и снести его чужим
  файлом значило бы молча поменять человеку разрешение имён. `dns.final`,
  `dns.strategy` и `dns.default_domain_resolver` — все три одиночных значения
  секции — **замещаются** файлом: это не список, и «слить» два
  взаимоисключающих ответа нечем. Правило одно на всю тройку, и перечень здесь
  закрытый: пропуск третьего скаляра означал бы, что писатель кладёт ключ в
  файл, а читатель теряет его молча.
- **`vars`** — применяются только переносимые имена; остальные пропускаются
  с `backup_var_skipped` (непереносимое имя на другой машине значит другое).
- **`route.final`** — замещает **только при известной цели**, иначе
  `backup_final_dropped`: маршрут по умолчанию в несуществующий outbound
  роняет конфиг ядра целиком.

**6. `warp[]` — добавление.** Аккаунт совпал по ключу → **локальный
остаётся**, приехавший пропускается **молча**; иначе добавляется. Ключ —
`device_id`, а при его отсутствии приватный ключ: это то, чем регистрация
опознаётся у провайдера. Аккаунт WARP привязан к ключу, и затереть здешний
приехавшим значило бы осиротить узлы, которые на нём стоят. У LxBox
аккаунты — слоты по типу; у лаунчера тоже (WG и MASQUE), поэтому «добавить»
там означает «занять пустой слот».

**7. `rules[]` — единственная секция ПОЛНОЙ ЗАМЕНЫ.** Порядок — порядок
файла, номера оси каждая сторона проставляет свои. Правило с неизвестной
целью приезжает **выключенным** с `backup_unknown_outbound`, а не теряется и
не роняет конфиг.

**Перенумерация оси — общая для корневых и узловых правил.** Ось `num` одна
на всё состояние, и правила из `sources[].sections.rules[]` встают на неё
вместе с корневыми. Норма нумерации, одна на обе стороны:

- **один проход** по размеченным правилам файла — корневым `rules[]`
  (включая `preset`) и `sections.rules[]` узлов вместе — в порядке их `num`
  из файла;
- нумерация **сплошная**: правило на позиции `i` этого порядка (с нуля)
  получает `1000 + i`;
- `rules[]` замещаются целиком, поэтому локальные правила с приехавшими **не
  перемешиваются** — перемешивать нечего;
- номера шаблона применяются только к пресетам, которых в файле **нет**
  (досев при загрузке); пресет, приехавший файлом, держит номер из
  перенумерации.

Относительный порядок сохраняется, абсолютные номера — нет: зоны шаблона
(0, 945, 950 …) после импорта не восстанавливаются, и системная голова
оказывается в пользовательской зоне. Это семантика 0.12, названная здесь
вслух, чтобы вторая сторона не изобрела своей (кейс корпуса
`order_renumbered_preserving_sequence`): сохранять абсолютные номера значило
бы переносить чужую раскладку шаблона на свой.

**Секции узла: файл замещает.** Поле `sections` в записи узла **есть** → оно
замещает локальные секции этого узла целиком; поля **нет** → локальные секции
остаются нетронутыми. Поштучного слияния записей нет: у них не существует
ключа, по которому их можно было бы сопоставить. Запись чужого вида внутри
секций (`kind: preset` у правила, `template`/`preset` у DNS) отбрасывается с
`backup_section_record_dropped`, остальные записи узла применяются; тем же
кодом отбрасывается поле `sections` у записи, которой оно не положено.

**8. Порядок и `id`.** Совпавшие записи **сохраняют локальную позицию**;
новые встают **в конец**, в порядке файла. Совпавшая запись держит
**локальный `id`**. `id` в файле необязателен: у новой записи он берётся из
файла, если есть и не занят, иначе минтится свежий — два источника с одним
`id` дали бы двух владельцев одной адресации.

### Отчёт импорта

Счётчики применённого раскладываются по видам события: добавлено, обновлено,
пропущено. Одного числа «применено» после перехода на слияние мало —
«добавлено 3» и «обновлено 3» для пользователя разные новости, а
«пропущено» вообще не потеря и warning'а не даёт.

Раскладка: добавленные и обновлённые подписки, добавленные и пропущенные
корневые серверы, добавленные и обновлённые папки, добавленные цепочки. Папки
считаются обновлёнными только для формата 1.0: у 0.12 собственной записи у
папки нет, обновлять там нечего.

## 10. Что изменилось против 0.10.x (исторически, внутри 0.x)

Раздел описывает разрыв **внутри семейства 0.x** (`lx_backup: 1`) и остаётся
в силе для legacy-входа. Переход на формат 1.0 — следующий раздел.

**Механизм `extensions` упразднён целиком** (П3). Его больше нет ни в схеме,
ни в экспорте, ни в импорте — ни на корне, ни внутри записей.

| Было (0.10.x) | Стало (0.11.0) |
|---|---|
| `extensions.launcher.{id, skip, outbounds, node_tag, fold, exclude_from_global, expose_group_tags_to_global, detour_tag, detour_node_*}` | те же имена — НЕОБЯЗАТЕЛЬНЫЕ поля самих записей (§2) |
| `extensions.lxbox` провозится нетронутым до следующего экспорта | не провозится: непонятое отбрасывается с warning |
| непонятые поля записи хранились в состоянии и возвращались при re-export | не хранятся: состояние после импорта неотличимо от настроенного руками |
| `subscriptions[].skip` — boolean (LxBox) | `skip` — список фильтров отсева (launcher); булев `skip` отбрасывается с warning `backup_field_type_mismatch`, остальные поля записи и весь остальной файл применяются. Это ЕДИНСТВЕННАЯ коллизия типов между версиями, и разбор обязан быть к ней терпим: уронить файл целиком из-за одного поля значило бы потерять всё прочее молча, вопреки П6 |
| `subscriptions[].detour` / `servers[].detour` — объект (LxBox) | `detour_tag` + `detour_node_*` (launcher); объектный `detour` отбрасывается с warning |
| `extensions.launcher.detour_node_hash` | в схему не входит; отбрасывается с warning |
| цепочки могли читаться из блоба `extensions.launcher.chains` (релизы v1.5.0–v1.5.1) | единственный путь — секция `chains[]`; блоб отбрасывается с warning |
| `additionalProperties: false` на большинстве уровней | `true` везде: схема не валит чужой файл, отбрасывает импортёр (П3) |

**Цена разрыва.** Файл, снятый версией 0.10.x, читается — общие поля
применяются, — но всё, что лежало в `extensions`, теряется:

- у файла, снятого ЛАУНЧЕРОМ: `id` источников, `skip`, локальные `outbounds`,
  `node_tag` серверов, `fold`, `exclude_from_global`,
  `expose_group_tags_to_global`, `detour_tag`, ссылки detour-на-узел и
  legacy-цепочки из блоба. Практически: после восстановления такого файла эти
  настройки нужно проставить руками; ссылки detour, потерявшие `id`
  источника-цели, придётся выбрать заново;
- у файла, снятого LXBOX: его mobile-only содержимое (папки, import-rules,
  identity-override) не применяется и не провозится обратно.

Обо всём этом импортёр обязан сказать: `extensions` любой глубины даёт **один
warning на файл** с перечнем затронутых записей, прочие неизвестные ключи —
warning с именем ключа и сущности (П6). Молчаливых потерь нет.

### Цена канонизации источников — ТОЛЬКО формат 0.12

Второй ряд потерь, у другой границы: не «канон беднее записи», а «в схеме нет
дома». Все они названы предупреждениями — молчаливых потерь нет (П6).

**В формате 1.0 этого ряда потерь НЕТ.** Дом появился у каждого из
перечисленных полей (§2, §11), и `backup_local_only_dropped` писатель 1.0 не
эмитирует вовсе. Таблица ниже описывает писателя 0.12 — исторически: с D-110
формат 0.12 не пишет ни одна сторона, а таблица объясняет, почему в уже
выпущенных файлах 0.12 этих полей нет.

**Не едут в файл 0.12 вовсе** (предупреждение на ЭКСПОРТЕ,
`backup_local_only_dropped`):

| Внутреннее поле | Что теряется | Дом в 1.0 |
|---|---|---|
| `relays_in_directions` (подписка) | предлагать ли служебные узлы подписки (релеи BYPASS) в выборе Направлений. На маршрут не влияет (релей материализуется всегда), но список целей после restore будет другим. У LxBox такой развилки нет вовсе | `sources[].relays_in_directions` |
| `tag_policy`, `replace`, `detour` (папка) | настройки САМОЙ папки: в схеме 0.12 у неё есть ровно имя, потому что своей записи там нет | `sources[]` вида `folder`: `tag_policy`, `fold`+`fold_tag`, `detour` |
| члены папки не-server | цепочка внутри папки и неразобранная запись: секция `servers[]` их не выражает, а положить цепочку в `chains[]` значило бы вынуть её из папки молча. Перечисляются видом и тегом: `Работа: chain hop-1` | `sources[].nodes[]` — узлы всех видов |
| `sections` (узел) | фрагмент конфига, который узел носит с собой: у 0.12 для него дома нет, и писатель 0.12 его не пишет. Правило действует у ОБЕИХ сторон | `sources[].sections` |

Предупреждение перечисляет **только заданные** поля, одной строкой на
сущность: `Liberty: relays_in_directions`, `Работа: tag_policy, replace`,
`ts-node: sections`. Односторонне заводить эти ключи в схему 0.12 было нельзя —
это вернуло бы ровно тот тайный груз, ради сноса которого убран механизм
`extensions` (П1/П3). После импорта такого файла эти настройки восстанавливают
руками; новый бэкап (1.0) их несёт.

UA и HWID-семейство подписки сюда больше НЕ входят: с контрактом 0.12 они
едут объектом `identity` (§«`subscriptions[].identity`»), и код
`backup_source_identity_dropped` остался за ключами этого объекта —
«поле есть, но здесь не применяется». Два разных разговора с пользователем:
«такого поля в общем формате нет» и «формат его знает, а эта сторона нет».

**Едут в файле, но не применяются на импорте** (предупреждение на ИМПОРТЕ):

| Поле контракта | Код | Что происходит |
|---|---|---|
| `exclude_from_global`, `expose_group_tags_to_global` | `backup_source_flag_dropped` | класс флагов упразднён (SPEC 118); узлы источника остаются в общем пуле кандидатов. Прежнее поведение даёт свёртка источника в группу |
| `label` у `servers[]` | `backup_label_dropped` | **LEGACY-ВХОД**: с контрактом 0.12 поля в схеме нет, оно читается для файлов 0.11 и раньше. У канона v7 имени, кроме тега, нет: узел зовут его тегом (SPEC 112). Подпись, разошедшаяся с тегом, отбрасывается; у сервера без `node_tag` она ещё может стать тегом — тогда потери нет и предупреждения тоже. Экспорт `label` в этой секции не пишет вовсе. На `label` ПОДПИСКИ правило не распространяется: это имя источника, ссылочного тега в паре с ним нет. У `chains[]` и `directions[]` `label` с контракта 0.12.4 объявлен полем LxBox (D-094) — лаунчер игнорирует его МОЛЧА, предупреждения нет |
| ключи `identity`, которых сторона не знает | `backup_source_identity_dropped` | mobile-only `device_os`/`ver_os`/`device_model` и всё незнакомое: один warning на подписку с перечнем |

Флаги и `label` объявлены в типах контракта, поэтому общий разбор неизвестных
ключей их не ловит — предупреждение ставится отдельно, иначе они пропадали бы
совсем молча. Потеря подписи осталась только у `servers[]`: у `chains[]` и
`directions[]` `label` (а с 0.12.6 и `ping_url`/`ping_timeout_ms` Направления,
D-096) — объявленные поля LxBox, и молчание тут норма (§1), а не молчаливая
потеря. Внутрь `identity` общий обход тоже не спускается намеренно:
иначе одна потеря давала бы два предупреждения разными кодами.

Полный словарь кодов бэкапа с указанием стороны эмиссии — в
`registry/backup_warnings.json`. Два кода там side-specific и эмитируются
**LxBox**: `backup_dns_entry_skipped` (DNS-запись файла не применена — у
принимающей стороны нет такого вида записи/пресета) и `backup_warp_skipped`
(WARP-аккаунт пропущен — вид аккаунта не поддержан или не применим). Лаунчер
DNS-записи контракта применяет, а `warp[]` переносит как есть, и ни того, ни
другого кода не даёт.

### Цена канонизации Направлений

Отдельное ограничение, не связанное с разрывом 0.10.x → 0.11.0: оно
существовало для `directions[]` и раньше и действует на обе секции, где
Направление встречается (`directions[]` и `subscriptions[].outbounds[]`).

Переносится каноническая модель `direction.schema.json`, а внутренняя запись
Направления богаче. При экспорте **не переносятся**:

| Внутреннее поле | Что теряется |
|---|---|
| `ref` + `updates` | привязка к пресету/шаблону и стек патчей. Ссылочная запись экспортируется MERGED-телом: у принимающей стороны нет ни нашего шаблона, ни наших пресетов, и тонкая ссылка приехала бы туда пустой оболочкой. После импорта Направление — обычное, «прямое»; связь с пресетом восстанавливается только вручную |
| `comment` | заметка пользователя |
| `options`, кроме `interrupt_exist_connections` | прочие опции селектора |
| ключи `filters`, кроме `tag` | отбор узлов по чему-либо, кроме итогового тега |
| `type` | импорт всегда ставит `selector`: тип не объявлен в каноне, и других значений в переносимой модели нет |
| `invert` у `preferredDefault` | `default` едет ТЕЛОМ регулярки; инверсия умолчания не переносится (у `filter` — переносится, ключом `invert`) |

**Переносятся**, вопреки первому впечатлению, `addOutbounds` и
`preferredDefault`: первое — признаками `include_direct` / `include_block` и
списком `include` (тег блокировки и прямого соединения у сторон свой, и
переносить его буквально значило бы сослаться на чужое имя), второе — телом
регулярки в `default`.

Значение `tolerance` / `pool_tolerance`, заданное ссылкой на переменную
шаблона (`@urltest_tolerance`), в файл не едет: у принимающей стороны свой
шаблон, где это имя может не значить ничего. В файле оказывается `0` —
«не задано», и приёмник берёт собственное умолчание.

Практически: восстановленное из бэкапа Направление ведёт трафик так же, но
теряет связь с пресетом, заметку и нестандартные фильтры. Заново их ставят
руками.

Правильный путь переноса на 0.11.0 — снять бэкап **новой** версией
приложения: она пишет всё то же самое общими полями схемы, и roundtrip снова
тождественен.

## 11. Что изменилось против 0.12

Формат 1.0 (`lx_backup: 2`) — не набор переименований, а снятие маппера: файл
стал сериализацией состояния (§1). Поэтому таблица ниже читается не как
«переименовали поле», а как «у поля появился его настоящий дом».

### Структура

| 0.12 (`lx_backup: 1`) | 1.0 (`lx_backup: 2`) |
|---|---|
| четыре секции `subscriptions[]`, `servers[]`, `chains[]` + поле `folder` у сервера | одна секция `sources[]`, вид задаёт `kind` (`subscription\|server\|chain\|folder`; `auto` и `unsupported` — только внутри `nodes[]` папки) |
| папка выражена **именем** в поле `servers[].folder`; своей записи нет | папка — запись `sources[]` с `id`, `name`, `tag_policy`, `fold`, `detour` и составом в `nodes[]` |
| члены папки, которых `servers[]` не выражает (цепочки, неразобранные записи), теряются с `backup_local_only_dropped` | едут: `nodes[]` держит узлы всех видов |
| настройки самой папки теряются тем же кодом | едут своими полями записи |
| `subscriptions[].outbounds[]` — локальные Направления источника | класс упразднён (SPEC 118); дома в 1.0 нет |

### Ключи записей

| 0.12 | 1.0 | Примечание |
|---|---|---|
| `servers[].node_tag` | `tag` | имя узла и есть его тег (SPEC 112) |
| `servers[].uri`, `servers[].config_json` | `origin{kind, raw}` + `body` | исходник записи и разобранное тело — разные вещи, и в 1.0 они лежат отдельно |
| `subscriptions[].label` | `name` | имя источника |
| `subscriptions[].tag{prefix, postfix, mask}` | `tag_policy{prefix, postfix}` | `mask` снят вместе с формой 0.12 |
| `subscriptions[].update{interval_hours, auto}` | `update{interval_hours, auto_refresh}` | |
| `chains[].chain{hops[], …}` | `body{…}` + `hops[]` | позиции — ссылки, и лежат полем записи, а не в теле; форма позиции — `{folder_id?, tag}`, а не строка |
| `detour_tag`, `detour_node_source_id`, `detour_node_tag`, `detour_node_label` | `detour{folder_id?, tag}` | одна ссылка вместо плоской четвёрки (§6) |
| `exclude_from_global`, `expose_group_tags_to_global` | нет | класс флагов упразднён (SPEC 118) |
| `rules[].match` + `rules[].outbound` | `body` | матчеры и цель одним куском в форме sing-box (§2) |
| `rules[].ref` у `kind: srs` | `refs[]` | всегда список, даже из одного URL |
| `rules[].kind: json` | `kind: inline` | это был тот же inline |
| `dns.servers[].name`, `dns.rules[].name` | `tag` (у сервера) | у правила имя необязательно и идентичностью не является |
| `dns.servers[].value`, `dns.rules[].value` | `body` | |
| нет | `dns.default_domain_resolver` | было в файле у лаунчера и раньше, но не описано и не читалось |
| нет | `fold_tag` | **новый ключ 1.0**: явное имя группы свёртки (§2) |
| `servers[].sections` — объявлено, но писателями 0.12 не писалось | `sections` у записи `sources[]` | у 0.12 дома для секций не было: потерю называл экспорт 0.12 кодом `backup_local_only_dropped` с полем `sections`. Про уже существующие 0.12-файлы с этим блоком — ниже |

### Что НЕ менялось

`directions[]` (форма `direction.schema.json` со всеми полями LxBox), `fold`
(форма `source_fold.schema.json`), `disabled{}` (карта «тег → unix seconds»),
`identity{}`, `vars`, `route{final}`, `warp[]` — исключения тонкого слоя из
§1. Правила слияния §9 по смыслу те же; новое в них — только ступень по `id`
у папки, ключ `ref` у preset-серверов DNS и явно названная перенумерация оси
вместе с узловыми правилами.

### 0.12-файлы с `servers[].sections`

Dev-сборки лаунчера успели написать файлы формата 0.12, в которых у записи
`servers[]` лежит блок `sections` (релизов с ним не было; форма записей
внутри — состояния v8). Legacy-вход **читает** такой блок как секции узла и
**ничего не предупреждает**: парсер записей у обоих форматов один, и чтение
бесплатно, а warning о том, что мы же сами и записали, был бы шумом.

`schema/backup-0.12.schema.json` поле `sections` объявляет — оно там было и
до контракта 1.0, и копия схемы не правится. Но **писатели 0.12 его не
писали**: дома у секций в этом формате не было, и потерю называл экспорт
кодом `backup_local_only_dropped` с полем `sections` (§10). Объявленное, но
не писавшееся поле — это ровно окно для чтения таких файлов, а не обещание
их создавать.

### Запись только 1.0

С синхронных релизов (лаунчер 1.6.0, LxBox 2.23.3) обе стороны пишут только
формат 1.0 и читают оба (D-110, §1). Окна «два писателя, дефолт 0.12» больше
нет, как нет и выбора формата на экспорте. Файл с `lx_backup` выше читаемого
сторона отвергает целиком (§8), а не разбирает частично.
