# CANON — правила канонизации канонического узла

Нормативно. Версия контракта: см. `../VERSION`. Решения: DECISIONS.md (SPEC 103).

## 1. Конверт

Форма — `schema/node.schema.json`: `{v, nodes[], dropped[], meta?}`. Узел:
`{kind, scheme, label, entry, chain?, warnings?}`.

**`scheme` — имя схемы URI, не тип sing-box.** Канон берётся из
`registry/protocols/<scheme>.json` → поле `scheme`; тип ядра лежит рядом в
`singbox_type`. Разница видна ровно на shadowsocks: схема `ss`, тип
`shadowsocks`. Лаунчер пишет в конверт схему, LxBox — тип, поэтому раннер
LxBox приводит имя (`_canonScheme`). Расхождение косметическое (поведение
одинаково), но без приведения составы узлов не сходятся.

## 2. Канонизация `entry` (sing-box map)

1. **Без `tag`.** Tag-политика (prefix/mask/uniquify) — постобработка приложений,
   вне контракта. Человекочитаемое имя — в `label` конверта.
2. **Без `detour`.** Цепочка — в `chain[]` (ближний хоп первым, cap 8).
3. **Ключи отсортированы** рекурсивно (byte-order UTF-8), **порядок элементов
   списков сохраняется** (alpn, allowed_ips — значимы).
4. **Дефолтные поля не пишутся.** Поле, значение которого совпадает с дефолтом
   ядра или «пустым» смыслом, опускается (D-010: WG `name`/`system` не эмитятся).
5. **Числа — числами** (`server_port: 443`, не `"443"`); bool — bool.
6. **Компактный JSON без пробелов** при сериализации для хеша (identity —
   `IDENTITY.md`); в фикстурах — pretty-print для читаемости, сравнение — по
   разобранным значениям, не по байтам файла.
7. **Escaping: нет** (D-007). Строки — сырой UTF-8: без HTML-escaping
   (`<`, `>`, `&`), без ` `/` `-эскейпов. Go: `SetEscapeHTML(false)`
   и выравнивание юникод-эскейпов.

## 3. Порядок `nodes`

Порядок появления во входе. Для Xray-массивов — после нормативных проходов
владения идентичностью (ownership); фикстуры `corpus/body/` фиксируют результат.
Для sing-box-конфигов — порядок `outbounds[]`, затем `endpoints[]`, группы — на
месте появления.

## 4. Деградация

Философия обоих проектов, теперь нормативно:

- битое **значение** → чинится/выкидывается с warning-кодом
  (`registry/warnings.json`), нода живёт;
- битая **нода** → в `dropped[{ref, index, code, reason}]`, подписка живёт
  (форма записи — §4.1);
- битый **контейнер/элемент** → try/catch на гранулярности узла; потерянный
  протокол виден через warning `unsupported_protocol`;
- значение, которое ядро отвергнет fatal'ом на весь конфиг, в `entry` попадать
  **не имеет права** (пример: `tls.ech` — вычищается с `ech_ignored`, D-006).

### 4.1. Запись отбраковки `dropped[]` (контракт 1.1.47)

`{ref, index, code, reason}`. Нормативны `ref`, `index` и `code`; `reason`
— человеческий текст стороны и сравнением не покрывается (D-088).

- `ref` — что отвергнуто, как это видно глазами: тег outbound'а у JSON-тел,
  сама ссылка у одиночной ссылки. Смысл не менялся.
- `index` — позиция отвергнутого ЭЛЕМЕНТА в нарезке `elements` вида
  источника (`registry/source_kinds.json`), с нуля: `lines` — непустые
  не-комментарные строки, `outbounds[]+endpoints[]` — outbound'ы, затем
  endpoint'ы, `[].outbounds[]` — outbound'ы всех конфигов подряд. У одиночной
  ссылки — всегда `0`. Это ДОПОЛНИТЕЛЬНЫЙ адрес рядом с `ref` (подсветка
  места во входе), а не его замена: `ref` у JSON-тела — тег, которого у
  элемента может не быть или который повторяется.
- `code` — код из `registry/warnings.json`, обязателен у КАЖДОЙ отбраковки.
  Отказ санитайзера несёт код своего правила; отказ РАЗБОРА — один из общих:
  `form_unrecognized` (ни одна форма не прочитала текст: нет схемы, оболочка
  не раскрылась, пейлоад не JSON/ini), `field_missing` (обязательное поле,
  запись или userinfo пусты), `protocol_unsupported` (тип записи ядру
  неизвестен), `uri_too_long`.

Ожидание корпуса без `index`/`code` сравнивается снисходительно (старые
файлы); сторона, выдающая конверт, обязана их ставить.

## 5. Группы

`kind:"group"`: `entry.type` = `selector`|`urltest`; члены группы — по `label`
исходных узлов (теги в контракте не существуют). Синтетические группы приложений
(autogroup LxBox) — вне контракта, в фикстурах не появляются.

**Род группы — это тип тела sing-box** (`entry.type`), отдельного имени рода
нет (решение владельца 19.09.2026, контракт 1.1.47). Таблица —
`registry/protocols/group.json` → `genus`:

- `genus.values` — допустимые значения `entry.type` узла-группы. `scheme`
  группы в конверте — `group` (§1: имя схемы, не тип); сторона, которая пишет
  в конверт тип, приводит `selector`/`urltest` к `group` по этому списку —
  `singbox_type: "selector|urltest"` обратного хода не даёт;
- `genus.by_source` — во что разрешается род у вида источника: sing-box несёт
  тип сам (`$as_is`, `selector` остаётся `selector`), Xray-балансировщик
  (`routing.balancers[0]`) рода не объявляет и становится `urltest`.
  Кейс — `body/xray/balancer_group`.

## 6. Warnings

`warnings[]` — список `{code, path?, value?, params?}` (контракт 1.1.0, SPEC 131;
до 1.1.0 — список строк-кодов, читается по-прежнему):

- `code` — из `registry/warnings.json`;
- `path` — путь поля в `entry` (`tls.reality.short_id`), обязателен для кодов
  уровня поля, отсутствует у кодов уровня узла (`field_missing` на узле в
  `dropped`, `protocol_unsupported`);
- `value` — исходное значение до деградации, обрезано до 64 символов; у полей
  с `secret: true` в реестре — `"***"`;
  Форма строки нормативна для всех реализаций (корпус сверяет побайтно):
  скаляр — как есть (`true`, `443`, строка без кавычек); объект —
  `map[k:v k:v]` с ключами по алфавиту, вложенные объекты так же, массив —
  `[a b c]` (это Go-печать `%v`; не-Go реализации воспроизводят её сами);
  обрезка — по РУНАМ (не байтам): первые 64 руны + `…` (U+2026), строка в 64
  руны и короче не меняется;
- `params` — подстановки шаблона `text_*` кода (имена — `params` записи кода).

Порядок `warnings[]` (нормативен для обеих сторон):

1. **Коды маппера** — записи с `maps_to: null`, у которых `path` = имя
   записи (`dns` у `wgconf_dns_ignored`, `$extra_vnext` у
   `xray_extra_entries_dropped` и родня). Идут **впереди** кодов тела.
2. **Коды тела** — санитайзер по `body.order` реестра; коды уровня узла
   без пути — в порядке появления при разборе.
3. **Внутри группы** — порядок объявления правил секции (маппер: порядок
   `params`; санитайзер: `body.order`).

Дубли по паре `(code, path)` снимаются. Текст рисуют приложения по
`title_*`/`text_*` из реестра; контракт сам переводит коды (оба языка в
реестре), приложения не держат собственных таблиц.

Warnings — производные данные: пересчитываются из исходника узла при любом
повторном разборе и не являются авторитетными при переносе (бэкап, обмен).

### 6.1. `absent_when` — объект, которого нет

Атрибут поля-объекта (и секции суб-схемы) в реестре: **если перечисленные
ключи объекта равны указанным значениям, объект снимается ЦЕЛИКОМ и ТИХО** —
кода нет. Это запись «настройки нет», а не деградация, и сообщать человеку
нечего.

Нужен там, где выключатель секции лежит ВНУТРИ неё самой. У ядра
`tls: {enabled: false}` значит «TLS не задан» (конструктор возвращает
`(nil, nil)`), а не «TLS с выключенным флагом»; тем же атрибутом, а не особым
случаем, описаны вложенные `utls`, `reality`, `ech` со своим `enabled: false`.
Атрибут `absent_values` это не выражает — он про значение САМОГО поля и только
строковый.

**Норма порядка (нормативна для обеих сторон).** `absent_when` судится:

- **ДО** правил полей самого объекта;
- **ДО** связей соседей — `conflicts`, `requires`, `forbidden_for` и условий
  `when.any_set`.

Снятый объект для любой проверки наличия «не задан», и вместе с ним для этих
проверок исчезает всё, что внутри (`tls.reality.enabled` при снятом `tls`).
Иначе `tls: {enabled: false, reality: {…}}` дал бы коды на поля блока, которого
в теле не будет, а сосед потерял бы своё значение из-за конфликта с
несуществующим блоком.

Сравнение значений — по печатной форме скаляра (как у `values` и `advisory`):
`false` и `"false"` совпадают, потому что тело приезжает и разбором JSON, и от
маппера, где булев флаг бывает строкой. Перечислено несколько ключей — объект
снимается, только когда совпали ВСЕ.

## 7. Сравнение в раннерах

Раннер разбирает вход → строит конверт → сравнивает с `expected.json`
**по значению** (после канонизации), не по байтам. Per-app override
(`<case>.expected.launcher.json` / `<case>.expected.lxbox.json`) допустим только
со ссылкой на задокументированное by-design различие (см. `IDENTITY.md` §4);
бесхозный override — ошибка линтера корпуса.

## 8. Конвейер (SPEC 131)

Любой вход — share-URI, sing-box/Xray JSON, wg-conf, ручное тело — проходит
три ступени, одинаковые для обеих сторон:

1. **маппер** — перевод диалекта в канонический путь `entry` по
   `uri.*.maps_to` и `body.*.aliases` реестра; значений не проверяет, дефолтов
   не ставит, незнакомое кладёт как есть;
2. **санитайзер** — по `body`-секциям реестра (`registry/protocols/<scheme>.json`,
   `tls.json`, `transports.json`, `multiplex.json`, `dialer.json`): тип, enum,
   формат, алиасы, `allowed_for`/`forbidden_for`, `conflicts`/`requires`,
   `unknown_key`; каждое снятие/приведение — запись в `warnings[]`. Объекты,
   объявленные незаданными (`absent_when`), снимаются первыми и молча — см.
   §6.1, там же норма порядка;
3. **эмиттер** — сериализация в порядке `body.order`; схемных ветвлений в коде
   нет.

Инвариант, проверяемый корпусом: значение, которое ядро пина отвергает
фатально на весь конфиг (`sing-box check` = B по `DRIFT.md` SPEC 131), после
санитайзера в `entry` остаться не может. Гейты по версии ядра (`min_core`,
`platform`) — не при разборе, а при сборке конфига: `entry` от ядра не
зависит.

## 9. Core-rejected node

Страховка на то, что ступени §8 пропустили. Ядро проверяет конфиг ЦЕЛИКОМ и
на первом же неприемлемом узле отказывается стартовать вовсе — одна строка в
одном узле оставляет без связи все остальные. Дублировать грамматики ядра в
клиентах нельзя (копия расходится с ним на бампе пина и начинает резать
годные узлы), поэтому поверх дешёвых проверок реестра стоит общий второй
эшелон: **ядро назвало узел → приложение выключает этот узел → пересборка**.

Норма общая для обеих сторон (лаунчер SPEC 132, LxBox фича 478).

### 9.1. Формат строки ошибки ядра

Нормативная форма — ядро `sing-box-lx` ≥ `1.14.1-lx.7` (SPEC 092 ядра):

```
initialize <outbound|endpoint>[<i>] <type>[<tag>]: <text>
```

- `<outbound|endpoint>` — **вид** записи конфига, ровно одно из двух слов;
- `<i>` — **индекс** в массиве, десятичные цифры. Индекс диагностический: он
  нумерует ПОЗИЦИЮ в собранном конфиге, а не узел состояния, и сопоставлять
  по нему запрещено;
- `<type>` — **тип** sing-box (`vless`, `wireguard`, …);
- `<tag>` — **финальный тег** записи в собранном конфиге. Произвольная строка:
  пробелы, эмодзи, двоеточия и скобки — всё это законные символы тега;
- `<text>` — текст ядра, сам по себе цепочка обёрток через `: `.

Ядра старше lx.7 пишут ту же строку **без** ` <type>[<tag>]`
(`initialize outbound[26]: unknown uTLS fingerprint`). Это форма «без тега»:
разбор обязан её распознать и вернуть «узел не назван».

### 9.2. Разбор: где кончается тег

`<tag>` и `<text>` разделяет `]: `, и обе стороны могут содержать эту
последовательность — значит однозначного разреза по строке НЕ существует.
Правило, снимающее неоднозначность, опирается на то, что тег всё равно
подлежит сопоставлению (§9.3):

1. Слева снимается **фиксированный префикс**: `initialize `, затем `outbound`
   или `endpoint`, `[`, цифры, `] `, затем имя типа и `[`. Префикс не совпал —
   ошибка не про узел, разбор окончен.
2. В остатке берутся **все** вхождения `]: `, справа налево. Каждое даёт
   кандидата: тег — всё до него, текст — всё после.
3. Кандидаты проверяются по тегам собранного конфига в том же порядке
   (справа налево, то есть от самого длинного тега к самому короткому).
   **Побеждает первый сопоставившийся.** Ни один не сопоставился — узел не
   назван, автоматики нет.

Право-налево, а не наоборот: тег берётся максимально длинным, и `]: ` внутри
ТЕКСТА отрезается раньше, чем `]: ` внутри ТЕГА. Сопоставление превращает
остальные варианты в кандидатов, а не в догадки.

Примеры (тег в кавычках — что должно получиться):

| строка | тег | текст |
|---|---|---|
| `initialize outbound[3] vless[🇩🇪 Frankfurt]: parse encryption: bad` | `🇩🇪 Frankfurt` | `parse encryption: bad` |
| `initialize outbound[0] vless[A]: B]: c` при теге `A]: B` в конфиге | `A]: B` | `c` |
| `initialize outbound[0] vless[A]: B]: c` при теге `A` в конфиге | `A` | `B]: c` |
| `initialize endpoint[1] wireguard[wg: home]: bad key` | `wg: home` | `bad key` |
| `initialize outbound[26]: unknown uTLS fingerprint` | — (нет тега) | — |
| `initialize inbound[0] tun: permission denied` | — (не про узел) | — |

### 9.3. Сопоставление с узлом

Только по **финальному тегу в собранном конфиге**. Теги в конфиге уникальны;
обратное отображение «финальный тег → исходный узел» строит та же сборка,
которая эти теги выдала, поэтому производные записи (хоп цепочки, узел папки,
префикс подписки, WARP) ведут к своему ИСХОДНОМУ узлу. Тег, которому узла не
нашлось (служебная запись приложения), сопоставленным не считается.

**Страховка действует ТОЛЬКО когда ошибка называет узел и тег сопоставлен.**
Ошибка не про узел, ошибка без тега, тег без узла — обычная ошибка, как
сейчас, без автоматики. Перебором виновника не ищут: выключать узлы по
очереди, пока конфиг не заработает, — это гадание, а не диагностика.

### 9.4. Модель хранения

**Новых сущностей нет — ни поля, ни записи.** Узел выключается тем же флажком
`enabled=false`, что и рукой человека, а причина живёт записью в УЖЕ
существующем списке предупреждений узла:

```json
{"code": "core_rejected", "params": {"reason": "<text>"}}
```

`<text>` — **дословный текст ядра**, без префикса с тегом. Severity кода —
`error`, тексты берутся из реестра (§6), своих таблиц приложения не держат.

Отдельного поля причины НЕ вводится (решение владельца 18.09.2026, обе
стороны): `warnings[]` персистятся и едут в бэкап сами, а второе поле с тем же
смыслом рядом с ними означало бы два ответа на один вопрос.

- «выключило ПРИЛОЖЕНИЕ» = у выключенного узла есть запись `core_rejected`;
  её отсутствие при `enabled=false` = «выключил человек»;
- дубль по коду **замещается** свежим: причина у узла ровно одна — та, что
  ядро назвало последней. Запись идёт **первой** в списке: это вердикт уровня
  узла, а не деградация отдельного поля;
- запись **авторитетна**, в отличие от остальных кодов списка: те —
  производные, пересчитываемые санитайзером из тела узла, и любой пересчёт
  замещает их целиком. Вердикт ядра пересчётом по телу **не воспроизводится и
  стираться им не вправе**. Реализации нужно ОДНО место-правило замещения
  производных кодов, иначе каждая точка пересчёта сотрёт причину молча.

**Вердикт привязан к ТЕЛУ узла.** Ядро судило о конкретном теле, и снимают
вердикт ровно два события:

1. **тело изменилось** — обновление подписки принесло другое тело под тем же
   тегом, человек поправил узел в форме или JSON: запись стирается И узел
   **включается обратно**, следующая сборка проверит его заново. Оживает
   только узел, выключенный СТРАХОВКОЙ; выключенный человеком сменой тела не
   включается — его выключенность решение человека, а не вердикт о теле.
   Сравнение тел **семантическое** (канонизация значения), а не побайтовое:
   иначе любая нормализация снимала бы вердикт;
2. **человек включил узел обратно** — запись стирается, узел проверится
   заново; ядро снова отказало → узел снова выключен с тем же объяснением.

**Смена версии ядра вердикты НЕ снимает** (решение владельца): ручного
механизма достаточно, а обход всех сохранённых состояний ради приговора,
который человек снимает одним кликом, не окупается. Иного автоснятия тоже
нет — осознанная цена простоты.

Запись **идёт в бэкап** вместе с `enabled: false`, как и прочие
`warnings[]`.

### 9.5. Пределы

Триггеры, число попыток и вид сообщения человеку — на усмотрение приложения:
это UX, и он у сторон разный. Нормативны ровно три запрета:

1. страховка действует только при сопоставленном теге (§9.3);
2. перебором виновника не ищут;
3. один и тот же тег, названный повторно, автоматику прекращает — иначе цикл
   перестаёт быть конечным.

Выключенный узел дальше — обычная причина «узел недоступен» для сборки:
пустая группа, цепочка с выключенным хопом, `detour` — по существующим
правилам, `fail-closed` у `detour` сохраняется.
