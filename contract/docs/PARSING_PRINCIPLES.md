# Принципы разбора источников

Нормативно. Версия контракта: см. `../VERSION`. Решения: DECISIONS.md (SPEC 103).

## 0. О чём документ и откуда берутся термины

**Зачем этот документ.** Лаунчер написан на Go, LxBox — на Dart. Оба читают одни
и те же ссылки и подписки и обязаны получать из них одинаковые узлы, иначе бэкап
одной стороны не сойдётся с другой, а один и тот же сервер будет считаться двумя
разными. Реестр (`registry/`) задаёт правила чтения, движок (`MAPPER_ENGINE.md`)
их исполняет, а этот документ задаёт **форму выхода**: как выглядит результат
разбора, как выглядит узел внутри него и по каким правилам его приводят к
единому виду.

**Источник.** Любой текст, из которого приложение достаёт узлы: ссылка,
вставленная руками, тело подписки по URL, файл `.conf`, Xray-массив,
`vpn://`-профиль Amnezia, бэкап. Слово общее намеренно: правила разбора не
зависят от того, откуда текст пришёл.

**Результат разбора.** То, что движок отдаёт наверх после чтения одного
источника. Это не просто список узлов, а три части — потому что у пользователя
три разных вопроса:

- `nodes[]` — узлы, которые прочитались. Ответ на «что я получил»;
- `dropped[]` — записи, которые движок распознал, но отверг целиком: что именно
  отвергнуто (`ref`), на какой позиции в источнике (`index`), по какому коду
  (`code`). Ответ на «почему узлов меньше, чем строк в подписке». Отдельный
  список нужен, чтобы битая запись не роняла остальные и не исчезала молча;
- `meta` — что движок понял о самом источнике: какого вида оказалось тело.
  Ответ на «как вообще был прочитан этот текст»; нужен диагностике и корпусу.

**Узел.** Одна запись в `nodes[]`: `{kind, scheme, label, entry, chain?, warnings?}`.

- `kind` — вид записи: сервер, endpoint (WireGuard), группа. Нужен, потому что
  ядро sing-box обращается с ними по-разному, и приложение обязано знать, куда
  узел класть;
- `scheme` — имя схемы из реестра (`vless`, `ss`, `wireguard`). Нужно, чтобы
  найти правила, по которым узел читали и будут эмитить обратно в ссылку. Это
  имя схемы ссылки, а не тип ядра: у shadowsocks схема `ss`, тип `shadowsocks`;
- `label` — человекочитаемая метка, как её дал автор источника, до того как
  приложение навесит префиксы и уберёт дубли. Хранится отдельно от тега, потому
  что тег приложение меняет, а метка автора должна пережить любую перестановку;
- `entry` — тело узла в форме outbound или endpoint sing-box, без тега. Это то,
  что реально уедет в конфиг ядра. Тег из него вынесен, потому что тег — имя в
  приложении, а не свойство сервера;
- `chain` — цепочка detour: через какие узлы этот узел ходит, ближний хоп
  первым. Вынесена из `entry`, потому что ссылается на другие узлы по тегам, а
  теги в `entry` не живут;
- `warnings` — записи о том, что в узле пришлось починить или снять: код, путь
  поля, исходное значение. Нужны, чтобы пользователь увидел, что узел не совсем
  такой, каким пришёл, и почему.

**Канонизация.** Один и тот же сервер можно записать десятком способов: порт
числом или строкой, ключи в любом порядке, `security=tls` явно или по
умолчанию, пробелы, регистр, escaping юникода. Если каждая сторона будет
складывать `entry` как получится, два одинаковых сервера окажутся разными
байтами — и identity (`IDENTITY.md`), бэкап и корпус развалятся. Канонизация —
приведение `entry` к единственной допустимой записи: ключи отсортированы,
числа — числами, поля со значением по умолчанию выброшены, тег и detour
вынесены наружу, строки — сырой UTF-8 без escaping. Правила — §2. Канонический
узел — узел, чей `entry` через это прошёл; только такие узлы сравниваются,
хешируются и кладутся в бэкап.

**Деградация.** Что делать с мусором во входе. Принцип один: битое значение
чинится или снимается с предупреждением, узел живёт; битый узел уходит в
`dropped[]`, подписка живёт. Правила — §4, коды — `registry/warnings.json`.

**Куда идёт результат.** Как есть он не хранится. Узлы ложатся в состояние
приложения и в бэкап вместе со своим происхождением (`origin`, см.
`BACKUP.md`), предупреждения показываются пользователю в итоге импорта,
отвергнутые записи — в диагностике. Корпус (`corpus/`) сверяет результаты
разбора обеих сторон побайтно: каждый кейс — вход и ожидаемый результат в этой
форме, поэтому форма нормативна до последнего поля.

## 1. Форма результата разбора

`schema/node.schema.json`: `{v, nodes[], dropped[], meta?}`. Узел:
`{kind, scheme, label, entry, chain?, warnings?}` (смысл полей — §0).

**`scheme` — имя схемы URI, не тип sing-box.** Канон берётся из
`registry/protocols/<scheme>.json` → поле `scheme`; тип ядра лежит рядом в
`singbox_type`. Разница видна ровно на shadowsocks: схема `ss`, тип
`shadowsocks`. Лаунчер пишет в результат разбора схему, LxBox — тип, поэтому раннер
LxBox приводит имя (`_canonScheme`). Расхождение косметическое (поведение
одинаково), но без приведения составы узлов не сходятся.

## 2. Канонизация `entry` (sing-box map)

1. **Без `tag`.** Tag-политика (prefix/mask/uniquify) — постобработка приложений,
   вне контракта. Человекочитаемое имя — в `label` узла.
2. **Без `detour`.** Цепочка — в `chain[]` (ближний хоп первым, cap 8).
3. **Ключи отсортированы** рекурсивно (byte-order UTF-8), **порядок элементов
   списков сохраняется** (alpn, allowed_ips — значимы).
4. **Дефолтные поля не пишутся.** Поле, значение которого совпадает с дефолтом
   ядра или «пустым» смыслом, опускается (D-010: WG `name`/`system` не эмитятся).
5. **Числа — числами** (`server_port: 443`, не `"443"`); bool — bool.
6. **Компактный JSON без пробелов** при сериализации для хеша (identity —
   `IDENTITY.md`); в фикстурах — pretty-print для читаемости, сравнение — по
   разобранным значениям, не по байтам файла.
7. **Escaping: нет** (D-007). Строки — сырой UTF-8: без HTML-escaping
   (`<`, `>`, `&`), без ` `/` `-эскейпов. Go: `SetEscapeHTML(false)`
   и выравнивание юникод-эскейпов.

## 3. Порядок `nodes`

Порядок появления во входе. Для Xray-массивов — после нормативных проходов
владения идентичностью (ownership); фикстуры `corpus/body/` фиксируют результат.
Для sing-box-конфигов — порядок `outbounds[]`, затем `endpoints[]`, группы — на
месте появления.

## 4. Деградация

Философия обоих проектов, теперь нормативно:

- битое **значение** → чинится/выкидывается с warning-кодом
  (`registry/warnings.json`), нода живёт;
- битая **нода** → в `dropped[{ref, index, code, reason}]`, подписка живёт
  (форма записи — §4.1);
- битый **контейнер/элемент** → try/catch на гранулярности узла; потерянный
  протокол виден через warning `unsupported_protocol`;
- значение, которое ядро отвергнет fatal'ом на весь конфиг, в `entry` попадать
  **не имеет права** (пример: `tls.ech` — вычищается с `ech_ignored`, D-006).

### 4.1. Запись отбраковки `dropped[]` (контракт 1.1.49)

`{ref, index, code, reason}`. Нормативны `ref`, `index` и `code`; `reason`
— человеческий текст стороны и сравнением не покрывается (D-088).

- `ref` — что отвергнуто, как это видно глазами: тег outbound'а у JSON-тел,
  сама ссылка у одиночной ссылки. Смысл не менялся.
- `index` — позиция отвергнутого ЭЛЕМЕНТА в нарезке `elements` вида
  источника (`registry/source_kinds.json`), с нуля: `lines` — непустые
  не-комментарные строки, `outbounds[]+endpoints[]` — outbound'ы, затем
  endpoint'ы, `[].outbounds[]` — outbound'ы всех конфигов подряд. У одиночной
  ссылки — всегда `0`. Это ДОПОЛНИТЕЛЬНЫЙ адрес рядом с `ref` (подсветка
  места во входе), а не его замена: `ref` у JSON-тела — тег, которого у
  элемента может не быть или который повторяется.
- `code` — код из `registry/warnings.json`, обязателен у КАЖДОЙ отбраковки.
  Отказ санитайзера несёт код своего правила; отказ РАЗБОРА — один из общих:
  `form_unrecognized` (текст не прочитан: оболочка не раскрылась, пейлоад
  не JSON/ini, у тела не опознан вид источника), `scheme_unsupported` (схему
  ссылки не ведёт ни одна секция), `field_missing` (обязательное поле,
  запись или userinfo пусты), `protocol_unsupported` (тип записи ядру
  неизвестен), `uri_too_long`; служебная запись (`incy://routing/…`) —
  `service_record_ignored` (info).
  **Граница двух кодов непрочитанного:** `scheme_unsupported` — строке формы `xxx://`, схему которой не ведёт ни одна секция реестра; `form_unrecognized` — тексту, который не прочитан: у тела не опознан ни один вид источника, у строки нет схемы вовсе либо секция схему опознала, но ни одна её форма не прочитала пейлоад.

Ожидание корпуса без `index`/`code` сравнивается снисходительно (старые
файлы); сторона, выдающая результат разбора, обязана их ставить.

## 5. Группы

`kind:"group"`: `entry.type` = `selector`|`urltest`; члены группы — по `label`
исходных узлов (теги в контракте не существуют): `entry.outbounds`/`entry.default` несут
`label` узлов тела как есть, без замен (у Xray-массива — remarks, а не слаг тега сборки;
контракт 1.1.104); член, которого в теле нет, — как записан в источнике. Синтетические группы приложений
(autogroup LxBox) — вне контракта, в фикстурах не появляются.

**Род группы — это тип тела sing-box** (`entry.type`), отдельного имени рода
нет (решение владельца 19.09.2026, контракт 1.1.49). Таблица —
`registry/protocols/group.json` → `genus`:

- `genus.values` — допустимые значения `entry.type` узла-группы. `scheme`
  группы в результате разбора — `group` (§1: имя схемы, не тип); сторона, которая пишет
  в результат разбора тип, приводит `selector`/`urltest` к `group` по этому списку —
  `singbox_type: "selector|urltest"` обратного хода не даёт;
- `genus.by_source` — во что разрешается род у вида источника: sing-box несёт
  тип сам (`$as_is`, `selector` остаётся `selector`), Xray-балансировщик
  (`routing.balancers[0]`) рода не объявляет и становится `urltest`.
  Кейс — `body/xray/balancer_group`.

**Подписи пула Xray** (решение владельца 29.09.2026, контракт 1.1.105): в
элементе с балансировщиком чистое имя `remarks` получает группа, а каждый
сервер пула — `remarks + " " + tag` своей записи outbound. Подпись, уже
занятая в элементе (запись без `tag` — её `remarks` за группой; `tag`
повторён), получает через пробел номер записи в пуле с 1: `pool 3`,
`pool p 2` (контракт 1.1.106). Две одинаковые подписи узла и группы путают выбор.
Элемент без балансировщика не меняется: его сервер подписан `remarks`.

**Состав пула Xray** (контракт 1.1.107): члены группы — серверы элемента,
которые выбирает `selector` балансировщика. Селектор матчит `tag` записи
префиксом, только среди записей своего элемента. Запись без `tag` —
член пула (селектор её назвать не может). Селектора нет или он пуст — пул
весь элемент. Сервер, которого селектор не выбрал, остаётся узлом элемента
(подпись по правилу выше), но в группу не входит. Кейс —
`body/xray/balancer_selector_subset`.

## 6. Warnings

`warnings[]` — список `{code, path?, value?, params?}` (контракт 1.1.0, SPEC 131;
до 1.1.0 — список строк-кодов, читается по-прежнему):

- `code` — из `registry/warnings.json`;
- `path` — путь поля в `entry` (`tls.reality.short_id`), обязателен для кодов
  уровня поля, отсутствует у кодов уровня узла (`field_missing` на узле в
  `dropped`, `protocol_unsupported`);
- `value` — исходное значение до деградации, обрезано до 64 символов; у полей
  с `secret: true` в реестре — `"***"`;
  Форма строки нормативна для всех реализаций (корпус сверяет побайтно):
  скаляр — как есть (`true`, `443`, строка без кавычек); объект —
  `map[k:v k:v]` с ключами по алфавиту, вложенные объекты так же, массив —
  `[a b c]` (это Go-печать `%v`; не-Go реализации воспроизводят её сами);
  обрезка — по РУНАМ (не байтам): первые 64 руны + `…` (U+2026), строка в 64
  руны и короче не меняется;
- `params` — подстановки шаблона `text_*` кода (имена — `params` записи кода).
- `applied` — применено ли правило к телу (контракт 1.1.87). `false` —
  тело авторское, правило мягкое, тело НЕ изменено (§10). Отсутствие =
  `true`; пишется только `false`. Парных кодов и вторых текстов у
  «не применено» нет: показ решает приложение (§10.5).

Порядок `warnings[]` (нормативен для обеих сторон):

1. **Коды маппера** — записи с `maps_to: null`, у которых `path` = имя
   записи (`dns` у `wgconf_dns_ignored`, `$extra_vnext` у
   `xray_extra_entries_dropped` и родня). Идут **впереди** кодов тела.
2. **Коды тела** — санитайзер по `body.order` реестра; коды уровня узла
   без пути — в порядке появления при разборе.
3. **Внутри группы** — порядок объявления правил секции (маппер: порядок
   `params`; санитайзер: `body.order`).

Дубли по паре `(code, path)` снимаются. Текст рисуют приложения по
`title_*`/`text_*` из реестра; контракт сам переводит коды (оба языка в
реестре), приложения не держат собственных таблиц.

Warnings — производные данные: пересчитываются из исходника узла при любом
повторном разборе и не являются авторитетными при переносе (бэкап, обмен).

Узел-группа (`kind: group` в результате разбора, `kind: auto` в состоянии и бэкапе)
несёт `warnings[]` на тех же правах (контракт 1.1.66): код уровня узла
`group_member_missing` (`params.count` — сколько членов не разрешилось в
узел) ставится на саму группу, одна запись на группу; потеря на нескольких
шагах разбора складывает число. Тела у группы нет, поэтому при переносе её
записи едут как есть (`BACKUP.md` §2).

### 6.1. `absent_when` — объект, которого нет

Атрибут поля-объекта (и секции суб-схемы) в реестре: **если перечисленные
ключи объекта равны указанным значениям, объект снимается ЦЕЛИКОМ и ТИХО** —
кода нет. Это запись «настройки нет», а не деградация, и сообщать человеку
нечего.

Нужен там, где выключатель секции лежит ВНУТРИ неё самой. У ядра
`tls: {enabled: false}` значит «TLS не задан» (конструктор возвращает
`(nil, nil)`), а не «TLS с выключенным флагом»; тем же атрибутом, а не особым
случаем, описаны вложенные `utls`, `reality`, `ech` со своим `enabled: false`.
Атрибут `absent_values` это не выражает — он про значение САМОГО поля и только
строковый.

**Норма порядка (нормативна для обеих сторон).** `absent_when` судится:

- **ДО** правил полей самого объекта;
- **ДО** связей соседей — `conflicts`, `requires`, `forbidden_for` и условий
  `when.any_set`.

Снятый объект для любой проверки наличия «не задан», и вместе с ним для этих
проверок исчезает всё, что внутри (`tls.reality.enabled` при снятом `tls`).
Иначе `tls: {enabled: false, reality: {…}}` дал бы коды на поля блока, которого
в теле не будет, а сосед потерял бы своё значение из-за конфликта с
несуществующим блоком.

Сравнение значений — по печатной форме скаляра (как у `values` и `advisory`):
`false` и `"false"` совпадают, потому что тело приезжает и разбором JSON, и от
маппера, где булев флаг бывает строкой. Перечислено несколько ключей — объект
снимается, только когда совпали ВСЕ.

### 6.2. Снятое правилом поле — отсутствующее (контракт 1.1.63)

**Норма (нормативна для обеих сторон).** Поле, снятое санитайзером ПО ХОДУ
обхода — правилом значения (`on_invalid`, `pattern`, `format`, `min_when`…)
или связью (`requires`/`conflicts`), — для **последующих** связей и условий
(`requires`, `conflicts`, `unless_set`, `when.any_set`, предикаты путей,
связи набора `body.relations`) считается **отсутствующим**, ровно как поле,
снятое запретом схемы, и объект по `absent_when`. Объект, снятый целиком,
забирает с собой всё, что внутри. Прежде такое поле оставалось видно соседям
в исходной карте, и связь судила по значению, которого в теле нет:
`ip=quic` снят за пустой `id`, а `ib`, требующий `ip`, оставался.

Уточнения:

- «Последующих» — по порядку обхода (`body.order`): поле, идущее раньше, уже
  рассудило свои связи по исходному значению соседа;
- связь `requires` к ОБЯЗАТЕЛЬНОМУ полю своего объекта, снятому своим
  правилом, снимает зависимое поле **без второго кода**: объект уходит
  целиком (обязательного поля нет), и причину уже назвал код соседа —
  `short_id`/`key_share` при негодном `public_key` REALITY уходят всем блоком;
- `requires … set` к снятому соседу его **материализует** (сосед для связи
  отсутствует), и пометка «снят» с пути уходит: условия отложенных правил
  видят записанное значение.

## 7. Сравнение в раннерах

Раннер разбирает вход → строит результат разбора → сравнивает с `expected.json`
**по значению** (после канонизации), не по байтам. Per-app override
(`<case>.expected.launcher.json` / `<case>.expected.lxbox.json`) допустим только
со ссылкой на задокументированное by-design различие (см. `IDENTITY.md` §4);
бесхозный override — ошибка линтера корпуса.

## 8. Конвейер (SPEC 131)

Любой вход — share-URI, sing-box/Xray JSON, wg-conf, ручное тело — проходит
три ступени, одинаковые для обеих сторон:

1. **маппер** — перевод диалекта в канонический путь `entry` по
   `uri.*.maps_to` и `body.*.aliases` реестра; значений не проверяет, дефолтов
   не ставит, незнакомое кладёт как есть;
2. **санитайзер** — по `body`-секциям реестра (`registry/protocols/<scheme>.json`,
   `tls.json`, `transports.json`, `multiplex.json`, `dialer.json`): тип, enum,
   формат, алиасы, `allowed_for`/`forbidden_for`, `conflicts`/`requires`,
   `unknown_key`; каждое снятие/приведение — запись в `warnings[]`. Объекты,
   объявленные незаданными (`absent_when`), снимаются первыми и молча — см.
   §6.1, там же норма порядка. Тело схемы с `fields_unchecked: true`
   (контракт 1.1.99, `openvpn-client`) санитайзер не обходит вовсе: снимает
   только `tag` и `type`, остальное — как написано, без кодов; эмиттер пишет
   такое тело ключами по алфавиту. Раздел конфига узла (`endpoints[]` или
   `outbounds[]`) задаёт поле `kind` записи протокола — и только оно;
3. **эмиттер** — сериализация в порядке `body.order`; схемных ветвлений в коде
   нет.

Инвариант, проверяемый корпусом: значение, которое ядро пина отвергает
фатально на весь конфиг (`sing-box check` = B по `DRIFT.md` SPEC 131), после
санитайзера в `entry` остаться не может. Исключение — авторское тело (§10): на нём
мягкое правило не применяется, и защиту от отказа дают только жёсткие
правила (`core_rejects`) и проверка ядром при сохранении. Гейты по версии ядра (`min_core`,
`platform`) — не при разборе, а при сборке конфига: `entry` от ядра не
зависит.

## 9. Core-rejected node

Страховка на то, что ступени §8 пропустили. Ядро проверяет конфиг ЦЕЛИКОМ и
на первом же неприемлемом узле отказывается стартовать вовсе — одна строка в
одном узле оставляет без связи все остальные. Дублировать грамматики ядра в
клиентах нельзя (копия расходится с ним на бампе пина и начинает резать
годные узлы), поэтому поверх дешёвых проверок реестра стоит общий второй
эшелон: **ядро назвало узел → приложение выключает этот узел → пересборка**.

Норма общая для обеих сторон (лаунчер SPEC 132, LxBox фича 478).

### 9.1. Формат строки ошибки ядра

Нормативная форма — ядро `sing-box-lx` ≥ `1.14.1-lx.7` (SPEC 092 ядра):

```
initialize <outbound|endpoint>[<i>] <type>[<tag>]: <text>
```

- `<outbound|endpoint>` — **вид** записи конфига, ровно одно из двух слов;
- `<i>` — **индекс** в массиве, десятичные цифры. Индекс диагностический: он
  нумерует ПОЗИЦИЮ в собранном конфиге, а не узел состояния, и сопоставлять
  по нему запрещено;
- `<type>` — **тип** sing-box (`vless`, `wireguard`, …);
- `<tag>` — **финальный тег** записи в собранном конфиге. Произвольная строка:
  пробелы, эмодзи, двоеточия и скобки — всё это законные символы тега;
- `<text>` — текст ядра, сам по себе цепочка обёрток через `: `.

Ядра старше lx.7 пишут ту же строку **без** ` <type>[<tag>]`
(`initialize outbound[26]: unknown uTLS fingerprint`). Это форма «без тега»:
разбор обязан её распознать и вернуть «узел не назван».

### 9.2. Разбор: где кончается тег

`<tag>` и `<text>` разделяет `]: `, и обе стороны могут содержать эту
последовательность — значит однозначного разреза по строке НЕ существует.
Правило, снимающее неоднозначность, опирается на то, что тег всё равно
подлежит сопоставлению (§9.3):

1. Слева снимается **фиксированный префикс**: `initialize `, затем `outbound`
   или `endpoint`, `[`, цифры, `] `, затем имя типа и `[`. Префикс не совпал —
   ошибка не про узел, разбор окончен.
2. В остатке берутся **все** вхождения `]: `, справа налево. Каждое даёт
   кандидата: тег — всё до него, текст — всё после.
3. Кандидаты проверяются по тегам собранного конфига в том же порядке
   (справа налево, то есть от самого длинного тега к самому короткому).
   **Побеждает первый сопоставившийся.** Ни один не сопоставился — узел не
   назван, автоматики нет.

Право-налево, а не наоборот: тег берётся максимально длинным, и `]: ` внутри
ТЕКСТА отрезается раньше, чем `]: ` внутри ТЕГА. Сопоставление превращает
остальные варианты в кандидатов, а не в догадки.

Примеры (тег в кавычках — что должно получиться):

| строка | тег | текст |
|---|---|---|
| `initialize outbound[3] vless[🇩🇪 Frankfurt]: parse encryption: bad` | `🇩🇪 Frankfurt` | `parse encryption: bad` |
| `initialize outbound[0] vless[A]: B]: c` при теге `A]: B` в конфиге | `A]: B` | `c` |
| `initialize outbound[0] vless[A]: B]: c` при теге `A` в конфиге | `A` | `B]: c` |
| `initialize endpoint[1] wireguard[wg: home]: bad key` | `wg: home` | `bad key` |
| `initialize outbound[26]: unknown uTLS fingerprint` | — (нет тега) | — |
| `initialize inbound[0] tun: permission denied` | — (не про узел) | — |

### 9.3. Сопоставление с узлом

Только по **финальному тегу в собранном конфиге**. Теги в конфиге уникальны;
обратное отображение «финальный тег → исходный узел» строит та же сборка,
которая эти теги выдала, поэтому производные записи (хоп цепочки, узел папки,
префикс подписки, WARP) ведут к своему ИСХОДНОМУ узлу. Тег, которому узла не
нашлось (служебная запись приложения), сопоставленным не считается.

**Страховка действует ТОЛЬКО когда ошибка называет узел и тег сопоставлен.**
Ошибка не про узел, ошибка без тега, тег без узла — обычная ошибка, как
сейчас, без автоматики. Перебором виновника не ищут: выключать узлы по
очереди, пока конфиг не заработает, — это гадание, а не диагностика.

### 9.4. Модель хранения

**Новых сущностей нет — ни поля, ни записи.** Узел выключается тем же флажком
`enabled=false`, что и рукой человека, а причина живёт записью в УЖЕ
существующем списке предупреждений узла:

```json
{"code": "core_rejected", "params": {"reason": "<text>"}}
```

`<text>` — **дословный текст ядра**, без префикса с тегом. Severity кода —
`error`, тексты берутся из реестра (§6), своих таблиц приложения не держат.

Отдельного поля причины НЕ вводится (решение владельца 18.09.2026, обе
стороны): `warnings[]` персистятся и едут в бэкап сами, а второе поле с тем же
смыслом рядом с ними означало бы два ответа на один вопрос.

- «выключило ПРИЛОЖЕНИЕ» = у выключенного узла есть запись `core_rejected`;
  её отсутствие при `enabled=false` = «выключил человек»;
- дубль по коду **замещается** свежим: причина у узла ровно одна — та, что
  ядро назвало последней. Запись идёт **первой** в списке: это вердикт уровня
  узла, а не деградация отдельного поля;
- запись **авторитетна** внутри состояния, в отличие от остальных кодов
  списка: те — производные, пересчитываемые санитайзером из тела узла, и
  любой пересчёт замещает их целиком. Вердикт ядра пересчётом по телу **не
  воспроизводится и стираться им не вправе** (перенос бэкапом — ниже, там
  запись снимается). Реализации нужно ОДНО место-правило замещения
  производных кодов, иначе каждая точка пересчёта сотрёт причину молча.

**Вердикт привязан к ТЕЛУ узла.** Ядро судило о конкретном теле, и снимают
вердикт ровно два события:

1. **тело изменилось** — обновление подписки принесло другое тело под тем же
   тегом, человек поправил узел в форме или JSON: запись стирается И узел
   **включается обратно**, следующая сборка проверит его заново. Оживает
   только узел, выключенный СТРАХОВКОЙ; выключенный человеком сменой тела не
   включается — его выключенность решение человека, а не вердикт о теле.
   Сравнение тел **семантическое** (канонизация значения), а не побайтовое:
   иначе любая нормализация снимала бы вердикт;
2. **человек включил узел обратно** — запись стирается, узел проверится
   заново; ядро снова отказало → узел снова выключен с тем же объяснением.

**Смена версии ядра вердикты НЕ снимает** (решение владельца): ручного
механизма достаточно, а обход всех сохранённых состояний ради приговора,
который человек снимает одним кликом, не окупается. Иного автоснятия тоже
нет — осознанная цена простоты.

**Авторитетность действует внутри ОДНОГО состояния.** Запись — кэш вердикта
конкретного ядра на конкретной машине. Перенос бэкапом (контракт 1.1.67,
решение владельца 25.09.2026):

- **экспорт** пишет запись как есть, вместе с `enabled: false`, как и прочие
  `warnings[]`;
- **импорт** запись **снимает**, а `enabled` берёт из файла как есть: узел
  остаётся выключенным, импорт его НЕ включает. Вердикт заново вынесет ядро
  приёмника, когда человек включит узел. На приёмнике такой узел неотличим от
  выключенного рукой — это осознанно: чужое ядро о теле здесь не судило;
- исключение «записи как есть» — только узел-группа `kind=auto` (§6,
  1.1.66), к `core_rejected` не относится;
- узлы подписки едут в бэкап картой `disabled{}` без причины — формат не
  расширяется.

### 9.5. Пределы

Триггеры, число попыток и вид сообщения человеку — на усмотрение приложения:
это UX, и он у сторон разный. Нормативны ровно три запрета:

1. страховка действует только при сопоставленном теге (§9.3);
2. перебором виновника не ищут;
3. один и тот же тег, названный повторно, автоматику прекращает — иначе цикл
   перестаёт быть конечным.

Выключенный узел дальше — обычная причина «узел недоступен» для сборки:
пустая группа, цепочка с выключенным хопом, `detour` — по существующим
правилам, `fail-closed` у `detour` сохраняется.

## 10. Авторское тело: реестр сообщает, не правит (контракт 1.1.87)

Решение владельца 27.09.2026 (LxBox §577). Узел, написанный руками в форме
ядра, уходит в ядро как написан. Реестр на нём сообщает о каждом правиле,
которое сработало бы, но тело не меняет — кроме жёстких правил (§10.3).

### 10.1. Условие

Тело авторское, когда выполнены ВСЕ четыре условия:

1. контейнер: свободный узел в корне (свой сервер) или член папки;
2. узел не группа автовыбора;
3. вид источника записи (`registry/source_kinds.json`) ровно
   `singbox_outbound` — голое тело узла (§11);
4. текст узла разбирается как JSON-объект.

Узел подписки авторским не бывает, даже если провайдер прислал sing-box
JSON. Условием НЕ являются: кто набрал текст, вид хранения `json`, факт
правки. Дословность (узел уходит в ядро без модели) включается ровно по тем
же четырём условиям.

### 10.2. Поведение

| Тело | Правило мягкое | Правило жёсткое |
|---|---|---|
| обычное | правка применяется, предупреждение | правка применяется, предупреждение |
| авторское | тело не меняется, предупреждение с `applied: false` | правка применяется, предупреждение |

Что с авторским телом делается всегда: `detour` снимается (его назначает
сборка), пустой `tag` заполняется тегом модели. Больше ничего.

Предупреждения на авторском теле — те же коды, что санитайзер дал бы
обычному телу, в том же порядке (§6), включая коды, которые у обычного тела
ставит только сборка (`unknown_key` и родня): санитайзер прогоняется по
дословному телу, берутся только предупреждения.

Правка тела по правилу реестра в приложении идёт через ОДНУ точку, которая
знает, авторское ли тело и жёсткое ли правило. Шаги сборки и пробы, меняющие
тело узла мимо неё, запрещены.

### 10.3. Жёсткие правила

Действуют и на авторском теле:

1. запись без строкового непустого `type` — узел снимается;
2. узловой гейт ядра (`on_core_unsupported`: `build_tag`, `min_core`) —
   узел снимается; полевой гейт сборки (`min_core`, `platform`) — ключ
   снимается, как у обычного тела;
3. правило или связь реестра с признаком `core_rejects: true` — нарушение
   роняет старт всего конфига, правка применяется. Где стоит признак —
   `schema/registry_body.schema.json`, определение `coreRejects`, и
   `README.md`, «Атрибуты поля».

### 10.4. Вход и уступки

- **Вход `singbox`** для исключений по входу (`except_sources`) получает
  ТОЛЬКО авторское тело. Узел подписки получает вход `other` и при разборе,
  и на сборке. `awg_mtu_high` остаётся кодом, который отдаётся вместо
  `awg_mtu_clamped` на входе `singbox`.
- **Глобальные настройки TLS** приложения (фрагментация, смешанный регистр
  SNI) — настройки пользователя, а не правила реестра; этим параграфом не
  затрагиваются.
- **Уступка `detour`** (`conflicts {with: detour}`): на авторском теле
  `tls.fragment` при назначенном `detour` НЕ снимается, предупреждение
  `detour_with_tls_fragment` с `applied: false`. `listen_port` WireGuard при
  `detour` — жёсткое (`core_rejects`): ядро отказывает конфигу
  (sing-box-lx `protocol/wireguard/endpoint.go` NewEndpoint: «`listen_port`
  is conflict with `detour`»), поле снимается и у авторского тела.

### 10.5. Показ

Уровень предупреждения при `applied: false` не меняется. Карточка узла:
заголовок — `title_*` кода; вместо `text_*` («что произошло» — он
утверждает, что поле изменено) — общая строка приложения: узел написан
вручную, приложение ничего не изменило; причина и «что можно сделать» —
`cause_*`/`fix_*` кода. Диагностика (Debug API) отдаёт `applied`, отчёт
сборки помечает строку неприменённого правила `not applied`.

## 11. Источник узла — только тело узла (контракт 1.1.87)

Решение владельца 27.09.2026 (LxBox §576).

1. **После ручной правки** в источнике записи своего сервера и члена папки
   лежит только тело узла: JSON-объект с ключом `type`, вид источника ровно
   `singbox_outbound`. Документ (`outbounds`/`endpoints` в корне) и массив
   тел — формы ВВОДА, не формы хранения. Из документа берётся тело первого
   узла, не служебного и не группы; из массива — первый элемент. О
   несохранённом остатке пользователь получает одно сообщение на сохранение.
   Голое тело пишется как набрано. Правило одно для свободного узла в корне,
   для члена папки и для путей импорта своих узлов (мастер, буфер, файл): на
   каждый узел входа — запись с голым телом этого узла. Подписки не
   затрагиваются: их источник — ответ провайдера.
2. **Старые записи** своего сервера и члена папки, у которых в источнике
   документ или массив (виды `singbox_config`, `singbox_config_array`,
   `singbox_outbound_array`), при чтении получают в источник тело узла этой
   записи. Тело, уходившее в ядро, не меняется; меняется только обёртка.
   Версия формы хранения не меняется.
