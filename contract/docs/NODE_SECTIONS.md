# Секции узла и Tailscale — норма для обеих сторон (контракт 0.13, черновик)

Статус: **черновик; форма согласована с LxBox 13.09.2026** (D-101, D-102), ждёт реализации обеих сторон и решения по AAR. Пока сторона не подтвердила,
поле `servers[].sections` остаётся полем лаунчера (BACKUP.md §2, D-098/D-099),
а этот документ — предложением формы, которую обе стороны реализуют
одинаково. После подтверждения: колонка «Поддержка» у `sections` → **обе**,
`contract/VERSION` → 0.13.0, статус документа → норма.

Смысл в одном абзаце. Часть узлов не работает без сопутствующих секций
конфига: endpoint Tailscale бесполезен без DNS-сервера типа `tailscale`,
привязанного к нему, DNS-правила на `*.ts.net` и правила маршрута на
`100.64.0.0/10`; та же связка нужна WireGuard-узлу с подсетями за пиром.
Узел носит эту связку **с собой** в поле `sections`, в формате записей самого
приложения, а сборка конфига **дописывает** записи к общим спискам перед
обычным резолвом. Никаких пресетов, ссылок из состояния на узел и неявной
префиксации тегов.

## 1. Форма

Форма секций в бэкапе — **ровно корневая форма бэкапа**, не внутренняя форма
состояния какой-либо стороны (уточнение LxBox 13.09.2026, D-102):
`sections.rules[]` — элемент `properties.rules.items` схемы (плоское
правило: `kind, name, enabled, num, outbound, ref/refs, match`),
`sections.dns.servers[]` и `sections.dns.rules[]` — `$defs/dnsRef`
(`kind, name, enabled, value`; у сервера `name` = тег, тело в `value`).
Имя поля номера — `num`, как у корня; второго имени быть не должно, иначе
перенумерация оси одним проходом ломается.

```json
{
  "id": "…", "node_tag": "tailscale-node", "enabled": true,
  "config_json": { "type": "tailscale", "auth_key": "tskey-auth-…", "accept_routes": true },
  "sections": {
    "rules": [
      { "kind": "inline", "name": "@{self} network", "enabled": true, "num": 945,
        "match": { "ip_cidr": ["100.64.0.0/10"] }, "outbound": "@self" }
    ],
    "dns": {
      "servers": [ { "kind": "user", "name": "@{self}-dns", "enabled": true,
                     "value": { "type": "tailscale", "endpoint": "@self" } } ],
      "rules":   [ { "kind": "user", "enabled": true,
                     "value": { "domain_suffix": [".ts.net"], "server": "@{self}-dns" } } ]
    }
  }
}
```

- `sections.rules[]` — те же элементы, что `rules[]` корня: `kind` ∈
  `inline` | `srs` (у `srs` — `ref`/`refs` вместо `match`), `enabled`, `num`
  на общей оси порядка, `outbound`. Виды `preset`, `json` и любые другие
  внутри секций **недопустимы**: запись отбрасывается с warning
  `backup_section_record_dropped` (side=import; заводит лаунчер в
  `registry/backup_warnings.json`).
- `sections.dns.servers[]` / `sections.dns.rules[]` — те же `dnsRef`, что в
  `dns` корня, только `kind: user`; тело — в `value`. Другие виды — то же
  отбрасывание с тем же кодом.
- **Тела (`match`, `value`) сырые.** Контракт их не типизирует намеренно: у
  DNS-сервера `tailscale` есть `endpoint`, у правил за пиром — свои поля, а
  типизация потеряла бы незнакомое молча. Порядок ключей не значим.
- Каждая сторона переводит секции в свою внутреннюю форму и обратно тем же
  кодом, что и корневые `rules[]`/`dns` — второго парсера быть не должно.
- Секции допустимы **только у свободных узлов**: `servers[]` в корне и
  `servers[]` с `folder`. У узлов `subscriptions[]`, у `chains[]`, у
  Направлений и у записей `unsupported` поля нет; приехавшее там —
  отбрасывается с тем же кодом `backup_section_record_dropped` (в тексте
  предупреждения случаи различаются: «у узла подписки/цепочки/Направления»
  и «чужой kind внутри секции»).
- Пустой набор (`{}` или все списки пусты) равен отсутствию поля: сторона
  при сохранении поле не пишет.

## 2. Плейсхолдер `@self`

`@self` означает **финальный тег этого узла** — тот, под которым узел
эмитится в конфиг, с учётом политики тегов контейнера (префикс/постфикс
папки или подписки). Не сырой `node_tag`.

Грамматика, ровно две формы:

| Форма | Где | Пример | Результат при финальном теге `home-ts` |
|---|---|---|---|
| `@self` | значение целиком | `"outbound": "@self"` | `"outbound": "home-ts"` |
| `@{self}` | внутри строки, любое число раз | `"tag": "@{self}-dns"` | `"tag": "home-ts-dns"` |

- Подставляется во **все строковые значения** записей секции на любой
  глубине: `tag`, `name`, `server`, `outbound`, `endpoint`, `detour`,
  элементы массивов. Ключи объектов не трогаются.
- `@selfish`, `@self_dns`, `@selftag` — **не** плейсхолдеры, остаются как
  есть. Внутри строки допустима только скобочная форма.
- Других переменных в секциях **нет**. Строка с другим `@…` уходит в конфиг
  как есть.
- Экранирования нет: литерал `@self` в секциях записать нельзя.

Подстановка делается **при сборке** и при показе в UI. В состоянии и в
бэкапе секции лежат **с плейсхолдерами** — иначе переименование узла или
перенос в папку с другим префиксом рвали бы связку.

## 3. Сборка = инъекция

1. Узел эмитится как обычно (в `outbounds[]` или `endpoints[]`). Узел
   выключен, отброшен деградацией или санитайзером → **ничего из его
   секций в конфиг не попадает**.
2. Записи секции проходят подстановку §2.
3. `sections.rules[]` дописываются к общему списку правил маршрута и
   **сортируются по номеру на оси (`num`) вместе с правилами корня и якорями
   пресетов**. Запись с `enabled: false` пропускается. Дефолтный
   номер для записи без `num` — 945 (перед якорем `private-ips` = 950:
   подсеть tailnet и подсети за пиром должны матчиться раньше общих правил).
4. `sections.dns.servers[]` дописываются в конец `dns.servers[]`,
   `sections.dns.rules[]` — в конец `dns.rules[]` (после пользовательских).
   Оси порядка у DNS нет.
5. Дальше — обычный конвейер стороны без узловых веток: резолв `inline`/`srs`,
   санитайзер висячих ссылок (`detour`, `outbound`, **`endpoint` у
   DNS-сервера** — висячий → сервер выбрасывается целиком, правила на него
   чинятся), дедуп тегов DNS (первый побеждает, дубль — warning стороны).

Инвариант: состояние без единого узла с секциями даёт **байт-в-байт** тот
же конфиг, что до появления поля.

## 4. Экспорт

- `servers[].sections` пишется в корневой форме бэкапа (§1): с
  плейсхолдерами, с `num` и `enabled` записей, без подстановки.
- **В `rules[]` бэкапа правила узла НЕ пишутся** и enum `rules[].kind` не
  расширяется: правило узла живёт внутри узла и приезжает вместе с ним.
- Пустые секции не пишутся (§1).
- `state_directory` в `config_json` узла `tailscale` **не дописывается
  экспортом**: путь этой машины другой стороне бесполезен. Если пользователь
  сам вписал его в тело, он едет как есть — это его решение.
- Секреты (`auth_key`) едут открыто, как ключи WireGuard (BACKUP.md §7).

## 5. Импорт

- **Полная замена `rules[]`** (BACKUP.md §9 п. 7) секций узлов **не
  касается**: они приезжают со своим узлом.
- **Слияние серверов по телу** (BACKUP.md §9 п. 2): тело совпало → узел
  «тот же», и тогда поле `sections` в файле **есть** → замещает локальные
  секции узла целиком; поля **нет** → локальные остаются. Поштучного слияния
  записей нет — ключа для сопоставления у них не существует.
- **Перенумерация оси** (BACKUP.md §2, `rules[].num`): абсолютные номера у
  сторон свои, важен относительный порядок. Перенумеровывается **вся ось
  целиком**: правила корня **и** `sections.rules[]` всех приехавших узлов
  одним проходом, с сохранением относительного порядка между ними. Разные
  проходы для корня и для узлов дали бы пересечение номеров и потерю
  взаимного порядка. Записи без `num` встают на 945 до перенумерации.
- Чужой `kind` внутри секций → запись отбрасывается с
  `backup_section_record_dropped`; остальные записи узла живут.
- Узел `tailscale` на стороне, чьё ядро собрано без `with_tailscale`,
  **импортируется как есть** (состояние — не конфиг) и выбрасывается только
  при **сборке** с warning `tailscale_core_unsupported`. Так узел переживает
  обновление ядра, а бэкап с телефона не теряет узлы на десктопе и наоборот.

## 6. Tailscale — семантика обеих сторон

Реестр: `registry/protocols/tailscale.json` (`kind: endpoint`, безадресный
тип, URI-формы нет). Обе стороны:

- **импорт из sing-box JSON**: `type: tailscale` в `outbounds[]` или
  `endpoints[]` принимается без `server`/`server_port`; эмитится всегда в
  `endpoints[]`, тело как есть;
- **целый конфиг как источник**: если в конфиге ровно один не-групповой и
  не-служебный узел, его связка извлекается в `sections`: DNS-серверы, у
  которых `detour` или `endpoint` равны тегу узла (или уже `@self`); DNS-правила,
  чей `server` — один из взятых серверов; правила маршрута, чей `outbound`
  равен тегу узла. Ссылки на тег переписываются в `@self`, теги серверов —
  в `@{self}-<тег>`. Всё остальное в `dns`/`route` игнорируется как раньше;
- **`state_directory`**: если в теле нет — сторона подставляет **при
  эмиссии** свой путь `<каталог данных стороны>/tailscale/<финальный тег>`
  (лаунчер: `<exec>/bin/tailscale/…`; LxBox: каталог файлов приложения).
  Дефолт ядра общий для всех узлов, два узла tailnet сели бы в один каталог.
  В хранимое тело путь не пишется;
- **гейт ядра**: узел на ядре без тега выбрасывается при сборке целиком с
  `tailscale_core_unsupported` (severity `warning`), остальной конфиг
  собирается. Один такой узел иначе валит `check` для всего конфига;
- **Направления**: узел без непустого `exit_node` — **не кандидат** в
  Направления (в интернет он не выпускает); с `exit_node` — кандидат.
  `detour` на такой узел законен;
- **DNS-сервер типа `tailscale`**: `{ "type": "tailscale", "tag", "endpoint": <тег узла>, "accept_default_resolvers"? }`;
  на один узел не больше одного такого сервера (ограничение ядра);
- **конструктор** («Add server → Tailscale» / Add Server Wizard): поля Tag,
  Auth key (секрет), Control URL, Hostname, Ephemeral, Accept routes, Exit
  node; отдаёт узел с канонической связкой из §1 (сервер `@{self}-dns`,
  правило `.ts.net`, маршрут `100.64.0.0/10` на 945 с именем
  `@{self} network`). Подсказка под ключом обязательна: одноразовый ключ
  расходуется при первом входе, идентичность живёт в каталоге состояния,
  удаление каталога/профиля регистрирует новое устройство;
- **несколько узлов tailnet** — не особый режим: второй узел = ещё один
  конструктор с другим тегом; маршрут на `100.64.0.0/10` у второго узла
  пользователь снимает сам.

## 7. UI, что обязана уметь сторона

- Список правил показывает записи `sections.rules[]` узлов **как строки той
  же оси** с пометкой «из узла <тег>»: тумблер и перетаскивание пишут
  `enabled`/`num` **в запись узла**; редактирования и удаления
  отдельно от узла нет. После правки узла список перечитывается.
- Список DNS показывает серверы и правила узлов read-only, с подписью после
  подстановки.
- Редактор узла принимает: голое тело (`type` на верхнем уровне; секции не
  трогает), документ `{ "endpoints"|"outbounds": [тело], "sections": {…} }`
  и sing-box-документ `{ "endpoints"|"outbounds": [ровно один], "dns": {…},
  "route": {…} }`, который переводится в хранимую форму тем же извлечением,
  что и целый конфиг (§6). Оба вида секций в одном документе — ошибка.
- Форма DNS-сервера открывает тип `tailscale` формой (`tag`, `endpoint`
  выбором из узлов `tailscale`, чекбокс `accept_default_resolvers`).

## 8. Корпус

Лаунчер добавляет кейсы, оба раннера обязаны их проходить:

- `corpus/body/singbox/whole_config_sections` — целый конфиг с одним
  WireGuard-узлом и связкой → узел с `sections` (WireGuard, а не Tailscale,
  чтобы кейс не зависел от тега ядра);
- `corpus/body/singbox/tailscale_endpoint` — endpoint `tailscale` без
  адреса → принят, `kind: endpoint`;
- `corpus/backup/node_sections` — экспорт/импорт: секции с плейсхолдерами,
  слияние «файл замещает», `rules[]` без узловых правил, перенумерация оси с
  сохранением относительного порядка корня и узлов.
