# Секции узла и Tailscale — норма для обеих сторон (контракт 1.0)

Статус: **норма контракта 1.0.0**. Форма согласована с LxBox 13.09.2026 (D-101, D-102), AAR
libbox с `with_tailscale` — решено «да» (D-103), форма записей приведена к
одному пространству имён (SPEC 127, `ONE_NAMESPACE.md` §2). Реализовано:
лаунчер — волны 1–3 SPEC 127; LxBox — их ## 13, релиз v2.23.2 (ядро
v1.14.0-lx.38 с Tailscale в AAR). Поле `sections` в схеме бэкапа 1.0 —
**Поддержка: обе**; в формате 0.12 его нет, и 0.12 с синхронных релизов не
пишет ни одна сторона (BACKUP.md §2, §11; D-110).

Смысл в одном абзаце. Часть узлов не работает без сопутствующих секций
конфига: endpoint Tailscale бесполезен без DNS-сервера типа `tailscale`,
привязанного к нему, DNS-правила на `*.ts.net` и правила маршрута на подсети
tailnet (`100.64.0.0/10` и `fd7a:115c:a1e0::/48`, вместе с суффиксом `.ts.net`
в ТОМ ЖЕ правиле — §6 норма (1)); та же связка нужна WireGuard-узлу с
подсетями за пиром.
Узел носит эту связку **с собой** в поле `sections`, в формате записей самого
приложения, а сборка конфига **дописывает** записи к общим спискам перед
обычным резолвом. Никаких пресетов, ссылок из состояния на узел и неявной
префиксации тегов.

## 1. Форма

Форма секций — **ровно корневая форма записей** (`ONE_NAMESPACE.md` §2): та
же, что у `rules[]` и `dns` в корне состояния и в корне файла бэкапа. Узловое
правило отличается от корневого только тем, где оно лежит; второй набор имён
у тех же сущностей означал бы маппинг, ради сноса которого и затеян
контракт 1.0.

```json
{
  "kind": "server", "tag": "tailscale-node", "enabled": true,
  "body": { "type": "tailscale", "auth_key": "tskey-auth-…", "accept_routes": true },
  "sections": {
    "rules": [
      { "kind": "inline", "name": "@{self} network", "enabled": true, "num": 945,
        "body": { "domain_suffix": [".ts.net"],
                  "ip_cidr": ["100.64.0.0/10", "fd7a:115c:a1e0::/48"],
                  "outbound": "@self" } }
    ],
    "dns": {
      "servers": [ { "kind": "user", "tag": "@{self}-dns", "enabled": true,
                     "body": { "type": "tailscale", "endpoint": "@self" } } ],
      "rules":   [ { "kind": "user", "enabled": true,
                     "body": { "domain_suffix": [".ts.net"], "server": "@{self}-dns" } } ]
    }
  }
}
```

- `sections.rules[]` — форма `kind / name / enabled / num / body`, та же, что
  у корневых правил: `kind` ∈ `inline` | `srs` (у `srs` ещё `refs[]`), `num`
  на **общей** оси порядка, цель — ключом внутри `body`
  (`"outbound": "@self"` либо `"action": …`). Имя поля номера — `num`, как у
  корня; второго имени быть не должно, иначе перенумерация оси одним проходом
  ломается. Виды `preset` и любые другие внутри секций **недопустимы**
  (см. ниже).
- `sections.dns.servers[]` — форма `kind / tag / enabled / body`,
  `sections.dns.rules[]` — `kind / enabled / body` (плюс необязательные
  `id`/`name`). Только `kind: user`; тело — в `body`, тег сервера — полем
  `tag`, как в корне.
- **Тела (`body`) сырые.** Контракт их не типизирует намеренно: у
  DNS-сервера `tailscale` есть `endpoint`, у правил за пиром — свои поля, а
  типизация потеряла бы незнакомое молча. Порядок ключей не значим.
- Каждая сторона читает и пишет секции **тем же кодом**, что корневые
  `rules[]`/`dns` — второго парсера быть не должно. Это и есть выигрыш одной
  формы: разошедшиеся кодеки расходятся молча.
- Секции допустимы **только у свободных узлов** (`kind: server` в корне
  `sources[]` и внутри папки). У узлов подписки, у цепочек, у групп, у
  Направлений и у записей `unsupported` поля нет; приехавшее там
  отбрасывается с `backup_section_record_dropped` (в тексте предупреждения
  случаи различаются: «у узла подписки/цепочки/Направления» и «чужой kind
  внутри секции»).
- Пустой набор (`{}` или все списки пусты) равен отсутствию поля: сторона
  при сохранении поле не пишет.

### Отбраковка записи — норма B3

Запись секции отбрасывается **целиком**, а не чинится вырезанием ключа:

- **чужой `kind`** (`preset` у правила, `template`/`preset` у DNS-записи);
- **`rule_set` в теле правила**: наборы правил у узла жить не могут — они
  едут полем `refs[]`, а `rule_set` вписывает сборка. Вырезать ключ нельзя:
  правило без своего единственного матчера становится match-all и начинает
  ловить весь трафик.

Код — `backup_section_record_dropped`, параметры `node` (тег узла), `kind`
(вид отброшенной записи) и `reason` (`kind` | `rule_set` | `not_allowed` |
`unknown_key`). Остальные записи узла применяются. Тем же кодом
отбрасывается поле `sections` у записи, которой оно не положено. Перечень
`reason` закрытый: `kind` — такого вида у секции не бывает; `rule_set` — в
теле правила стоит `rule_set`; `not_allowed` — узлу этого вида секции не
положены; `unknown_key` — сторона со строгим разбором тела отбросила запись
за незнакомый ей ключ тела (ниже), detail называет ключ.

**Допустимая строгость стороны.** Норма задаёт минимум отбраковки; сторона
вправе быть строже там, где её собственная модель тела уже.

- LxBox отбрасывает запись целиком ещё и при **любом незнакомом ей ключе
  тела**: у неё матчеры типизированы, и провезти незнакомый ключ ей некуда.
  На импорте это `reason: unknown_key`, detail называет ключ; в редакторе это
  снекбар, при извлечении из конфига — предупреждение на узле.
- У лаунчера незнакомые sing-box-ключи проходят **как есть**: тело у него
  сырое, и терять ключ, который ядро понимает, а приложение нет, — потеря без
  причины. `unknown_key` лаунчер не эмитит.

Оба поведения законны: строже нормы — можно, мягче — нет.

## 2. Плейсхолдер `@self`

`@self` означает **финальный тег этого узла** — тот, под которым узел
эмитится в конфиг, с учётом политики тегов контейнера (префикс/постфикс
папки или подписки). Не сырой `node_tag`.

Грамматика, ровно две формы:

| Форма | Где | Пример | Результат при финальном теге `home-ts` |
|---|---|---|---|
| `@self` | значение целиком | `"outbound": "@self"` | `"outbound": "home-ts"` |
| `@{self}` | внутри строки, любое число раз | `"tag": "@{self}-dns"` | `"tag": "home-ts-dns"` |

- Подставляется во **все строковые значения** записей секции на любой
  глубине: `tag`, `name`, `server`, `outbound`, `endpoint`, `detour`,
  элементы массивов. Ключи объектов не трогаются.
- `@selfish`, `@self_dns`, `@selftag` — **не** плейсхолдеры, остаются как
  есть. Внутри строки допустима только скобочная форма.
- Других переменных в секциях **нет**. Строка с другим `@…` уходит в конфиг
  как есть.
- Экранирования нет: литерал `@self` в секциях записать нельзя.

**Норма B4: данные принимаются как есть.** Строка с чужим `@…` из бэкапа или
из извлечения конфига обеими сторонами **принимается** и хранится без
изменений. Рубеж у неё один и общий — санитайзер сборки: висячая ссылка там
снимается по общим правилам, а не выдумывается импортное «выключить на всякий
случай».

**Допустимая строгость стороны — при ВВОДЕ документа.** Сторона вправе
отказать пользователю, который вписывает чужой `@…` руками в редакторе узла:
у лаунчера синтаксис `@имя` занят переменными шаблона, и пропустить такую
строку значило бы принять её за подстановку, которой не будет. Отказ — с
внятным текстом, в момент ввода. На данные из бэкапа и из извлечения это
правило не распространяется: там сторона не автор, и отвергать чужое
содержимое нечем.



Подстановка делается **при сборке** и при показе в UI. В состоянии и в
бэкапе секции лежат **с плейсхолдерами** — иначе переименование узла или
перенос в папку с другим префиксом рвали бы связку.

## 3. Сборка = инъекция

1. Узел эмитится как обычно (в `outbounds[]` или `endpoints[]`). Узел
   выключен, отброшен деградацией или санитайзером → **ничего из его
   секций в конфиг не попадает**.
2. Записи секции проходят подстановку §2.
3. `sections.rules[]` дописываются к общему списку правил маршрута и
   **сортируются по номеру на оси (`num`) вместе с правилами корня и якорями
   пресетов**. Запись с `enabled: false` пропускается. Дефолтный
   номер для записи без `num` — 945 (перед якорем `private-ips` = 950:
   подсеть tailnet и подсети за пиром должны матчиться раньше общих правил).
4. `sections.dns.servers[]` дописываются в конец `dns.servers[]`,
   `sections.dns.rules[]` — в конец `dns.rules[]` (после пользовательских).
   Оси порядка у DNS нет.
5. Дальше — обычный конвейер стороны без узловых веток: резолв `inline`/`srs`,
   санитайзер висячих ссылок (`detour`, `outbound`, `endpoint` у
   DNS-сервера), дедуп тегов DNS (первый побеждает, дубль — warning стороны).

**Висячий `endpoint` у DNS-сервера — одинаково у обеих сторон.** Узел, на
который сервер смотрит, не доехал до конфига (выключен, снят гейтом ядра,
отброшен деградацией):

1. **сервер выбрасывается целиком** — не чинится и не оставляется без
   `endpoint`: DNS-сервер без своего транспорта отвечать не может;
2. **DNS-правила, чей `server` — этот сервер, выбрасываются тоже** — правило,
   отправляющее запрос в несуществующий сервер, роняет конфиг;
3. `dns.final`, указывавший на него, переводится на **первый доехавший**
   сервер списка — иначе резолва не будет вовсе;
4. `domain_resolver` / `default_domain_resolver`, указывавший на него,
   **снимается**.

Изобретать здесь своё сторонам запрещено: расхождение означало бы, что один и
тот же бэкап на двух устройствах даёт разный DNS.



Инвариант: состояние без единого узла с секциями даёт **байт-в-байт** тот
же конфиг, что до появления поля.

## 4. Экспорт

- `sources[].sections` пишется в форме §1: с плейсхолдерами, с `num` и
  `enabled` записей, без подстановки. **Только в формате 1.0**
  (`lx_backup: 2`).
- **В формате 0.12 секций нет**: дома у них там не было, и писатели 0.12 их
  не писали (потерю называл код `backup_local_only_dropped` с полем
  `sections`, BACKUP.md §10). С синхронных релизов формат 0.12 не пишет ни
  одна сторона (D-110). О 0.12-файлах, в которых секции всё-таки лежат
  (dev-сборки лаунчера), — BACKUP.md §11.
- **В корневых `rules[]` бэкапа правила узла НЕ пишутся**: правило узла живёт
  внутри узла и приезжает вместе с ним. Общая у корня и узла только ось
  порядка.
- Пустые секции не пишутся (§1).
- **Секции подписочных узлов не сохраняются** — норма E1. У узла подписки
  свободы нет: его тело придёт заново с выдачей провайдера, и связка, которую
  к нему приписали, пережила бы не своё обновление. Сторона сообщает об этом
  уровнем **info, без кода контракта** (у лаунчера — строкой «ignored
  sections: route, dns» в диагностике fetch; у LxBox — записью в лог). Кода
  нет намеренно: это не потеря пользовательской настройки, а граница модели.
- `state_directory` в теле узла `tailscale` **не дописывается экспортом**:
  путь этой машины другой стороне бесполезен. Если пользователь сам вписал его
  в тело, он едет как есть — это его решение.
- Секреты (`auth_key`) едут открыто, как ключи WireGuard (BACKUP.md §7).

## 5. Импорт

- **Полная замена `rules[]`** (BACKUP.md §9 п. 7) секций узлов **не
  касается**: они приезжают со своим узлом.
- **Слияние серверов по телу** (BACKUP.md §9 п. 2): тело совпало → узел
  «тот же», и тогда поле `sections` в файле **есть** → замещает локальные
  секции узла целиком; поля **нет** → локальные остаются. Поштучного слияния
  записей нет — ключа для сопоставления у них не существует.
- **Перенумерация оси — одним проходом по объединённой оси.** Абсолютные
  номера у сторон свои, важен относительный порядок. Перенумеровываются
  **все** размеченные правила файла разом: правила корня **и**
  `sections.rules[]` всех приехавших узлов, в порядке их `num` из файла, с
  сохранением относительного порядка между ними. Разные проходы для корня и
  для узлов дали бы пересечение номеров и потерю взаимного порядка. Записи
  без `num` встают на 945 до перенумерации. Абсолютные зоны (0, 945, 950) при
  этом не сохраняются — см. BACKUP.md §9 п. 7.
- Запись, которую норма §1 не допускает (чужой `kind`, `rule_set` в теле),
  отбрасывается с `backup_section_record_dropped` (`reason` называет причину);
  остальные записи узла живут. Тем же кодом отбрасывается поле `sections` у
  записи, которой оно не положено.
- **Секции узла подписки не применяются** (E1, §4): сторона сообщает уровнем
  info без кода контракта.
- Узел `tailscale` на стороне, чьё ядро собрано без `with_tailscale`,
  **импортируется как есть** (состояние — не конфиг) и выбрасывается только
  при **сборке** с warning `tailscale_core_unsupported`. Так узел переживает
  обновление ядра, а бэкап с телефона не теряет узлы на десктопе и наоборот.

## 6. Tailscale — семантика обеих сторон

Реестр: `registry/protocols/tailscale.json` (`kind: endpoint`, безадресный
тип, URI-формы нет). Обе стороны:

- **импорт из sing-box JSON**: `type: tailscale` в `outbounds[]` или
  `endpoints[]` принимается без `server`/`server_port`; эмитится всегда в
  `endpoints[]`, тело как есть;
- **целый конфиг как источник**: связка извлекается в `sections` — DNS-серверы,
  у которых `detour` или `endpoint` равны тегу узла (или уже `@self`);
  DNS-правила, чей `server` — один из взятых серверов; правила маршрута, чей
  `outbound` равен тегу узла. Ссылки на тег переписываются в `@self`, теги
  серверов — в `@{self}-<тег>`. Всё остальное в `dns`/`route` игнорируется.
  Кому достаётся связка — см. норму (3) ниже;
- **`state_directory`**: если в теле нет — сторона подставляет **при
  эмиссии** свой путь `<каталог данных стороны>/tailscale/<имя>`
  (лаунчер: `<exec>/bin/tailscale/…`; LxBox: каталог файлов приложения).
  Дефолт ядра общий для всех узлов, два узла tailnet сели бы в один каталог.
  В хранимое тело путь не пишется. Имя каталога — финальный тег узла с
  заменой всего вне `[A-Za-z0-9._-]` на `_` (паритет сторон желателен, но
  нормой не является: каталог локален);
- **гейт ядра**: узел на ядре без тега выбрасывается при сборке целиком с
  `tailscale_core_unsupported` (severity `warning`), остальной конфиг
  собирается. Один такой узел иначе валит `check` для всего конфига;
- **Направления**: узел без непустого `exit_node` — **не кандидат** в
  Направления (в интернет он не выпускает); с `exit_node` — кандидат.
  `detour` на такой узел законен;
- **DNS-сервер типа `tailscale`**: `{ "type": "tailscale", "tag", "endpoint": <тег узла>, "accept_default_resolvers"? }`;
  на один узел не больше одного такого сервера (ограничение ядра);
- **конструктор** («Add server → Tailscale» / Add Server Wizard): поля Tag,
  Auth key (секрет), Control URL, Hostname, Ephemeral, Accept routes, Exit
  node; отдаёт узел с канонической связкой — нормой (1) ниже. Подсказка под
  ключом обязательна: одноразовый ключ расходуется при первом входе,
  идентичность живёт в каталоге состояния, удаление каталога/профиля
  регистрирует новое устройство;
- **несколько узлов tailnet** — не особый режим: второй узел = ещё один
  конструктор с другим тегом; маршрут на подсети tailnet у второго узла
  пользователь снимает сам.

### Каноническая связка — норма обеих сторон

Принята с LxBox 14.09.2026 (их спека 437). Четыре пункта, каждый обязателен
для обеих сторон.

**(1) Состав связки — три записи, и правило маршрута РОВНО ОДНО:**

```json
{ "type": "tailscale", "tag": "@{self}-dns", "endpoint": "@self" }
{ "domain_suffix": [".ts.net"], "server": "@{self}-dns" }
{ "domain_suffix": [".ts.net"],
  "ip_cidr": ["100.64.0.0/10", "fd7a:115c:a1e0::/48"],
  "outbound": "@self" }
```

Первые две — DNS-сервер и DNS-правило; третья — правило маршрута. Внутри
одного правила sing-box соединяет поля по **ИЛИ**, поэтому правило с
`domain_suffix` И `ip_cidr` срабатывает на любом из двух признаков. Разнести
их по двум правилам **нельзя**: при FakeIP запрос приходит именем, один
`ip_cidr` его не матчит, и трафик уходит мимо tailnet — молча, потому что имя
резолвится, а маршрут выбирается не тот. IPv6-подсеть `fd7a:115c:a1e0::/48`
обязательна наравне с CGNAT: без неё tailnet с включённым IPv6 наполовину
мимо маршрута.

**(2) Голый узел tailnet получает связку ПО УМОЛЧАНИЮ.** Голый = узел
`type: tailscale`, у которого секций нет вовсе: вкладка JSON с одним телом,
одиночный outbound как источник, узел из конфига, на который ни одна запись
`dns`/`route` не ссылается. Без связки узел бесполезен — tailnet поднимется,
но ни имена, ни адреса в него не пойдут, и пользователь узнал бы об этом по
молчащим `*.ts.net`. Подстановка живёт на путях **рождения** узла, не на пути
правки: связку, которую пользователь снял, назад не возвращают. Уже
имеющаяся связка не трогается никогда, даже если она отличается от
канонической, — это настройка пользователя.

**Снятие связки** — документ узла без `dns`/`route` на вкладке JSON: секции
заменяются пустыми. Это единственный путь, и он обязан работать, иначе
норма (2) означала бы «связку нельзя убрать».

**(3) Многоузловой конфиг.** Обычный узел получает связку конфига, только
когда он в конфиге **один**: связка принадлежит узлу, а не файлу, и раздать
её нескольким значило бы придумать за пользователя. Узел `tailscale` —
исключение: он получает свои записи **по явной ссылке на свой тег** и в
многоузловом конфиге, потому что гадать не о чем (DNS-сервер `type:
tailscale` несёт `endpoint` с тегом узла, правило маршрута метит в него же).
Без исключения пользователь, вставивший конфиг с tailnet и парой обычных
серверов, терял бы MagicDNS молча.

**(4) Tailscale из ПОДПИСКИ — info, а не отказ** (`tailscale_from_subscription`,
severity `info`). Узел законен и остаётся в составе, но связку подписка
принести не может: связка ссылается на финальный тег узла на этой машине, а
идентичность машины в tailnet живёт в локальном каталоге состояния и
одноразовым ключом провайдера не переносится. Связку пользователь заводит у
себя. Молчать нельзя: узел виден в списке, и о неработающих именах
пользователь узнал бы уже в бою.

### Жизненный цикл каталога состояния — норма обеих сторон

Каталог `<root>/tailscale/<имя>` хранит идентичность устройства в tailnet:
одноразовый `auth_key` расходуется при первом входе, а дальше устройство
опознаётся содержимым каталога. Поэтому каталог переживает ровно то, что
переживает узел:

1. **удаление узла** → каталог удаляется. То же при удалении папки вместе с
   её членами;
2. **смена финального тега** (переименование, перенос в папку с другим
   префиксом) → каталог **переименовывается**, а не заводится заново: иначе
   переименование стоило бы пользователю новой регистрации устройства;
3. **при сборке осиротевшие каталоги удаляются** с сообщением уровня info;
4. **в бэкап каталог не едет**: ключ устройства — секрет конкретной машины.
   Восстановление на другой машине = новая идентичность и повторный
   `auth_key`. Это цена, а не недоработка.

**Ожидаемый набор имён для пункта 3 строится по ВСЕМ хранимым узлам
Tailscale**, включая выключенные и снятые гейтом ядра, — а не по тем, что
попали в конфиг. Иначе выходит ловушка: выключил узел → сборка снесла его
идентичность → включил → `auth_key` потрачен. У невыключенного узла имя =
финальный тег после уникализации; у выключенного финального тега у сборки нет
вовсе, и имя считается от префикса контейнера плюс тега **без** суффикса
уникализации — такой каталог тоже остаётся.

## 7. UI, что обязана уметь сторона

- Список правил показывает записи `sections.rules[]` узлов **как строки той
  же оси** с пометкой «из узла <тег>»: тумблер и перетаскивание пишут
  `enabled`/`num` **в запись узла**; редактирования и удаления отдельно от
  узла нет. **Тап по такой строке открывает узел** — редактор у неё один, и
  им является узел. После правки узла список перечитывается.
- **Строки правил выключенного узла приглушены** (A9): узел выключен — его
  секции в конфиг не идут, и строка обязана это показывать, не исчезая.
  Исчезновение читалось бы как «правило удалено», а оно на месте и вернётся
  вместе с узлом.
- Список DNS показывает серверы и правила узлов read-only, с подписью после
  подстановки.
- Редактор узла принимает: голое тело (`type` на верхнем уровне; секции не
  трогает), документ `{ "endpoints"|"outbounds": [тело], "sections": {…} }`
  и sing-box-документ `{ "endpoints"|"outbounds": [ровно один], "dns": {…},
  "route": {…} }`, который переводится в хранимую форму тем же извлечением,
  что и целый конфиг (§6). Оба вида секций в одном документе — ошибка.
- Форма DNS-сервера открывает тип `tailscale` формой (`tag`, `endpoint`
  выбором из узлов `tailscale`, чекбокс `accept_default_resolvers`).

Отказ при вводе чужого `@…` (§2) и отбраковка записи по строгой модели тела
(§1, B3) предъявляются пользователю **в момент ввода**: снекбар или текст
ошибки в редакторе, а не молчаливое сохранение с потерей.

## 8. Корпус

Кейсы заводит лаунчер, оба раннера обязаны их проходить.

**Конверт `body/singbox/*`** — узел плюс секции из целого конфига:

- `corpus/body/singbox/whole_config_sections` — целый конфиг с одним
  WireGuard-узлом (endpoint), DNS-сервером на него и route-правилом → узел с
  `sections` в форме §1, ссылки переписаны в `@self` / `@{self}-…`. WireGuard,
  а не Tailscale, чтобы кейс не зависел от тега сборки ядра;
- `corpus/body/singbox/tailscale_endpoint` — endpoint `type: tailscale` без
  адреса → узел принят, `scheme: tailscale`, в entry нет `state_directory`
  (путь локален и в хранимое тело не пишется, §6).

Правила конверта, чтобы ожидания сошлись у двух раннеров: `nodes[].sections`
пишутся **без `id` и без `num`**; имя извлечённого правила — `body.name`, а
при его отсутствии `@{self} rule N` (N — порядковый среди правил узла, с 1);
тег извлечённого DNS-сервера — `@{self}-<тег из конфига>`; `"outbound":
"@self"` дописывается в тело, если в нём нет ни `outbound`, ни `action`.
`meta.extension` у этих кейсов **не ставится** ни одной стороной.

**Конверт `corpus/backup/*`** — кейсы формата 1.0 (`lx_backup: 2`):

- `v10_sources_union` — все четыре вида в `sources[]`; у кейса есть
  предсостояние (`.pre.backup.json`), поэтому он проверяет и слияние.
  Обе ступени лестницы §9 п. 3 разведены НАМЕРЕННО, иначе они
  неразличимы: папка «Europe» совпадает по ИМЕНИ (id у файла и у
  предсостояния разные), папка «Nordics» — по `id` (имя у файла и у
  предсостояния разное). Ожидание поэтому несёт `folder_ids`: совпавшая
  папка обязана держать ЛОКАЛЬНЫЙ id, и по нему видно, какая ступень
  сработала. Ссылки `hops[].folder_id` проверяются отдельным ключом
  ожидания `hops` (тег + ИМЯ папки, на которую хоп обязан указывать): канон
  `chain` схлопывает хопы до плоских тегов, и перепись по карте id в нём не
  видна. Подписка совпадает по `url`;
- `v10_node_sections` — секции у корневого сервера И у члена папки (носители
  оба, §1). Узловые правила встают на общую ось между корневыми по
  относительному порядку после перенумерации. Три секционные записи
  отбраковываются: `kind: preset` (правило) и `kind: template`
  (DNS-сервер) — с `reason: kind`, правило с `rule_set` в теле — с
  `reason: rule_set` (норма B3). Ожидание несёт `warning_reasons`:
  множество кодов причины не различает, а B3 нормирует именно их;
- `v10_rules_body_action` — цель внутри `body` во всех формах
  (`action: reject`, `action: reject` + `method: drop`, тег), плюс `srs` с
  двумя `refs` и `preset` с `vars` (переменные сверяются ключом `vars`
  ожидания правила — это настройка пресета, а не глобальные `vars`);
- `v10_dns_body` — DNS-записи всех видов; тело сверяется deep-equal ключом
  `body`, а три скаляра секции (`strategy`, `final`,
  `default_domain_resolver`) — своими ключами: у второй стороны тело
  проходит через её собственный декодер, и «едет байт в байт» — свойство
  одного кодека, а не контракта.

Старые кейсы 0.12 остаются как есть — они же кейсы legacy-чтения. Файл с
`lx_backup` выше читаемого сторона **пропускает как чужой**; override-файлов
на этот случай не заводят.
