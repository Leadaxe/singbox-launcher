# Корпус выпуска правила-дерева: наборы, теги, маршрут, DNS-зеркало

Контракт 1.1.179 (SPEC 188 лаунчера, D-156, D-157). Нормы —
`docs/TEMPLATE_LANG.md` §6.13 (наборы правила и их теги) и §6.11 (зеркало
по дереву). Гоняют обе стороны: лаунчер — раннер `TestContractCorpusRuleTree`
(`core/build/contract_rule_tree_test.go`, SPEC 188 волна 3; **до него
каталог не читает ни один раннер**), LxBox — свой раннер (TASKS_LXBOX §182).

## Формат

- `<case>.rules.json` — вход:
  - `_` — что проверяет кейс, по-русски;
  - `template_rule_set_tags` — теги `route.rule_set` шаблона (заняты заранее);
  - `preset_rule_set_tags` (необязательно) — `{ "<preset_id>": ["<preset_id>:<tag>", …] }`:
    теги наборов пресетов, чьи записи стоят в `rules[]` (заняты заранее,
    включённые и нет); тела пресетов в кейс не входят;
  - `rules` — записи `rules[]` в форме состояния / бэкапа 3 (`refs` внутри
    `body`), в порядке оси (`num`). Все наборы считаются скачанными,
    `srs_mode` — `local`.
- `<case>.expected.json` — нормативный выход:
  - `rule_set[]` — записи `route.rule_set`, которые выпускают записи
    `inline` | `srs` кейса, в порядке выпуска (порядок оси, внутри правила —
    обход pre-order: ссылки узла по `refs`, затем его inline-набор; одна
    ссылка — одна запись). У `local` | `remote` сверяются `tag`, `type`,
    `format`; `path` и `url` — нет. У `inline` — `tag`, `type`, `rules`;
  - `route_rules[]` — выпущенные `route.rules` записей `inline` | `srs` в
    порядке оси (пресеты и шаблон не входят);
  - `dns_rules[]` — DNS-правила зеркал этих записей в порядке выпуска;
    **матчер нормативен** (в отличие от `corpus/rule_dns/`);
  - `mirror_empty` (необязательно) — имена правил, у которых DNS-опция
    включена, а зеркало пустое (⚠ «DNS options have no effect: the rule has no
    condition DNS can see»). Нет ключа — таких правил нет.

Порядок ключей внутри объекта не нормативен. `rule_set` из одного тега —
строка, из нескольких — массив (§6.13 п. 3).

**Выбор стороны — простой узел без `refs`.** Ключи `set: true` такого узла
сторона может оставить на узле или увести в inline-набор (§6.13 п. 4).
Ожидания написаны в форме «на узле»; раннер стороны, уводящей ключи в набор,
до сравнения сворачивает каждый такой inline-набор обратно в узел (ключи
набора — на место тега в `rule_set`, тег снимается из `rule_set[]` выхода и
из `rule_set` зеркала). Тег такого набора при этом нормативен: у корня —
`B'`, у листа — `B':inline:<путь>`; раннер проверяет его до свёртки.

## Кейсы

| Кейс | Что проверяет |
|---|---|
| `flat_refs_domains` | плоское: 2 ссылки + `domain_suffix` + `ip_cidr` + `port` → `B`, `B:<h8>`, `B:inline`; `port` на правиле; зеркало с inline-набором (домены есть) |
| `flat_refs_ip_only` | ссылка + `ip_cidr` → `B:inline` только с адресом исключён из зеркала |
| `flat_no_refs_bytes` | плоское без ссылок — тело на правиле как есть, наборов нет (критерий 5) |
| `tree_and_or` | `and` [условия, `or` группа] → ссылка листа `B:<h8>`, `B:inline:1.0`; зеркало-дерево |
| `invert_port_dropped` | `not port 443` + DNS → зеркала нет, `mirror_empty` |
| `invert_carried` | `invert` с доменами переносится в зеркало |
| `single_child_unwrap` | после выброса пустых детей обёртка снята; `invert` обёртки переходит на ребёнка |
| `same_ref_two_leaves` | одна ссылка в двух листах — один тег, одна запись |
| `name_dedup` | тег шаблона и тег пресета заняты; выключенное правило берёт базу: `Ads (2)`, `Ads (3)`, `Ads (4)`, `blk:lists (2)` |
| `derived_tag_collision` | правило `X` и правило `X:inline` → `X:inline (2)` у inline-набора `X` |
| `h8_collision` | две ссылки с одинаковыми 8 hex → 16 hex у обеих (пара подобрана перебором) |
| `ip_cidr_inbound_mirror` | лист `{ip_cidr, inbound}` с DNS → зеркало `{inbound}` на все запросы входа |
| `block_https_over_tree` | Block HTTPS, глушилка AAAA, Fixed IP над `logical` — обёртка `and`; сервер — на корне `M` |

h8 — первые 8 hex sha256 строки ссылки (UTF-8, края обрезаны), нижний
регистр.
