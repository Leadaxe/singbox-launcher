# corpus/backup — фикстуры LX Backup (контракт 0.12.5)

Кейсы переноса настроек между приложениями. Семантика — `contract/docs/BACKUP.md`,
принципы — `contract/docs/BACKUP_PRINCIPLES.md` (П1–П7, нормативны),
схема — `contract/schema/backup.schema.json`.

## Формат

```
<case>.pre.backup.json  ПРЕДСОСТОЯНИЕ (необязательно): импортируется в пустое
                        состояние ПЕРВЫМ, и уже в него сливается сам кейс
<case>.backup.json      входной файл бэкапа
<case>.expected.json    что обязано получиться после импорта:
                        {"rules": [...], "vars": {...}, "warnings": ["код", …],
                         "directions": [...], "chains": [...],
                         "subscriptions": {...}, "root_servers": [...],
                         "folders": {...}, "replace_tags": {...},
                         "extensions_dropped": true|false}
```

### Конвенция предсостояния (контракт 0.12.5, D-095)

Импорт — **слияние** по идентичности, а не замена, и проверить его импортом в
пустоту невозможно: там слияние и замена дают один и тот же итог, а стороны,
разошедшиеся в ключе слияния, остаются неразличимы. Поэтому кейс, который
проверяет слияние, кладёт рядом `<case>.pre.backup.json`.

Порядок раннера строгий: пустое состояние → импорт `pre` → импорт самого
кейса → сверка с `expected`. Предупреждения предсостояния в сверку **не
идут** — оно декорация сцены, а не предмет кейса; сверяются только
предупреждения основного импорта. Файла `pre` нет → импорт идёт в пустое
состояние, как во всех прежних кейсах. `<case>.pre.backup.json` **не является
самостоятельным кейсом**: раннер обязан отсеять его из списка кейсов, иначе
он погонит его отдельно и будет искать несуществующий `<case>.pre.expected.json`.

### Ожидания слияния

`subscriptions` — **исчерпывающая** карта `url → {label, prefix, postfix,
enabled?, nodes?, pending_disabled?}`. Ключ тот же, по которому идёт слияние
(`url` как есть). Список исчерпывающий не для красоты: подписка, которой в
ожиданиях нет, — это либо не оставленная локальная, либо задвоенная, и обе
ошибки видны только сверкой всего набора. `nodes` — сырые теги узлов, которые
обязаны пережить слияние (состав локальной подписки в файл не едет и
потеряться не вправе); `pending_disabled` — отметки выключения, ждущие
первого fetch, сверяются отсортированными (это объединение двух множеств,
порядок в нём смысла не несёт). `enabled` необязателен: отсутствие ключа
значит «не проверяем».

`root_servers` — теги корневых одиночных узлов **в порядке состояния**
(совпавшие держат локальную позицию, новые встают в конец). Дедуп по телу
проверяется именно отсутствием второй записи в этом списке.

Оба поля необязательны: отсутствие ключа значит «не проверяем».

`chains[]` в ожиданиях — исчерпывающий список `{tag, label?, enabled?, chain}`:
`chain` сверяется deep-equal канона (включая `null`-значения `rewrite` —
RFC 7396), число записей — строго (пропущенная по занятому тегу запись не
должна материализоваться второй). `label` — поле **LxBox** (D-094): у него оно
проверяется как значение в re-export, у лаунчера ключа в ожидании нет вовсе —
он подпись цепочки молча игнорирует и не пишет.
`enabled` в ожиданиях **необязателен**: отсутствие ключа значит «не
проверяем», а не «ожидаем false» — иначе умолчание схемы (true) стало бы
требованием выключенности во всех остальных кейсах.

`extensions_dropped` — файл несёт упразднённый механизм `extensions`
(схема 0.10.x). Импортёр обязан его отбросить, назвать одним warning'ом на
файл и не воскресить при обратном экспорте.

Раннеры: Go — `core/backup/corpus_test.go`, Dart — `test/contract/backup_contract_test.dart`.

## Что фиксируют кейсы

Не «happy path», а именно те решения, которые легко нарушить:

- **битая символическая ссылка** (`broken_outbound_ref`) — правило с
  несуществующим `outbound` импортируется ВЫКЛЮЧЕННЫМ, а не теряется и не
  включается (включённое правило с мёртвой целью роняет конфиг ядра целиком);
- **`route.final` в никуда** (`final_target_missing`) — не применяется: иначе
  весь трафик уходит в несуществующий outbound;
- **непереносимая переменная** (`non_portable_var_skipped`) — не применяется,
  факт назван (на другой машине то же имя значит другое: путь, интерфейс,
  платформенный флаг);
- **чужой `kind` правила** (`unknown_rule_kind_skipped`) — пропускается с
  warning, остальные правила приезжают: одно чужое правило не роняет весь файл;
- **ось порядка** (`order_renumbered_preserving_sequence`) —
  перенумеровывается, относительный порядок сохраняется;
- **цепочка со всеми полями канона** (`chains_roundtrip`) — приезжает
  источником, правило на её тег — рабочим (тег пополняет известные цели),
  `null` внутри `rewrite` переживает перенос. Подпись `label` — поле LxBox
  (D-094): он её возвращает (side-specific ожидание), лаунчер молча
  игнорирует, и предупреждения нет ни у одной стороны;
- **занятый тег цепочки** (`chain_tag_duplicate`) — вторая запись с тем же
  тегом не применяется и ВСЕГДА предъявляется `backup_chain_exists`:
  молчание склеило бы случайных тёзок незаметно;
- **умолчание `enabled` у цепочки** (`chain_disabled_enabled_default`) — в
  одном файле выключенная запись (`enabled: false`) и запись без ключа:
  первая обязана приехать выключенной, вторая — включённой. Обе стороны
  читают отсутствие ключа как `true`; кейс существует затем, чтобы сторона,
  однажды прочитавшая его как `false`, упала здесь, а не у пользователя;
- **упразднённый `extensions`** (`extensions_dropped`) — карман провоза
  отброшен с warning'ом и не воскресает в обратном экспорте (П3). Файл этого
  кейса написан по схеме 0.10.x НАМЕРЕННО: это вход теста «старый файл
  читается общим правилом», а не legacy-путь кода — отдельного разбора
  старого формата не существует (П4);
- **старый файл лаунчера** (`legacy_0_10_launcher_extensions`) — то же с
  наполненным `extensions.launcher` (id, skip, detour_node_hash): общие поля
  записи применяются, карман отбрасывается ОДНИМ warning'ом, потеря его
  содержимого — задокументированная цена разрыва (`BACKUP.md` §10);
- **неизвестные ключи** (`unknown_keys_warned_import_continues`) — ключи
  чужой стороны на всех уровнях (корень, запись подписки, поле правила) дают
  warning, а импорт продолжается: понятное применяется, непонятое названо
  (П3/П6). `directions[].label` в этом же файле warning'а НЕ даёт: с
  контракта 0.12.4 это объявленное поле LxBox, а не неизвестный ключ (D-094);
- **чужой ТИП знакомого ключа** (`boolean_skip_type_mismatch`) —
  `subscriptions[].skip` пришёл boolean'ом (форма LxBox 0.10.x) при списке
  фильтров отсева в 0.11.0. Отбрасывается ОДНО поле с
  `backup_field_type_mismatch`, всё остальное — соседняя подписка с корректным
  `skip`, Направление, правило — приезжает (`BACKUP.md` §10). Строгий разбор
  ронял бы здесь весь файл, то есть терял бы всё прочее молча, вопреки П6.
  Это единственная коллизия типов между 0.10.x и 0.11.0;
- **счёт позиционного деривативa** (`replace_tag_index`, D-081) — тег группы
  свёрнутой подписки контракт не несёт, он вычисляется: префикс тегов, а при
  пустом префиксе — `<номер записи в subscriptions[]>:` плюс `select`. В файле
  сервер стоит ПЕРВЫМ источником, подписка — единственная в своей секции,
  значит имя группы `1:select`, а не `2:select`. Правило и `route.final` того
  же файла метят в него и обязаны приехать РАБОЧИМИ: цель приезжает этим же
  файлом, и принимающая сторона, чей список известных целей снят до импорта,
  обязана пополнить его группами приехавших свёрток. Считала сторона номер по
  позиции среди всех источников — здесь она получит `2:select`, выключенное
  правило и отброшенный final.

Ожидание `replace_tags` (`{URL подписки: имя группы}`) — необязательное поле
конверта: отсутствие ключа значит «не проверяем». Оно единственное место, где
имя группы видно снаружи, — в самом контракте такого поля нет.

**Часть входных файлов НЕ валидна против `backup.schema.json` — намеренно.**
Схема нормативна для 0.11.0 и обязана отвергать `skip: true`; терпимость к
такому полю живёт в импортёре, а не в схеме. Кейсы
`boolean_skip_type_mismatch`, `extensions_dropped` и
`legacy_0_10_launcher_extensions` — входы «файл прошлой схемы читается общим
правилом», и валидатор схемы к ним неприменим. Все остальные `*.backup.json`
обязаны проходить схему.

Данные синтетические: хосты `example-N.com`, UUID из единиц. Секретов и
реальных URL провайдеров в фикстурах нет.

Ключи disabled-отметок в корпусе — 64 hex-символа: это **legacy-форма**
(identity-хеш до SPEC 112). Она оставлена намеренно — фикстуры проверяют, что
такой ключ переживает перенос НЕТРОНУТЫМ и доезжает до приёмника, где его
мигрирует первый разбор источника (`docs/IDENTITY.md` §5.1). Новая
идентичность — тег узла (`docs/IDENTITY.md` §1), и в бэкапе она едет обычной
строкой ключа; отдельного кейса под неё нет, потому что для формата обмена
ключ непрозрачен: он копируется как есть.

**Требует зеркальной правки LxBox** — обе стороны обязаны и сохранять
legacy-ключи при переносе, и мигрировать их по одному правилу, и одинаково
отбрасывать `extensions` (статус зеркала — `docs/BACKUP_PRINCIPLES.md`).

## Папки (контракт 0.12.0)

Кейс `folders_roundtrip` — сборка папки на импорте. Папка **не имеет секции в
файле**: собственных данных, кроме имени, она не несёт, а вторая секция
потребовала бы держать два места в согласии. Вместо этого запись `servers[]`
носит пометку `folder` — имя папки, и обе стороны собирают контейнер ПО ЭТОМУ
ИМЕНИ: записи с одинаковым `folder` становятся одной папкой, запись без
пометки остаётся в корне списка.

Нормативны две вещи, и обе проверяются кейсом:

- **порядок членов** — порядок записей в файле. Перетасованный состав это
  расхождение: пользователь раскладывал узлы сам;
- **одно имя = одна папка** — второй встреченный `folder: "Proton"` дополняет
  уже собранную, а не заводит тёзку.

Ожидание `folders` (`{имя папки: [теги членов по порядку]}`) — необязательное
поле конверта: отсутствие ключа значит «не проверяем». Сравнение идёт БЕЗ
сортировки, потому что порядок здесь и есть предмет договорённости.

Что в файл не едет и почему: настройки САМОЙ папки (политика тегов, свёртка,
общий detour) и члены, которых `servers[]` выразить не может (цепочки,
неразобранные записи). Это не забывчивость формата, а его граница — потеря
объявляется на экспорте кодом `backup_local_only_dropped`, одним
предупреждением на папку с перечнем. Односторонний ключ в общей схеме был бы
возвращённым тайным грузом, ради сноса которого убран `extensions` (П1/П3).

**Требует зеркальной правки LxBox**: папка = контейнер одиночных серверов у
обеих сторон, и собирается она по имени одинаково.

Side-specific ожидание `chains_roundtrip.expected.lxbox.json` (класс различия
**B** по `docs/IDENTITY.md` §4a — платформенное поле записи, решение D-094):
подпись цепочки `label` объявлена в схеме как поле **LxBox**, он её пишет и
читает, поэтому в его ожидании `chains[0].label` присутствует. Лаунчер зовёт
цепочку тегом (SPEC 112): приехавшую подпись он игнорирует МОЛЧА (`warnings`
пусты у обеих сторон — предупреждения об объявленном чужом поле не бывает,
`BACKUP.md` §1) и на экспорте не пишет, поэтому в базовом ожидании ключа
`label` нет. Различие ровно в одном ключе; всё прочее у ожиданий совпадает.

Side-specific ожидание `replace_tag_index.expected.lxbox.json` (класс различия
A по `docs/IDENTITY.md` §4a, решение D-081): у LxBox свёртка (`fold`) не
применяется и группа `1:select` не создаётся, поэтому правило `Work` и
`route.final`, метящие в неё, приезжают выключенными с предупреждениями
`backup_unknown_outbound` и `backup_final_dropped`; поля `replace_tags` в
ожидании нет. Базовое ожидание описывает сторону лаунчера, где группа
создаётся и правило включено.

## Слияние источников (контракт 0.12.5)

Кейс `merge_sources_by_url` — единственный на сегодня кейс с предсостоянием, и
он фиксирует все четыре ключа слияния разом (D-095, `docs/BACKUP.md` §9).

Предсостояние: подписки **A** и **B** (у B локальные настройки — префикс
`b:`, включена, отметка `local-mark`), корневой сервер **S1**, папка
**Proton** с членом **P1**.

Предсостояние несёт ещё и сервер **S3**, заданный `config_json` (для проверки
канонической формы тела).

Файл кейса: подписка **B** с ДРУГИМИ настройками (`label` «B new», префикс
`bb:`, `disabled: {x}`), подписка **C**, сервер с тем же телом, что у S1, но
под чужим тегом `S1-renamed-elsewhere`, ещё один S1 под тегом
`S1-other-fragment` и **другим `#фрагментом`** в URI, новый сервер **S2**,
папка **Proton** с членами `P1-elsewhere` (тело P1) и **P2**, и сервер
`S3-reordered` — то же тело, что у S3, но с **переставленными ключами
`config_json`** и собственными `tag`/`detour` внутри JSON.

Что обязано получиться:

- подписки **A, B, C**: A осталась нетронутой (её в файле нет), B держит
  локальную позицию и `id`, но настройки взяла из файла, а отметки
  выключения ОБЪЕДИНИЛИСЬ (`local-mark` + `x`), C дописана в конец;
- корневые серверы **S1, S3, S2** (в этом порядке — совпавшие держат
  локальную позицию, новый встал в конец). Три дубля узнаны **по телу** и
  пропущены **без warning** — это не потеря, а «у тебя уже есть»: дубль S1
  под чужим тегом, дубль S1 с другим `#фрагментом` (фрагмент — имя узла, а
  не тело) и `S3-reordered` (порядок ключей `config_json` не значим, а
  верхнеуровневые `tag`/`detour` из сравнения сняты — форма identity-хэша,
  D-007);
- папка **Proton** = `[P1, P2]`: P1 узнан по телу внутри папки, P2 дописан
  в конец;
- **предупреждений нет вовсе**: ни одна из этих операций потерей не является.

Сломать кейс легко ровно теми способами, ради которых он написан: сливать
серверы по тегу (появятся `S1` и `S1-renamed-elsewhere`), сравнивать `uri`
вместе с фрагментом (появится `S1-other-fragment`), не снимать `tag`/`detour`
у `config_json` (появится `S3-reordered`), заменять `disabled` вместо
объединения (пропадёт `local-mark`), терять локальное (исчезнет A) или
задваивать совпавшее (две записи на `sub-b`). Каждая из трёх ветвей дедупа
проверена отключением: без неё кейс краснеет.
