# Корпус golden-фикстур

Общие конформанс-фикстуры контракта (SPEC 103). Раннеры живут в приложениях
(Go — лаунчер, Dart — LxBox) и читают этот каталог; сам корпус — только данные.

## Структура

```
corpus/
├── uri/<scheme>/<case>.uri     # одиночные share-URI (Фаза 1)
│     <scheme> = имя файла реестра registry/protocols/ (vless, vmess, trojan,
│     shadowsocks, hysteria2, tuic, anytls, naive, ssh, socks, http,
│     wireguard, masque); алиасы схем (hy2://, socks://, wg://) лежат
│     в каталоге канонической схемы
├── body/<container>/<case>.body  # целые тела (Фаза 2): uri-list, base64,
│     singbox-JSON, xray-массив, wgconf (INI), vpn://
├── emit/                       # entry → share-URI + cross-emit (Фаза 2)
├── template/                   # шаблон + vars → итоговый JSON (Фаза 3)
└── backup/                     # экспорт ↔ импорт LX Backup (Фаза 4)
```

## Формат файла кейса

- Первые строки — комментарии `# `: описание кейса по-русски + откуда взят
  (файл:строка теста или путь фикстуры-источника). Парсеры обоих приложений
  скипают такие строки штатно.
- Дальше — полезная нагрузка: для `.uri` ровно **одна** строка с URI;
  для `.body` — тело целиком.
- Имя кейса — короткий `snake_case` по сути кейса
  (`ws_early_data_ed_no_eh.uri`, `reality_pbk_junk_enabled.uri`).
  Один кейс = одна проверяемая особенность; граничные варианты одной
  фичи — отдельные кейсы.
- Битые/деградационные кейсы — полноправная часть корпуса (мусорный fp,
  `pbk=enabled`, нечётный sid, отсутствующий обязательный параметр):
  они фиксируют деградацию и warning'и, а не только happy-path.

## Синтетичность данных

Только синтетические, детерминированные данные:

- хосты `example-N.com`, `192.0.2.x` (TEST-NET-1), `[2001:db8::x]`;
- UUID вида `11111111-1111-1111-1111-111111111111`;
- пароли `testpass123` и подобные;
- ключи — **валидные по формату** заглушки (для WG/Reality — корректная
  длина base64/base64url, для ss2022 — base64-ключ нужной длины).

Переносишь кейс из реального бага — анонимизируй, сохранив свойство,
которое кейс проверяет (длину, спецсимволы, кодировку).

## Отбраковки и `meta.extension`

- Запись тела, которую сторона узнала и осознанно отвергла (ссылка
  `dialerProxy` на несуществующий outbound, битый обязательный параметр),
  едет в конверте списком `dropped[]` — `{ref, index, code, reason}` (D-088,
  форма записи — CANON §4.1).
  Пустой `nodes[]` без `dropped[]` означает другое: тело не распознано вовсе.
- **Нормативны в записи отбраковки `ref`, `index` и `code`**, `reason` — нет.
  `index` (с 1.1.47) — позиция элемента в нарезке `elements` вида источника,
  у корпуса `uri/` всегда `0`.
  `ref` называет отвергнутое (тег outbound'а у JSON-тел, сам URI у корпуса
  `uri/`), `code` — машинная причина из `registry/warnings.json`
  (`dialer_proxy_unusable` и т.д.). `reason` — человеческий текст СТОРОНЫ:
  у лаунчера это формат ошибки Go, у LxBox свой; побайтовая нормативность
  заставила бы вторую сторону копировать чужие строки, поэтому раннеры его
  **не сравнивают** (при `-update` в файл пишется текущий текст стороны).
- С 1.1.47 **каждое** ожидание корпуса несёт `code` и `index`, включая отказы
  разбора (`form_unrecognized`, `field_missing`, …): раннер лаунчера сам
  отказывается выдать отбраковку без них. Ожидание, где поля нет (чужое или
  старое), сравнивается без него; объявленное поле сравнивается строго.
- `meta.extension` помечает кейс, схемы которого у одной из сторон нет
  (например `"extension": "desktop"` у тела с hysteria v1 — у LxBox для него
  парсера нет). Раннер стороны, которой схема недоступна, такой кейс
  пропускает; отдельного каталога для этого не заводится — пометка живёт
  в ожидании кейса и переживает `-update`.
- Пометка обязательна **в обе стороны**: пропуск, о котором сказано только
  в коде раннера, читается как «кейс сверен». Весь каталог
  `uri/hysteria/` (8 кейсов, hysteria v1 — расширение стороны лаунчера)
  помечен `"extension": "desktop"` явно; прежде LxBox проходил мимо него
  молча, и отсутствие сверки ничем не отличалось от зелёной сверки.
  Каталог кейсов со схемой-расширением пометку несёт целиком, а не
  выборочно: непомеченный сосед означал бы, что его сверять надо.

## Формат кейса бэкапа (`lx_backup`)

Кейсы каталога `backup/` лежат вперемешку в двух форматах: `lx_backup: 1` —
контракт 0.x (legacy-вход), `lx_backup: 2` — контракт 1.0. Раннер формат **не
выбирает**: он опознаёт его по этому ключу и гоняет кейс тем же импортом.
Ожидания у обоих форматов одни и те же по смыслу — итог импорта это
состояние, и оно обязано получиться одинаковым независимо от того, какой
писатель сделал файл. Кейсы 1.0 названы с префикса `v10_` для удобства чтения
каталога; признаком для раннера имя не является.

**Файл с `lx_backup` больше, чем сторона умеет читать, — это чужой extension,
а не сломанный кейс.** Сторона такой файл **пропускает** (её раннер отмечает
кейс как skipped) и ничего не сверяет: делать вид, что прочитала документ
следующей мажорной версии, хуже честного отказа. Override-файлов под такой
случай не заводят — пропуск это не расхождение сторон, а одинаковое поведение
обеих.

## Предсостояние кейса (`<case>.pre.backup.json`)

Кейс корпуса **бэкапа** может положить рядом `<case>.pre.backup.json` — файл,
который импортируется в ПУСТОЕ состояние ПЕРВЫМ, и уже в получившееся
состояние сливается сам `<case>.backup.json`.

Конвенция нужна с контракта 0.12.5 (D-095): импорт — слияние, а не замена, и
проверить его импортом в пустоту невозможно — там слияние и замена дают
одинаковый итог. Предупреждения предсостояния в сверку не идут: оно сцена, а
не предмет кейса. Файла `pre` нет → импорт идёт в пустое состояние, как во
всех прежних кейсах. Раннер обязан **отсеять** `*.pre.backup.json` из списка
кейсов, иначе погонит предсостояние отдельным прогоном и будет искать
несуществующий `<case>.pre.expected.json`. Подробности и поля ожиданий —
`corpus/backup/README.md`.

## Нормативность expected

- Рядом с каждым кейсом живёт `<case>.expected.json` — канонический конверт
  (узел после канонизации + `warnings[]`). Он **нормативен**: расхождение
  раннера с expected = баг приложения или осознанное изменение контракта.
- Сравнение — **по значению после канонизации**, не по байтам
  (`docs/CANON.md` §7).
- Per-app override — `<case>.expected.launcher.json` /
  `<case>.expected.lxbox.json` — допустим только со ссылкой на
  задокументированное by-design различие (`docs/IDENTITY.md` §4 и §4a);
  бесхозный override — ошибка линтера корпуса.
- **Имя файла — единственный признак стороны**, каталога у override'ов нет:
  `<case>.expected.<app>.json` лежит РЯДОМ с кейсом, где `<app>` —
  `launcher` либо `lxbox`. Каждая сторона читает свой файл, если он есть, и
  базовый `<case>.expected.json` иначе (`expectedPathFor`); **чужой
  override для неё невидим и сравнением не участвует**. Поэтому
  `.expected.lxbox.json` живёт в этом репозитории наравне с остальным
  корпусом (LxBox берёт vendored-копию каталога целиком) — класть его
  «к ним» не надо и нельзя: корпус общий, разъехаться ему нечем.
- Когда различие двустороннее, базового ожидания у кейса может не быть
  вовсе — тогда лежат ОБА override'а и ни одного базового
  (`uri/trojan/ws_ed_flat_no_eh`). Это не пробел: базовый файл здесь
  означал бы «стороны обязаны совпасть», а они обязаны разойтись, и
  причина расхождения написана шапкой самого кейса.
- **Override, побайтово равный базе, — мусор, а не «явная фиксация».**
  Он ничего не проверяет: раннер и так читает базу. Такой файл прячет
  настоящее расхождение (изменение базы перестаёт доезжать до приложения)
  и растёт лавиной — аудит 25.08 снёс 257 таких из 281. Прежде чем класть
  override, убедись, что он отличается от базы после канонизации, и
  укажи класс различия по `docs/IDENTITY.md` §4a (A — warning ждёт
  вторую сторону, B — платформенное поле `ext`, C — неканон в базе).

## Режим `-update`

Раннеры умеют перегенерировать expected (`go test -update` и аналог в Dart).
Это **осознанный PR, а не рутина**: diff expected-файлов — изменение
контракта, ревьюится как код, с бампом `VERSION` по правилам из
корневого README. Молча перезаписывать expected, чтобы «позеленел CI», нельзя.
