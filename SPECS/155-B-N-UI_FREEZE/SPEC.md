# Спецификация: зависания UI (два независимых бага с похожим симптомом)

## Обзор

Диагностика реального пользовательского сеанса (процесс жил 2+ суток, macOS) выявила **два независимых бага**, оба проявляющихся как «приложение зависло», но с разной механикой и разным фиксом:

| | Баг А: фриз главного потока (Live traffic) | Баг Б: «мёртвый drawable» после сна (macOS) |
|---|---|---|
| Симптом | Окно не отвечает ни на что 6–12 минут | Клики обрабатываются, но картинка не меняется никогда |
| Кто виноват | Код лаунчера (`ui/traffic/live_view.go`) | Fyne/GLFW + macOS (поверхность окна не пережила сон) |
| Само отпускает? | Да, через 6–12 минут | Нет — до ресайза окна |
| Лечится без перезапуска | Само | Ресайзом окна |

Оба воспроизведены и подтверждены на живом процессе 2026-10-01/02 (PID 33658).

---

## Баг А: многоминутные фризы главного UI-потока на вкладке Live traffic

### Симптомы (из продакшен-логов и дампов)

Встроенный `ui watchdog` (core/runUIWatchdog) фиксирует это в `singbox-launcher.log` и сохраняет дампы горутин в `ui-freeze-*.txt`:

```
[WARN] ui watchdog: UI thread unresponsive for 30s
[WARN] ui watchdog: goroutine dump written to .../ui-freeze-20261001-231044.txt
[INFO] ui watchdog: UI thread responsive again after 11m46s
```

8 эпизодов за один вечер (2026-10-01, 22:34–23:18), по 6–12 минут каждый. **Все 3 сохранённых дампа** (`goroutine 1 [runnable, locked to thread]`) указывают на `ui/traffic/live_view.go`:

1. `buildLiveView.func4` → `widget.Label.SetText/Refresh` — обновление текста строки списка.
2. `buildLiveView.func4` → … → `go-text/typesetting/shaping.HarfbuzzShaper.Shape` — шейпинг шрифта при переносе строк.
3. `(*liveView).filteredIndices` → `(*liveView).passes` — полный O(n) скан буфера при пересчёте layout списка.

### Причина

`buildLiveView` подписывается на канал событий профайлера и на **каждое отдельное сетевое событие** синхронно в UI-потоке делает `fyne.Do(list.Refresh() + updateStatus() + rebuildBanners())` — без дебаунса. Каждый такой колбэк — полный re-layout списка (скан до 5000 событий + шейпинг текста видимых строк). При всплеске событий очередь колбэков растягивает фриз единственного GL-потока на минуты. Это не deadlock — поток `runnable`, просто перегружен.

### Сопутствующий эффект

`footprint` процесса достигал **6.7 ГБ пика** (4.7 ГБ на момент снятия, большая часть в swap/compressed) — `vmmap` показывает это как `VM_ALLOCATE` (Go-heap), т.е. раздут буфер live-view и связанные виджеты.

## Баг Б: после сна macOS окно перестаёт перерисовываться («мёртвый drawable»)

### Симптомы (подтверждены на живом процессе 2026-10-02)

После ~10 часов сна (23:34 → 09:54):

- **Бэкенд полностью жив**: debug API отвечает за 6–7 мс, переключение прокси через `POST /remote/machines/home/proxies/switch` реально работает (`{"ok":true}`, `selected` меняется).
- **Клики обрабатываются**: клик пользователя по UI привёл к реальному переключению прокси в бэкенде и записи в лог.
- **Картинка — замороженный кадр**: скриншоты окна, снятые с интервалом в минуты, пиксель-в-пиксель идентичны и показывают устаревшее состояние (подсвечен старый прокси, хотя бэкенд давно переключён).
- **Оконный менеджмент работает**: окно двигается, зумится — но содержимое не перерисовывается.
- **Ресайз «отмораживает»**: после изменения размера окна рендер ожил и показал актуальное состояние.

### Диагностика

- `GET /debug/goroutines`: `goroutine 1 [select, locked to thread]` в нормальном `runGL` — рендер-цикл Go не завис в вычислениях.
- `sample` (OS-стеки): главный поток в штатном `glfwPollEvents → nextEventMatchingMask` — ждёт события ОС, не застрял.
- Вывод: приложение продолжает «рисовать» в GPU-поверхность (drawable), которую macOS инвалидировала за время сна. WindowServer показывает последний закэшированный кадр; ресайз окна заставляет Fyne запросить новый drawable — и рендер оживает.

### Причина (гипотеза)

macOS за длительный сон инвалидирует Metal/GL-поверхность окна. Fyne/GLFW не обнаруживает потерю поверхности и продолжает представлять кадры в мёртвый drawable без ошибок. Проект не имеет обработки power-resume на macOS — SPEC 011 (`011-B-C-launcher-freeze-after-sleep`) фиксирует этот пробел: `internal/platform/power_darwin.go` — заглушка (в отличие от Windows `WM_POWERBROADCAST` и Linux `systemd-logind`), т.е. нет кода, который после wake мог бы форсировать пересоздание поверхности.

## Цель

1. (Баг А) Live traffic не должен приводить к многоминутным зависаниям главного UI-потока при любой интенсивности событий профайлера.
2. (Баг Б) После пробуждения macOS окно должно продолжать перерисовываться без ручного ресайза и без перезапуска приложения.

## Требования

### Баг А (дебаунс Live traffic)

1. **Дебаунс/троттлинг обновления UI.** События копятся в `v.events` (ring 5000) без задержки; `v.list.Refresh()` / `updateStatus()` / `rebuildBanners()` — не чаще раза в 150–250 мс, даже при всплеске событий. Конкретный механизм — в PLAN.md.
2. **Не терять события** — буфер заполняется независимо от частоты рефреша.
3. **Поведение Pause (`v.paused`) не меняется.**
4. **Не регрессировать отзывчивость** при редких событиях (задержка ≤ 150–250 мс незаметна).

### Баг Б (восстановление drawable после сна)

1. **Обнаружение wake-from-sleep на macOS** — реализовать обработку power-событий (закрывает пробел SPEC 011 для darwin; варианты: `NSWorkspaceWillSleep/DidWakeNotification` через cgo, IOKit, либо polling-эвристика времени между тиками — выбор в PLAN.md).
2. **После wake форсировать пересоздание поверхности окна** — механизм, эквивалентный эффекту ресайза (например, программный микро-ресайз окна или штатный способ Fyne/GLFW инвалидировать drawable, если такой есть). Способ выбрать в PLAN.md с проверкой на реальной машине.
3. **Идемпотентность**: повторные wake-события и ложные срабатывания не должны ломать рендер или менять видимый размер окна.
4. **Не ломать Windows/Linux** — существующие реализации power-resume (SPEC 011) не трогаем, общий код вызываем только если применимо.

### Общие

5. Реализация — в рамках `SPECS/CONSTITUTION.md` и `SPECS/IMPLEMENTATION_PROMPT.md` (логирование, минимальный диф, без смены публичных API наружу).

## Критерии приёмки

### Баг А
- [ ] При синтетическом всплеске событий (сотни/тысячи за секунды) главный UI-поток не блокируется дольше одного кадра дебаунса; watchdog не фиксирует `unresponsive`.
- [ ] `v.events` после всплеска содержит ожидаемые данные (ring 5000, без потерь на границе).
- [ ] При редких событиях список обновляется отзывчиво (≤ 150–250 мс).
- [ ] Поведение Pause/Resume не изменилось.

### Баг Б
- [ ] После реального сна macOS (часы) окно продолжает перерисовываться без вмешательства пользователя.
- [ ] Программная имитация wake-события вызывает пересоздание поверхности (проверяемо по возобновлению перерисовки).
- [ ] Повторные/ложные wake-события не меняют размер окна заметно для пользователя и не ломают рендер.
- [ ] Windows/Linux-сборки и их power-resume поведение (SPEC 011) не затронуты.

### Общие
- [ ] Сборка и тесты проходят (`go build ./...`, `go test ./...`, `go vet ./...`); линтер без новых ошибок.
- [ ] Обновлён `docs/release_notes/upcoming.md` (заметные для пользователя исправления «зависаний»).

## Диагностические артефакты (вне репозитория)

- `~/Library/Logs/singbox-launcher/singbox-launcher.log` — 8 эпизодов `UI thread unresponsive` за вечер 2026-10-01 (баг А); записи о реальном переключении прокси во время «замороженного» экрана 2026-10-02 (баг Б).
- `ui-freeze-20261001-225854.txt`, `-231044.txt`, `-231734.txt` — дампы горутин от watchdog (баг А).
- Живые дампы `/debug/goroutines`, `sample PID`, `footprint`/`vmmap` процесса PID 33658 — отсутствие deadlock, idle главный поток при мёртвой картинке (баг Б), Go-heap 4.7 ГБ / пик 6.7 ГБ (баг А).
- Пиксельно идентичные скриншоты окна с интервалом в минуты + оживление после ресайза (баг Б).

## Связанные спеки

- `011-B-C-launcher-freeze-after-sleep` — фриз после сна на Windows/Linux; фиксирует пробел реализации power-resume на macOS, который закрывает Баг Б.
