# SPEC 172 — DNS у правила маршрута (`rules[].dns`), как в LxBox

Статус: **O** (написана 15.10.2026; развилки §6 решены владельцем 15.10 — все по умолчанию). Тип: Feature. Контракт: бамп `contract/VERSION` → следующий свободный (на момент написания **1.1.130**), решение **D-137** (следующий свободный), норма — `contract/docs/TEMPLATE_LANG.md` §6.11 (новый, рядом с §6.10), `ONE_NAMESPACE.md` §1, `BACKUP.md` (таблица `rules[]` и раздел «Поля стороны LxBox»), `schema/backup.schema.json`; LxBox — `contract/TASKS_LXBOX.md` §127 (следующий свободный).

Повод — issue [#140](https://github.com/Leadaxe/singbox-launcher/issues/140): пользователь направлял DNS своих SRS-наборов на отдельный сервер, заводя руками DNS-правило со ссылкой на теги `user:<имя>`. У LxBox для этого есть опция в самом правиле.

---

## 1. Проблема

1. **У своего правила нет DNS.** Запись `rules[]` вида `inline|srs` несёт матчеры и цель маршрута, но не «чей DNS-сервер отвечает за эти домены». У пресетов это есть (переменная `dns_server` у `russian`, `fakeip`), у своих правил — только обходом через вкладку DNS: отдельное правило, ссылка на сгенерированный тег набора, ручная синхронизация при переименовании правила.
2. **LxBox это уже умеет** («DNS follows the rule», их §117 задача 3 и §256): объект `dns` рядом с `body` записи правила, сборка выпускает DNS-правило-зеркало. Контракт объявляет поле как LxBox-only (`ONE_NAMESPACE.md` §1, `BACKUP.md`).
3. **Лаунчер поле теряет.** `BACKUP.md` в таблице `rules[]` говорит «лаунчер не применяет, но провозит», а раздел «Поля стороны LxBox» — «в состояние не кладёт, на экспорте не пишет»; код делает второе: `state.Rule` поля не имеет, импорт `1.0` молча его отбрасывает (`core/backup/file_keys_10.go` `lxboxRuleKeys10`), сохранение Конфигуратора пересобирает правило из `RuleState`. Бэкап LxBox → лаунчер → LxBox приезжает обратно без DNS-опций.

## 2. Решение

### 2.1 Поле записи (обе стороны)

`rules[].dns` — необязательный объект у записей `inline` и `srs` (у `preset` поля нет: DNS пресета — его слот в `dns.rules`, §6.10):

```json
"dns": { "enabled": true, "serverTag": "google_udp", "forceIpv4": true }
```

| Ключ | Тип | Смысл |
|---|---|---|
| `enabled` | bool | DNS-запросы, подходящие под правило, отвечает сервер `serverTag` |
| `serverTag` | string | тег DNS-сервера из `dns.servers[]` (своего или пресетного); хранится и при `enabled: false` |
| `forceIpv4` | bool, пишется только `true` | AAAA-запросы под правило получают пустой ответ — приложение берёт IPv4; сервер не нужен |

Форма — **ровно LxBox** (camelCase ключей — развилка 1, §6). Отсутствие объекта = опций нет. Объект, где `enabled: false` и нет `forceIpv4`, писатель может не писать.

### 2.2 Зеркало (норма сборки, обе стороны — D-137)

Для каждого правила `inline|srs`, которое **сборка выпускает в `route.rules`** (включено, наборы `srs` скачаны), при `dns.enabled` и непустом `serverTag` выпускается DNS-правило-зеркало, при `dns.forceIpv4` — правило-глушилка.

**Матчер зеркала** `M` — ключи выпущенного маршрутного тела из списка реестра `allowlists.json` **`rule_dns_mirror_match`**: `rule_set` (у `srs` его вписала сборка — `user:<id>`, `user:<id>:N`), `domain`, `domain_suffix`, `domain_keyword`, `domain_regex`, `process_name`, `process_path`, `process_path_regex`, `package_name`, `package_name_regex`, `user`, `user_id`, `wifi_ssid`, `wifi_bssid`, `network_type`, `source_ip_cidr`, `source_ip_is_private`, `inbound`. IP-матчеры (`ip_cidr`, `ip_is_private`) в зеркало не идут: у DNS-запроса адреса назначения нет. Вид правила на матчер не влияет — имён полей и видов в коде движка нет.

**Гейт** — список реестра **`rule_dns_mirror_gate`**: тело содержит `port`, `port_range`, `protocol` или `network` с ненулевым значением — зеркала и глушилки нет (DNS-запрос под такие условия не подходит; так у LxBox). Пустой `M` — зеркала и глушилки нет: пустое тело DNS-правила ловит **всё**.

**Тела:**
- глушилка: `M + {"ip_version": 6, "action": "predefined", "rcode": "NOERROR"}`;
- зеркало: `M + {"server": "<serverTag>"}`;
- глушилка стоит **перед** зеркалом того же правила (иначе AAAA уйдёт на сервер).

**Место в `dns.rules`.** Зеркала в состоянии не хранятся — их выводит сборка из `rules[]`. Норма продолжает §6.10 (DNS-слот пресета по оси): пара «глушилка + зеркало» правила с номером `N` встаёт **перед первым слотом пресета, чей номер больше `N`**; такого нет — **сразу после последнего слота пресета**; слотов пресетов нет — **в конец** `dns.rules`. Номер слота — по §6.10. Пользовательские DNS-правила (`kind: user`) не двигаются и не считаются. Несколько зеркал в одном месте — по оси маршрутных правил.

Это обобщение порядка LxBox (их решение №6: группа «зеркала + DNS пресетов» атомарна, в порядке маршрутных правил, у первого слота пресета): при блоке слотов пресетов подряд и в порядке оси обе формулы дают одну последовательность. Лаунчер слоты пресетов не уплотняет (порядок пользователя, SPEC 062), и формула с местом «по номеру» сохраняет и его перетаскивание, и смысл LxBox.

**Сервер.**
- `serverTag` нет среди `dns.servers[]` (удалён, не приехал) — зеркало не выпускается, **предупреждение в отчёте сборки** с именем правила (у LxBox молча; у лаунчера тихих отбраковок нет — расхождение в диагностике, не в конфиге);
- сервер есть, но выключен — по умолчанию **включается в конфиг принудительно**, как у LxBox (их locked №7) — развилка 2;
- сервер снят санитайзером detour (`sanitizeDNSSection`) — зеркало становится `reject`, как любое DNS-правило на такой сервер (fail-closed, без изменений).

### 2.3 Интерфейс (лаунчер)

- Окно правила (`add_rule_dialog.go`), под «Direction»: блок **DNS** — галка «Send DNS to a dedicated server», выбор сервера (`DNSEnabledTagOptions` + текущий тег, если его нет в списке — не теряем), галка «Force IPv4 (drop AAAA)». Блок недоступен с подсказкой, если сработал гейт или матчер пуст (правило только по IP). У SRS — подсказка «Works only if the rule set contains domains».
- Вкладка JSON окна правила показывает объект `dns` рядом с телом, как он лежит в записи.
- Строка правила в Rules — метка DNS при активной опции.
- Вкладка DNS — зеркала **строками только для чтения** на их месте («↳ <имя правила> → <сервер>», «↳ <имя правила>: IPv4 only»), правка — переход в окно правила (развилка 3).
- Новые ключи `locale.T` — сразу с переводом в `bin/locale/ru.json`.

### 2.4 Что НЕ вводится

- Поле `resolve{}` LxBox — отдельная история, остаётся «LxBox, провозится» (а фактически: см. §2.5).
- Номер оси у DNS-правил, уплотнение слотов пресетов, хранение зеркал в `dns.rules` — нет.
- DNS у `preset` и у узлов — нет.
- Миграции нет: поле новое для лаунчера; бэкап LxBox с `dns` начинает доезжать.

### 2.5 Провоз `resolve{}`

Раз запись правила получает поле, `resolve{}` LxBox продолжает теряться. По умолчанию — не трогаем (норма «игнорирует молча» остаётся честной после правки `BACKUP.md`: таблица `rules[]` перестаёт обещать провоз). Хранить чужие поля записи без применения — отдельное решение.

## 6. Развилки (решены владельцем 15.10.2026 — все по умолчанию)

1. **Ключи `serverTag` / `forceIpv4` в camelCase.** По умолчанию — принять форму LxBox как есть: она уже в их бэкапах и в состоянии, переименование — миграция у обеих сторон ради стиля. Альтернатива — `server` / `force_ipv4` (snake_case, как остальной контракт) с миграцией LxBox.
2. **Выключенный сервер, на который ссылается правило.** По умолчанию — включать принудительно, как LxBox (locked №7), во вкладке DNS у сервера подсказка «used by rule …». Альтернатива — зеркало не выпускается, предупреждение в отчёте (выключенный сервер тогда значит «выключен везде»).
3. **Зеркала во вкладке DNS.** По умолчанию — строками только для чтения на их месте: порядок DNS-правил виден целиком. Альтернатива — только метка в Rules (меньше UI, но итоговый порядок DNS виден лишь в превью конфига).
4. **`forceIpv4` в этой SPEC.** По умолчанию — да: тот же гейт, та же точка вставки, у LxBox уже есть. Альтернатива — только сервер, глушилка следующей SPEC.
