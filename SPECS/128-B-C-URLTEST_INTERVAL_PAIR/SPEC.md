# SPEC 128 · urltest: interval из подписки едет без пары idle_timeout и роняет старт ядра

Статус: C. Ветка develop. Платформо-независимо (`core/build`).

Предыстория: issue [#118](https://github.com/Leadaxe/singbox-launcher/issues/118),
полевой репорт 01.09.2026. Пользователь лечил вручную заменой `"3h"` → `"5m"` в
сгенерированном `config.json`, значение возвращалось после каждого обновления
подписки.

## 1. Проблема

### 1.1 Что случилось

Подписка отдаёт группу с редкой перепроверкой:

```json
{ "type": "urltest", "interval": "3h" }
```

Лаунчер переносит `interval` в конфиг дословно. Ядро не стартует:

```text
FATAL start service: start outbound/urltest[auto]: interval must be less or equal than idle_timeout
```

### 1.2 Настоящая причина — не «3h слишком много»

Ядро (`protocol/group/urltest.go`, `NewURLTestGroup`) достраивает пропуски
своими дефолтами и только потом сверяет пару:

```go
if interval == 0    { interval = C.DefaultURLTestInterval }    // 3m
if idleTimeout == 0 { idleTimeout = C.DefaultURLTestIdleTimeout } // 30m
if interval > idleTimeout {
    return nil, E.New("interval must be less or equal than idle_timeout")
}
```

`3h` фатален не сам по себе, а потому что рядом нет `idle_timeout`: ядро
подставляет 30m и получает `3h > 30m`. Пара валидна при любом `interval`, если
`idle_timeout` назван явно.

### 1.3 `sing-box check` этот класс не ловит

Проверка живёт в КОНСТРУКТОРЕ аутбаунда, а не в разборе схемы. Подтверждено на
ядре 1.14.0-lx.33:

```text
sing-box check -c before.json   → exit=0
sing-box run   -c before.json   → FATAL ... interval must be less or equal than idle_timeout
```

Тот же класс, что правило 4 графового санитайзера про вложенную цепочку
(`outbound_graph_sanitize.go:34-35`: «check это не ловит, падает только run»).

### 1.4 Дыра открыта с ЧЕТЫРЁХ сторон, а не только со стороны импорта

| # | Вход | Место | Что происходит |
|---|------|-------|----------------|
| 1 | sing-box JSON подписка | `core/config/subscription/singbox_groups.go:33-39` | allowlist `singboxGroupOptionKeys` переносит `interval` как есть |
| 2 | Xray-подписка | `core/config/subscription/xray_balancer.go:66-72,122-136` | `balancer` + `burstObservatory.pingConfig.interval` → `urltest`; `idle_timeout` не выставляется **вообще** |
| 3 | **Собственные настройки лаунчера** | `bin/wizard_template.json:486-494` | у `urltest_interval` есть штатный вариант `1h`, а `idle_timeout` шаблон не задаёт нигде → **1h > 30m ломает старт без всякой подписки** |
| 4 | Направления / свёртка | `direction_twins.go:135-145`, `adapter_source.go:246-252` | `Interval` и `IdleTimeout` копируются независимо, взаимной проверки нет |

Пункт 3 — самостоятельный баг, шире issue: воспроизводится на чистой установке
без подписок.

Дополнительно: пришедшее значение оседает в UI. `autogroupform/form.go:238-248`
добавляет неизвестный `interval` отдельным пунктом в дропдаун, и `3h` переживает
все последующие Save.

### 1.5 Почему предложенное в issue лечение не годится

Issue просит нормализовать провайдерский `interval` под настройку лаунчера
(`3h` → `5m`). Владелец это отклонил в комментарии:

> не согласен, а чего 5h превращается в 5m это же задрюкает сервер

Верно: `interval` — период перепроверки ВСЕХ узлов группы. Замена `3h` на `5m`
даёт серверу в 36 раз больше проб, чем он просил. Провайдер поставил `3h`
осознанно.

## 2. Решение

**Поднимать `idle_timeout` до `interval`, а не урезать `interval`.**

`idle_timeout` — таймер засыпания цикла проверок (`loopCheck`, urltest.go:341):
после стольких секунд без трафика через группу тикер останавливается и группа
перестаёт пинговать узлы фоном; новый трафик (`Touch()`) поднимает цикл обратно.
Он не про нагрузку на сервер и не про таймаут соединений — только про экономию
на простаивающих группах.

Отсюда асимметрия: удлинение `idle_timeout` стоит не больше одной лишней
проверки у неактивной группы, тогда как укорачивание `interval` умножает
нагрузку на провайдера.

Коэффициент — **×1** (`idle_timeout = interval`), решение владельца 15.09.2026.
Обсуждался ×2 (группа успевает сделать одну проверку «на грани» перед сном);
отклонён ради прослеживаемости: при ×1 в `config.json` стоит ровно то число,
что пришло из подписки, без изобретённого лаунчером значения.

## 3. Требования

1. **R1.** urltest с `interval` > `idle_timeout` (в т.ч. дефолтного 30m, когда
   `idle_timeout` не задан) обязан получить `idle_timeout` = `interval`.
2. **R2.** `interval` не меняется НИКОГДА — ни при каких значениях.
3. **R3.** Правило живёт в ЕДИНСТВЕННОЙ точке — графовом санитайзере сборки
   (`sanitizeOutboundGraph`), а не частными проверками в четырёх входах.
   Принцип «новое ребро добавляется в санитайзер» — `CONSTITUTION`, память
   `build-graph-sanitizer`.
4. **R4.** Валидные конфиги не переписываются: короткий `interval` без
   `idle_timeout` и уже сходящаяся пара остаются байт-в-байт.
5. **R5.** Длительности разбираются по правилам ЯДРА: ядро знает суффикс `d`
   (`sing/common/json/badoption/internal/my_time`), которого нет у
   `time.ParseDuration`. `1d` — валидный интервал и обязан быть распознан.
6. **R6.** Нераспознанный `interval` (мусор) не подменяется: ядро отвергнет его
   с сообщением про сам ключ, тихая подстановка спрятала бы ошибку конфига.
7. **R7.** `selector` правило не трогает — он не пингует узлы.
8. **R8.** Каждое вмешательство — WARN с обеими величинами и причиной.

## 4. Границы

**Не входит** (осознанно отложено):

- `idle_timeout` в шаблоне и в форме `autogroupform` (значение по-прежнему не
  редактируется пользователем) — отдельным куском;
- чистка залипшего `3h` в дропдауне у тех, кто уже импортировал: значение
  провайдера легитимно, санитайзер его обезвреживает на сборке.

Решение владельца 15.09.2026: сейчас — только санитайзер.

1. `sing-box run` на конфиге из issue стартует и держится. ✅ проверено живым
   ядром 1.14.0-lx.33: «до» — FATAL, «после» — работает.

## Дополнение 15.09.2026: сравнение действующих значений (сверено с LxBox, задача 442)

Конструктор ядра (`NewURLTestGroup`) заменяет ноль и отсутствие ключа дефолтом: interval → 3m, idle_timeout → 30m, и только потом проверяет `interval > idle_timeout`. Поэтому правило сравнивает ДЕЙСТВУЮЩИЕ величины, и фатал закрывается ещё в двух ветках:

- interval не задан (3m), `idle_timeout: "1m"` → idle_timeout поднимается до `3m`;
- `idle_timeout: "0"` означает «не задан» (30m) → при interval больше 30m поднимается до interval.

Пробелы вокруг значения не срезаются, как у ядра: `" 3h"` — невалидная длительность, её отвергает само ядро. Тест — `TestURLTestCoreDefaultsBranches`.
