# PLAN 128 · Пара interval/idle_timeout — правило 6 графового санитайзера

## 1. Где ставится фикс и почему там

Четыре входа (SPEC §1.4) сходятся в одной точке — `sanitizeOutboundGraph`
(`core/build/outbound_graph_sanitize.go:104`), вызываемой из
`buildOrderedSections` (`core/build/build.go:254`) ДО обхода секций. Это
единственное место, где виден весь итоговый набор outbounds целиком, и там уже
живут пять правил того же рода («деградировать элемент с warning, а не отдать
ядру конфиг, который оно отвергнет»).

Альтернатива — чинить каждый вход отдельно — отвергнута: четыре копии правила,
расходящиеся при следующем новом входе. Память `build-graph-sanitizer`:
новое ребро добавляется в санитайзер, а не новой частной проверкой.

У санитайзера уже есть всё нужное: `e.isGroup()` (selector||urltest),
`e.dirty` + `rebuildEntries` (перезапись изменённой записи), фикспойнт-цикл.

## 2. Изменения в файлах

### 2.1 Новый: `core/build/outbound_graph_urltest.go`

Правило вынесено в отдельный файл — в `outbound_graph_sanitize.go` оно было бы
чужеродным: там рёбра графа, здесь опции одной записи.

| Функция | Назначение |
|---------|------------|
| `sanitizeURLTestTimings(e *graphEntry) bool` | правило: разбор пары, поднятие `idle_timeout`, WARN |
| `stringField(m, key) (string, bool)` | отсутствующее / пустое / нестроковое = «не задано» |
| `parseCoreDuration(s) (time.Duration, error)` | разбор по правилам ядра: `d` → часы, дальше stdlib |
| `expandDayUnits(s) (string, error)` | разворачивает `<число>d` в часы |
| `coreDefaultURLTestIdleTimeout = 30m` | зеркало `C.DefaultURLTestIdleTimeout` |

Логика `sanitizeURLTestTimings`:

1. не `urltest` → выход (R7);
2. нет `interval` → выход (ядро возьмёт 3m, ≤ любого дефолта);
3. `interval` не парсится или ≤ 0 → выход, значение остаётся ядру (R6);
4. нет `idle_timeout`:
   - `interval` ≤ 30m → выход (R4);
   - иначе `idle_timeout := interval`, WARN;
5. есть оба: `interval` ≤ `idle_timeout` → выход (R4); иначе
   `idle_timeout := interval`, WARN.

`parseCoreDuration` НЕ копирует парсер ядра целиком: дни разворачиваются в часы,
остальное отдаётся `time.ParseDuration`. Держать вторую копию значило бы завести
место, расходящееся с ядром по крайним случаям (дроби, знаки, `1d12h`).

`expandDayUnits` ловит `d` только как ЕДИНИЦУ — суффикс числа, за которым не
идёт другая буква; иначе мусор вида `1ds` молча стал бы валидным.

### 2.2 `core/build/outbound_graph_sanitize.go`

- шапка: правило 6 в общий список правил, с указанием на файл и на то, что
  `check` этот класс не ловит;
- `sanitizeEntryRefs`, ветка `case e.isGroup():` — вызов ДО разбора состава:
  пара ломает старт даже у группы с безупречным составом.

Возврат `true` заводит ещё одну итерацию фикспойнта; второй проход отдаёт
`false` (пара уже сходится), зацикливания нет.

### 2.3 Новый: `core/build/outbound_graph_urltest_test.go`

Через существующий `sanitizeHelper` — тот же вход, что у остальных правил.

## 3. Чего план НЕ делает

- не трогает четыре входа (`singbox_groups.go`, `xray_balancer.go`,
  `direction_twins.go`, `adapter_source.go`) — они продолжают переносить
  значения как есть, санитайзер обезвреживает результат;
- не трогает `bin/wizard_template.json` и `autogroupform` (SPEC §4);
- не трогает бинарь ядра (память `core-binary-hands-off`).

## 4. Проверка

1. Юнит-тесты правила и разбора длительностей.
2. Полный `go test ./core/build/` — правило не задело соседние правила.
3. **Живое ядро**: `check` + `run` на конфиге из issue до и после — иначе
   проверка бессмысленна, `check` этот класс пропускает (SPEC §1.3).
   Тестовое ядро гасится по захваченному PID (память `never-pkill-singbox`).
