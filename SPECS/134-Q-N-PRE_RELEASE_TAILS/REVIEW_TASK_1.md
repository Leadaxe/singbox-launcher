Хвост 1.4 (бэкап) в этих трёх коммитах не встречается — не проверялся.

## 7ef20d62 — петля на Final Конфигуратора

Вердикт: **чисто**.

- Адаптер `draftDisabler` (`ui/configurator/presentation/draft_disabler.go:24-31`)
  пишет в `model.Sources` через `FindNodeByLink`, не трогает сохранённый
  state — ловушка §3.1 ТЗ учтена, `Commit()` — no-op, как и требовалось.
- `noPromote` (`core/rebuild_corereject.go:322-326`) не подменяет
  боевой `config.json` в превью Final — соответствует §5В SPEC 132.
- Поток Fyne соблюдён: `progress` в `final_tab.go:445-450` завёрнут в
  `fyne.Do` перед вызовом `r.onProgress`; сама сборка идёт в горутине
  (`runner` уже был асинхронным до правки).
- `SaveGateAllows` не задваивается — новый код не вводит второй флаг,
  использует существующий предикат состояния сборки.
- Тест добавлен в существующий файл `core/rebuild_corereject_test.go`
  (не расползание по новым файлам) — соответствует правилу «один тест».

## e4c4d053 — сигнал демона на реальном старте

Вердикт: **исправлено** (найден и устранён дефект блокирующей защиты).

- **Дефект (исправлен):** `core/backend_daemon_darwin.go:281` безусловно
  сбрасывал `b.rejectTries` в 0 на входе в `applyCurrentConfig`. Асинхронный
  повтор `retryAfterCoreFatal` → `applyCurrentConfig("core-reject-fatal", …)`
  (`:409-411`) заходил в ту же функцию и обнулял свой же счётчик на каждом
  круге — `daemonRejectStartCap` (потолок из ловушки §3.8 ТЗ и SPEC 132)
  фактически не работал для цепочки «FATAL → выключили → apply → FATAL…»:
  при последовательности разных отвергаемых тегов цикл не останавливался бы
  по счётчику. Правка: сброс — только когда `caller != "core-reject-fatal"`
  (т.е. на настоящем новом заходе Start/Restart), см.
  `core/backend_daemon_darwin.go:278-289`. Естественный сброс на успехе
  (`:373`) и на статусе `STARTED` (`:571`) сохранён без изменений.
- Гонки: счётчик `rejectTries` — `int32`, все чтения/записи через
  `atomic.*` (`:281/373/395/402/571`); `applyCurrentConfig` целиком под
  `b.applyMu` (`:279-280`), повторный заход из `retryAfterCoreFatal` идёт в
  своей горутине (`go b.retryAfterCoreFatal(msg)` — `:582`), поэтому
  блокировки `applyMu` не пересекаются с потоком статусов — дедлока нет.
  Горутина не течёт: либо быстро возвращается (cap/no-match), либo уходит
  в штатный `applyCurrentConfig`, который сам конечен по `applyOnce`.
- UI не тронут — весь код лога/статуса без обращения к виджетам Fyne.
- Соответствие ТЗ §2.3/§4 (хвост 1.2): `ApplyError.Rejected()` и `FATAL`
  оба ведут в `corereject.Parse` через `DisableNodeNamedByCore`
  (`core/rebuild_corereject.go`, добавлено в 7ef20d62), выключение — в
  **сохранённом** состоянии (`savedStateDisabler`), как требует ТЗ.

## b9d31f68 — цикл страховки для remote

Вердикт: **чисто**.

- `writeRemoteConfig` переведён на `runDraftRejectLoop(configText, outPath,
  false, nil)` (`ui/configurator/presentation/presenter_save.go:417-421`) —
  тот же адаптер черновика из 7ef20d62, атомарная замена через
  `promoteCandidate` внутри общего цикла (не прямой `os.WriteFile`, как было
  до правки).
- Локальные dirty-маркеры не поднимаются — путь не добавляет новых вызовов
  к ним, комментарий на `:414-416` подтверждает намерение.
- Санитарный fallback на `:428-432` (если файл не заменён — Stop/ошибка не
  про узел — пишем последний кандидат как раньше) не ломает поведение до
  правки и не вводит собственный бесконечный цикл — цикл уже ограничен
  `coreRejectAskAfter`/`coreRejectHardCap` внутри `RunRejectLoop`.
- Зависимость от адаптера 1.1 соблюдена (сделано после 1.1, как требует
  ТЗ §2.4).

## Пределы циклов (общий пункт проверки)

`coreRejectAskAfter = 10`, `coreRejectHardCap = 200`
(`core/rebuild_corereject.go:57/65`) — не изменены, используются во всех
трёх путях (Final, remote, демон опирается на `savedStateDisabler`+общий
`coreRejectLoop` через `DisableNodeNamedByCore`). Отдельный
`daemonRejectStartCap = 10` для асинхронного пути демона — после правки
выше действительно ограничивает один заход Start/Restart.
