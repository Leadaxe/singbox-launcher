# ТЗ 4 · Остаток аудита мёртвого кода

**Цель одной фразой:** закрыть хвост аудита легаси — пересадить незакрытые
пункты `LEGACY_AUDIT` на файлы, которые существуют сегодня (половина адресов
указывает в удалённое), и вымести код, осиротевший после перевода разбора
источников на реестр.

---

## 0. Контекст для того, кто репозиторий видит впервые

Приложение — десктопный лаунчер VPN-ядра `sing-box`. Узлы приезжают
ссылками, подписками, JSON-конфигами Xray и файлами `.conf`.

Раньше под каждую схему ссылки был свой рукописный парсер на Go, плюс
отдельный конвертер Xray, плюс отдельный конвертер `.conf`. В ходе крупной
кампании (SPEC 133) всё это заменено **одним движком** `core/config/linkmap`,
который работает по **таблицам** в `contract/registry`. Рукописные парсеры
удалены — около полутора тысяч строк за один заход.

Удаляли аккуратно, но не начисто: часть вспомогательных функций осталась в
живых файлах, потому что их никто не звал уже из удалённого кода. Их и надо
вымести. Параллельно есть журнал `LEGACY_AUDIT` с находками, которые на
момент его написания были не сделаны, — но написан он **до** кампании, и его
адреса устарели.

## 1. Границы

### Входит

1. Ревизия незакрытых пунктов `LEGACY_AUDIT` — пересадить на живые адреса и
   честно отметить, какие закрылись сами.
2. Удаление осиротевшего неэкспортируемого кода в `core/config/subscription`
   и `core/config` (верхний уровень).

### НЕ трогать (в работе у других исполнителей)

- `core/config/subscription/shareuri_*.go`
- `core/config/subscription/body_classify.go`
- `core/config/subscription/xray_json_array.go`
- `core/config/subscription/xray_balancer.go`
- весь `core/config/linkmap/**`
- весь `contract/registry/**`

Находки в этих файлах **записать в отчёт, но не править**. В частности,
`staticcheck` покажет `core/config/linkmap/emit.go:87` и
`core/config/linkmap/exec.go:1993` — это чужое, пройти мимо.

### НЕ трогать (по существу)

- Экспортируемые функции (`func Имя` с большой буквы). У них могут быть
  вызовы из GUI-пакетов, которые исключены из `go test`, и из debug-API.
  Удаление экспортируемого = изменение public API = **спросить владельца**.
- Поведение. Это уборка, а не рефакторинг. Ни одного изменения в том, что
  видит пользователь.
- Тесты чужих пакетов.

### 2.2 Главная особенность: адреса аудита протухли

Незакрытые пункты ссылаются на файлы, которых **больше нет**:
`xray_hysteria.go`, `node_parser_wireguard.go`, `node_parser_vmess.go`,
`node_parser_hysteria.go`, `node_parser_masque.go`, `node_parser_naive.go`,
`outbound_tls_emit.go`.

Значит, по каждому незакрытому пункту вопрос **не** «как починить», а
**сначала**: «существует ли ещё проблема, или она уехала вместе с файлом?»
Для многих ответ — уехала: правило переехало в реестр. Это надо **проверить
фактом и записать**, а не предполагать.

Проверить, куда делся файл:

```
git log --diff-filter=D --name-only --pretty=format:'%h %s' -- core/config/subscription | sort -u
git show <commit>^:<путь> | rg '^func '
```

### 2.4 Почему грепом это не находится

Прогон «для каждой неэкспортируемой функции сделать `rg` по репозиторию и
оставить те, у кого ноль вызовов» дал **ноль результатов**. Причина: мёртвый
код образует **замкнутые графы вызовов** — `queryFlagTrue` зовёт
`queryParam`, тот зовёт `queryParamNames`, и все трое «используются», хотя ни
до одного нет дороги от живого входа.

**Вывод: авторитетный сигнал здесь — `staticcheck U1000`, а не греп.** Это
же стоит записать в `LEGACY_AUDIT.md` §4 («Как диагностировать остатки
впредь»).

## 3. Ловушки

1. **`staticcheck U1000` учитывает тесты.** Функция, которую зовёт только
   `*_test.go`, помечена **не будет**. Значит, удаляя функцию по подсказке
   staticcheck, вы можете сломать компиляцию теста, который зовёт её
   **соседа** из того же графа. Удалять графами, а не по одной, и
   пересобирать после каждого графа.
2. **Тестовый мусор — отдельный вопрос.** `parse_warnings_test.go:50`
   (`hasWarning`) мёртв, но это может быть остаток сокращённого теста.
   Удаление вспомогательной функции из теста трогает тест — отметить, не
   сносить молча.
3. **GUI-пакеты исключены из `go test`.** Символ, который staticcheck по
   `./core/config/...` считает мёртвым, мог бы звать UI-пакет. Для
   **неэкспортируемых** это невозможно (они видны только своему пакету) —
   отсюда и жёсткое ограничение задачи экспортируемых не трогать.
4. **Похожие имена — не одно и то же.** `applySubscriptionRequestHeaders`
   (`fetcher.go:99`, мёртвая) и `applySubscriptionRequestHeadersFor`
   (`fetcher.go:281`, живая). Удалить не ту — сломать загрузку подписок.
   Сверять точное имя.
5. **`go vet` этот класс не ловит.** Он прошёл чисто на `./core/config/...`.
   Не считать его зелёный вывод доказательством чистоты.
6. **Win7-сборка на go1.20.** Если по ходу уборки захочется «заодно упростить»
   — нельзя: без builtin `min`/`max`, без пакетов `slices`/`maps`, без
   `http.Request.PathValue`, без `range` по целому числу. В репозитории уже
   есть свои замены, например `slicesContains` в
   `ui/clash_api_tab_helpers.go:42`.
7. **Незакрытые пункты аудита могли закрыться сами.** Не чинить по инерции
   то, чего уже нет: сперва проверить, существует ли адрес.
8. **`DRIFT.md` §12.2 требует решения владельца** (подпись миграции у
   здоровых узлов). Ссылается из `LEGACY_AUDIT.md`. Не решать самому.
9. **Удаление — это дифф на сотни строк.** Ревьюеру нужна возможность читать
   его по частям: кластер = коммит.

## 4. Шаги

1. Прочитать `LEGACY_AUDIT.md` целиком, выписать незакрытые пункты (§3.1–3.5,
   строки 71–144) с их адресами.
2. По каждому проверить фактом: файл существует? функция существует? Если
   нет — найти по `git log --diff-filter=D`, куда правило уехало, и
   **отметить пункт закрытым с обоснованием** прямо в `LEGACY_AUDIT.md`
   (в стиле соседних `✅ ЗАКРЫТО`, с датой).
3. Оставшиеся живые пункты пересадить на актуальные адреса. **Чинить их в
   этом заходе не надо** — задача про мёртвый код; живые пункты просто
   перестают врать адресом.
4. Прогнать `staticcheck -checks U1000 ./core/config/...` на текущем дереве
   (цифры могли сдвинуться) и отфильтровать по границам §1.
5. Удалять графами, в порядке дешевизны:
   кластер 2 (`uri_params.go`) → кластер 1
   (`node_parser_transport.go`) → кластер 4 (`node_ref.go` целиком,
   `detour_topo.go`, `outbound_jsonbuilder.go`) → кластер 3 (россыпь).
   После каждого графа — `go build ./...`.
6. Повторить `staticcheck` и убедиться, что удалённое не оставило новых
   сирот (удаление вызывающего часто вскрывает следующий слой).
7. Дописать в `LEGACY_AUDIT.md` §4 наблюдение из §2.4: греп по одному имени
   мёртвые графы не видит, авторитетный инструмент — `staticcheck U1000`.

## 5. Как проверить

Локально:

```
go build ./...
staticcheck -checks U1000 ./core/config/...
```

Если написан новый тест (нужен максимум **один** на весь заход, и в задаче
про удаление кода он скорее всего **не нужен**) — только он, по имени:

```
go test ./core/config/... -run 'TestИмяВашегоТеста' -count=1
```

**Запрещено локально:** `go test ./...`, прогон пакета целиком «на всякий
случай», `go vet ./...` по репозиторию, Win7-сборка с `go.win7.mod`.

**Запрещено вообще:** запускать `sing-box run`, убивать процессы sing-box
(`pkill`, `killall`) — на машине живой VPN; трогать бинарь ядра в бандле.

Полный прогон — **обязателен** для этой задачи, потому что удаление может
задеть тест, который локально не гоняли:

```
gh workflow run ci.yml --ref develop -f run_mode=tests
```

Упавшее разбирать отдельным заходом: `gh run view <ID> --log-failed`.

## 6. Как коммитить

Ветка **только `develop`**. Запрещены `git checkout`/`switch`, `stash`,
`reset`, `rebase`, `clean`, `git add -A`, `git commit -a`. Рабочая копия
разделяемая — чужие незакоммиченные правки не трогать.

Явным списком путей, **по коммиту на кластер**:

```
git commit -m "refactor(config): снят мёртвый транспортный легаси входа ссылки" -- \
  core/config/subscription/node_parser_transport.go \
  core/config/subscription/uri_params.go
git commit -m "docs(audit): LEGACY_AUDIT пересажен на живые адреса" -- \
  SPECS/131-F-O-UNIFIED_NODE_PIPELINE/LEGACY_AUDIT.md \
  docs/release_notes/upcoming.md
git push origin develop
```

В `docs/release_notes/upcoming.md` — по одному пункту в
`### Technical / Internal` и `### Техническое / Внутреннее` (пользователю
уборка не видна, в Highlights не место).
