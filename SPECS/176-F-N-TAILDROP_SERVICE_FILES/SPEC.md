# SPEC 176 — Служебные файлы Taildrop на десктопе: буфер и ссылки

Решение владельца 03.11.2026: лаунчер принимает и отправляет служебные файлы
LxBox ↔ лаунчер. Норма — контракт `docs/SERVICE_FILES.md` (1.1.148, ключ
разрешения 1.1.149, чувствительный клип 1.1.153), константы —
`registry/service_files.json`. Опора — SPEC 175 (файлы Taildrop) и задача
LxBox 707 (их сторона готова и проверена на эмуляторе).

## 1. Где работает

Только у своего ядра (локальный демон: macOS, Windows amd64/arm64). Команда
служебного файла — про ЭТОТ компьютер: буфер обмена и браузер. Узлы удалённых
машин служебные файлы не разбирают: у них они остаются обычными файлами
входящих, как у официального клиента Tailscale.

## 2. Приём

Фоновая подписка на входящие у каждого tailscale-узла своего ядра, пока ядро
работает (тот же поток, что автосохранение SPEC 175 §3.4; у узла с галкой
автосохранения — одна подписка на оба дела). Узел с выключенным Taildrop
(`disable_taildrop`) отдаёт пустые входящие — подписка ничего не делает.

По кадру входящих, до автосохранения и до уведомления «принят»:
1. Кандидат — имя с `name_prefix` и `name_suffix`, размер не больше
   `max_bytes`. Тело читается в память.
2. Не служебный (§4 контракта: не UTF-8 / не JSON / `lx` не из `versions` /
   `commands` не список) — обычный файл: остаётся во входящих, дальше —
   автосохранение, если галка стоит.
3. Служебный — возраст = сейчас − `modifiedAt`; старше `ttl_seconds` —
   команды не выполняются. Иначе команды по порядку: неизвестный `kind` и
   команда без разрешения пропускаются. `clipboard` — из всех служебных файлов
   кадра в буфер идёт последний по `modifiedAt` (при равенстве — по имени).
   `open_url` — схема из `kinds.open_url.schemes`; ссылка открывается в
   браузере сразу (разрешение дано на устройство явно).
4. Файл удаляется ВСЕГДА после разбора.

После выполнения — уведомление: «Clipboard updated» / «Link opened» с именем
устройства. Текст буфера и ссылку в уведомление и журнал не пишем.

Обычный файл (не кандидат или кандидат-не-служебный): с галкой автосохранения —
в Downloads (SPEC 175 §3.4); без неё — уведомление «File received: <имя> с
<устройство>» (вопрос владельца 03.11.2026: «а когда приходит файл, уведомления
появляются?»). Файлы, лежавшие до подписки (первый кадр), не объявляются.
Уведомление — свой путь macOS, на остальных платформах — Fyne.

## 3. Разрешения

На устройство и вид команды: «Accept clipboard», «Accept links» — пункты с
галкой в меню `…` устройства на вкладке Network окна узла своего ядра. По
умолчанию выключены. Хранятся в `settings.json`
(`taildrop_service_permissions`: `sender_id`, `sender_name`, `clipboard`,
`open_url`) — настройка этого компьютера, в бэкап не идёт.

Ключ — `senderID` файла (stable node ID = `StableID` пира в статусе). Если
`senderID` пуст (ядро старше `1.14.4-lx.30-rc.2`) — `senderName` против
`sender_name` записи (DNS-имя устройства без домена = `ComputedName`). После
перезапуска ядра у лежащих файлов оба поля пусты — разрешения нет, файл
удаляется без выполнения (норма контракта).

## 4. Отправка

Пункт «Send text…» в меню устройства (те же условия, что у «Send file…», и
только у своего ядра). Окно: многострочное поле, заполненное текущим буфером
обмена (текст виден перед отправкой — контракт §7 п.3), кнопки:
- «Send to clipboard» — команда `clipboard`;
- «Open on <устройство>» — команда `open_url`, только если в поле одна
  http(s)-ссылка;
- Cancel.

Имя `lx-<UTC YYYYMMDDTHHMMSSZ>-<5 символов [a-z0-9]>.json`, тело
`{"lx":1,"commands":[…]}`. Не отправляем и называем причину: пустой текст,
тело больше `max_bytes`, не UTF-8. Отправка только по кнопке, выполненная у нас
команда дальше не уходит.

## 5. Что не входит

Пункт в трее и горячая клавиша (только по слову владельца), не-текстовые
клипы, история буфера, служебные файлы у удалённых машин.
