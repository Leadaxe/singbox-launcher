### 1.2 Корень

Запись сервера и её переменные живут **отдельно** и связаны только склейкой
имени. Разрыв N8 закрыт разворачиванием (`contract/docs/TEMPLATE_LANG.md:571`):
вложенная запись `{vars[], server{}}` при загрузке шаблона становится плоской,
а её объявленные `vars` — **переменными шаблона** с именем `dns_<tag>_<var>`
(`core/template/dns_server_form.go:22-25`, `:137-151`; `wizard_ui: hidden` —
`:148`), плейсхолдеры в теле переписываются `@outbound` → `@dns_<tag>_outbound`
(`:159-189`), список уходит в общий `root.Vars` (`core/template/loader.go:291-295`).
Значения — в корневых `vars` состояния (`ui/configurator/presentation/presenter_state.go:222-231`).
Запись же на диске — только `{kind, tag, enabled}` (`core/state/dns_options.go:34-36`, `:76-96`).

Следствия склейки:

- переносимость решается **по имени переменной**, а не по записи: реестр
  пришлось учить пяти склеенным именам (`contract/registry/vars.json:41-70`);
- связь «переменная → сервер» восстанавливается разбором префикса, и тег с
  подчёркиванием даёт неоднозначность (`google_doh` / `google_doh_vpn`),
  которую UI лечит правилом «самый длинный тег» в двух местах
  (`ui/configurator/tabs/dns_template_vars.go:44-53`,
  `ui/configurator/tabs/settings_tab.go:186-197`);
- у LxBox форма одна — запись (`app/lib/models/codec/dns_record.dart:40-47`), и
  две стороны говорят о той же настройке на разных языках.

## 2. Решение владельца (15.09.2026, согласовано с LxBox) и границы

```json
"dns": { "servers": [
  { "kind": "template", "tag": "google_udp", "enabled": true,
    "vars": { "outbound": "vpn-1", "dns_ip": "8.8.4.4" } } ] }
```

| Что | Норма |
|---|---|
| Где значения | в записи сервера `dns.servers[kind=template].vars` — и в state v8, и в файле 1.0 |
| Имена | локальные имена объявления сервера в шаблоне (`dns_options.servers[].vars[].name`); подставляются в `@outbound`, `@dns_ip` тела (`server.detour`, `server.server`) |
| Нет значения | `default_value` объявления |
| Корневые `dns_<tag>_<var>` | писатель не пишет; читатель принимает терпимо и перекладывает в запись |
| Реестр | пять имён D-117 — терпимая форма чтения (`portable: false`); `dns.servers[].vars` — «Поддержка: обе» |
| Не меняется | `kind: user` (тело sing-box в `body`, маршрут в `body.detour`); `kind: preset` DNS-сервера (переменные — в записи правила пресета `rules[].vars`) |
| LxBox | форма уже такая; меняются терпимость, нормы §3 и тест реестра (§11) |

Расширение объёма (решение владельца, передано через LxBox): нормы §3
действуют **сразу для двух носителей** — `dns.servers[kind=template].vars` и
`rules[kind=preset].vars`.

Следствие решения «умолчание не писать» (Н4): шаблоны у сторон разные, поэтому
незаданное значение на другом устройстве берёт умолчание **его** шаблона.

## 3. Нормы «значения переменных записи» (оба носителя)

> Нормы **Н4** (умолчание не пишется) и **Н2** (необъявленное имя выкидывается)
> — **решения владельца от 15.09.2026**. Нормы **Н9–Н10** (две линии
> fail-closed) — согласованы с LxBox 15.09.2026; правило на выпавший сервер
> становится `reject` (ответ LxBox №4). **Н11** (необъявленный `@name` в теле —
> ошибка шаблона) — ответ LxBox №5.

Носители:

| Носитель | Запись | Объявление имён и умолчаний |
|---|---|---|
| D | `dns.servers[]` с `kind: template` | `dns_options.servers[]` шаблона этой стороны, запись с тем же тегом: `vars[].name`, `vars[].default_value` |
| P | `rules[]` с `kind: preset` | `presets[]` шаблона этой стороны с `id` = `ref`: `vars[].name`, `vars[].default_value` (у лаунчера алиас `default`, `core/template/preset_types.go:246-255`) |

**Н1. Форма.** `vars` — объект `string → string`, необязательный. Отсутствие
ключа `vars` и пустой объект равнозначны: «все переменные следуют шаблону».
Писатель пустой объект не пишет. У D ключ стоит в записи рядом с `kind`, `tag`,
`enabled`; у P — как сегодня (`core/state/rule_types.go:105-107`). У записей
других видов (`user`, `preset` у DNS; `inline`, `srs` у правил) `vars` нет:
импорт называет такой ключ `backup_unknown_field` (§8, ловушка Л5).

**Н2. Имена (решение владельца).** Законны только имена, объявленные
носителем в шаблоне **своей** стороны.

- Импорт: необъявленное имя выкидывается и называется —
  `backup_var_skipped` `{name, record, reason: undeclared}` (П6).
- Своё хранение (шаблон обновился и переменную убрал): имя снимается при
  следующей записи **без предупреждения**.
- Сборка необъявленное имя не использует никогда.
- Запись, чей носитель в шаблоне не объявлен вовсе (сервера с таким тегом нет,
  пресета с таким `id` нет), обрабатывается правилами записи (§4.4, §5.4), а не
  поимённо: её имена отдельными предупреждениями не называются.
- Нет объявления — нет нормализации: у лаунчера список пресетов шаблона
  отфильтрован платформой хоста и валидацией (`core/template/loader.go:344`,
  `:353`; `preset_loader.go:144-158`), а у удалённой машины и мобильных `id`
  пресета может не быть вовсе. Такие `vars` пишутся как есть; корпус на этом
  стоит (`corpus/backup/v10_rules_body_action.backup.json:46-50` →
  `expected.json:16`, `block_ads` с `list_mode`).
- Переменная пресета с `ref` (значение в глобальных `vars`, `TEMPLATE_LANG.md`
  §8.2) нормализацией не трогается: `ExpandPresetWithGlobals` её хранимое
  значение игнорирует (`core/build/preset_expand.go:122-128`), а
  `buildPresetVarsMap` (`resolve_dns.go:476-481`) и `ExpandPresetOutbounds`
  (`preset_outbounds.go:80-86`) читают — снятие изменило бы гейт DNS-серверов
  пресета. В шаблонах `ref`-переменных сейчас нет.

**Н3. Значения.** Строки, как в схеме (`object string→string`). Сравнение и
хранение — после `TrimSpace`: значение хранится подрезанным, пустое после
подрезки равно отсутствию ключа и не пишется (ответ LxBox №6; у лаунчера сборка
так уже читает: `core/template/vars_resolve.go:461-470`).

**Н4. Умолчание не пишется (решение владельца).**

1. Писатель — **сохранение из UI, импорт, миграция, экспорт** — снимает ключ,
   если значение совпадает с `default_value` объявления в шаблоне **своей**
   стороны на момент записи. У лаунчера умолчание разрешается тем же движком,
   что на сборке, для цели этого состояния (`VarDefaultValue.ForTargetIn`,
   per-platform `default_value` — `TEMPLATE_LANG.md` §7.4).
2. Выбор в UI значения, равного умолчанию, снимает ключ — это сброс к
   умолчанию. Отсутствие ключа означает «следовать шаблону».
3. Читатель значение, равное умолчанию, **принимает** (старые файлы LxBox, старые
   состояния лаунчера), но при следующей записи снимает.

Обоснование владельца: смена умолчания в новой версии шаблона меняет поведение
у всех, кто его не трогал. **Цена:** закрепить значение, совпадающее с текущим
умолчанием, так, чтобы оно пережило смену умолчания в шаблоне, нельзя.
Прецедент у лаунчера уже есть — `rules[].vars` задуманы «только diff от
дефолтов» (`core/state/rule_types.go:105-107`, `:115-119`), но нормой это не
было и писатели его не соблюдают (§7.3).

**Н5. Полнота (а).** Писатель кладёт в `vars` **все** значения, выбранные
пользователем и не снятые Н2/Н4 — не только маршрут: `outbound`, `dns_ip`,
`safe_profile`, `dom_resolver` и любые будущие имена объявления.

**Н6. Типы значений.** По типу объявления (`TEMPLATE_LANG.md` §2.2):
`outbound` — корневое имя (Направление и его `-auto`, свёртка и её `-auto`,
корневой узел, системный тег шаблона, зарезервированный литерал); `dns_server`
(синоним чтения `dns_servers`, так объявлен `dom_resolver` в шаблоне лаунчера;
приводится к канону при загрузке, `core/template/preset_types.go:443-451`) — тег
DNS-сервера; прочие — как есть.

**Н7. Корневые склеенные имена не пишутся.** Ни state, ни файл не несут
`vars.dns_<tag>_<var>`. Пять имён D-117 в реестре — терпимая форма чтения (д).

**Н8. Терпимое чтение корневых `dns_<tag>_<var>` (в).** Корневое имя `N`
разрешается против объявлений шаблона своей стороны: кандидаты — пары
`(tag, var)`, для которых `"dns_" + tag + "_" + var == N`; из нескольких
кандидатов выигрывает **самый длинный тег** (правило уже живёт в
`dns_template_vars.go:44-53`). Дальше:

| Ситуация | Импорт (файл) | Своё хранение лаунчера (§7) |
|---|---|---|
| кандидата нет | имя остаётся корневым и идёт общим правилом `vars`: не в реестре переносимых → `backup_var_skipped {reason: not_portable}` (как сегодня) | корневое имя-сирота, снимается существующим фильтром сирот (`presenter_state_helpers.go:163-172`) |
| у записи сервера **непустой** `vars` | побеждает запись: корневое значение выкидывается, `backup_var_skipped {reason: superseded}` | побеждает запись; корневое снимается молча |
| запись сервера есть, `vars` пуст | значение переносится в `vars` записи, затем Н2–Н4 | то же |
| записи сервера с этим тегом **нет** | корневое выкидывается, `backup_var_skipped {reason: no_record}` | запись **создаётся**: `{kind: template, tag, enabled: <умолчание шаблона>, vars: {var: value}}` — у лаунчера отсутствие записи и так значит «включённость по умолчанию» (`core/build/resolve_dns.go:432-443`), и конфиг не меняется |

После переноса корневой ключ удаляется. Правило одно на все файлы 1.0 и 0.x —
без развилки по версии (П4 «разбор внутри мажора один»).

**Н9. Fail-closed, линия 1 — импорт.** Список известных целей — единый список
D-117, считанный **после** слияния (`core/backup/import.go:435`,
`importKnownTags`).

- Шаблонный сервер, у которого значение переменной типа `outbound` вне списка,
  приезжает `enabled: false` с `backup_unknown_outbound {server, outbound}`.
  Значение остаётся в записи — пользователь видит, куда метил файл.
- У совпавшей записи (§5.2) значение файла **применяется**, и сервер
  выключается так же: пользователь видит, куда метил файл, и ничего не утекает
  (ответ LxBox №7). Проверяются значения, оставшиеся в записи после
  нормализации: значение, равное умолчанию, снято Н4 и целью файла не считается.
- То же у `kind: user`: `body.detour` вне списка → `enabled: false` +
  `backup_unknown_outbound {server, outbound}`.
- Проверяются записи, которых импорт коснулся: дописанные и те, чьи имена
  наложены из файла (§5). Локальные записи, которых файл не касался, импорт не
  трогает — их ловит линия 2.
- Значения типа `dns_server` (`dom_resolver`) на импорте не проверяются:
  висячий резолвер лечит сборка (Н10, ответ LxBox №9).
- «Проверять нечем» (список `nil`, `import.go:582-588`) — цели не режутся,
  как у правил.

**Н10. Fail-closed, линия 2 — сборка.** DNS-сервер, чей `detour` после
подстановки указывает на тег, которого нет в финальном конфиге, **не
эмитится**, с предупреждением. Ссылки на него:

| Ссылка | Что делает сборка | Почему |
|---|---|---|
| `dns.rules[].server` | правило остаётся со своим условием и становится `action: reject`; ключи маршрута (`server`, `strategy`, `disable_cache`, `rewrite_ttl`, `client_subnet`) снимаются (ответ LxBox №4) | сервер выпадает только из-за висячего detour — пользователь хотел эти домены через конкретный маршрут; уход в `dns.final` (часто прямой) — утечка того же класса, что detour fail-closed. Сломанный резолв виден пользователю, утечка — нет |
| `dns.final` | ключ снимается, последним DNS-правилом встаёт `{"action": "reject"}` без условий | без `final` ядро берёт первый сервер списка — у шаблонов это системный резолвер; правило-заглушка не пускает к нему ни один запрос |
| член DNS-группы | выпадает из состава; группа, опустевшая от этого, выпадает сама и лечится как сервер | прежняя норма групп (`preset_merge.go:852-915`) |
| `domain_resolver` DNS-сервера, `route.default_domain_resolver`, `outbounds[]`/`endpoints[]` `.domain_resolver` | **замена**: резолвер по умолчанию шаблона (`TemplateData.DefaultDomainResolver`), если он в конфиге, иначе первый эмитированный сервер не `fakeip`/`hosts` (как LxBox `heal_dangling_dns_resolvers.dart`); у DNS-сервера с IP-адресом ключ просто снимается; если замена — сам этот сервер (сослаться на себя нельзя), берётся следующий пригодный сервер, иначе ключ снимается (сверено с LxBox 15.09.2026). Группа DNS-серверов, опустевшая от выпавших членов, выпадает и лечится как сервер (`pruneDNSGroupMembers`) | резолвер адреса сервера работает ДО туннеля: имя VPN-сервера разрешается раньше, чем туннель поднят, и соединение с его IP сеть видит и так — пользовательских доменов тут нет. Без резолвера ядро не стартует: `sing-box check` → FATAL «missing `route.default_domain_resolver` or `domain_resolver` in dial fields» (проверено на lx.39) |

Форма проверена ядром 1.14.0-lx.39: `sing-box check` принимает правило
`{"action": "reject"}` без условий (`option/rule_dns.go` `IsValid` учитывает
действие), логическое правило и правило с `rule_set` в форме `reject`; прогон
отдельного ядра на 127.0.0.1 отвечает REFUSED и на имя, и на корневой запрос
`.` (у `domain_regex` пустое имя не матчится — поэтому заглушка без условий).

Лечение привязано к серверам, выпавшим ВТОРОЙ линией (и к группам, опустевшим
от этого): у конфига, где линия 2 не сработала, ни один байт не меняется.
Сервер, выпавший из-за `endpoint` (SPEC 121, резолвер tailnet без узла), лечится
прежним механизмом: правило снимается, `final` — первым сервером; висячий
`domain_resolver` на этапе слияния пресетов (`preset_merge.go:808-818`) — прежним
снятием ключа. Эта спека их не меняет. `detour: direct-out` после подстановки
снимается, как сегодня у обеих сторон (`resolve_dns.go:571-575`; LxBox
`preset_expand.dart:638-644`) — это не висячая ссылка.

**Н11. Необъявленный `@name` в теле — ошибка шаблона (ответ LxBox №5).** В теле
шаблонного DNS-сервера плейсхолдер `@name` обязан быть объявлен самим сервером;
у лаунчера расширением стороны допускается ещё переменная шаблона верхнего
уровня (§4.1 п. 2). Имя, не объявленное ни там, ни там, — ошибка ШАБЛОНА
стороны, а не данных пользователя: валидатор шаблона отвергает шаблон при
загрузке (у лаунчера `ParseTemplateData` → ошибка, скачанный шаблон не ставится;
`core/template/dns_server_form.go`). Бандл-шаблон проверку проходит. Имя из
`vars` записи, не объявленное сервером, не подставляется никогда (Н2).

### 3.1 Таблица сверки сторон по пунктам (а)–(д)

## 4. Семантика сборки

### 4.1 Порядок разрешения `@name` в теле шаблонного DNS-сервера

1. Имя объявлено **этим** сервером: значение из `vars` записи (Н3: непустое
   после подрезки) → иначе `default_value` объявления (у лаунчера — для цели
   состояния) → иначе «не задано»: ключ с этим плейсхолдером выпадает
   (LxBox: `null` → ключ убирается, `dns_servers.dart:51-58`). Сверено: лаунчер
   до волны оставлял в ключе пустую строку — `SubstituteVarsInJSONStrict` на
   объявленном имени без значения отдаёт `""` с WARN «substitute: empty scalar»
   (`core/template/substitute.go:433-446`), а на необъявленном имени — ошибку, и
   тело уезжало неподставленным (`resolve_dns.go:563-566`). С волной ключ
   выпадает, как у LxBox; в бандл-шаблоне у всех переменных серверов есть
   умолчания, и конфиг от этого не меняется.
2. Имя не объявлено сервером — у лаунчера **расширение desktop**: глобальная
   переменная шаблона (как сегодня, `resolve_dns.go:560-566` подставляет по
   всему `td.Vars`). Локальное имя затеняет глобальное. В общую норму это не
   входит (ответ LxBox №5): LxBox подставляет только имена, объявленные
   сервером, а имя, не объявленное ни сервером, ни (у лаунчера) шаблоном, —
   ошибка шаблона (Н11), до сборки такой шаблон не доходит.

### 4.2 Без склейки имён

- `NormalizeDNSOptions` по-прежнему разворачивает вложенную запись в плоскую
  (шесть читателей верхнеуровневого `tag`, `dns_server_form.go:16-20`), но
  **не** порождает переменные шаблона и **не** переписывает плейсхолдеры:
  объявления остаются при сервере — `TemplateData.DNSServerVars[tag] []TemplateVar`
  (новое поле), тело держит локальные `@outbound`, `@dns_ip`.
- `loader.go:291-295` перестаёт дописывать DNS-переменные в `root.Vars`;
  валидация объявлений сервера — теми же проверками, что у переменных шаблона
  (лексика и дубли имён, `if`/`if_or`, `#if` в `default_value`), отдельным
  вызовом на список каждого сервера, плюс Н11 для плейсхолдеров тела
  (ловушка Л7).
- `substituteTemplateDNSServer` (`resolve_dns.go:548-578`) получает
  объявления сервера и `vars` его записи; разрешённая карта = объявления
  сервера (§4.1 п. 1) поверх глобальных (§4.1 п. 2); движок подстановки тот же.

### 4.3 В шаблоне приёмника нет переменной

Имя записи не используется сборкой; при следующей записи снимается (Н2),
на импорте называется `backup_var_skipped {undeclared}`.

### 4.4 В шаблоне приёмника нет самого сервера

Запись не эмитится — у обеих сторон уже так: лаунчер обходит библиотеку
шаблона, а не записи состояния (`resolve_dns.go:171-203`); LxBox —
`templateByTag[tag] == null` → тело не собирается (`dns_servers.dart:189-198`).
Хранение: LxBox снимает запись-сироту молча (`dns_servers.dart:96-109`).
Сверено у лаунчера: сохранение из UI сироту тоже уже теряет — модель её не
загружает (`populateUserDNSFromState` берёт только `kind: user`,
`presentation/preset_ref_helpers.go:165-200`), а досев из `DNSTemplateOverrides`
пропускает теги, которых шаблон не объявил (`models/preset_ref_sync.go:470-472`);
живут сироты только в файле, пока его не перепишет UI, — debug API, импорт и
экспорт провозили их как есть. По Н2 запись-сирота снимается при записи молча у
обеих сторон и у всех писателей лаунчера. Импорт — §5.2.

### 4.5 Вторая линия fail-closed: что сейчас и что будет

**Сейчас у лаунчера — тихая утечка.** `SanitizeDNSDetours`
(`core/build/dns_detour_sanitize.go:89-94`) у сервера с висячим `detour`
**удаляет ключ** и пишет только `WarnLog` «resolution will go direct»;
обоснование в `:21-27` («сняв ключ, ядро резолвит напрямую… выбросить сервер
значило бы уронить весь DNS»). Вызов — `core/build/build.go:340-344`, в превью
не работает (`:342`). Сервер google_udp, настроенный через удалённое
Направление, после этого резолвит **мимо VPN** без единого слова в UI.

**Будет.** Ветка `detour` повторяет ветку `endpoint` того же прохода
(`dns_detour_sanitize.go:79-87`): сервер выбрасывается целиком, тег — в
`droppedTags`, ссылки чинит `repairAfterServerDrop` (`:105-112`, `:135-187`) по
таблице Н10. Комментарий `:21-27` переписывается: у DNS-сервера `detour` — такая
же ручка анонимности, как у узла (`detour-failclosed-uniform`).

Что умеет лечение сегодня (`core/build/preset_merge.go`):
`repairDanglingDNSRefs` (`:784-834`) — `dns.final` → первый эмитированный тег
или ключ удаляется (`:798-806`); `servers[].domain_resolver` → ключ удаляется
(`:808-818`); `dns.rules[].server` → правило снимается целиком (`:820-833`);
`pruneDNSGroupMembers` (`:852-915`) — члены групп, пустая группа выпадает.
`repairAfterServerDrop` передаёт в корне только `final`
(`dns_detour_sanitize.go:146-152`).

Остаток, закрытый в той же волне (Н10):

- **`route.default_domain_resolver` и `outbounds[]`/`endpoints[].domain_resolver`
  не лечились нигде** (`route_merge.go:57-62`, `:149-153`; ядро-контекст эти поля
  не заполняет — `core/config_service_context.go:179-200`). Без лечения
  fail-closed превратился бы в отказ ядра стартовать. Секция `dns` теперь
  собирается раньше остальных (`build.go`, `buildOrderedSections`), итог второй
  линии — выпавшие теги и резолвер замены — доходит до секций `route`,
  `outbounds`, `endpoints`, и те заменяют ссылку (аналог LxBox
  `heal_dangling_dns_resolvers.dart`). В логических DNS-правилах сервер стоит на
  верхнем уровне правила (вложенные действий не несут), поэтому отдельного
  обхода не нужно;
- DNS-правило на выброшенный сервер не снимается, а становится `reject`, `final`
  — заглушкой `reject` (ответ LxBox №4, таблица Н10): прежнее снятие правила
  уводило его домены в `dns.final`, и при прямом `final` это была утечка.

### 4.6 `rules[].vars` пресетов на сборке

Все читатели берут значение пользователя только непустым, иначе умолчание, и
только объявленные имена: `ExpandPresetWithGlobals`

менялся**. Исключение — `ref`-переменные (Н2). Условие приёмки — байт-в-байт

## 5. Импорт: слияние

### 5.1 Сверка с текущей нормой

Формулировка «DNS замещаются» (`BACKUP.md` §9) **не совпадает с текущей
нормой**: §9 п. 5 (`contract/docs/BACKUP.md:795-822`) — DNS-серверы сливаются
«своё сильнее» по `kind`+`tag` (у preset — `kind`+`ref`), совпавшая запись
остаётся локальной целиком, дубли ищутся только среди записей приёмника до
импорта (`import.go:804-864`). Замещаются лишь три скаляра. D-117 переносил
маршрут корневыми `vars` поимённо (`import.go:711-744`, `setVar`): имя из файла
замещает значение, отсутствующее — не трогается. У LxBox — то же «своё
сильнее» (`dns_backup.dart:138-139`), и так как записи шаблонных серверов у
него стоят всегда, `vars` из файла не применяются никогда (П-1).

### 5.2 Норма для `kind: template` (ответы LxBox №1, №2)

| Случай | `enabled` | `vars` |
|---|---|---|
| запись с этим тегом у приёмника **была до импорта** | локальный (§9 п. 5 без изменений) | **наложение по именам**: каждое имя из `vars` записи файла (после Н8) замещает значение приёмника; имён, которых в файле нет, импорт не трогает; затем Н2 (с предупреждением) и Н4 (молча) против шаблона приёмника |
| записи не было | из файла | из файла, затем Н2 и Н4 |
| тег не объявлен шаблоном приёмника | запись не ввозится: `backup_dns_entry_skipped {entry: "template:<tag>"}` (код есть в реестре, `backup_warnings.json:125`; LxBox уже эмитит, лаунчер начинает — ответ №2) | не называются поимённо (Н2, последний пункт) |

Порядок: сперва значения файла как прочитаны (включая равные умолчанию —
Н4 п. 3: читатель принимает), потом нормализация результата. Значение файла,
равное умолчанию приёмника, поэтому сбрасывает локальный выбор к умолчанию —
файл сказал это явно.

**Почему наложение, а не замена целиком.** (1) П7: импортёр не выбрасывает
данные на неполном входе. Файлы 0.x и файлы лаунчера до этой спеки несут либо
ничего, либо только имена маршрута; замена целиком сбросила бы у приёмника
явный маршрут к умолчанию шаблона — у `google_udp` это `direct-out`, то есть
**DNS мимо VPN на восстановлении**. (2) Преемственность: D-117 переносил
маршрут поимённо. (3) `BACKUP.md` §2, «Поля стороны LxBox»: отсутствие поля в
файле значение у приёмника не сбрасывает. **Цена:** сброс к умолчанию,
сделанный на машине-источнике, в непустое состояние приёмника не переносится
(в пустое — переносится: там накладывать не на что, D-117 выполняется). Вариант
«целиком» отклонён (§13 №1).

### 5.3 `kind: user` и `kind: preset` у DNS

Без изменений (§9 п. 5). Добавляется только Н9 для дописанных `user`-записей
(`body.detour`).

### 5.4 `rules[kind=preset].vars`

`rules[]` замещаются целиком (§9 п. 7), значения едут как есть; после
замещения — Н2 (`backup_var_skipped {name, record: "preset:<ref>", reason:

## 9. Корпус

### 9.1 Новый кейс `corpus/backup/v10_dns_template_vars`

Условие: раннер знает объявления шаблона приёмника (Н2/Н4/Н8 без них
непроверяемы). Сегодня шаблона у Go-раннера нет: приёмник `&state.State{}`,
из опций — только `KnownOutbounds {"proxy","direct"}`
(`core/backup/corpus_test.go:358-452`, `:412`, `:418-422`), а `checkDNS`
(`:681-729`) `vars` не сверяет. Поэтому кейс несёт фикстуру объявлений рядом —
`v10_dns_template_vars.template.json` — **объявления шаблона приёмника для
этого кейса**. Умолчания шаблонов у сторон РАЗНЫЕ (у LxBox
`google_dot.outbound = vpn-1`, `cloudflare_dot.outbound = vpn-1`,
`safe_dns_dot.outbound = direct-out`, пресет «russian» зовётся `ru-direct`),
поэтому оба раннера нормализуют Н2/Н4/Н8 **только по фикстуре**, а не по своему
шаблону, и `expected.lxbox.json` не нужен. Кейс без фикстуры идёт без
объявлений: нормализации нет (Н2, «нет объявления — нет нормализации»). `checkDNS`
сверяет `vars`.

Форма фикстуры (README корпуса, рядом с `.pre.backup.json`; LxBox делает свой
раннер по нему):

```json
{
  "dns_options": { "servers": [ <запись шаблона, вложенная форма {description, enabled, vars[], server{}}>, … ] },
  "presets": [ { "id": "<id>", "vars": [ {"name", "type", "default_value"}, … ] }, … ]
}
```

`dns_options.servers[]` — те же записи, что в шаблоне (вложенная форма; у
плоской объявлений нет); из них берутся тег (`server.tag`), имена, типы и
`default_value` переменных и умолчание `enabled`. `presets[]` — `id` и `vars[]`
пресета (`default_value`, у лаунчера читается и алиас `default`); прочие ключи
пресета раннер не читает. Фикстура импортируется ОДНИМИ объявлениями и в
предсостояние, и в кейс. Цель у объявлений фикстуры — локальная, `default_value`
в ней простые строки.

Фикстура этого кейса объявляет пять серверов: четыре из
`bin/wizard_template.json` (`google_udp` — `outbound`=`direct-out`,

`dns_ip`; `safe_dns_dot` — `outbound`=`direct-out`, `safe_profile`,

## 13. Вопросы к LxBox — ответы 15.09.2026

Все девять закрыты; нормы выше записаны по ответам.

1. **Слияние `vars` совпавшей записи** — наложение по именам (§5.2, П7). Замена
   целиком отклонена: старый файл без `vars` сбрасывал бы маршрут приёмника к
   `direct-out`.
2. **Запись шаблонного сервера с тегом, которого нет в шаблоне приёмника** — не
   ввозится, `backup_dns_entry_skipped` (LxBox уже эмитит; лаунчер начинает).
3. **Параметры кодов** — `backup_var_skipped {name, record, reason}` с перечнем
   `not_portable | undeclared | superseded | no_record`, `backup_unknown_outbound`
   + `server` — приняты (§5.6).
4. **DNS-правило на сервер, выпавший второй линией,** — FAIL-CLOSED: правило
   становится `action: reject` с предупреждением, а не снимается. Сервер выпадает
   только из-за висячего detour — пользователь хотел эти домены через конкретный
   маршрут; уход в прямой `dns.final` — утечка того же класса, что detour
   fail-closed; сломанный резолв виден пользователю, утечка — нет. `dns.final` и
   резолверы на выпавший сервер — решение лаунчера в таблице Н10 (заглушка
   `reject` и замена резолвера); LxBox повторяет.
5. **Незнакомый `@name` в теле шаблонного сервера** — имя, не объявленное
   сервером, из записи не подставляется; глобальная переменная — расширение
   стороны. Необъявленный `@name` в теле — ошибка ШАБЛОНА стороны (валидатор
   шаблона), а не данных пользователя (Н11).
6. **Подрезка значений** — хранить подрезанным, пустое после подрезки = нет ключа
   (Н3).
7. **Н9 на совпавшей записи** — значение из файла применяется, сервер
   выключается с `backup_unknown_outbound`: пользователь видит, куда метил файл, и
   ничего не утекает.
8. **Версия** — `1.0.2` (§10).
9. **Значения типа `dns_server`** (`dom_resolver`) на импорте не проверяются,
   висячий резолвер лечит сборка (Н10).
