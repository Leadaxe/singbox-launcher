# PLAN 111 — Локализация на естественных ключах

План реализации к [SPEC.md](SPEC.md). Порядок этапов важен: каталог мигрируется
**до** переписывания call-sites, чекеры пишутся **после** — иначе они падают на
незавершённой миграции и мешают работать.

## Этап 1 — Движок

`Entry` и разбор:

```go
// internal/locale/entry.go
type Entry struct {
	Value   Value            // строка или карта форм
	Special map[string]Entry // "1", "2", … — формы для коллизий
}

type Value struct {
	Text  string            // непустой для обычной строки
	Forms map[string]string // непустой для plural
}
```

`UnmarshalJSON` у `Entry` принимает три вида: голую строку (эквивалент
`{"value": строка}` — так живёт `_display_name`, а заодно старый формат
каталога разбирается без ошибок и деградирует мягко), `{"value": "…"}` и
`{"value": {"one": …, …}}`. Битая запись — не паника: пропускается с
`debuglog.WarnLog`, ключ деградирует в английский.

Резолвер выбирается по тегу языка: `ru` → `RuPluralResolver`, иначе
`EnPluralResolver`. Набор форм резолвера (`resolver.Forms()`) читает чекер —
список не дублируется.

Правила CLDR для русского (`RuPluralResolver`):

```
n%10==1 && n%100!=11            → one
n%10 in 2..4 && n%100 not 12..14 → few
иначе                            → many
не целое                         → other
```

Единая внутренняя функция рендера:

```go
func render(form int, key string, plural bool, n int, args ...any) string
```

Публичные `T`/`Tf`/`TN`/`TfN`/`Plural`/`PluralN` — тонкие обёртки над ней.
Порядок деградации: активный язык → форма 0 → ключ. Аргументы подставляются
всегда, включая fallback на ключ (иначе на экране остался бы `%s`).

**Sanity-гейт этапа:** `internal/locale` собирается и проходит тесты, проект
работает без единой правки call-sites: толерантный парсер держит старый
формат каталогов, `en.json` остаётся вшитым (см. «Порядок» ниже).

## Этап 2 — Миграция каталога

`scripts/l10n_migrate.py`, режим `--catalog`:

1. Читает `internal/locale/en.json` и `bin/locale/ru.json`.
2. Строит `новый_ключ = en[k]` для каждого `k`.
3. Группирует старые ключи по английскому значению.
4. Для группы с **одинаковым** русским переводом — одна запись
   `{"value": "…"}`.
5. Для группы с **разными** переводами — **останавливается** и печатает
   список. Разводится руками: выбирается форма 0, остальные уходят в
   `special["1"]`, `special["2"]`; скрипт запоминает соответствие
   `старый_ключ → индекс_формы` в `scripts/l10n_collisions.json` для этапа 3.
6. 130 мёртвых ключей отбрасываются (их нет в коде).
7. `_display_name` копируется как простая строка.

Ожидаемый результат: ~1091 запись, 13 из них со `special`.

## Этап 3 — Call-sites

`scripts/l10n_migrate.py`, режим `--code`:

1. Regex по `locale.T("KEY")` / `locale.Tf("KEY"` — ключ должен быть в
   `en.json`, иначе строка не трогается и попадает в отчёт.
2. Замена на английский текст с корректным экранированием Go-строки
   (кавычки, `\n`, обратные слэши).
3. Если ключ есть в `l10n_collisions.json` — вызов меняется на
   `locale.TN(N, "…")` / `locale.TfN(N, "…"`.
4. Значения длиннее 120 символов или многострочные (62 + 31 шт.) **не**
   вписываются инлайн: скрипт заводит `const` рядом с местом использования и
   ставит `locale.T(constName)`. Имя константы — из старого ключа
   (`settings.daemon_pair_help` → `daemonPairHelpText`).
5. `gofmt` по изменённым файлам.
6. Отчёт: сколько заменено, сколько пропущено и почему.

7 динамических call-sites (`ui/command_row.go:48,104`,
`ui/connection_local_daemon_darwin.go:26`, `ui/traffic/by_client_view.go:200`,
`ui/configurator/tabs/source_tab.go:523`, `dns_tab.go:153`,
`source_edit_window.go:1202`) правятся руками: переменная-ключ заменяется на
переменную/константу с английским текстом, а константы, которые сканер не
увидит напрямую (уходят в `locale.T` через функцию), помечаются
`// l10n-key` — см. этап 4.

**Гейт этапа:** `go build ./...` зелёный; grep по форме точечного ключа
(`locale.T("` + только `[a-z0-9_.]` до закрывающей кавычки, минимум одна
точка) даёт 0 — не осталось старых ключей. Наивный `[a-z_]*\.` не годится:
английский текст тоже может начинаться со строчной и точки (`"e.g. …"`).

## Этап 4 — Чекер `l10n_check`

AST-скан через `go/parser` + `go/ast` по всем пакетам проекта, кроме
`tools/`. Собирает:

- вызовы `locale.T`, `Tf`, `TN`, `TfN`, `Plural`, `PluralN`;
- для каждого — литеральный ключ либо резолвит `const` в том же пакете;
- индекс special-формы, если первый аргумент — целочисленный литерал;
- вид использования (`T`-семейство или `Plural`-семейство).

Сверяет с `bin/locale/ru.json`. Плейсхолдеры сравниваются нормализованно:
`%s`/`%d`/`%[N]s`, `%%` не считается. Для plural — против каждой формы.

Вывод — как в LxBox, машиночитаемая сводка плюс детали:

```
[l10n_check] keys: 1091, missing: 0, orphan: 0, dynamic: 7
```

`--strict` превращает warn-находки в ненулевой exit.

Константа с маркером `// l10n-key` на строке объявления считается
использованным ключом — это закрывает orphan-ложняки на 7 динамических
call-sites (например, `dns_tab.go:153` получает ключ из функции, и прямой
резолв невозможен).

Ограничение на оба чекера: **только stdlib** (`go/ast`, `go/parser`,
`encoding/json`) и синтаксис не новее go1.20 — легаси-джоба Win7 гоняет
`go get ./...` тулчейном go 1.20.14 по всем пакетам модуля, включая
`tools/` (см. memory «Win7-сборка = go1.20»).

Self-тест `scan_test.go` гоняет сканер на строковых исходниках в памяти —
без обращения к реальному дереву проекта.

## Этап 5 — Ratchet `hardcoded_check`

Скан display-позиций из `display_positions.json`. Находка — строковый литерал
в display-позиции, если он не является аргументом вызова `locale.*`.

- Рекурсия в `*ast.IfStmt`, `*ast.SwitchStmt`, тернарные конструкции внутри
  display-аргумента: каждая ветка — самостоятельный сайт.
- Исключение `// l10n-exempt: <причина>` — комментарий на строке литерала или
  строкой выше; причина обязательна, пустая — ошибка.
- Baseline: `{файл: количество_сайтов}`. Правило — счётчик файла не растёт и
  файл, которого не было в baseline, не может появиться. `--write-baseline`
  перезаписывает (для точечных hotfix).
- Пакеты `internal/debuglog`, `core/debugapi`, `tools/` из скана исключены —
  там английский легитимен по SPEC §8.

Перед включением: прогнать по текущему `ui/` и вычистить найденное — baseline
должен получиться пустым.

Сообщения `core/` **не локализуются** — это diagnostic passthrough (SPEC
§8). Перевод в точке отображения не работает логически: после
`fmt.Sprintf("position %d is empty", 5)` строка уже не совпадает с ключом
`"position %d is empty"`. Типизированная ошибка (ключ + аргументы, рендер в
UI) — отдельная будущая задача; здесь строки просто становятся английскими,
записи в `ru.json` для них не заводятся.

## Этап 7 — CI и документация

Шаг в `.github/workflows/ci.yml`, job `Test`, только Ubuntu (чекеры

## Порядок: инкрементальный переход (принято вместо «одного коммита»)

Работа идёт коммитами прямо в `develop` (ветки не переключаем — рабочую
копию делят другие агенты). Чтобы каждый промежуточный коммит был рабочим,
переход инкрементальный:

1. Движок ставится **параллельно старому**: толерантный парсер читает и
   старый плоский формат (`ключ → строка`), и новый (`Entry`); `en.json`
   с легаси-ключами остаётся вшитым до конца миграции. Оба стиля ключей
   работают одновременно: точечные резолвятся по каталогам, естественные —
   по новым записям в `ru.json` или деградируют сами в себя (английский).
2. Скрипт добавляет в `ru.json` записи с естественными ключами для всех
   легаси-ключей (старые записи пока остаются рядом) и генерирует
   `scripts/l10n_collisions.json`.
3. Call-sites мигрируются пачками (скрипт + вычитка субагентами); после
   каждой пачки проект собирается и полностью локализован.
4. Финальный шаг: снять легаси-записи из `ru.json`, удалить `en.json` и
   `//go:embed`, включить чекеры в CI.

Этапы 4–7 добавляются поверх и обратимы по отдельности.
