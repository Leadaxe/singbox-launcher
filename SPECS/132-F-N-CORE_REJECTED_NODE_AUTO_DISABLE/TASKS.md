## Волна 1 · Разбор строки ошибки ядра

Норма — `contract/docs/CANON.md` §9.1-9.2.

- [ ] Разборщик строки `initialize <outbound|endpoint>[<i>] <type>[<tag>]: <text>`:
      снятие фиксированного префикса слева, кандидаты по `]: ` справа налево,
      выбор по сопоставлению с тегами собранного конфига. Форма без тега
      (ядра до lx.7) распознаётся как «узел не назван».
- [ ] Индекс `<i>` НЕ используется для сопоставления — только диагностика.
- [ ] Обратное отображение «финальный тег → исходный узел»: строит сборка,
      которая эти теги выдала (подписка с префиксом, папка, хоп цепочки,
      WARP). Тег без узла = не сопоставлено.
- [ ] Тексты ошибок обоих движков приводятся к одному входу разборщика:
      classic — вывод `check` / `sing-box.log` (§4.1 SPEC.md), daemon —
      `ApplyError.Message` и `ServiceStatus.ErrorMessage`.

**Тесты (данные):** таблица примеров из CANON §9.2 целиком; теги с эмодзи,
пробелами, двоеточиями и `]`; `endpoint`; строка без тега; ошибка не про узел
(`inbound`, `dns`, `route`); оба кандидата `]: ` при разных тегах в конфиге.

## Волна 2 · Поле причины: state + бэкап + миграция

- [ ] `disabled_reason string \`json:"disabled_reason,omitempty"\`` в
      `core/state/sources_v7.go` `Node`, между `Enabled` и `Origin`.
      Документировать отличие от `Reason` (текст парсера у `unsupported`) и
      от `Warnings` (производные коды) — §4.4 SPEC.md.
- [ ] Перенос при refetch рядом с `Enabled`:
      `core/state/subscription_merge.go:49` `refreshMergedNode`. Узел,
      выключенный страховкой, после обновления подписки остаётся выключенным
      И с причиной.
- [ ] Бэкап: экспорт и импорт симметрично (allowlist ↔ export). Схема уже
      есть — `contract/schema/backup.schema.json`, оба `$defs` (`node` и
      `sourceServer`).
- [ ] Миграция: узлы из state без поля читаются как «выключил человек»
      (поля нет = причины нет). Отдельного шага миграции не требуется —
      поле аддитивное.
- [ ] Стирание причины при включении рукой (единственная точка: тумблер
      узла).

**Тесты (данные):** round-trip state; refetch по тегу сохраняет пару
`enabled=false` + причина; бэкап export→import; включение стирает причину.

## Волна 3 · check кандидата ДО записи config.json

Требование §5А SPEC.md. Идёт ОТДЕЛЬНОЙ волной и ДО цикла: цикл опирается на
кандидата.

- [ ] `RebuildConfigIfDirty` (`core/rebuild.go:100`) пишет собранный конфиг
      во временный файл-кандидат **в каталоге `config.json`**, а не в
      системный temp: относительные пути внутри конфига обязаны резолвиться
      так же, как в работе.
- [ ] `check` идёт по кандидату; чисто → атомарная замена `config.json`.
- [ ] Не чисто и узел не назван → `config.json` НЕ заменяется, на диске
      остаётся предыдущий рабочий; диалог как сейчас, `ConfigStale`
      остаётся, `ConfigBuilt{OK:false}`.
- [ ] Побочные действия — ТОЛЬКО после реальной замены:
      `refreshOwnTunNames` (сейчас `core/rebuild.go:226`, стоит МЕЖДУ
      записью и check) и orphan GC rule-set'ов (Step 5.5,
      `core/rebuild.go:257-271`, сейчас выполняется даже при
      `configValid=false`). GC по кандидату удалил бы `.srs`, на которые
      ссылается ещё живой предыдущий конфиг.
- [ ] Кандидат убирается за собой при любом исходе, включая панику. Имя —
      НЕ `.tmp`: так зовётся промежуточный файл обычной атомарной записи
      (`core/config_service.go:379-390`), путать их нельзя.
- [ ] Graceful skip: бинаря ядра нет → `validateConfigViaSingBox` отдаёт
      `nil` (`core/rebuild.go:30-34`), проверять нечем, страховка не
      действует, кандидат сразу становится `config.json` без диалога.
      Формулировка лога обязана отличать «проверено и чисто» от «проверять
      было нечем».
- [ ] Текст диалога `core/rebuild.go:237-239` переписать: «Connect won't
      work until this is fixed» станет неправдой — на диске останется
      прежний рабочий конфиг.
- [ ] Daemon-режим: **ничего не менять**. `applyCurrentConfig` уже
      начинается с `rebuildConfigBeforeStart`
      (`core/backend_daemon_darwin.go:280`), то есть получает кандидата и
      `check` даром; демон читает не диск, а тело запроса. Закрыть тестом,
      что правка `prepareConfigForDaemon` не ломает инвариант.
- [ ] Remote (SPEC 097/098) — **в объём первой реализации НЕ входит**,
      записать хвостом: `writeRemoteConfig`
      (`ui/configurator/presentation/presenter_save.go:373-421`) пишет
      неатомарно и без `check` вовсе; отказ приходит только от демона на
      Deploy. Выключать узлы по вердикту ЧУЖОГО ядра владелец не решал.

**Тесты (данные):** битый конфиг не попадает на диск; предыдущий рабочий
переживает неудачную пересборку; GC не трогает наборы предыдущего конфига;
нет бинаря → запись без проверки.

## Волна 4 · Цикл страховки в ОБЩЕЙ функции сборки

Один механизм на все входы. Цикл живёт в функции сборки, а не у каждого
вызывающего.

- [ ] Цикл: пересобрать кандидата → `check` → назван узел → выключить +
      причина → следующий круг; чисто → замена `config.json`.
- [ ] Прерывание: ошибка не про узел / без тега / тот же тег назван
      повторно (иначе цикл перестаёт быть конечным).
- [ ] Предел 10 кругов → диалог (§6.2 SPEC.md); `Keep checking` снимает
      предел до конца этого прохода; `Stop` завершает без замены конфига,
      выключенные остаются выключенными.
- [ ] **Адаптер «выключателя»** — интерфейс `disable(tag, reason)`, две
      реализации:
      - сохранённый state → запись в `state.json`;
      - черновик Конфигуратора → запись в модель визарда (волна 6).
      Цикл о разнице не знает.
- [ ] Реальный старт ядра — второй источник сигнала (§5 SPEC.md):
      названный на старте узел выключается с причиной, третьего старта нет.
- [ ] Входы, которые получают цикл БЕЗ своего кода: pre-start rebuild
      (оба движка), кнопка Rebuild, фоновое автообновление подписок,
      API `/action/rebuild-config`. Фоновые отрабатывают тихо, итог —
      плашка.

**Тесты (данные), на поддельном клиенте ядра:** чистый конфиг → ни одного
круга; один негодный; три негодных; одиннадцать → диалог, `Keep checking`
доводит до конца, `Stop` останавливает; ошибка не про узел → без автоматики;
тот же тег повторно → цикл прерван; выключенный узел и граф (цепочка с
выключенным хопом, опустевшая группа, detour fail-closed — §4.6 SPEC.md).

## Волна 6 · Конфигуратор: цикл на вкладке Final

- [ ] Цикл выполняется на последнем шаге Конфигуратора ДО разблокировки
      Save: вход в Final уже собирает конфиг для предпросмотра → кандидат →
      `check` → выключение названных → пересборка.
- [ ] Save блокируется СУЩЕСТВУЮЩИМ гейтом — отдельного механизма не
      заводить: `guiState.SaveGateAllows` / `updateGlobalSaveGate`
      (`ui/configurator/tabs/final_tab.go:197`, `:305-316`) уже ФУНКЦИЯ
      состояния (SPEC 115 §1), один предикат на кнопку вкладки и на
      глобальную. Цикл просто держит предикат закрытым. Статус — §6.3
      SPEC.md.
- [ ] **Выключение пишется в ЧЕРНОВИК** (`enabled=false` + причина), а не в
      сохранённый state: иначе Save перезапишет state
      (`presenter_state.go:113` — поверхностная копия слайса) и отметки
      пропадут. Реализация — адаптер `disable(tag, reason)` волны 4 поверх
      `FindNodeByLink` (`ui/configurator/models/node_rule_ref.go:216-238`).
      НЕ переиспользовать `setNodeEnabled`
      (`tabs/source_edit_window.go:99-112`): она правит deep-copy источника,
      а не черновик.
- [ ] Соблюсти контракт потоков Final: сборка в горутине, `onStart`/`onDone`
      только через `fyne.Do` (`final_tab.go:337`, `:377`, `:396`).
- [ ] По окончании Save разблокируется; человек видит список выключенных и
      причины ДО сохранения (тот же список, что по `Show` у плашки).
- [ ] Диалог предела действует и здесь.
- [ ] После Save сборка `config.json` НЕ гоняет цикл второй раз впустую:
      кандидат уже чист, достаточно одного `check`.
