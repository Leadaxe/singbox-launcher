## 1. Зачем

Ядро проверяет конфиг ЦЕЛИКОМ и на первом же неприемлемом узле отказывается
стартовать вовсе:

```text
initialize outbound[3] vless[🇩🇪 Frankfurt]: parse encryption: unknown encryption appearance
```

Одна строка в одном узле подписки — и VPN не поднимается ни на одном узле.
Провайдер обновил подписку, человек нажал Connect и остался без связи.

Дублировать грамматики ядра в клиенте — тупик: копия обязана сверяться на
каждом бампе пина, а отставшая копия отбраковывает ГОДНЫЕ узлы. Дешёвые
проверки реестра (перечисления, типы, форматы ключей, `pattern`) остаются
первым эшелоном; эта фича — общий второй, на всё, о чём мы не знаем.

Прямой предшественник в истории проекта — SPEC 093 (`fp=HelloChrome_120`):
один узел с чужим написанием отпечатка ронял весь конфиг, и лечилось это
частной проверкой под конкретное поле. Каждая такая дыра закрывалась
отдельной заплатой. Страховка закрывает класс.

## 2. Решения владельца (не обсуждаются)

1. **Новых сущностей нет.** Узел выключается тем же флажком, что и рукой
   человека; рядом — необязательное поле причины.
2. **Триггер — отказ ядра принять конфиг.** Успешный старт не платит ничего.
3. **Остальных негодных вычищает тихий цикл `check`** — без туннеля.
4. **Предел — 10 кругов, дальше вопрос человеку.**
5. **Сообщение — плашка** на главном экране, а не всплывашка.
6. **Перебором виновника не ищут.**

## 3. Поведение (схема владельца, дословно)

```
Start
└─ реальный старт ядра (первый, сигнальный)
   ├─ принято → VPN поднят → конец
   └─ отказ
      ├─ ошибка не про узел / без тега / тег не сопоставился → ошибка, как сейчас → конец
      └─ ошибка называет узел → выключить узел + причина
         └─ цикл check (тихо, без туннеля): пересобрать конфиг → check
            ├─ назван узел → выключить + причина → следующий круг
            │  └─ после 10 кругов → диалог: Keep checking (дальше без предела) | Stop (VPN не поднят, выключенные остаются выключенными)
            ├─ ошибка не про узел / тот же тег назван повторно → ошибка → конец
            └─ чисто → реальный старт ядра (второй, финальный)
               ├─ принято → VPN поднят → плашка «выключено N» → конец
               └─ отказ → ошибка, как сейчас → конец (если называет узел — он тоже выключается с причиной, третьего старта нет)
```

Реальных стартов на одно нажатие — два: сигнальный и финальный. Редкая
ошибка, которую `check` пропускает, а старт ловит, третьего захода не
получает — но названный узел выключается, поэтому следующее нажатие Connect
уже пройдёт дальше, а не упрётся в тот же узел.

**Цикл конечен по построению:** каждый круг выключает один узел; круг, на
котором выключить нечего (тег не сопоставился, ошибка не про узел, тот же тег
назван повторно), цикл прерывает.

### 4.1. Два движка, и текст ошибки есть только у одного

**Daemon (`sing-box lxd`)** — `core/backend_daemon_darwin.go:147`

  `b.admin.Apply(config)` (`core/backend_daemon_darwin.go:336`);

- второй, асинхронный источник — gRPC-стрим статуса:

(предпочтительно) опереться на pre-start `check`, у которого текст есть на
обоих движках (§4.2).

### 4.2. Pre-start `check` у лаунчера УЖЕ есть — и это главное отличие от LxBox

- реализация — `core/rebuild.go:29` `validateConfigViaSingBox`:
  `sing-box check -c <config>`, таймаут 10 с, `CombinedOutput`, strip ANSI
  (`core/rebuild.go:58`), обрезка до 1500 символов
  (`core/rebuild.go:51-53`). Бинаря нет → `nil`, graceful skip;
- зовётся ВНУТРИ пересборки, `core/rebuild.go:234` (Step 5.4), сразу после
  атомарной записи `config.json`;
- **при провале** (`core/rebuild.go:234-255`): `ErrorLog` → модальный

  generated config.json: …») → `events.ConfigBuilt{OK:false}` →
  `configValid=false`, `ConfigStale` НЕ снимается. **`return` не делается** —
  поток идёт дальше, и ядро стартует на уже отвергнутом `config.json`;
- общая точка обоих движков — `core/rebuild.go:358`
  `rebuildConfigBeforeStart`; classic зовёт её на
  `core/process_service.go:174-178`, daemon — на
  `core/backend_daemon_darwin.go:281-286`. Прерывает старт только *fatal*
  пересборки, но не провал `check`;
- память проекта «шаблон заменяется, а не удаляется»: провал pre-start
  пересборки = диалог, ядро не стартует, старое ядро продолжает работать.

### 4.4. Где живёт Enabled и куда класть причину

`core/state/sources_v7.go:199-280`, структура `Node`:

```go
Kind     SourceKind      `json:"kind"`
Tag      string          `json:"tag"`            // СЫРОЙ тег = идентичность, merge-ключ
Enabled  bool            `json:"enabled"`
Origin   *Origin         `json:"origin,omitempty"`
Body     json.RawMessage `json:"body,omitempty"`
Detour   *NodeLink       `json:"detour,omitempty"`
Hops     []NodeLink      `json:"hops,omitempty"`
Group    *AutoGroup      `json:"group,omitempty"`
Service  bool            `json:"service,omitempty"`
Reason   string          `json:"reason,omitempty"`   // unsupported only
Warnings []NodeWarning   `json:"warnings,omitempty"`
Sections *NodeSections   `json:"sections,omitempty"`
```

**Поля причины нет, и два соседних кандидата НЕ подходят:**

- **`Reason`** (`sources_v7.go:244-248`) занят строго `kind=unsupported`:
  английский текст парсера, который едет ещё и в диагностику fetch. В коде
  прямо сказано «с Warnings не сливать (Л20)». Переиспользовать нельзя —
  получилось бы одно поле на два несовместимых смысла;
- **`Warnings`** (`sources_v7.go:249-270`) — коды деградаций ВЫЖИВШЕГО узла,
  данные **производные**: пересчитываются из `Origin.Raw` любым повторным
  разбором и не авторитетны при переносе. Причина отключения ядром —
  авторитетный факт, производным быть не может.

**РЕШЕНИЕ ВЛАДЕЛЬЦА 19.09.2026 — поля нет, причина живёт в `Warnings`.**

Рассуждение выше про «два соседних кандидата не подходят» верно для `Reason`,
но не для `Warnings`: их отвергли как производные, а причина авторитетна.
Владелец заметил, что противоречие снимается не новым полем, а ПРАВИЛОМ —
список сам по себе ничему не мешает, мешает лишь то, что его целиком
замещает пересчёт.

Причина — обычная запись того же списка:

```json
{"code": "core_rejected", "params": {"reason": "<дословный текст ядра>"}}
```

Плюсы, ради которых поле и не понадобилось: `Warnings` уже персистятся, уже
едут в бэкап, уже показываются на строке узла и в шторке (`nodewarn`), и код
`core_rejected` уже объявлен в реестре с текстами. Ни одной новой сущности не
появляется НИГДЕ, а не только в модели.

**Цена — ровно одна ловушка, и её закрывает одно место-правило.** Список
пересчитывается по телу узла в ШЕСТИ местах, и каждое присваивает его
целиком (правило Л5, SPEC 131 §3.5):

| место | что делает |
|---|---|
| `core/state/node_warnings_migration.go` `recountOneNode` | досчёт кодов на загрузке state |
| `core/state/masque_uri_migration.go:104` | пересбор тела из исправленного URI |
| `ui/configurator/tabs/source_body_edit.go:91` | правка тела руками |
| `ui/configurator/tabs/source_body_edit.go:172` | regen из исходника |
| `ui/configurator/tabs/source_awg_edit.go:335` | форма AmneziaWG |
| `ui/configurator/business/source_record_paste.go:159` | вставка записи |

Прямое присваивание в любом из них стёрло бы причину молча, и узел остался бы
выключенным БЕЗ объяснения — то есть стал бы неотличим от выключенного рукой.
Поэтому все шесть переведены на `Node.ReplaceDerivedWarnings(fresh)`
(`core/state/node_enabled.go`): метод переносит авторитетные записи в новый
список и ставит их впереди. Новый авторитетный код вносится в
`authoritativeWarningCodes` одной строкой, и шесть мест править снова не
придётся.

**Вердикт привязан к ТЕЛУ узла** (норма CANON §9.4). Снимают его два события:

1. **тело изменилось** — refetch принёс другое тело под тем же тегом, либо
   человек поправил узел: запись стирается И узел **включается обратно**,
   следующая сборка проверит его заново. Оживает только узел, выключенный
   СТРАХОВКОЙ; выключенный человеком сменой тела не включается. Сравнение
   тел семантическое (`state.BodiesEquivalent`), не побайтовое: иначе любая
   нормализация порядка ключей снимала бы вердикт. Отпечатки не хранятся — в
   точке refetch и правки оба тела под рукой;
2. **человек включил узел обратно** — единый сеттер `Node.SetNodeEnabled`
   (см. ниже).

**Смена версии ядра вердикты НЕ снимает** — решение владельца: ручного
механизма достаточно, а обход всех сохранённых состояний (их много: каждый
файл `bin/wizard_states/*.json` плюс состояния удалённых машин) ради
приговора, который человек снимает одним кликом, не окупается. Вместо него
заведена ПУСТАЯ закладка `core/maintenance` с отметками `last_launcher_version`
/ `last_core_version` в `settings.json`: событие смены версии пишется WARN'ом
(релиз логирует только WARN — память `release-log-warn-only`), список работ на
нём пуст.

**Единый сеттер включения.** Мест, где UI ставил `Enabled`, было четыре, и все
писали поле напрямую: чекбокс строки источника (`source_tab.go:869`),
`setNodeEnabled` окна правки (`source_edit_window.go:99`), пара drilldown'а
(`source_folder_drilldown.go:1111`, `:1197` — в том числе «включить все»). Все
переведены на `Node.SetNodeEnabled(bool)`: он стирает вердикт и отвечает
«изменилось ли что-нибудь» (по этому ответу вызывающие решают, поднимать ли
ревизию модели). Выключение рукой вердикт тоже стирает — иначе выключенный
человеком узел продолжал бы объясняться чужим текстом, будто это решение ядра.

**Известный зазор бэкапа.** У подписки состав в бэкап не едет вовсе: вместо
`nodes[]` экспортируется карта `disabled: {tag: 0}`
(`core/backup/convert_v7.go` ↔ `core/backup/import10.go`). Причина
выключения узла ПОДПИСКИ через бэкап поэтому не переносится — ни в прежней
форме с полем, ни в нынешней с записью. У папок и ручных серверов состав
едет целиком, и запись переносится. Расширять форму `disabled{}` ради этого
владелец не заказывал; записано хвостом в TASKS.md.

Готовый прецедент отложенного «выключить узел по тегу» —
`PendingDisabled`, `core/state/subscription_merge.go:145-166`: одноразовые
отметки выключения из импорта бэкапа, применяются по сырым тегам на первом
достоверном fetch и стираются. Реализации стоит на него опереться.

### 4.5. Перенос состояния при обновлении подписки

Перенос идёт **по СЫРОМУ тегу** — `core/state/subscription_merge.go:1-21`
(шапка), `core/state/subscription_merge.go:49` `refreshMergedNode`:
`fresh.Enabled = old.Enabled` (`:58`). Особые случаи: `unsupported →
обычный` — enabled НЕ переносится, узел оживает включённым (`:50-57`);
`обычный → unsupported` — принудительно `Enabled=false` (`:59-63`).
Подписка — `MergeSubscriptionNodes` (`:99`), папка —
`MergeFolderNodesFromSubscription` (`:197`).

**Реализовано** (`refreshMergedNode`, вызов `fresh.CarryCoreVerdict(old)` сразу
за переносом `Enabled`): вердикт едет по правилу «привязан к телу» — то же
тело держит его вместе с `enabled=false`, другое снимает и включает узел
обратно. Метод правит `Enabled`, поэтому зовётся ПОСЛЕ его переноса. На
неразобранную запись вердикт не переносится: её выключенность объясняет
собственный `Reason`.

### 4.6. Граф-санитайзер уже умеет обходиться с выключенным узлом

`core/build/outbound_graph_sanitize.go:108` `sanitizeOutboundGraph`, вызов из
`core/build/build.go:247`. Выключенный узел просто не попадает в `finalTags`,
дальше каскад по рёбрам:

- **detour на него → выбрасывается НОСИТЕЛЬ перехода**, fail-closed
  (`:235-239`, `dropDetourCarrier` `:158-187`): снять ключ detour нельзя,
  «the hop exists for anonymity and must not silently become a direct dial»;
- **группа/Направление**: участник-призрак вычищается (`:265-279`), пустая
  группа удаляется целиком (`:280-283`), `default` вне состава заменяется
  первым участником (`:284-289`);
- **цепочка**: позиция на несуществующий тег → цепочка удаляется целиком
  (`:243-247`);
- **кольца** — `breakDependencyCycle` (`:352`); **фикспойнт** (`:192-211`):
  удаление узла делает висячими новые ссылки, проход повторяется;
- потери группируются по ИСТОЧНИКУ (`:154-156`, `:182-186`), тип
  `SourceExclusion` (`core/build/parsed_cache.go:147-155`), в отчёт —

## 5. Решение владельца: сигналов два, check — первый

Схема §3 начинается с «реальный старт ядра (первый, сигнальный)», а у
лаунчера pre-start `sing-box check` уже существует и идёт ДО старта (§4.2).
**Решение владельца 18.09.2026: вариант А.**

1. **Провал существующего `check` — тот же сигнал**, что и отказ реального
   старта: назван узел → выключить + причина → пересборка → `check` → …
   Живое ядро при этом не трогается вовсе.
2. **Реальный старт остаётся ВТОРЫМ источником сигнала** — на те ошибки,
   которые `check` пропускает (память «chain: check не ловит ошибки старта»:
   `sing-box check` пропускает `strip tls.utls` на reality-узле, падает
   только `run`). Названный на старте узел тоже выключается с причиной.

   **Уточнение владельца 19.09.2026: только в daemon-режиме.** У classic
   текста ошибки старта нет вовсе — stdout и stderr уходят прямо в файл
   (§4.1), и вытаскивать его оттуда ради второго сигнала владелец не
   заказывал. Это **сознательное ограничение**, а не отложенная волна: у
   classic страховка работает только через `check` при сборке, и этого
   достаточно — редкий случай, который `check` пропускает, выключит узел на
   следующем нажатии Connect в daemon-режиме либо не выключит вовсе. Цикл
   при сборке работает в ОБОИХ режимах.
3. **Реальных стартов на одно нажатие — не больше двух**, по схеме §3.

Основание: `check` — единственный источник текста ошибки в classic-режиме
(§4.1), он ловит поломки шаблона и правил, а не только узлов, и он уже стоит
в единственном writer'е конфига.

## 5А. Кандидат: check ДО записи config.json

**Новое обязательное требование владельца.** Сегодня
`RebuildConfigIfDirty` пишет `config.json` на Step 5 и только ПОТОМ
проверяет его на Step 5.4 (`core/rebuild.go:234`). Битый конфиг остаётся на
диске: диалог «Config validation failed», `ConfigStale` не снимается, и
ядро может стартовать на заведомо отвергнутом файле (§4.2 — `return` там не
делается).

Со страховкой порядок меняется:

1. собранный конфиг пишется во **временный файл-кандидат** — **рядом с
   `config.json`, в том же каталоге**;
2. `check` идёт **по кандидату**;
3. **чисто** → атомарная замена `config.json` кандидатом;
4. **назван узел** → цикл выключения; кандидат пересобирается, круг
   повторяется;
5. **ошибка не про узел / без тега / повтор тега** → `config.json` **НЕ
   заменяется**, на диске остаётся предыдущий рабочий конфиг; диалог как
   сейчас, `ConfigStale` остаётся.

**Итог инварианта: в `config.json` попадает только конфиг, принятый ядром.**

Механика записи уже есть и почти готова: `core/config_service.go:376-389`
`atomicWriteConfig` — это `path + ".tmp"` → `os.WriteFile` → `os.Rename`,
**уже в том же каталоге**. Нужно разнять её на две половины: «написать
кандидата» и «переименовать поверх», а между ними вставить `check`. Имя
кандидата стоит сделать отличным от `.tmp`, чтобы не путать с обычной
атомарной записью.

**Про каталог.** Разведка: относительные пути внутри собранного конфига
резолвятся НЕ ядром, а сборкой — локальные `.srs` раскрываются в абсолютные
через `ExecDir` (`core/build/preset_merge.go:161-162`,
`core/config_service_context.go:74-76`). То есть каталог кандидата на
результат `check` сегодня не влияет. Требование «рядом с `config.json`»
остаётся в силе как страховка от будущих относительных путей и потому, что
`os.Rename` через границу файловых систем не атомарен, — но обосновывать его
резолвом путей нельзя, это было бы неверно.

**Отдельная находка (не чинить в этой волне, записать).** `check` запускается
БЕЗ `Dir` (`core/rebuild.go:38` — `exec.CommandContext` без `cmd.Dir`), то
есть с рабочим каталогом лаунчера, а рабочее ядро стартует с `Dir = bin/`
(`core/process_service.go:223`). Условия проверки и работы уже расходятся;
для SPEC 132 это не блокер (пути абсолютные), но при появлении первого же
относительного пути в конфиге разойдутся и результаты.

**Graceful skip.** Бинаря ядра нет → `validateConfigViaSingBox` возвращает
`nil` (`core/rebuild.go:33-35`). Страховка в этом случае **не действует**:
проверять нечем, узлы никто не называет. Запись идёт как сейчас — кандидат
сразу становится `config.json`, без диалога и без цикла.

Заполняется по результатам разведки (§4 и отдельный проход). Каждый пункт

  `ConfigStale` остаётся, как сейчас;
- **daemon-режим — своего кандидата НЕ заводит, всё достаётся даром.**
  `applyCurrentConfig` начинается с полной локальной пересборки
  (`core/backend_daemon_darwin.go:280` `rebuildConfigBeforeStart`), то есть
  **весь конвейер §5А, включая `check`, отрабатывает до доставки**. Дальше

  (`core/backend_daemon_darwin.go:302` `os.ReadFile(ConfigPath)`), правит в

  целиком живёт в общей функции сборки, а daemon-путь не трогаем вовсе.

  сигнала** из §5, наравне с отказом реального старта classic. Расхождение
  между двумя вердиктами само по себе полезный сигнал: его даёт ровно та
  правка, которую вносит `prepareConfigForDaemon`;
- **remote-машины (SPEC 097/098) — В ОБЪЁМ ВХОДЯТ, и там ДЫРА.** «Удалённая
  машина» — не отдельный конвейер, а `TargetSpec` той же локальной сборки
  (`core/build/build.go:91-98`, `core/config_service_context.go:38`).
  Но путь сохранения у неё свой и **без единой проверки ядром**:
  `ui/configurator/business/create_config.go:266` `BuildRemoteConfig` →
  `ui/configurator/presentation/presenter_save.go:373-421`

  `sing-box check` не зовётся, локальные dirty-маркеры намеренно не
  поднимаются (`:350-353`). Отвергнутый ядром узел всплывает только на
  `Deploy`, ответом демона `ApplyError.Rejected()`

  **РЕШЕНИЕ ВЛАДЕЛЬЦА 19.09.2026: страховка действует так же, как локально.**
  Оговорка принята сознательно: конфиг чужой машины проверяет ЛОКАЛЬНЫЙ
  бинарь, и его версия может отличаться от ядра той машины («обновят»).

  **В этот заход не вошло, и вот почему.** `writeRemoteConfig` собирает из

  Объём: адаптер поверх `FindNodeByLink` + перевод `writeRemoteConfig` на
  «кандидат → check → замена» (сегодня там простой `os.WriteFile`, даже не
  атомарный). Шов готов, ломать текущую доставку ради полудела незачем —
  отдельная волна;
- **graceful skip** — см. §5А. Отдельно отметить существующий зазор: при
  отсутствии бинаря `validateConfigViaSingBox` возвращает `nil`
  (`core/rebuild.go:30-34`), и сегодня `configValid` остаётся `true`. С
  кандидатом это означает «писать без проверки», и так и должно быть, но
  формулировка диалога и лога обязана отличать «проверено и чисто» от
  «проверять было нечем».

## 5В. Конфигуратор: цикл на вкладке Final

**Требование владельца.** Цикл страховки выполняется на ПОСЛЕДНЕМ шаге
Конфигуратора (вкладка Final) **до разблокировки Save**: на входе в Final
конфиг и так собирается для предпросмотра → тут же кандидат → `check` →
выключение названных узлов → пересборка → … Человек видит, какие серверы
отключены и почему, **ещё до сохранения**.

### 5В.1. Как устроен Final сейчас

### 5В.2. Черновик — та же структура, что state

Ключевое, и оно сильно упрощает задачу: **своего типа узла у черновика
нет**. Модель визарда несёт `Sources []corestate.Source`
(`ui/configurator/models/wizard_model.go:67-71`, SPEC 117 — «канонический
источник истины»), то есть те же `state.Node` с тем же `Enabled`
(`core/state/sources_v7.go:199-205`). Значит поле `disabled_reason` волны 2
работает в черновике **без единой дополнительной структуры**, а выключение
узла — ровно то же присваивание, что и в сохранённом state.

Адресация в черновике:

```
model.Sources[i].Node.Enabled      // узловой источник: server/chain/auto
model.Sources[i].Nodes[j].Enabled  // узлы контейнера: subscription/folder
```

**Готовый примитив для адаптера уже есть:** `FindNodeByLink(m *WizardModel,
link corestate.NodeLink) *corestate.Node`
(`ui/configurator/models/node_rule_ref.go:216-238`) — единственная публичная
функция уровня модели, которая по ссылке `{FolderID, Tag}` возвращает
УКАЗАТЕЛЬ на узел черновика. `FindNodeByLink(m, link).Enabled = false` — и
есть искомое «выключить по тегу». Реализации волны 6 стоит строить адаптер
на ней, а не заводить третий способ адресации.

Что НЕ переиспользовать: `setNodeEnabled`
(`ui/configurator/tabs/source_edit_window.go:99-112`) принимает `*Source`, а
не модель, и по комментарию `:97-98` правит рабочую **deep-copy** источника,
до модели доезжающую только на Save окна. Прямой вызов на
`&model.Sources[i]` дал бы другую семантику, чем у текущего вызывающего, —
это ловушка.

**Выключение на Final обязано писаться в ЧЕРНОВИК**, а не в сохранённый
state: Save затем перезапишет `state.json` из черновика
(`presenter_state.go:113` — `state.Sources = append([]Source(nil),
p.model.Sources...)`, **поверхностная** копия слайса, сами `Source`/`Node`
общие с моделью), и отметки, поставленные мимо черновика, пропали бы.

Отдельно: у `kind=unsupported` `enabled` всегда `false` и включение
запрещено (`core/state/sources_v7.go:190-198`) — страховке такие узлы
адресовать нечего, они и так не в конфиге.

### 5В.3. Где живёт цикл

Цикл живёт в **ОБЩЕЙ функции сборки** — один механизм на все входы: Final,
фоновое автообновление подписок, pre-start rebuild обоих движков, кнопка
Rebuild, API `/action/rebuild-config`. Final лишь зовёт его заранее и
показывает ход; фоновые входы отрабатывают тихо, итог — плашка (§6.1).

Доступ к «выключателю» цикл получает через узкий интерфейс-адаптер:

```go
// disable(tag, reason) — выключить узел по ФИНАЛЬНОМУ тегу и записать причину.
type nodeDisabler interface {
    Disable(tag, reason string) bool // false = тег не сопоставлен
}
```

Две реализации, цикл о разнице не знает:

- **сохранённый state** — запись в `state.json`;
- **черновик Конфигуратора** — запись в `model.Sources` (`state.Node`
  напрямую, §5В.2).

### 5В.4. Поведение Save

- на время цикла гейт закрыт, статус — `Checking servers… (%d disabled)`
  (§6.3);
- по окончании гейт открывается обычным предикатом
  `saveButtonVisible`; список выключенных с текстом ядра показывается
  здесь же — **тот же список**, что открывает `Show` у плашки (§6.1);
- **после Save сборка `config.json` не гоняет цикл второй раз впустую**:
  кандидат уже чист, достаточно одного `check`. Реализации нужен признак
  «этот конфиг уже проверен в этом проходе» — иначе Конфигуратор заплатит
  за проверку дважды на каждом сохранении.

### 5В.5. `Stop` на Final — РЕШЕНО (вариант А)

Диалог предела (§6.2) действует и на Final, но кнопка `Stop` там означает не
то же, что при Connect. При Connect всё однозначно: VPN не запускается,
выключенные остаются выключенными. На Final VPN никто и не поднимал —
вопрос в том, что делать с **Save**.

Ситуация после `Stop`: часть узлов уже выключена в черновике, но конфиг
заведомо НЕ чист — в нём остались узлы, которых ядро не примет.

**Вариант А (рекомендую): Save остаётся доступной.** Черновик — это
намерение человека, а не работающий конфиг; запретить сохранить свою же
работу из-за незаконченной проверки — значит держать человека в
Конфигураторе заложником. Выключенные остаются выключенными, причины
записаны, и первый же Connect продолжит цикл с того места, где `Stop` его
прервал. Цена: человек может сохранить конфиг, который не стартует, — но
ровно это происходит и сегодня, без всякой страховки.

**Вариант Б: Save заблокирована до чистого прохода.** Гарантирует, что
сохранённый черновик стартует. Цена: `Stop` превращается в тупик — человек
нажал «остановить» и не может ни сохранить, ни выйти без потери правок.

**Решение владельца 19.09.2026: вариант А.** `Stop` — это «не сейчас», а не
«отменить мою работу»: Save остаётся доступной, правки не теряются,
выключенные остаются выключенными, первый Connect продолжит цикл с того
места, где `Stop` его прервал.

## 7. Чего не делаем

- Не чиним узел сами — только исключаем.
- Не выключаем ничего по ошибкам ВРЕМЕНИ РАБОТЫ (таймаут, отказ сервера,
  urltest) — только по отказу ядра принять конфиг.
- Не вводим отметку «карантин», отпечатки тела, версию ядра в хранении.
- Не ищем виновника перебором.
- Не снимаем причину автоматически — ни по смене тела узла, ни по смене
  версии ядра. Осознанная цена простоты.

## 8. Проверка

Юниты разбора строки ошибки: `outbound` и `endpoint`; теги с эмодзи,
пробелами, двоеточиями и `]`; строка БЕЗ тега (форма ядра до lx.7); ошибка не
про узел (`inbound`, `dns`, `route`); кандидаты `]: ` справа налево и выбор по
сопоставлению (CANON §9.2, таблица примеров оттуда — готовый набор кейсов).

Тег → исходный узел: подписка, папка, цепочка, ручной сервер, служебная
запись (не сопоставляется).

`disabled_reason`: кодек state, перенос при refetch по тегу (§4.5), бэкап
(экспорт ↔ импорт симметрично), стирание при включении рукой.

Интеграционный тест цикла на поддельном клиенте ядра: чистый старт → ни
одного круга; один негодный; три негодных; одиннадцать → диалог, `Keep
checking` доводит до конца, `Stop` останавливает с выключенными; ошибка не
про узел → без автоматики; тот же тег назван повторно → цикл прерван.

Граф: выключенный страховкой узел — цепочка с выключенным хопом, опустевшая
группа, detour fail-closed (§4.6).

Тестов на форматирование строк и вёрстку НЕ писать (память «Без тестов на
UI-формат»).

## 10. Что реализовано (19.09.2026, волны 1-4)

### 10.1. Где живёт цикл

`core/rebuild_corereject.go` — `coreRejectLoop.run`. Зовётся из
`RebuildConfigIfDirty` (`core/rebuild.go`, Step 5), то есть из
задокументированного ЕДИНСТВЕННОГО writer'а `config.json`. Все входы получают
цикл БЕЗ своего кода: pre-start обоих движков (`rebuildConfigBeforeStart`),
кнопка Rebuild, автообновление подписок, API `/action/rebuild-config`,
пересборка после Save Конфигуратора, смена `log_level`.

Порядок Step 5 теперь такой:

```
собранный конфиг → config.json.candidate (рядом с config.json)
  → check по кандидату
     ├─ принят → os.Rename поверх config.json
     │            → refreshOwnTunNames → orphan GC → ClearConfigStale
     │            → ConfigBuilt{OK:true, DisabledNodes}
     └─ отказ  → кандидат удалён
          ├─ назван НАШ узел → выключить + причина → пересобрать → круг
          └─ иначе → config.json НЕ заменён, диалог, ConfigStale остаётся,
                     ConfigBuilt{OK:false, DisabledNodes}
```

Имя кандидата — `config.json.candidate`, НЕ `.tmp`: так зовётся
промежуточный файл обычной атомарной записи (`atomicWriteConfig`), и уборка
одного снесла бы другой. Кандидат убирается при любом исходе.

`refreshOwnTunNames` и orphan GC переехали ЗА реальную замену (§5Б).
Текст диалога переписан: «config.json was NOT replaced — the previous working
config is still on disk» вместо прежней неправды про «Connect won't work».

### 10.2. Адаптер выключателя

Интерфейс `nodeDisabler` (`Disable(link, reason) bool` / `Commit()` /
`Label(link)`). Реализация этой волны — `savedStateDisabler` над сохранённым
состоянием: держит загруженный `state` в памяти весь проход (круг правит его
и пересобирает конфиг из него же), на диск пишет ОДИН раз в `Commit` —
десять кругов иначе означали бы десять перезаписей `state.json`, каждая со
своим окном на сбой.

`Commit` зовётся независимо от исхода: нажатый `Stop` и оборвавшийся цикл
выключенные узлы не возвращают.

Вторая реализация — черновик Конфигуратора (волна 6) — встаёт сюда же:
у черновика тот же тип узла (`state.Node` в `model.Sources`), и адаптер
сводится к `FindNodeByLink(m, link).SetCoreRejected(reason)`. Цикл о разнице
не знает.

### 10.3. Сопоставление «финальный тег → узел состояния»

Карту отдаёт **сама сборка**, которая теги и выдала (CANON §9.3). Пересчитать
её снаружи нельзя: тег-политика с переменными (`{$num}`, `{$label}`)
раскрывается только эмиссией, а суффикс глобальной уникализации при
столкновении тегов знает тоже только она. Это и отличает страховку от
`business/node_warnings.go`, который через `state.NodeLinkFinalTag` считает
финальный тег ПРИБЛИЗИТЕЛЬНО и на политике с переменными молчит (`ok=false`).

Путь: `ParsedNode.CanonicalLink` (`configtypes.NodeLink`, ставится у КАЖДОГО
узла канона — в отличие от `SectionsLink`, который едет только с секциями) →
`OutboundGenerationResult.NodeLinks` (заполняется в цикле эмиссии, то есть
только узлами, ДОШЕДШИМИ до конфига) → `stateNodeLinks` → `buildRound.NodeLinks`.

Что ставит ссылку:

- `buildCanonicalServer` / `buildCanonicalAuto` (`canonical_emit.go`) —
  `{FolderID контейнера, СЫРОЙ тег}`;
- цепочки — проход 2: `BuiltChain.Link` заполняется в
  `ResolveCanonicalChainHops`, `buildChainNode` переносит её в узел;
- корневые узлы (`server`/`chain`/`auto`) — `{FolderID: "", NodeTagOrLabel()}`:
  ровно та адресация, которой пользуется `FindNodeByLink`.

**Узлы с переменными в тег-политике сопоставляются нормально** — именно
потому, что карту строит эмиссия, а не предсказание.

Тег БЕЗ ссылки сопоставленным не считается, и страховка на него не действует:
селекторы, Направления, группы шаблона, `direct`/`block`, узлы сборочной
формы, положенной вызывающим напрямую. То же и для узла, дошедшего до канона,
но не выпущенного эмиссией: его в конфиге нет, ядро назвать его не может.

При столкновении финальных тегов побеждает первый владелец: выключить не тот
узел хуже, чем не выключить никакой.

### 10.4. Пределы и решение по умолчанию для фоновых входов

- `coreRejectAskAfter = 10` — после десяти выключений цикл спрашивает
  человека через колбэк `decide(disabled int) bool`;
- `coreRejectHardCap = 200` — жёсткий потолок для входов БЕЗ человека.

**Решение по умолчанию: фоновые входы (`decide == nil`) идут дальше молча до
жёсткого потолка.** Спросить там некого — автообновление подписок, API,
pre-start без окна, — а подписка на 500 узлов с пачкой негодных обязана
собраться ночью сама. 200 заведомо больше любой реальной пачки и заведомо
конечно.

Сегодня `decide` возвращает `nil` для ВСЕХ входов: диалог предела (§6.2)
приезжает волной UI, и заводить окно, за которым нет ни списка, ни плашки,
рано. Сам цикл диалог уже поддерживает и покрыт тестом (`Stop` /
`Keep checking`).

Колбэк хода `progress(disabled int)` для строки «Checking servers… (%d
disabled)» (§6.3) объявлен, пока `nil`.

Итог прохода едет в `events.ConfigBuiltPayload.DisabledNodes`
(`[]events.DisabledNode{SourceLabel, Tag, Reason}`) — и при `OK:true`, и при
`OK:false`: цикл мог выключить несколько узлов и упереться в ошибку не про
узел, и человек обязан узнать об этом обоими путями.

### 10.5. Показ warning'а на узле

Отдельной точки внедрения НЕ потребовалось — и это прямое следствие решения
хранить причину в `Warnings`. Существующие поверхности (индекс
`business/node_warnings.go` для вкладки Servers, строки превью
`tabs/preview_rows.go`, шторка `nodewarn.Section`) читают `Node.Warnings` и
расшифровывают коды по `contract/registry/warnings.json`, где `core_rejected`
уже объявлен с текстами и severity `error`.

### 10.6. Graceful skip

Бинаря ядра нет → `validateConfigViaSingBox` возвращает `nil`, цикл считает
кандидата принятым и заменяет `config.json` без диалога. Страховка при этом
не действует: проверять нечем, узлы никто не называет.

## 10.7. UI (волна 5, 19.09.2026)

Три поверхности, один источник — `ui/core_rejected_notice.go`:

- **плашка** на вкладке Local, НАД списком узлов: скруглённая полоса
  (`internal/fynewidget.NoticeBar` — готовой в проекте не было) с ⚠,
  заголовком, текстом и кнопками `Show` / ✕. Контейнер отдаётся пустым и
  скрытым, поэтому до первого выключения раскладка вкладки не меняется.
  Кормится `ConfigBuilt.DisabledNodes` при ОБОИХ исходах сборки;
- **`Show`** — отдельное окно (`Application.NewWindow`, не модальный попап:
  высокий попап в Fyne раздувается на весь экран) со списком выключенных:
  имя жирным, источник приглушённо, текст ядра мелким с переносом. Кнопки
  «включить всё обратно» НЕТ (решение владельца);
- **строка хода** — `progress(disabled)` пишет «Checking servers… (%d
  disabled)» в статус списка вкладки Local, туда же, где «Sing-box is
  stopped.» и «Pinging 5/9…».

**Диалог предела достаётся не всем входам.** Колбэк `decide` один на
pre-start, кнопку Rebuild, ночное автообновление и debug API, а спрашивать в
трёх последних некого — блокирующее ожидание ответа повесило бы сборку
навсегда. Гейт стоит ВНУТРИ UI-колбэка и проверяет то, чего цикл знать не
может: видно ли человеку главное окно. **Окно в трее приравнено к фоновому
входу.** Ожидание ответа — НЕ на UI-потоке: цикл идёт в фоне, диалог
показывается через `fyne.Do`, ответ приезжает каналом.

Колбэки ставит UI (`SetCoreRejectDecider` / `SetCoreRejectProgress` на
`AppController`, под мьютексом). nil у обоих = прежнее поведение фонового
входа, поэтому headless-сборка и тесты не меняются.

**Попутная правка:** «warning на узле уже работает без правок UI» (§10.5)
оказалось верно не везде — в превью источника Конфигуратора выключенный узел
не доходит до эмиссии, и подстрока отдавала ему голое «off» раньше, чем
читались коды. Узел, выключенный ядром, был неотличим от выключенного рукой
ровно в том списке, где смотрят состав. Теперь у него `✖ <заголовок кода>`.
