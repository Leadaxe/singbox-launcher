# SPEC 119 · Origin и Regen для узлов из wg-quick (INI)

Статус: C (реализовано, обе фазы — см. IMPLEMENTATION_REPORT.md). Ветка develop. Нормативная база:
`SPECS/features/subscriptions.md` (разбор тела, `origin.raw` — запись как
пришла), `SPECS/features/sources.md` (§Происхождение: Origin и Regen).

## 1. Проблема

Узел, собранный из тела wg-quick, теряет исходный текст своего блока.
Пользователь не может ни посмотреть комментарии внутри блока, ни
пересобрать узел из правленого текста — хотя модель обещает и то, и другое.

Живой пример — конфиг Proton VPN:

```ini
[Interface]
# Bouncing = 0
# NAT-PMP (Port Forwarding) = off
# VPN Accelerator = on
PrivateKey = 0GCSi+xv9uacc7rK5S8WmwNlf/eqD/6+I34xw6+iDnU=
Address = 10.2.0.2/32, 2a07:b944::2:2/128
DNS = 10.2.0.1, 2a07:b944::2:1

[Peer]
# US-FREE#109
PublicKey = 0q5TxQQMNVQ6wEcLqnHa20G0DP/fpk8YdgLJUYApfTo=
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = 149.22.88.129:51820

# Uncomment the following line (delete the # symbol) to connect to Proton VPN using IPv6.
# Endpoint = [2a02:6ea0:d802:5519::10]:51820
PersistentKeepalive = 25
```

Здесь комментарии несут рабочую информацию: имя локации (`# US-FREE#109`),
состояние опций провайдера, и — главное — **готовый альтернативный
endpoint**, который пользователь должен уметь включить, раскомментировав
строку. Сейчас всё это до узла не доезжает.

### Причина

INI — единственная ветка разбора, которая **переписывает тело** перед
разбором. `parse_body.go:179-188`: блоки конвертируются в канонические
`wireguard://`-URI, `contentStr` подменяется на них, `bodyKind` становится
`BodyKindURIList`, и дальше работает общая URI-ветка. Она и штампует origin
— но штампует уже **сгенерированную ссылку** (`parse_body.go:283`,
`st.accept(node, OriginKindURI, line)`), а не исходный блок.

Итог: `origin.kind = "uri"`, `origin.raw` = синтетический
`wireguard://…?…`, комментарии потеряны на шаге конвертации.

Косвенное подтверждение, что так не задумывалось: константа
`OriginKindWGIni = "wg_ini"` объявлена (`core/state/sources_v7.go:58`) и
проброшена в UI (`ui/configurator/models/wizard_state_file.go:63`), но
**не присваивается нигде** — ни один узел её не получает. Вид происхождения
был предусмотрен и остался незаполненным.

### Чему это противоречит

- `features/subscriptions.md`: `origin.raw` — «запись как пришла». Для
  URI-списка и JSON так и есть, INI из правила выпадает.
- `features/sources.md` §Происхождение: «`raw` — исходник байт в байт»,
  «Raw редактируем в UI, но действует только через явный Regen». Для
  INI-узла Regen сегодня пересоберёт узел из синтетической ссылки, а не из
  конфига провайдера, — то есть комментарии не вернёт и правку в них
  применить не даст.

### Масштаб

Обследованы все ветки, переписывающие тело до записи origin:

| Ветка | Тело переписывается | origin сегодня | Вердикт |
|---|---|---|---|
| wg-quick INI | да, блок → URI | `uri` + синтетическая ссылка | **чиним этой задачей** |
| `vpn://` (Amnezia) | да, контейнер → узлы | пустой (`""`), осознанно | вне задачи |
| URI-список | нет | строка как пришла | верно |
| sing-box JSON | нет | маршал элемента | верно |
| Xray JSON | нет | маршал элемента | верно |

`vpn://` трогать не будем: там пофрагментного исходника нет **по устройству
формата** (контейнер разворачивается в несколько узлов, «своего» куска
текста у узла не существует), и пустой origin там — записанное решение, а
не дефект. INI отличается принципиально: у блока `[Interface]` кусок текста
есть, он самодостаточен и разбирается сам по себе.

Решение принимается **как частный случай INI**, не как общий рефактор
происхождения.

## 2. Цель

Узел из wg-quick несёт свой блок дословно и пересобирается из него.

- `origin.kind = "wg_ini"`, `origin.raw` = текст блока байт в байт, со
  всеми комментариями, пустыми строками и порядком ключей.
- Пользователь видит этот текст у узла и может его править.
- Regen пересобирает узел из правленого текста — раскомментированный
  `Endpoint` вступает в силу.

## 3. Фазы

### Фаза 1 — origin сохраняется

Блок перестаёт терять себя на конвертации. Конвертация в `wireguard://`
остаётся (разбор INI один, в `parseWireGuardURI` — SPEC 103 B11), но
исходный текст блока едет вместе с узлом и попадает в origin.

Приёмка:

- узел из тела wg-quick имеет `origin.kind = "wg_ini"`;
- `origin.raw` совпадает с блоком байт в байт (сравнение строкой, не
  «эквивалентно по полям»);
- многосекционный conf (несколько `[Interface]` одним файлом) даёт каждому
  узлу **свой** блок, а не весь файл;
- пропущенный блок (без `[Peer] endpoint`) по-прежнему считается
  пропущенным и сообщается пользователю — поведение не меняется;
- узел, вставленный одиночным conf'ом руками (не из подписки), получает
  тот же origin.

### Фаза 2 — просмотр и Regen

Модель Regen уже описана в `features/sources.md` и реализована для других
видов origin; здесь она включается для `wg_ini`.

- Исходник блока показывается у узла и доступен для правки.
- Regen разбирает правленый raw, пересоздаёт body, сохраняет raw как новый
  `origin.raw`.
- Regen с неразбираемым raw — ошибка и откат, узел не портится (правило
  битого фрагмента, `features/sources.md`).

Вопросы, которые решаются внутри фазы (не предрешены здесь):

- **Отвязка от подписки.** По модели правка копии узла из подписки
  отвязывает её с уведомлением. Регенерация — правка; значит ли это
  отвязку, или INI-узел остаётся связанным и следующий fetch перетрёт
  правку?
- **Merge при следующем fetch.** `origin.raw` «освежается при merge-заливке»
  — как это сочетается с локально правленым raw.
- **Точка входа в UI.** Где живёт просмотр и правка исходника: вкладка
  JSON окна узла, отдельная вкладка, что-то ещё. Согласовать до кода —
  визуал и архитектурные решения предлагаются вариантами.

## 4. Границы

Не входит:

- общий рефактор происхождения и origin у `vpn://`;
- изменение самого INI-разбора (какие ключи понимаем) — это контракт
  протокола, `contract/registry/protocols/wireguard.json`;
- сохранение комментариев **обратно** в эмитируемый конфиг: комментарии
  живут в origin узла, а не в `config.json`.
