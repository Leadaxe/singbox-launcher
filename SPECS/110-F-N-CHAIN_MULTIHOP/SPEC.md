# SPEC 110 — Цепочка хопов (`chain`) в лаунчере

Статус: **переносится** — фазы 1–6 реализованы в модели Направления, идёт перенос в источники (см. «Ревизия: цепочка — источник, а не Направление»). Реализует в лаунчере
[FEATURE 015 CHAIN](/Users/macbook/projects/sing-box-lx/SPECS/FEATURES/015-CHAIN/FEATURE.md)
форка ядра (задача 073).

## Что даёт фича

Многохоповый маршрут `клиент → хоп 1 → хоп 2 → … → цель`. Сегодня в лаунчере
он собирается только через `detour` (SPEC 077/101): узлу прописывается
«ходить через тег», связь зашита в сам узел.

`chain` снимает три ограничения `detour`:

| | `detour` (есть) | `chain` (добавляем) |
|---|---|---|
| Хоп — группа | нет: `detour` на группу переадресует один узел, но не даёт выбирать, ЧЕРЕЗ ЧТО он идёт | да: любая позиция — узел, endpoint или группа любой вложенности |
| Узел в двух ролях | приходится дублировать в конфиге | нет: звено — рантайм-экземпляр, конфиг не копируется |
| Больше двух хопов | цепочкой `detour` по узлам, вручную | список позиций |

Переключение группы на любой позиции меняет путь **без перезапуска**.

## Ядро: фича есть в форке, но НЕ в текущем бинаре

Проверено фактически на бандле (`1.14.0-lx.27-rc.3-dev`):

```
$ sing-box check -c chain_probe.json
FATAL decode config: outbounds[2]: unknown outbound type: chain
```

Список тегов сборки: `with_lx_command`, `with_lxd`, `with_awg`, `with_xhttp`
— **`with_lx_chain` отсутствует**. Реализация в форке при этом есть
(`protocol/chain/`, `include/lx_chain.go`), собирается по тегу.

**Отсюда главное требование:** лаунчер обязан проверять поддержку ядром и
деградировать, а не писать `type: chain` вслепую. Ядро отвергает конфиг
**целиком** — один такой outbound лишил бы пользователя VPN, а не одной
цепочки. Механизм уже есть: `NaiveSupportProbe`
(`core/config/outbound_generator.go:88`) — тот же приём для naive.

## Ревизия: цепочка — источник, а не Направление

Первая редакция ТЗ поместила цепочку в Направления. Довод был такой:
«снаружи `chain` — обычный outbound, его кладут в правило, в селектор, в
urltest — ровно то, чем Направление и является». **Довод неверен.** «То,
что кладут в селектор и urltest» — это определение УЗЛА. Направление —
это сам селектор, точка выбора между маршрутами; цепочка — маршрут.

Второй довод («позиции могут быть группами, значит цепочка выше узлов»)
тоже не держится: `detour` узла точно так же может указывать на группу, и
это не сделало `detour` Направлением — он живёт на источнике
(`Source.DetourTag`, SPEC 077/101). Само это ТЗ называет `chain`
преемником `detour`.

**Правильное место — третий тип источника**, рядом с подпиской и сервером:

| | цепочка = Направление (первая редакция) | цепочка = источник (принято) |
|---|---|---|
| Правило ссылается | напрямую | через Направление, как на любой сервер |
| Попадает в `proxy-out` | нет: только через `include`, а он разрешён лишь для стоящих ВЫШЕ, и шаблонный `proxy-out` обычно первый → практически никак | да: фильтр Направления ловит её как узел |
| Автогруппа меряет маршрут целиком | нет: двойник не берёт Направления | **да** — urltest сравнит «через два хопа» с прямыми узлами |
| Форма | половина вкладок скрыта (фильтра, состава, автовыбора у цепочки нет) — признак чужого места | своя форма источника, прятать нечего |

Решающий довод — вторая и третья строки: в модели Направления главный
сценарий «собрал маршрут и переключился на него» не работает вовсе, а
измерить маршрут нечем.

**Цена решения — риск цикла.** В модели Направления циклы были невозможны
по построению (`include` только вверх). У источника они возможны и в самом
частом сценарии: цепочка `[proxy-out, exit-node]`, а `proxy-out` своим
фильтром ловит саму цепочку → `proxy-out` содержит цепочку, которая через
`proxy-out` идёт. Отсюда обязательное правило: **группа никогда не
содержит цепочку, которая через неё проходит** (транзитивно) — отбор узлов
в селектор исключает такие цепочки. Это ровно то свойство, которое первая
редакция получала даром.

## Модель

### Тип записи

Цепочка — это источник (`Source.Type == "chain"`), материализующийся в один
outbound типа `chain`. Для остального лаунчера она узел: попадает в пул,
отбирается фильтрами Направлений, живёт в Clash API как переключаемая
опция.

Механизм эмиссии — тот же, что у ручного `config_json`
(`ParsedNode.EmitRaw`, `subscription/manual_config.go`): объект уходит в
конфиг как есть, лаунчер перештамповывает только тег. Отличие в том, что
объект собирает форма, а не пишет пользователь.

```go
// state.Source (type == "chain") — настройка пользователя
Chain *SourceChain `json:"chain,omitempty"`

type SourceChain struct {
    // Hops — позиции В ПОРЯДКЕ ПАКЕТА: [0] — первый хоп от клиента,
    // последний — тот, чей адрес видит цель. Минимум два.
    Hops []string `json:"hops"`
    IdleTimeout string `json:"idle_timeout,omitempty"`
    StripEvasion *bool `json:"strip_evasion,omitempty"`
    Strip map[string]bool `json:"strip,omitempty"`
    Rewrite map[string]interface{} `json:"rewrite,omitempty"`
}
```

Имя поля `Hops`, а не `Outbounds`: рядом в состоянии живут составы групп,
и два похожих поля с разным смыслом — источник ошибок. В конфиг эмитится
как `outbounds` — форма ядра (`option/chain_lx.go:13`) неизменна.

### Каталог `strip`

Ровно четыре ключа ядра (`protocol/chain/transform.go:24-27`), выдумывать
свои нельзя — неизвестный ключ это ошибка старта:

| Ключ | По умолчанию | Что снимает |
|---|---|---|
| `tls.fragment` | снимается | фрагментация ClientHello — сервер её не видит, внутри туннеля только задержки |
| `multiplex.padding` | снимается | паддинг мультиплексора |
| `xhttp.padding` | снимается | паддинг XHTTP |
| `tls.utls` | **не** снимается | отпечаток ClientHello; на узлах с `reality` снимать НЕЛЬЗЯ — ошибка старта |

## UI

### Где создаётся

Вкладка **Sources**, третий тип записи рядом с подпиской и сервером.
Кнопка добавления предлагает «Цепочка»; окно правки — форма цепочки.

В Направлениях цепочка не создаётся и не настраивается: она попадает туда
как узел — фильтром, наравне с серверами подписки.

### Форма цепочки

- **Список позиций** с порядком: строка = позиция, показывает тег и что это
  (узел / группа / Направление / другая цепочка). Порядок задаётся
  перетаскиванием — тем же механизмом, что на остальных списках (SPEC 109).
- **Добавление позиции** — `+` с выбором из существующих целей, как
  участники группы DNS. Вписывать тег руками нельзя: имена приходят из
  шаблона и подписок.
- **Подпись направления пакета** над списком: «сверху — первый хоп от вас,
  снизу — тот, чей адрес видит сайт». Это единственное, что нужно
  запомнить, и единственное, чем `chain` отличается от `detour` в чтении.
- **Настройки** (свёрнуты по умолчанию): `idle_timeout`, `strip_evasion`,
  четыре ключа `strip` галками, `rewrite` — на вкладке JSON.

### Деградация без поддержки ядром

Если проба показала, что ядро не знает `chain`:

- запись помечается в списке Sources как неработающая с пояснением;
- в конфиг **не эмитится** — то есть её просто нет в пуле узлов, ровно как
  у выключенного источника; ссылок в никуда не возникает по построению
  (правила ссылаются на Направления, а не на цепочку);
- в логе — предупреждение с версией ядра и нужным тегом сборки.

Не «тихо пропустить» и не «сломать конфиг»: пользователь должен понять,
почему настроенная цепочка не работает.

## Открытое (решено)

**Что делать с ядром без `with_lx_chain`.** На момент написания ТЗ в бандле
было именно такое.
Варианты: (а) реализовать с деградацией и ждать сборку ядра с тегом;
(б) сначала попросить сборку ядра, потом делать UI; (в) реализовать и
собрать ядро самим.

Принят **(а)**: UI и модель не зависят от наличия тега, а проба и
деградация нужны в любом случае — ядро у пользователей обновляется
отдельно от лаунчера, и версия без `chain` будет встречаться ещё долго.
