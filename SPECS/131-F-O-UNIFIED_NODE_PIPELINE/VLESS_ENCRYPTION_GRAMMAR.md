# VLESS `encryption` — грамматика постквантового слоя

Статус: **справка, НЕ правило реестра.** Формат `vless_encryption` в
`contract/registry` и корпус кейсов решением владельца 18.09.2026 **не
вносятся**: класс «негодный узел роняет весь конфиг» закрывается общей
страховкой — `sing-box check` → исключить названный в ошибке узел →
пересборка. Этот файл нужен затем, чтобы по префиксу ошибки ядра можно было
показать человеку дружелюбный текст, а не сырой `parse encryption: …`.

Грамматика подтверждена сессией ядра по исходникам **sing-box-lx v1.14.1-lx.8**:

- `protocol/vless/outbound.go:107` — точка входа, вызов разбора;
- `protocol/vless/lx_encryption.go`, `parseClientEncryption` — разбор строки;
- `encryption/common.go`, `ParsePadding` — разбор padding-блоков;
- `encryption/client.go`, `Init` — приём ключей.

Нормативно для пина ядра **1.14.1-lx.8**. При бампе пина сверять
`protocol/vless/lx_encryption.go` (так же, как сверяется `key_share` по
`option/tls.go`).

## 0. «Нет слоя»

Ядро сравнивает значение **точно и до trim**: слой выключен только при `""`
и `none`. Любое `None`, `NONE`, `" none "` уходит в парсер как настоящее
значение и роняет конфиг.

Наше правило (если бы оно писалось): клиент мягче на входе, строже на выходе —
`strings.ToLower(strings.TrimSpace(v)) ∈ {"", "none"}` считать выключенным
слоем и поле в тело **не класть**, без кода деградации.

Важно: `normalize: trim_lower` ко всему значению неприменим — ключи base64
регистрозависимы, lower-case их уничтожит.

## 1. Разрез на сегменты

Вся строка `TrimSpace`, затем `Split(".")`. Сегментов меньше четырёх — отказ.

## 2. Сегменты 0–2 (метод, appearance, rtt)

Не тримятся, сравнение точное, с учётом регистра:

- `[0]` — только `mlkem768x25519plus`;
- `[1]` — `native` | `xorpub` | `random`;
- `[2]` — `0rtt` | `1rtt`.

## 3. Хвост

`parts[3:]` — каждый сегмент `TrimSpace`. Пустой сегмент — отказ.

## 4. Padding или ключ — только по длине

Идём слева направо, `paddingPhase = true`.

- если `paddingPhase` и длина сегмента **в байтах** после trim `< 20` →
  padding-блок;
- иначе — ключ: base64 **RawURL** (алфавит `A–Z a–z 0–9 - _`, без `=`),
  после декода ровно **32** или **1184** байта;
- после первого ключа `paddingPhase = false` навсегда: короткий сегмент
  после ключа трактуется как ключ и даёт отказ по длине.

Ключей ноль — отказ. Смешение 32 и 1184 в любом порядке разрешено, лимитов на
число ключей и блоков нет.

**СТРОЖЕ ЯДРА** (наше решение, если правило когда-нибудь появится): Go
`base64.RawURLEncoding` молча пропускает `\r` и `\n` внутри сегмента и не
требует каноничных хвостовых битов. Такие значения мы бы **отбраковывали**:
любой символ вне алфавита (включая `\r`, `\n`, пробел, `+`, `/`, `=`) →
отказ; неканоничные хвостовые биты → отказ (в Go: собственная проверка
алфавита, затем декод через `base64.RawURLEncoding.Strict()`).

## 5. Форма padding-блока

Split по `-`, частей **не меньше трёх**; лишние игнорируются
(`100-111-1111-9` годен). Первые три непустые, каждая — целое по
`strconv.Atoi` (ведущий `+` допустим; `-` невозможен, его съел split).
Верхней границы у первого числа нет, но переполнение `int` → отказ. Для
переносимости в Dart: число помещается в `int64`.

## 6. Первый padding-блок

Индекс 0: `y0 ≥ 100`, `y1 ≥ 35`, `y2 ≥ 35`.

## 7. Индексация блоков с НУЛЯ

Блоки `0, 2, 4…` — «длины», `1, 3, 5…` — «паузы». Сумма `max(y1, y2)` по
блокам-длинам ≤ **65553** (= 18 + 65535). У пауз проверяется только форма.

## 8. Ключи

- **32 байта** — любые 32 байта годны.
- **1184 байта** — ML-KEM-768 encapsulation key. Первые **1152** байта =
  768 коэффициентов по 12 бит little-endian (`ByteDecode₁₂`), на каждые три
  байта `b0, b1, b2`:

  ```
  c0 = b0 | ((b1 & 0x0F) << 8)
  c1 = (b1 >> 4) | (b2 << 4)
  ```

  Каждый коэффициент должен быть `< 3329`, иначе отказ. Последние 32 байта
  (rho) не проверяются.

  Реализация руками, без `crypto/mlkem`: Win7-джоба собирает модуль
  тулчейном go1.20, там этого пакета нет.

## Тексты ошибок ядра

Общий вид фатала на старте — ядро не поднимает **весь** конфиг:

```
initialize outbound[i] vless[tag]: parse encryption: …
initialize outbound[i] vless[tag]: initialize encryption: …
```

`box.New` падает, ни один узел конфига не работает. Оба префикса и обе точки
отказа (`parse` — шаги 1–7, `initialize` — приём ключей, шаг 8) подтверждены
сессией ядра; именно по префиксу и стоит опознавать этот класс ошибки.

**Дословно проверен в дереве ровно один текст** —
`invalid encryption key length: 1198 (expected 32 or 1184)`: на нём
спотыкается синтетический ключ корпуса, см.
`core/config/corpus_singbox_check_test.go:208` (`uncheckableFields`, поле
`encryption` оттуда исключено осознанно: фикстура синтетическая, тест
отвечает за конвейер, а не за подлинность ключей). Формат текста —
`invalid encryption key length: N (expected 32 or 1184)`.

Остальные тексты дословно **не снимались**: исходников ядра в дереве и в
module cache нет, а выдумывать строки, по которым потом будут матчиться
подсказки пользователю, нельзя. Ниже — только сама причина отказа по шагам;
дословные строки снимать прогоном `sing-box check` на пине 1.14.1-lx.8, когда
за подсказки возьмутся.

| шаг | что не так | где падает |
|-----|-----------|------------|
| 1 | сегментов меньше четырёх | `parse encryption` |
| 2 | метод не `mlkem768x25519plus` (в т.ч. другой регистр) | `parse encryption` |
| 2 | appearance вне `native\|xorpub\|random` | `parse encryption` |
| 2 | rtt вне `0rtt\|1rtt` | `parse encryption` |
| 3 | пустой сегмент в хвосте | `parse encryption` |
| 4 | сегмент ≥20 ушёл в ветку ключа и не декодируется как base64url | `parse encryption` |
| 4 | ключ декодировался, но длина не 32 и не 1184 | `parse encryption` (текст выше, дословный) |
| 4 | ключей ноль (только padding) | `parse encryption` |
| 5 | padding-блок из двух частей / нечисло | `parse encryption` (`ParsePadding`) |
| 6 | первый блок: `y0 < 100` или `y1 < 35` или `y2 < 35` | `parse encryption` (`ParsePadding`) |
| 7 | сумма длин больше 65553 | `parse encryption` (`ParsePadding`) |
| 8 | ключ 1184 с коэффициентом ≥ 3329 | `initialize encryption` (`client.Init`) |

Для дружелюбных текстов префикса `parse encryption:` / `initialize
encryption:` достаточно: узел с таким `encryption` ядро не принимает,
поэтому он исключён из сборки; обновите подписку, возьмите строку
`encryption` у провайдера заново, а если сервер без постквантового слоя —
уберите параметр `encryption` из ссылки. Снимать поле молча **нельзя**: узел
без `encryption` к серверу, который его требует, не подключится, а тихое
снятие слоя — это тихое понижение защиты.

## Что маппер делает с `encryption` сегодня (проверено на HEAD d18537c5)

Разбирался прогоном через `subscription.ParseNode` →
`materializeParsedNodeBody` и через `nodeflow.SanitizeFrom("vless", "singbox", …)`.

**Ссылка (`vless://…?encryption=…`)** — `core/config/subscription/node_parser_core.go:770-775`:

```go
if enc := queryParam(node.Query, "vless", "encryption"); enc != "" && !strings.EqualFold(enc, "none") {
    outbound["encryption"] = enc
}
```

`EqualFold` — значит `none`, `None`, `NONE` одинаково выключают слой; сам
`queryParam` значение тримит, поэтому `" none "` тоже не доезжает. Пустое
значение и отсутствие параметра — поля в теле нет. Всё прочее (включая
`garbage`) уезжает в тело как есть, без единого кода. Прогон подтвердил все
четыре исхода.

**Xray-JSON** — `core/config/subscription/xray_outbound_convert.go:145,160`:
значение сначала `strings.TrimSpace`, затем то же `EqualFold(…, "none")`.
Поведение совпадает с URI-веткой.

**sing-box JSON (импорт тела)** — специальной ветки нет вовсе: `encryption`
приезжает в карту как есть и проходит санитайзер без правил (в реестре у
поля только `type: string`, `lx_only`, `min_core`). Прогон: `"none"`,
`"None"`, `" none "`, `"garbage"` — **все четыре остаются в теле**, кодов
нет. Из них `"none"` ядро примет (сравнение точное, это его собственный
литерал), а `"None"` и `" none "` — фатал на весь конфиг. Это и есть самая
дырявая из трёх веток: две другие свой диалект `none` уже переводят, а
JSON-импорт — нет.

**Пометки поля.** У URI-параметра в `contract/registry/protocols/vless.json`
стоит `"ext": "mobile"` («Supported by LxBox only» в
`contract/docs/generated/protocols/vless.md:66`) — и это **неверно**: Go
параметр читает (`node_parser_core.go:773`), `impl`-заметка рядом
(«Go параметр НЕ парсит») отстала от кода. У поля тела стоят `lx_only: true`
и `min_core: "1.14.0-lx.18"`; ни то, ни другое исполнению правила значения не
мешает — `min_core` работает в гейте сборки (`core/config/nodeflow/gate.go:138`),
`lx_only` в санитайзере не читается вовсе.
