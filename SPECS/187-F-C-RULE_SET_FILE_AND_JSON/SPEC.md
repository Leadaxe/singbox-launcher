# SPEC 187 — Наборы правил из файла (`file://`) и в формате JSON

Issue: Leadaxe/singbox-launcher#153. Решения владельца — 22.11.2026.
Строится поверх SPEC 185 (цикл обновления наборов).

## 1. Проблема

- Свой набор правил с диска подключить нельзя: тип SRS принимает только URL,
  а загрузчик ходит только по HTTP(S).
- Набор в формате JSON (исходный, `format: source`) не работает ни по URL, ни
  с диска: сборка всегда пишет `"format": "binary"`, имя копии всегда
  `<тег>.srs`.

Ядро умеет и то и другое (`type: local` + `path`, `format: source|binary`) —
ограничение только в лаунчере.

## 2. Решение

Нового вида правила нет. Тот же `kind: srs`, то же поле `refs[]`, тот же цикл
обновления. Меняются два независимых свойства строки `refs[]`:

| | `.srs` (binary) | `.json` (source) |
|---|---|---|
| `https://` | есть | **новое** |
| `file://` | **новое** | **новое** |

### 2.1 Формат — по расширению

- Путь ссылки оканчивается на `.json` → `format: source`; всё остальное
  (включая ссылки без расширения) → `binary`, как сейчас.
- Одна функция на всё: сборка (local и remote-режим SPEC 185), имя копии,
  проверка содержимого. `format` в конфиг пишется всегда явно.
- У набора пресета явный `format` шаблона сильнее расширения.
- Копия хранится с настоящим расширением. Тег файла `.json`-набора несёт
  расширение сам: `<имя>-<хеш>.json` (у `.srs` тег прежний, `<имя>-<хеш>`,
  файл `<тег>.srs`). Имя копии и формат выводятся из одного тега — одной
  функцией во всех местах. То же имя уезжает в ресурс-стор удалённой машины;
  Deploy берёт имя из `path` и правок не требует.
- Проверка содержимого до замены копии: копия `.json` обязана начинаться с
  `{`; копия `.srs` принимает `SRS` либо `{`, как до этой задачи (набор
  пресета с явным `format: source` и ссылкой без расширения).

### 2.2 `file://` — новый транспорт загрузчика

- В `refs[]` допускается `file://`-ссылка (RFC 8089): `file:///Users/a/x.json`,
  `file:///C:/Rules/x.srs`. Сетевые пути Windows (`\\server\share`) не
  поддерживаются — строка не сохраняется, с понятной ошибкой.
- «Загрузка» = копирование исходника в каталог наборов машины-цели: временный
  файл → проверка содержимого → атомарная замена (тот же хвост, что у HTTP).
  Ядро читает только копию; исходник ему не нужен (TCC у root-демона macOS,
  удалённые машины).
- Изменился ли исходник: размер или время изменения отличаются от копии.
  После копирования копии ставится время изменения исходника.
- Проверка — на каждом проходе цикла SPEC 185 (раз в час), при Update, по
  кнопке, перед сборкой и перед Deploy; интервал правила для `file://` не
  действует, кроме `0` (автообновление выключено). Работающее ядро
  перечитывает копию само.
- Исходник пропал или не читается: копия остаётся; для цикла это обычная
  неудача загрузки (запись в лог, повтор не чаще раза в час), в подсказке
  кнопки правила — строка о пропавшем исходнике. Нет ни исходника, ни копии — правило выпадает из
  конфига (SPEC 185 §2.2), ядро не падает.
- Режим remote SPEC 185 к `file://` неприменим. Правило, в котором есть хотя
  бы один `file://`-набор, целиком идёт в режиме local (правило — одна
  единица); выбор Mode в окне такого правила заперт.
- Путь — всегда на машине лаунчера. Для удалённой машины копия кладётся в её
  каталог наборов у лаунчера и заливается при Deploy как любой набор; без
  Deploy правка исходника до машины не доезжает (SPEC 185 §2.3).

### 2.3 UI

- Тип правила «SRS» → «Rule set». Подпись поля: «Rule sets — URL or file
  (one per line)». Рядом с «?» кнопка «Add file…» — стандартный файловый
  диалог (фильтр `.srs`, `.json`), дописывает строку `file://…` в поле.
- Вставленный абсолютный путь (`/Users/…`, `C:\…`, `C:/…`) при сохранении
  превращается в `file://` (буква диска, слэши, пробелы → `%20`). Обе стороны
  преобразования — одна общая функция.
- Сохранение строки `file://`: файл существует, читается, проходит проверку
  содержимого по формату. Иначе — ошибка у поля, правило не сохраняется.
- Кнопка строки правила: `⬇ srs / 🔄 srs / ✔️ srs` → `⬇ upd / 🔄 upd / ✔️ upd`
  (набор теперь не только `.srs`).

### 2.4 Контракт (1.1.177 → 1.1.178)

- `rules[].refs[]` у `kind: srs`: `http(s)://` или `file://`; формат набора —
  по расширению пути (`.json` → source). Норма общая: LxBox делает формат по
  расширению так же.
- `file://`-ссылка осмысленна только на машине, где лежит файл:
  - лаунчер экспортирует и импортирует запись как есть; файла нет — правило
    выпадает на сборке (п. 2.2), в списке видно «не загружено»;
  - LxBox (Android): правило с `file://` в `refs[]` ввозится **выключенным**
    с предупреждением `backup_rule_ref_local_file` (новый код реестра),
    ссылка сохраняется и уходит обратно в экспорт; сам LxBox таких ссылок не
    создаёт.
- BACKUP.md, схема, `backup_warnings.json`, кейс корпуса бэкапа, строка
  changelog, параграф `TASKS_LXBOX.md`.

## 3. Вне задачи

- Путь к файлу, лежащему на удалённой машине (не копируется, не проверяется).
  Решение владельца: не делаем. Замечание: «Custom JSON» этого сегодня тоже
  не закрывает — правило может сослаться на `rule_set`, но объявить сам набор
  из диалога негде; отдельная задача, если понадобится.
- Слежение за исходником в реальном времени (хватает часового цикла и Update).
- Сетевые пути Windows.
- Компиляция JSON → `.srs`.

## 4. Критерии приёмки

1. `https://…/list.json` в правиле: копия `<тег>.json`, в конфиге
   `type: local, format: source`; ядро проходит check.
2. `file://…/x.srs` и `file://…/x.json`: копия создана, в конфиге `local` с
   верным `format`; правка исходника доезжает до копии циклом/Update без
   перезапуска ядра.
3. Исходник удалён: копия и правило живут, есть предупреждение. Удалены оба —
   правило выпало, ядро стартует.
4. Вставленный путь Windows и путь с пробелами сохраняются как корректный
   `file://` и находят файл.
5. Удалённая машина: набор из `file://` и набор `.json` заливаются при Deploy,
   конфиг ссылается на `resources/<тег>.<расширение>`.
6. Запись с `file://` переживает save/load и экспорт/импорт бэкапа; кейс
   корпуса проходит.
7. Существующие `.srs`-правила и файлы не перекачиваются и не меняют тегов.
