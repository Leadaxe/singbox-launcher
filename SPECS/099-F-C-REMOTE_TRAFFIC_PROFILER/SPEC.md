# SPEC 099 — Профайлер трафика удалённой машины

**Тип:** Feature · **Статус:** Complete · **Платформа:** все

У каждой удалённой машины свой профайлер: своё окно, свой поток соединений,
свой буфер. Открывается из её строки на вкладке Remote. Источник — только
gRPC; вместо разбивки по процессам — разбивка по клиентам сети.

**Depends on:** SPEC 059 (профайлер, локальный), SPEC 098 (вкладки и список
машин), SPEC 097 (транспорт и реестр машин), форк: SPEC 017 (detour),
SPEC 018 (DNS-стрим), SPEC 063 (ресурсы), `docs-lx/lxd-grpc-api.md`.

---

## 1. Проблема

**Профайлер один на приложение.** `TrafficProfiler` — синглтон
(`GetInstance`), его источник переключается по режиму бэкенда: classic →
Clash HTTP, daemon → gRPC своего демона. Понятия «чей профайлер» в нём нет.
Подключить к нему удалённую машину значило бы получить ровно ту болезнь, что
SPEC 098 вылечил в списке узлов: открыл профайлер роутера — потерял
локальный, две машины рядом не посмотреть.

**Clash к машине неприменим.** У её конфига Clash API нет by design, `/connections`
не отвечает, а `sing-box.log` лежит на её файловой системе. Оба источника
локального профайлера для неё недоступны.

**Процессов на роутере нет.** Вкладка «Per-process» построена вокруг выбора
процесса: пикер зовёт `platform.ListProcesses()` — список процессов ЭТОГО
компьютера. Для машины он бессмыслен дважды: там нет ни этих процессов, ни
процессов вообще — трафик идёт от устройств сети. `find_process` в конфиге
роутера выключен, и это не упущение, а следствие: атрибутировать нечего.

## 2. Целевая модель

### 2.1 Экземпляр на машину

Профайлер машины — отдельный `TrafficProfiler` со своим окном, стримами и
кольцевым буфером. Локальный синглтон не трогается.

Повторное открытие фокусирует существующее окно, а не поднимает второй стрим.
Экземпляр гаснет вместе с каналом: при `Disconnect` и при удалении машины —
иначе стрим продолжал бы жить к машине, с которой разговор уже не идёт.

Открывается из блока «Ещё» в строке машины (SPEC 098 §2.1), требует живого
соединения: источник — её gRPC-стрим.

### 2.2 Источники — только gRPC

| Что | RPC | Зачем |
|---|---|---|
| соединения | `SubscribeConnections{interval}` | таблица соединений, трафик |
| DNS | `SubscribeDNSQueries{includeAnswers}` | домены, CNAME, отказы |
| сводка | `SubscribeStatus{interval}` | связи, скорости, память |
| справочники | `GetRules`, `GetOutbounds`, `GetStartedAt` | расшифровка и uptime |
| устройства | `GET /admin/clients-info` (REST) | имена клиентов сети (§2.5) |
| действие | `CloseConnection{id}` | обрыв соединений клиента |

Три правила протокола, каждое из которых уже стоило кому-то отладки:

**`interval` — наносекунды**, демон клампит снизу 200 мс. Прислать `1000`,
подумав про миллисекунды, значит попросить тикер раз в микросекунду; так уже
сжигали ядро CPU (`fca1d367e` в форке).

**`SubscribeConnections` — дельта-протокол, а не повторяющийся снимок.**
`NEW` несёт полный объект, `UPDATE` — **только id и приращения** (объект
всегда nil), `CLOSED` — id и closedAt (объект может отсутствовать). Клиент,
который пропускает событие с пустым `connection`, показывает соединения,
никогда не набирающие трафик. Итоги ведутся на стороне клиента.

**`reset=true` — полная пересинхронизация.** Приходит первым кадром и
повторно при перезапуске ядра под клиентом (apply, Start/Stop). Таблица
очищается ДО применения событий того же кадра. Обрыв стрима равнозначен
`reset`: всё, что помним, больше не подтверждено.

Плюс инвариант отображения: **«нет данных» ≠ «нет соединений»**. До первого
кадра снимок отдаётся как «неизвестно», иначе график падает в пол на каждом
переподключении.

### 2.3 Вместо процессов — клиенты

Клиент — исходный адрес соединения (`Connection.source`, `ip:port`);
группировка по хосту без порта. Имя устройства недоступно: в gRPC-контракте
его нет, и придумывать резолв через аренды DHCP — вне scope.

Окно машины показывает две вкладки:

- **Live** — тот же поток событий, что у локального, но подпись источника
  берётся из адреса клиента, а не из имени процесса.
- **By client** — агрегат по устройствам вместо «Per-process».

Вкладка «Per-process» в окне машины **отсутствует**, а не выключена: пикер
процессов там показывал бы процессы чужой машины.

### 2.4 Вкладка By client

Таблица, свёрнутая по клиентам; раскрытие показывает соединения. **Строка —
одно соединение, как в Live**: меняется только ось группировки (клиент вместо
процесса), а не единица строки. Сворачивать соединения по хосту нельзя — они
различаются портом, маршрутом и временем жизни, и агрегат прятал бы ровно то,
ради чего таблицу открывают.

```
Client [ all ▾ ]   Outbound [ all ▾ ]   Rule [ all ▾ ]        [ Reset ]
Search [ youtube                          ] ✕        12 / 26 conns

DESTINATION                    :      ~      УШЛО  ПРИШЛО  OUTBOUND   RULE
▾ 192.168.10.124 (iPhone-Vasya) ⚠ mixed outbounds  12  1.8M   55.0M
     youtube.com              443    2m    1.2M    40.0M  proxy-out  rule_set: …
     youtubei.googleapis.com  443    14s   600K    15.0M  proxy-out  rule_set: …
                                              [ ✕ Close connections ]
▸ 192.168.10.42 (NAS)                              2   18K    412K
```

**Фильтры разделены по природе данных.** Клиенты, outbound'ы и правила
перечислимы — они в списках, со счётчиками, и заполняются из ЖИВОГО потока, а
не из конфига: показывать неиспользуемые outbound'ы конфига бессмысленно,
важно то, куда трафик ушёл на самом деле. Домены, IP и порты исчисляются
сотнями — они в строке поиска. Условия складываются: `direct-out` + `youtube`
отвечает на типичный вопрос «что из ютуба ушло мимо VPN».

**Колонка OUTBOUND — главная.** Ради неё профайлер на роутере и открывают.
Рядом с ней — правило, которое этот outbound выбрало: `Connection.rule`
приходит уже человекочитаемой строкой (`metadata.Rule.String()` в ядре), а не
индексом, и расшифровки не требует.

**`⚠ mixed outbounds`** на клиенте, чьи соединения разошлись по разным
outbound'ам. Это и есть искомый симптом: устройство ушло мимо VPN частью
трафика — в общем потоке такое незаметно.

**`✕ Close connections`** рвёт все соединения клиента (`CloseConnection` по
каждому id). После смены правила устройство иначе доживает на прежних
сессиях и продолжает идти старым маршрутом.

Таблица строится по **живому снимку соединений**, а не по кольцевому буферу
событий: там открытия и закрытия, и итоговые байты длинной сессии в них не
видны.

Клик по строке открывает те же детали, что и клик в Live, — общий
`formatEventDetail` плюс блок устройства (§2.6). Два разных вида одного и того
же заставляли бы сверять поля глазами.

### 2.5 Имена устройств

`GET /admin/clients-info` (раздел 10a `lxd-daemon.md`) переводит адреса в
устройства: имя из аренды DHCP, MAC, SSID, интерфейс, порт коммутатора и
`source` — какие провайдеры заполнили запись.

Это **справочник, а не поле соединения**: имена меняются в масштабе часов,
демон отдаёт таблицу целиком, и join делает UI. Поток соединений не трогается.

Кэш — **минута, как у демона**. Свой TTL короче означал бы походы к роутеру за
данными, которые демон всё равно отдаёт из своего кэша. Обновление идёт в
фоне: справочник читается из UI-потока на каждой перерисовке, и синхронный HTTP
подвесил бы окно.

**Ключ везде остаётся IP** — группировка, фильтр и правила маршрутизации
работают по нему; имя только отображается, в скобках после адреса. Иначе
устройство, потерявшее аренду, меняло бы своё значение в списке на лету, и
выбранный фильтр переставал бы совпадать.

`source` показывается в карточке всегда: при разборе «почему устройство
потеряло имя» это первый вопрос, а одинокий `label` означает истёкшую аренду.

### 2.6 Что даёт DNS-стрим

Структурный поток вместо разбора лога, и богаче него: сервер, который
ответил, его тип, привязанный канал, признаки отказа, полный набор записей
ответа. CNAME-цепочка восстанавливается из `answers` — они приходят в
wire-порядке, CNAME-хопы перед A/AAAA; отдельной сущности для неё нет и не
нужно.

Пустой `outbound` у запроса — не сбой, а состояние: ответ из кеша, запрос не
покидал устройство.

## 3. Требования

### 3.1 Обязательные

1. Профайлер машины — отдельный экземпляр; локальный синглтон не затрагивается.
2. Повторное открытие фокусирует окно; экземпляр один на машину.
3. Экземпляр и все его стримы гаснут при `Disconnect` и удалении машины.
4. Источники только gRPC; Clash и чтение лога машины не используются нигде.
5. `interval` во всех `Subscribe*` — наносекунды (`int64(time.Second)`).
6. `SubscribeConnections` обрабатывается как дельта-протокол (§2.2).
7. `reset` и обрыв стрима очищают таблицу; «нет данных» отличается от «нет
   соединений».
8. Окно машины: вкладки Live и By client; вкладки Per-process нет.
9. Таблица By client строится по живому снимку соединений; строка = одно
   соединение.
10. Фильтры: три списка (клиент, outbound, правило) со счётчиками из живого
    потока + строка поиска по домену/IP/порту; условия складываются; Reset
    сбрасывает всё.
11. `Close connections` рвёт соединения выбранного клиента.
12. Все подписи через `bin/locale/*.json`.
13. Имена устройств из `/admin/clients-info`, кэш минута, обновление в фоне;
    ключом отбора остаётся IP.
14. Фильтры трёх списков продублированы в Live; строка поиска там своя
    (домен/IP/процесс) и не менялась.

### 3.2 Границы

- Имя устройства ЗАМЕСТО IP — нет: имя дополняет адрес, а не подменяет его
  (§2.5). Ключ отбора обязан быть стабильным.
- Запись сессии (`▶ Record`) для клиента — вне scope MVP; живого вида
  достаточно для диагностики маршрутизации.
- `GetRules`/`GetOutbounds` используются как справочники; отдельного экрана
  таблицы правил машины не делаем.
- Группировка по правилу и по outbound как отдельные оси — вне scope:
  колонки и фильтры отвечают на те же вопросы.

## 4. Критерии приёмки

1. Профайлеры двух машин открыты одновременно и показывают разные данные;
   локальный профайлер при этом работает своим потоком.
2. Трафик в таблице растёт: соединение, открытое до подписки, набирает байты
   (проверка обработки `UPDATE` без объекта соединения).
3. После `apply` на машине таблица очищается и наполняется заново, без
   мёртвых строк (проверка `reset`).
4. Обрыв связи с машиной не оставляет живых стримов и не роняет окно.
5. В окне машины нет вкладки Per-process и нет обращений к
   `platform.ListProcesses`.
6. Фильтр `outbound=direct-out` + поиск по домену показывает ровно те
   соединения, что ушли мимо VPN.
6a. Два соединения к одному хосту разными outbound'ами остаются двумя
   строками, а не схлопываются в одну.
6b. Имя устройства видно в заголовке клиента и в карточке соединения; при
   недоступном эндпоинте таблица работает на адресах.
7. `Close connections` закрывает сессии клиента; таблица это отражает на
   следующем тике.
8. `go build ./...`, `go vet ./...`, `go test ./...` — чисто.

## 5. Инварианты

1. **Профайлеры не делят состояние.** Ни поток, ни буфер, ни окно — как
   машины не делят файлы (SPEC 098 §5.7).
2. **К удалённой машине Clash не применяется.** Ни `/connections`, ни
   Clash-эндпоинт: у её конфига Clash API нет by design.
3. **Лог машины не читается.** Он на её файловой системе; DNS-плоскость
   приходит структурным стримом.
4. **UI не подменяет данные при отсутствии.** Пустая таблица до первого
   кадра — «неизвестно», а не «нет соединений».
5. **Локальный профайлер не меняется.** Те же вкладки, тот же источник, то
   же поведение, что до этой задачи.
6. **Клиенты — понятие удалённой машины.** У своего ядра их нет: трафик идёт
   от процессов этого компьютера, `SourceAddr` в соединениях Clash не
   заполняется, и это норма, а не пробел в данных. Поэтому в локальном окне
   нет ни колонки клиента, ни фильтра по нему — пустой список фильтра хуже
   отсутствующего: он обещает отбор, которого не будет.
