# SPEC 171 — DNS-слот пресета встаёт по оси правил

Статус: **C** (закрыта 15.10.2026). Тип: Feature (дефект порядка, вынесенный из SPEC 170). Контракт: бамп `contract/VERSION` → **1.1.127**, решение **D-135**, норма `contract/docs/TEMPLATE_LANG.md` §6.10 (новый), ссылки из §6.5.2 и §6.7.5, `contract/docs/BACKUP.md` (таблица `dns`), LxBox — `contract/TASKS_LXBOX.md` §124.

Повод — известное ограничение из `SPECS/170-F-C-TUNNEL_INGRESS/IMPLEMENTATION_REPORT.md` и `TASKS_LXBOX.md` §123.

---

## 1. Проблема

1. **Маршрутные правила живут на оси, DNS-правила — в слайсе.** `state.Rules[]` упорядочены номером `num` (SPEC 106, закон оси SPEC 113-C): пресет шаблона встаёт на свой номер, где бы он ни появился. `state.DNS.Rules[]` номера не имеют: порядок — позиция в массиве, и это порядок пользователя (SPEC 062: перетаскивание в DNS-вкладке, first-match ядра).
2. **Новый DNS-слот пресета дописывается в хвост.** Запись `{kind: preset, ref: <id>}` создаётся в трёх местах, и все три кладут её в конец:
   - `core/state/sync_dns.go` `SyncDNSOptionsWithActivePresets` (сохранение Конфигуратора, Debug API `core/stateedit`, новая установка);
   - `ui/configurator/models/dns_rule_slot.go` `ReconcileDNSRuleOrder` (загрузка в визард после `SeedLateDefaultRules`, включение пресета из Library, превью, сохранение);
   - `core/build/resolve_dns.go` Pass 4, «defensive fallback»: пресет активен в `state.Rules`, записи в `state.DNS.Rules` нет (сборка до первого сохранения визардом, в том числе после `lateSeededRules`) — правила пресета дописываются после всех.
3. **Следствие для `tunnel-ingress`** (SPEC 170, `num: 940`). Маршрутный `reject` встаёт на 940 — раньше всех остальных пресетов. DNS-reject закрытых пиров у существующего пользователя оказывается последним: если выше стоит правило, ловящее всё (`query_type: [A, AAAA] → fakeip` пресета `fakeip`, 1130), DNS-запросы закрытого пира обслуживаются, хотя маршрут их закрывает. На новой установке порядок верный только потому, что все слоты создаются одним проходом по уже отсортированным `state.Rules`.
4. То же у `tailscale` (945, поздний дефолт с 1.1.86): его DNS-правило `preferred_by` у существующих пользователей стоит после `fakeip`.

## 2. Решение

### 2.1 Норма (D-135) — одна на обе стороны

**DNS-слот пресета появляется по той же оси, что его маршрутное правило.** Когда запись `dns.rules[] {kind: preset, ref: <id>}` создаётся впервые — поздний дефолт, включение пресета пользователем, импорт состояния или бэкапа без такой записи, Debug API, сборка на состоянии без записи, — она встаёт **перед первым уже стоящим слотом пресета, чей номер оси больше** номера этого пресета; такого слота нет — в конец списка.

- **Номер слота** — `num` маршрутного правила `rules[]` с тем же `ref` (у неразмеченного — 1000, `DefaultRuleNum`); номер шаблона не нужен: маршрутное правило к этому моменту размечено (`NormalizeRuleOrder`, `SeedLateDefaultRules` ставят номер шаблона).
- **Пользовательские DNS-правила** (`kind: user`) номера не имеют и не двигаются: они остаются на своих местах относительно соседних слотов пресетов. Правило пользователя, стоящее выше всех пресетов, остаётся выше и нового слота — порядок пользователя не оспаривается.
- **Уже стоящие слоты не переупорядочиваются.** Порядок `dns.rules` — порядок пользователя (SPEC 062), и отличить «перетащил» от «дописано в хвост старой версией» по состоянию нечем. Равные номера — новый слот встаёт после (стабильно).
- Норма — про **место появления**, не про инвариант: после появления слот живёт по правилам DNS-вкладки, перетаскивание его двигает свободно.

Следствие: новая установка даёт тот же порядок, что сегодня (слоты по оси); у существующего пользователя `tunnel-ingress` (940) встаёт перед `tailscale` (945), `russian` (1120), `fakeip` (1130) — DNS-reject закрытых пиров срабатывает раньше `A/AAAA → fakeip`.

### 2.2 Существующие пользователи — решение по умолчанию

**Миграции нет, отметки в `state.json` нет.** Порядок уже записанных `dns.rules` не трогается; норма применяется только к слотам, которых в состоянии ещё нет. Основания: релиз с `tunnel-ingress` не выходил (пресет в `develop` с d0e96ebd), так что у пользователей релизов слота ещё нет — он появится уже по норме; `tailscale` у существующих пользователей стоит там, где стоит, и перенос «вслепую» сломал бы ручной порядок тех, кто его двигал. Состояние dev-сборки, где `tunnel-ingress` уже дописан в хвост, лечится перетаскиванием в DNS-вкладке или удалением записи `{kind: preset, ref: tunnel-ingress}` из `dns.rules` в `state.json` — синхронизация создаст её заново по оси. Это описано в отчёте.

### 2.3 Что НЕ вводится

- Номер `num` у DNS-правил и отдельная DNS-ось — нет: DNS-порядок остаётся порядком пользователя, ось даёт только место появления.
- Пересортировка слотов пресетов по оси при каждой загрузке — нет (ломает перетаскивание).
- Учёт пользовательских DNS-правил при вставке (например, «перед первым ловящим всё») — нет: тело пользовательского правила не анализируется.
