# PLAN — 102-B XHTTP `extra` в Xray-JSON ветке

---

## 1. Подход

Не дублировать список полей в конвертере, а **вынести общее ядро**.

Обе ветки уже сводят свой источник к плоскому набору строк:

- URI-ветка: `xhttpMergeSource(q)` → `map[string]string` (`extra`-JSON) + плоские
  query-параметры через `queryGetFold`;
- Xray-ветка: `xhttpSettings` — `map[string]interface{}`, внутри вложенный
  `extra` — тоже `map[string]interface{}`.

Значит достаточно свести Xray-раскладку к тем же двум плоским слоям и отдать их
в общий сборщик. Схема полей тогда физически одна, и R2 («расхождение не
допускается») держится не соглашением, а типом.

**Отвергнутая альтернатива:** скопировать циклы по `xhttpStringFields` в
конвертер. Быстрее на 15 строк, но воспроизводит ровно тот дефект, который
чиним, — два списка полей, расходящихся со временем.

## 2. Изменения по файлам

### 2.1 `core/config/subscription/node_parser_transport.go`

**Рефактор `xhttpTransportFromQuery` → общее ядро.**

Ввести внутренний сборщик, работающий поверх абстракции «источник значений»:

```
xhttpBuildTransport(primary, fallback map[string]string) map[string]interface{}
```

- `primary` — слой, выигрывающий при конфликте (`extra`);
- `fallback` — плоский слой (query-параметры / плоские `xhttpSettings`);
- внутри — существующая логика: `mode`/`path`/`host`, `x_padding_bytes`,
  bool-флаги, циклы по `xhttpStringFields` и `xhttpRangeFields`.

`xhttpTransportFromQuery(q)` становится тонкой обёрткой: строит `primary` через
уже имеющийся `xhttpMergeSource(q)`, `fallback` — из `q` (свёртка `url.Values`
в `map[string]string` с сохранением case-insensitive поиска).

Поиск по ключу с учётом регистра переносится внутрь ядра: сейчас его даёт
`queryGetFold`, для плоской карты нужен эквивалент (сравнение через
`strings.EqualFold`) — чтобы Xray-ветка тоже читала `camelCase`/`snake_case`
одинаково.

`xhttpStringifyJSON` переиспользуется как есть — это готовая нормализация
чисел/булей из JSON (R3), и она уже даёт `30` вместо `30.0` и `1000000` вместо
`1e+06`.

**Поведение URI-ветки не меняется** — только точка входа; существующие тесты
`xhttp_v2_test.go` фиксируют это.

### 2.2 `core/config/subscription/xray_outbound_convert.go`

Ветку `case "xhttp", "splithttp"` (`:282`) перевести на общее ядро:

1. взять `xhttpSettings` (с фолбэком на `splithttpSettings` — как сейчас);
2. плоский слой: все скалярные поля `xhttpSettings` через `xhttpStringifyJSON`;
3. приоритетный слой: `xhttpSettings.extra`, если это объект, — его скалярные
   поля через `xhttpStringifyJSON`;
4. вызвать `xhttpBuildTransport(extra, flat)`.

`extra` не-объект / отсутствует → `primary` пустой, узел собирается из плоского
слоя (R6). Вложенные объекты внутри `extra` (`xmux`) в плоский слой не попадают
— скаляров у них нет, а сам `xmux` вне scope (R7); зафиксировать комментарием,
чтобы следующий читатель не счёл это упущением.

`path` продолжает проходить через `xhttpCleanPath` — он уже внутри ядра.

### 2.3 Тесты

**`core/config/subscription/xray_protocols_test.go`** (существующий файл
Xray-ветки) — кейсы из критериев приёмки §3.1–3.5: `uplinkHTTPMethod`,
`xPaddingBytes` (`"50-150"` и `"0-0"`), числовые значения, приоритет
`extra` над плоским полем, битый `extra`.

**Тест паритета (§3.6)** — ключевой, страхует от повторения дефекта:
один и тот же набор полей, поданный (а) как `extra`-JSON в URI и (б) как
`xhttpSettings.extra` в Xray-JSON, даёт **идентичный** транспорт. Падает при
добавлении поля только в одну ветку.

Фикстуры — три реальных узла из SPEC §1.2, с обезличенными адресами/ключами
(CONSTITUTION §6.3: в репозиторий не кладём реальные учётные данные).

Тесты на форматирование строк/вёрстку не пишем (памятка `no-ui-format-tests`) —
здесь это и не нужно, проверяется структура конфига.

## 3. Порядок работ

1. Рефактор ядра в `node_parser_transport.go`, зелёные существующие тесты
   (доказательство, что URI-ветка не поехала).
2. Перевод Xray-ветки на ядро.
3. Тесты §2.3, включая паритет.
4. `go build ./...`, `go test ./...`, `go vet ./...`.
5. Проверка на живых узлах через `URLTestOutbound` (§3.7) — до и после.
6. `docs/release_notes/upcoming.md`.

## 4. Риски

| Риск | Митигация |
|------|-----------|
| Рефактор ломает URI-ветку | Шаг 1 отдельно, существующие тесты `xhttp_v2_test.go` — гейт до правки конвертера |
| Ядро начинает эмитить поля, которых раньше не было, на уже работающих узлах | Поля берутся только из источника; при отсутствии ключа значение не пишется — набор для узлов без `extra` не меняется |
| `x_padding_bytes: "0-0"` отфильтруется как «пустое» | Проверка на непустую строку, а не на «ненулевое»; отдельный тест-кейс (R5) |
| 400 на `stream-one` не уйдёт после фикса | Причина padding — гипотеза; §3.7 её проверяет. Если 400 останется — узкий остаток эскалируем команде ядра с уже корректным конфигом |

## 5. Вне изменений

`outbound_jsonbuilder.go` не трогаем — allowlist уже содержит нужные ключи.
`xmux` не добавляем (R7). Другие транспорты Xray-ветки не трогаем.
