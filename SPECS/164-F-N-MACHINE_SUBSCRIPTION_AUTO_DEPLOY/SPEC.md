# SPEC 164 — Автообновление подписок машин и авто-деплой при смене узлов

Статус: N (new). Тип: F. Дата: 2026-10-13. Продолжение SPEC 098/100 (профиль
машины), SPEC 052 phase 8 (автообновление подписок), SPEC 161/162 (окно
Service, паспорт).

Сторона ядра: изменений не требует. Используются существующие
`/admin/status`, `/admin/info`, `/admin/apply` (валидация → подмена инстанса
→ last-good с автооткатом) и ресурс-стор.

## 1. Проблема

Инцидент 13.10.2026, роутер Home (RouteRich, 192.168.10.1). Все vless-узлы
подписки Liberty на вкладке Remote показывают `Error`, hysteria2-узел жив.
Разбор показал, что роутер, DNS и лаунчер ни при чём:

- Liberty отдаёт новые хостнеймы `*.liberty-nodes.online` на каждый фетч и
  просит обновляться раз в час (`profile-update-interval: 1`). Старые IP
  того же /24 через ~сутки перестают принимать TCP (ping идёт, SYN молчит
  или получает RST) со всех точек выхода: SkyNet, IRA, Parnas, WARP.
- На роутере работал `last_good.json` от 12.10 13:35. Состояние Home в
  лаунчере пользователь обновил руками 13.10 11:11 (Configure → Refresh →
  Save), собранный конфиг уже содержал новые имена, кнопка Deploy горела
  оранжевой точкой. Нажатия Deploy не было — узлы на роутере мертвы.
- Одноразовое ядро из `/tmp` на роутере (mixed на loopback, без TUN):
  новый узел → `api.ipify.org` 200 за 0.34 с, старый → `i/o timeout`.

Корень: лаунчер умеет обновлять подписки и умеет деплоить, но не связывает
одно с другим для машин. Автообновление (`core/auto_update.go`) обходит
только локальное состояние `state.json`; состояние машины
(`wizard_states/remote/<id>/state.json`) обновляется только из её
Конфигуратора руками; доставка на машину — только кнопка Deploy. С
провайдером, который ротирует адреса, узлы на роутере будут умирать
примерно раз в сутки, пока оба шага ручные.

## 2. Цель

Машина с включённым флагом **«Auto-deploy subscription updates»** получает
свежие узлы без участия пользователя: лаунчер по своему часовому heartbeat
обновляет подписки её профиля, пересобирает её конфиг и, если изменение
вызвано только подпиской и машина в спокойном состоянии, деплоит его той же
цепочкой, что кнопка Deploy. Пользователь видит результат в журнале машины
и в уведомлении системы.

Не цель: агент на самой машине (headless-сборка лаунчера под linux/arm64).
Это отдельный проект с другим владельцем состояния; здесь фиксируется
ограничение «работает, пока лаунчер запущен».

## 3. Принципы

1. **Согласие на машину.** Флаг хранится в записи реестра машины, по
   умолчанию выключен, включается в окне Edit. Правило heartbeat «ходить
   по сети к записям реестра без спроса нельзя» сохраняется: флаг и есть
   спрос. Сетевые вызовы идут только к машинам с флагом.
2. **Один источник сборки и одна цепочка доставки.** Пересборка — та же
   функция, что Save Мастера и «Save choice» вкладки Network
   (`configurator.RebuildMachineConfig`); доставка — `RemoteRegistry.Deploy`
   (ресурсы строго раньше конфига). Никакого второго пути «авто иначе,
   чем кнопкой».
3. **Деплоится только изменение от подписки.** Критерий без диффа JSON:
   до обновления подписок sha256 собранного конфига совпадает с
   `active_sha` машины (пользователь ничего не оставил незадеплоенным),
   после пересборки sha изменился. Любая другая картина — только запись в
   журнал и оранжевая точка, как сейчас.
4. **Тишина важнее свежести.** Условия деплоя: машина ответила на health,
   `core_status = started`, `active_sha = last_good_sha`,
   `interrupted_apply = false`, ядро не старее требуемого (или
   предупреждение для этой версии уже снято галкой `core_warn_ack`).
   Любое несовпадение — пропуск до следующего тика, без ретраев внутри
   тика.
5. **Одна попытка на тик на машину.** Провал деплоя не повторяется
   досрочно: демон сам откатывается на last-good, лаунчер пишет в журнал и
   показывает уведомление. Следующая попытка — на следующем heartbeat, и
   только если sha снова изменился.
6. **Глобальный выключатель уважается.** Настройка
   `subscription_auto_update_disabled` выключает и обход машин. Во сне
   системы (`platform.IsSleeping`) и при переносе данных обход пропускается,
   как у локального.
7. **Выбор в селекторе переживает перезапуск.** Теги узлов подписки
   стабильны (страна), меняются хосты; `cache_file` на машине хранит выбор
   по тегу. Отдельной логики восстановления не нужно; если тег исчез из
   подписки, селектор ядра сам уходит на первый узел — это штатное
   поведение, не ошибка задачи.

## 4. Поведение

### 4.1 Флаг машины

- `RemoteDaemon.AutoDeploySubscriptions bool` (`auto_deploy_subscriptions`),
  по умолчанию `false`.
- Окно Edit машины: галка **«Auto-deploy subscription updates»** под полем
  SSH с подписью серым: «Refresh this machine's subscriptions hourly and
  deploy when only the nodes changed. The launcher must be running.»
- Debug API: поле в `machineView` (список, GET, PATCH) и
  `PATCH /remote/machines/{id}` принимает `auto_deploy_subscriptions: bool`.

### 4.2 Обход машин (heartbeat)

На каждом тике петли автообновления (startup-sweep через 30 с и далее раз в
час) после обхода локальных источников:

1. Список машин из реестра; берутся только с флагом.
2. Для каждой машины **последовательно** (не параллельно: одна сеть, один
   журнал):
   a. `HealthWithin(id, 10 с)`. Нет ответа — запись в журнал
      `auto-deploy: <name>: unreachable (<err>)`, следующая машина.
   b. `sha_before` = sha256 собранного `config.json` машины ("" — конфига
      нет: машина не настроена, пропуск с записью).
   c. Загрузка `wizard_states/remote/<id>/state.json`; для каждой enabled
      подписки с URL, устаревшей по `effectiveReload` (та же трёхступенчатая
      логика, что у локального: настройка подписки → заголовок провайдера →
      дефолт настроек), — фетч тем же `refreshOneSubscriptionSource`;
      результат пишется в файл машины под её мьютексом. Фетч неудачен —
      запись в журнал, один retry через 15 с (как у локального), деплоя на
      этом тике нет.
   d. Ни одна подписка не изменила состав узлов — конец, без пересборки.
   e. Пересборка `RebuildMachineConfig(id)`. Провал (узел не разобрался,
      `check` ядра отверг) — запись в журнал с причиной, уведомление
      «Auto-deploy: <name>: build failed», деплоя нет.
   f. `sha_after`. Если `sha_after == sha_before` — конец.
   g. Решение по §3.3–3.4. Не выполнено — запись в журнал с перечислением
      причин (`built config differs from active before refresh — manual
      Deploy expected`, `core status fatal`, `interrupted apply`, `core
      older than required`), оранжевая точка остаётся.
   h. `Deploy(id, nil)`. Успех — запись `auto-deploy: <name>: applied
      <sha12> (<N> node(s) changed in <subscription titles>)`, уведомление
      системы «Auto-deploy: <name> updated», событие шины
      `MachineConfigDeployed{ID}`; панель машин по нему перечитывает
      health, вкладка Remote у активной машины перезагружает список узлов.
      Ошибка — запись и уведомление «Auto-deploy: <name> failed: <err>»;
      демон сам на last-good.
3. Итог обхода в лог: `Auto-deploy[<trigger>]: M machine(s): K deployed,
   S skipped, F failed`.

### 4.3 Журнал и видимость

- Запись машины получает `LastAutoDeploy` (`last_auto_deploy`): `at`
  (RFC3339), `result` (`applied` | `skipped` | `failed` | `build_failed` |
  `unreachable`), `sha` (для applied), `note` (одна строка причины).
  Перезаписывается каждым тиком, где машина рассматривалась.
- Окно health-деталей машины (ⓘ) получает строки «Auto-deploy» (`on`/`off`)
  и «Last auto-deploy» (`<result> · <когда> · <note>`).
- Все записи идут в основной лог лаунчера с префиксом `auto-deploy:`;
  отдельного файла журнала нет.
- Уведомления — `fyne.App.SendNotification` без диалога (авто-деплой
  происходит, когда пользователь не смотрит; модальное окно поверх работы
  недопустимо).

### 4.4 Ручной запуск для проверки

`POST /remote/machines/{id}/auto-deploy/run` — выполнить шаги §4.2.2 для
одной машины сейчас, независимо от флага и свежести подписок (параметр
`?force_refresh=1` — фетчить все подписки машины, иначе только устаревшие).
Ответ: `{result, sha_before, sha_after, deployed, note}`. Нужен для живой
проверки без ожидания часа; в UI кнопки нет.

### 4.5 Что не меняется

- Кнопка Deploy, её подтверждения и предупреждение о старом ядре.
- Конфигуратор машины и его Refresh/Save.
- Локальное автообновление и его настройки.
- Демон и контракт данных.

## 5. Критерии приёмки

1. Home с флагом, Liberty с ротацией: через ≤ 1 ч после смены адресов у
   провайдера роутер работает на новых узлах без действий пользователя;
   в логе есть запись `applied`, в системе — уведомление.
2. Машина с незадеплоенной ручной правкой (sha собранного ≠ active до
   обхода): подписки обновлены, конфиг пересобран, деплоя нет, в журнале
   причина, оранжевая точка горит.
3. Машина недоступна: запись `unreachable`, без ошибок в лицо, следующий
   тик её снова пробует.
4. Флаг выключен (дефолт): к машине нет ни одного сетевого вызова из петли
   автообновления.
5. `subscription_auto_update_disabled = true`: обход машин не идёт.
6. `POST …/auto-deploy/run` на Home воспроизводит сценарий 1 за один вызов.
7. Один новый тест: решение о деплое (чистая функция от `sha_before`,
   `active_sha`, `last_good_sha`, `sha_after`, `core_status`,
   `interrupted_apply`, версии ядра и `core_warn_ack`) — таблица случаев
   §3.3–3.4.

## 6. Ограничения и наблюдения

- Работает, пока лаунчер запущен и машина достижима с него. Для роутера,
  который должен жить автономно неделями, следующий шаг — агент на машине
  (отдельная SPEC, не здесь).
- Деплой = перезапуск ядра на машине с коротким разрывом трафика. Он
  случается только когда подписка реально сменила узлы.
- `persistFetchResultForSource` (Refresh в Конфигураторе) пишет результат по
  **локальному** пути `state.json`, даже когда открыт Конфигуратор машины;
  спасает лишь то, что ID источников у Local и машины различаются. В этой
  задаче не правится; вынести в отдельный баг после подтверждения на
  профиле, скопированном «copy-from».
- У IRA и Parnas Liberty с 25.08 с нулём узлов по старому адресу
  `connliberty.com`; флаг им включать нечего, пока источник не починен.
