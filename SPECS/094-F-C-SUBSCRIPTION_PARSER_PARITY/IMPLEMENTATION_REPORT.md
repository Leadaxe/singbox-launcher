**Дата:** 2026-08-06
**Статус:** Complete. Фазы A, B, C, D реализованы, включая UI-переключатель

## 1. Что сделано

### Фаза A — импорт sing-box JSON

Подписка может отдавать sing-box конфиг вместо списка ссылок: одиночный
outbound, массив outbound'ов, целый конфиг, массив конфигов. До этой работы
любое тело, начинающееся с `{`, давало ноль нод — `decoder.go:68` отвергал его
до парсера.

| Новый файл | Назначение |
|---|---|
| `subscription/body_classify.go` | `BodyKind` + `ClassifySubscriptionBody` — единая точка определения формата |
| `subscription/singbox_import.go` | ядро импорта: нормализация четырёх форм → `ParseNodesFromSingboxConfigs` → `parseSingboxEntry` |
| `subscription/singbox_sanitize.go` | санитайзы над готовой outbound-map |
| `subscription/singbox_groups.go` | `selector`/`urltest` → узел со схемой `group` |

Ключевые решения:

- Модель `ParsedNode` не переписывалась (Р1). Входной outbound уже является
  sing-box JSON, поэтому кладётся в `node.Outbound` после санитайзов, а не
  разбирается на поля и не собирается обратно (Р2).
- Классификатор проверяет `type` раньше `outbounds`: одиночный `selector` несёт
  оба поля и является outbound'ом, а не конфигом.
- **Отклонение от первоначального наброска:** признак Xray-массива взят не из
  `IsXrayJSONArrayBody` (она отвечает лишь «это валидный JSON-массив» и на
  массиве sing-box-outbound'ов тоже вернула бы true), а из
  `xrayElementHasProtocolOutbounds`. Ошибку поймал тест, а не ревью.
- `outbounds` и `endpoints` читаются одним списком (A2).

### A5 — пересмотр модели групп по ходу работы

Изначально в спеке значилось «импортировать группы как локальные outbounds
источника» (`ProxySource.Outbounds`). После уточнения архитектуры решение
**отменено и заменено**: группа стала обычным узлом списка со схемой
`configtypes.SchemeGroup`.

Разграничение, ради которого это сделано:

| | Вкладка Outbounds | Импортированная группа |
|---|---|---|
| Что это | **каналы** лаунчера | **узел** в списке нод |
| Роутинг | правила ссылаются | не ссылается никто |
| Владение | пользователь настраивает состав | приходит из подписки как есть |
| Привилегии | значимая сущность конфигуратора | никаких |

Следствие: расширенный `SourceLoadResult` не понадобился для групп, а хук
`config.LoadSourceWithGroups` был удалён как избыточный. Для sing-box узел
по-прежнему эмитится настоящим selector/urltest — `generateGroupNodeJSON`.

### Фаза B — detour-цепочки

`ParsedJump` заменён на `ParsedNode.Chain []*ParsedNode` (Р3). `Jump` сохранён
как deprecated-поле и синхронизируется с `Chain[0]`, поэтому Xray-путь и
`state.json`, написанный до задачи, работают без миграции данных.

Новый файл `subscription/detour_chain.go`: `analyzeSingboxDetour`,
`findDetourCycleEdges`, `attachChain`.

**Баг, найденный тестом `TestDetourChainCycleKeepsBothNodes`:** порядка «кольца
первыми» из SPEC оказалось недостаточно. В кольце A→B→A обход помечает снятым
ребро A→B, но ребро B→A остаётся, и A попадает в `detourTargets` — исчезает как
узел. Добавлено правило: узел, владеющий снятым ребром, не поглощается как чужой
джамп. Без него кольцо стирало из подписки **обе** ноды.

### Фаза C — Xray-массив

До этой работы Xray-ветка разбирала **только VLESS** и брала **один узел на
элемент**: провайдер, отдающий vmess/trojan/ss/hysteria2, терял их целиком.

- Новый файл `subscription/xray_protocols.go` — конвертеры vmess, trojan,
  shadowsocks, hysteria2 плюс общие `xrayVNextEndpoint` / `xrayServerEndpoint`.
- `parseXrayJSONArrayElementNodes` возвращает список узлов вместо одного.
- Служебные протоколы (`freedom`/`blackhole`/`dns`/`loopback`) узлами не
  становятся; неподдержанный протокол логируется, а не исчезает молча (C1).
- **Именование (C3), обратная совместимость:** единственный узел элемента
  сохраняет чистый тег из `remarks` — ровно как раньше. Различитель добавляется
  только при нескольких узлах. Проверено на реальной фикстуре провайдера
  (`TestParseNodesFromXrayJSONArray_ProviderStyleFixture`).
- `xhttp`/`splithttp` и `httpupgrade` в `xrayTransportFromStreamSettings` (C5).
- dialerProxy-цепочки любой глубины через любой поддерживаемый протокол (C4):
  раньше глубина была ровно 1 и только socks/vless, причём неподдержанный хоп
  выбрасывал **весь узел**.

### Фаза D — идентичность узла

**Решение по итогам обсуждения: один механизм вместо двух.** Отдельного
строкового ключа `scheme|server|port|credential` нет — хеш обслуживает и
дедупликацию, и привязку пользовательского выбора.

`config/node_hash.go` — `NodeIdentityHash`: SHA-256 от эмитированного
outbound-JSON минус ровно два контекстных поля (`tag`, `detour`), ключи
рекурсивно отсортированы. Считается **от map, а не от строки**:
`GenerateNodeJSON` собирает JSON вручную, и порядок полей не является
контрактом.

**Отличие от LxBox зафиксировано сознательно.** Там дедуп идёт по ключу без
транспорта и TLS, и один сервер с двумя SNI схлопывается. Здесь — нет: разные
SNI это разные способы пройти фильтрацию, и объединение потеряло бы рабочий
запасной вариант.

- **Дедуп (D3)** — внутри источника, до простановки тегов (иначе `MakeTagUnique`
  успел бы выдать дублю тег `…-2`). Между источниками не применяется.
- **Выключение ноды (D4)** — `ProxySource.DisabledNodes map[string]int64`, ключ
  хеш, значение время подтверждения. GC по TTL `clamp(3 × интервал, 24h, 30d)`
  вызывается в `refreshSubscriptionsMetaAndCache` — единственном месте, где
  сетевое обновление заведомо успешно; на прогоне из кэша тело может быть
  неполным, и отметки исчезли бы для живых нод.
- **UI-переключатель** — чекбокс у каждой ноды на вкладке Preview окна
  редактирования источника (`source_edit_window.go`). Отметка идёт по цепочке
  `scratch ProxySource` → `applyProxyEditToSource` → `state.Source` →
  `ToProxySourceV4` → парсер. Узел без вычислимого хеша показывается
  включённым и заблокированным: отметку не к чему привязать, и она переехала
  бы на соседа при следующем обновлении.
- Хеш живёт в `config` (там эмиттер), парсер — в `subscription`; зависимость
  подставляется через `subscription.NodeIdentityHashFunc`, как `LookupCachedBody`.
  Без хука парсер работает, просто не дедуплицирует.

### Попутный фикс — пробел в userinfo

Не входил в SPEC. Обнаружен при прогоне live-теста: одна нода из 481 в реальной
публичной подписке не парсилась — промо-логин
`Telegramjoin:TurboConfigs @176.65.151.209` с сырым пробелом, `net/url`
отвергает такой URI целиком.

Проверено, что баг **существовал до этой работы**: чистая worktree на коммите
`8a6895d` даёт идентичную ошибку. Починен здесь же —
`percentEncodeUserinfoSpaces`, по образцу `percentEncodeWGUserinfoSlashes`.

## 3. Ограничения

**Ограничение фазы A, зафиксированное сознательно:** импортированная группа не
редактируется пользователем и пересобирается из свежего конфига при каждом
обновлении подписки. Прямое следствие того, что она узел подписки, а не канал.
