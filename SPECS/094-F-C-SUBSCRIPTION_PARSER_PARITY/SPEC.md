# SPEC 094 — Паритет парсера подписок с LxBox

**Тип:** Feature · **Статус:** Complete · **Платформа:** все

Зонтичная задача: перенос в лаунчер класса возможностей парсера, накопленного в
проекте LxBox (Dart/Flutter, `app/lib/services/parser/`). Четыре фазы A–D,
каждая поставляется самостоятельно.

---

## 1. Проблема

Парсер лаунчера разбирает подписки построчно (URI) и один JSON-формат —
Xray-массив, причём в сильно урезанном виде. Всё, что приходит пользователю в
виде готового sing-box конфига, не импортируется вовсе.

Конкретные симптомы, воспроизводимые сегодня:

1. **Пользователь вставляет sing-box конфиг (свой или чужой) — не работает.**
   `decoder.go:68` на теле, начинающемся с `{`, возвращает ошибку
   «Content is JSON configuration, not a subscription list». Ни одиночный
   outbound, ни массив outbound'ов, ни целый конфиг не дают ни одной ноды.
2. **Xray-подписка теряет большинство узлов.** `parseXrayJSONArrayElement`
   (`core/config/subscription/xray_json_array.go:83-86`) обрабатывает
   **только `protocol == "vless"`**, и берёт **один узел на элемент массива**
   (`pickMainXrayVLESS`, `:172`). Провайдер, отдающий в одном элементе
   vmess/trojan/ss или несколько vless — теряет всё, кроме одного.
   В коде на `:58` стоит явная пометка «sing-box array is follow-up».
3. **Цепочки прокси глубиной больше одной.** `ParsedNode.Jump` —
   одиночный указатель (`configtypes/types.go:204,232`), поэтому A→B→C
   непредставимо. Конвертер первого хопа (`xrayBuildJumpFromOutbound`,
   `xray_outbound_convert.go:314`) знает только `socks` и `vless`.
4. **Одинаковые серверы дублируются.** Дедупликации по идентичности сервера нет;
   `MakeTagUnique` (`source_loader.go:49`) лишь переименовывает коллизии тегов в
   `tag-2`, `tag-3`. Один сервер, перечисленный в подписке трижды с разными
   ремарками, даёт три ноды.
5. **Отдельную ноду нельзя выключить.** `Disabled` есть только у источника
   (`configtypes.ProxySource.Disabled`). Идентичность ноды — мутабельный `Tag`,
   который меняется от порядка в подписке, `tag_prefix` и `{$num}`, поэтому
   привязать к нему пользовательский выбор нельзя.

### Что уже есть и переносить не нужно

Санитайзы в лаунчере во многом на уровне LxBox: uTLS allowlist
(`node_parser_transport.go:84`), reality pbk/short_id (`:477`, `:448`),
ws early data `?ed=N` (`:380`), XHTTP normalize (`:236`), AWG MTU clamp
(`node_parser_wireguard.go:103`), vision+transport (`outbound_generator.go:329`),
packet_encoding allowlist (`node_parser_core.go:564`). Фазы A–D их
переиспользуют, а не дублируют.

Base64-тело подписки декодируется в `fetcher.go:293` до попадания в
`LoadNodesFromSource` — это не пробел.

Clash YAML в LxBox — заглушка (`parse_all.dart:152` возвращает пустой список),
в задачу не входит.

## 2. Цели

| Фаза | Цель |
|------|------|
| **A** | Импорт sing-box JSON: одиночный outbound, массив outbound'ов, целый конфиг, массив конфигов, секция `endpoints`, группы selector/urltest |
| **B** | Detour-цепочки произвольной глубины (лимит 8) с обнаружением колец |
| **C** | Xray-массив: все протоколы, все узлы элемента, dialerProxy-цепочки, сохранение порядка |
| **D** | Идентичность ноды: стабильный хеш, дедупликация, выключение отдельной ноды |

### Не-цели

- Переписывание `ParsedNode` в sealed-иерархию по образцу `NodeSpec`. Даёт
  типобезопасность, но ни одной пользовательской функции; ломает 35 тест-файлов.
- Clash YAML.
- Auto-узлы из подписки (`AutoSelectSpec`). Требует проектирования новой границы
  владения группой при refresh; выносится в отдельную задачу после D.
- Import rules (условия/Replace с backreference). Отдельная задача **после D** —
  правила обязаны применяться *до* вычисления хеша ноды, иначе патч
  меняет идентичность (в LxBox порядок именно такой:
  `subscription_controller.dart:248`).

## 3. Требования

### 3.1 Фаза A — импорт sing-box JSON

**A1. Распознавание формата.** Тело подписки классифицируется до разбора.
Порядок проверок фиксирован и значим:

| Условие | Формат |
|---|---|
| `[` + валидный JSON + элементы содержат Xray `protocol` | Xray-массив (существующая ветка) |
| `[` + элементы содержат `type` (string) | массив sing-box outbound'ов |
| `[` + элементы содержат `outbounds` | массив sing-box конфигов |
| `{` + есть `type` (string) | одиночный sing-box outbound |
| `{` + есть `outbounds` или `endpoints` | целый sing-box конфиг |
| иначе | построчный URI-разбор (существующая ветка) |

Проверка `type` идёт **раньше** проверки `outbounds`: одиночный `selector`
несёт оба поля, и это outbound, а не конфиг.

Все четыре sing-box-формы нормализуются к «массиву конфигов» и разбираются
одним ядром — отдельных путей для каждой формы быть не должно.

**A2. Источник узлов.** Разбираются `outbounds` и `endpoints` одним списком:
wireguard/masque в sing-box ≥ 1.11 живут в `endpoints`, правила для них те же.

**A3. Служебные типы.** `direct`, `block`, `dns` узлами не становятся.

**A4. Игнорируемые секции.** `route`, `dns`, `inbounds`, `experimental`, `log`
не читаются. Если они присутствовали во входе — пользователю в превью
показывается, что именно проигнорировано.

**A5. Группы — узлы, а не каналы.**

`selector` и `urltest` из входного конфига становятся **обычными узлами в
списке нод подписки** — `ParsedNode` со схемой `SchemeGroup` (`"group"`).

Это пересмотр первоначального решения. Ранее в спеке значилось «импортировать
как локальные outbounds источника» (`ProxySource.Outbounds`); от этого отказано
после уточнения архитектуры.

**Разграничение двух сущностей** — суть требования:

| | Вкладка Outbounds (`ParserConfig.Outbounds`, `ProxySource.Outbounds`) | Импортированная группа (`SchemeGroup`) |
|---|---|---|
| Что это | **каналы** лаунчера | **узел** в списке нод |
| Роутинг | правила ссылаются, трафик заворачивается | не ссылается никто |
| Кто владеет | пользователь настраивает состав | приходит из подписки как есть |
| Где виден | вкладка Outbounds | список нод, наравне с обычными |
| Привилегии | значимая сущность конфигуратора | никаких |

Импортированная группа **не попадает** во вкладку Outbounds и не участвует в
механике `Ref`/`Updates`/`addOutbounds` (SPEC 057/058). Для пользователя это
просто ещё одна строка среди нод; для sing-box — настоящий `selector`/`urltest`
внутри массива `outbounds`.

Требования:

- состав группы (`outbounds[]`) резолвится в итоговые теги импортированных
  узлов — после префикса/маски/уникализации, а не по сырым тегам провайдера;
- член, который не удалось разрешить (вложенная группа, служебный тип, битая
  ссылка, отфильтрованный skip-правилом узел), отбрасывается; счётчик потерь
  логируется;
- **группа с пустым составом не создаётся** — пустой `urltest` роняет старт
  ядра. Проверка дублируется на эмиссии как последний рубеж;
- параметры группы (`url`, `interval`, `tolerance`, `idle_timeout`,
  `interrupt_exist_connections`) переносятся по закрытому списку: незнакомое
  поле ядро отвергает как unknown field;
- `default` переносится, только если он входит в итоговый состав;
- при refresh подписки группа пересобирается из свежего конфига; пользовательских
  правок у неё нет по определению — она не редактируемая сущность.

**Следствие для архитектуры парсера.** `LoadNodesFromSource` возвращает группы
в общем списке `[]*ParsedNode`, а не отдельным каналом. Это упрощает контракт:
расширенный `SourceLoadResult` нужен только для `IgnoredSections`, а хук
`config.LoadSourceWithGroups` не требуется вовсе.

**A5.1. Сохранность существующих контрактов.**

Новая схема узла проходит через весь конвейер, поэтому каждое место, которое
делает `switch`/`if` по `node.Scheme` либо пишет узел на диск, обязано вести
себя предсказуемо. Требования, подлежащие проверке тестами:

1. **Шаблон не ломается.** `wizard_template.json` и его маркеры
   (`@ParserSTART`/`@ParserEND`, `@ParserSTART_E`/`@ParserEND_E`) работают как
   прежде; `RequiredTemplateRef` не меняется. Узел-группа попадает в секцию
   `outbounds`, **не** в `endpoints`.
2. **Каналы не затронуты.** `ParserConfig.Outbounds` и `ProxySource.Outbounds`
   после импорта конфига содержат ровно то же, что и до него. Три прохода
   (`buildOutboundsInfo` → `computeOutboundValidity` → `generateSelectorJSONs`)
   считают узел-группу обычной нодой пула, а не селектором.
3. **Круговая сохранность (round-trip).** `state.json` → чтение → генерация →
   `state.json` не теряет и не искажает узел-группу: состав, тип и параметры
   переживают сериализацию.
4. **Дедуп и хеш.** Узел-группа участвует в идентичности наравне с прочими:
   хеш считается от её эмитированного JSON минус `tag`/`detour`.
5. **Скрытые допущения о `server`.** Узел-группа не имеет `server`/`server_port`.
   Ни один существующий потребитель не должен на этом падать: skip-фильтры,
   превью, share-URI, ping/тесты, экспорт.
6. **`sing-box check`** принимает итоговый `config.json` с узлом-группой.

**A5.2. Контракт данных на проверку.** По итогам реализации предъявляются
фактические артефакты прогона, а не их описание: входной конфиг подписки и
полученный из него `config.json` целиком.

**A6. Гранулярность ошибок.** Битый outbound (неверный тип поля, `settings: []`,
`streamSettings: "none"`) гасит **только этот узел**. Соседние узлы и остальная
подписка живут. Тип неподдержанного протокола логируется.

**A7. Порядок.** Узлы отдаются в порядке их появления в конфиге. Группы — после
узлов.

### 3.2 Фаза B — detour-цепочки

**B1. Модель.** `ParsedNode.Jump *ParsedJump` заменяется на представление,
допускающее цепочку произвольной длины. Требуется миграция `state.json`
(поле сериализуется в кэш превью), совместимая со старой формой.

**B2. Глубина.** Лимит 8 хопов. Превышение — цепочка обрывается на лимите,
узел остаётся рабочим, факт логируется.

**B3. Кольца.** Обнаружение колец **до** отбора узлов-кандидатов: узел, чьё
исходящее detour-ребро замыкает кольцо, обязан остаться самостоятельным узлом,
а не исчезнуть как «цель чужого detour». Замыкающее ребро рвётся, узел живёт.

**B4. Цели detour исключаются из самостоятельных узлов** — кроме случая B3.

**B5. Особые цели.** Detour на служебный тип (`direct`) — цепочка просто
заканчивается, без предупреждения. Detour на группу — цепочка не строится
(развёрнутая группа в detour-списке дала бы её без членов), факт логируется.
Висячая ссылка — цепочка обрывается, узел живёт.

**B6. Существующие санитайзы сохраняются.** `sanitizeNodeDetours`
(`outbound_generator.go:908`) уже режет self-reference и циклы на этапе
генерации — после B он остаётся как второй рубеж, а не заменяется.

### 3.3 Фаза C — Xray-массив

**C1. Протоколы.** Помимо `vless` — `vmess`, `trojan`, `shadowsocks`,
`hysteria2`. Неподдержанный `protocol` не исчезает молча: тип логируется.

**C2. Все узлы элемента.** Из одного элемента массива берутся все
непослужебные outbound'ы, а не один. Служебные Xray-протоколы (`freedom`,
`blackhole`, `dns`, `loopback`) узлами не становятся.

**C3. Именование.** При нескольких узлах в элементе тег строится из `remarks`
плюс различитель (тег outbound'а либо порядковый номер). Единственный узел в
элементе сохраняет чистый `remarks` — обратная совместимость с текущими тегами.

**C4. dialerProxy.** Цепочки через `streamSettings.sockopt.dialerProxy`
поддерживают глубину из B и протоколы из C1, а не только socks/vless.

**C5. Транспорты.** `xhttp` и `httpupgrade` в Xray-ветке — сейчас
`xrayTransportFromStreamSettings` (`xray_outbound_convert.go:222`) знает только
`ws`/`grpc`/`http`/`h2`, тогда как URI-ветка их разбирает.

**C6. Порядок.** Порядок узлов в итоге соответствует порядку в подписке.
Если для выбора «кто даёт имя серверу» потребуется сортировка — она не должна
менять порядок выдачи (в LxBox для этого сделано два прохода: черновой
сортированный ради имён, боевой в порядке файла).

### 3.4 Фаза D — идентичность узла

**D1. Единственный механизм идентичности — хеш.** Отдельного строкового ключа
`scheme|server|port|credential` не вводится. Решение принято при постановке:
два механизма (грубый ключ для дедупа + строгий хеш для персистентности)
разошлись бы в поведении, и пользователю пришлось бы держать в голове, какой
из них где действует.

Отличие от LxBox зафиксировано сознательно: там дедуп идёт по ключу
`protocol|server|port|credential` без транспорта и TLS, и один сервер с двумя
SNI схлопывается в один узел. Здесь — не схлопывается: разные SNI это разные
конфигурации подключения, и объединение потеряло бы рабочий вариант.

**D2. Стабильный хеш.** SHA-256 от эмитированного outbound-JSON узла с
исключением ровно **двух контекстных** полей и с детерминированным
(рекурсивно отсортированным) порядком ключей.

Исключаются:

| Поле | Почему |
|---|---|
| `tag` | ремарка провайдера плюс наши `tag_prefix`/`tag_mask`/`-2` от уникализации — отображение, не свойство сервера |
| `detour` | тег соседнего узла: контекст, а не сам узел; иначе смена джампа отвязала бы пользовательский выбор |

Всё остальное в хеш **входит**, в том числе строковые поля подключения:
`server`, `server_port`, учётные данные, `tls.server_name` (SNI), `alpn`,
`utls.fingerprint`, `reality.*`, `transport` целиком (тип, `path`,
`headers.Host`, `service_name`), `flow`, `packet_encoding`, `obfs`.

`Label` и `Comment` узла исключать не требуется: `GenerateNodeJSON` не пишет их
в объект outbound'а — только в `//`-комментарий над ним, а хеш считается от
разобранной map, а не от текста.

Хеш считается **от map, а не от строки**: `GenerateNodeJSON` собирает JSON
вручную, и порядок полей в строке не является контрактом. Строковый хеш поехал
бы при первой же правке эмиттера.

Свойства:
- переименование узла провайдером хеш **не меняет**;
- `tag_prefix` / `tag_mask` источника хеш **не меняют**;
- смена порта, uuid, пароля, SNI, транспорта, reality — **меняет**.

**D3. Дедупликация.** Узлы с совпадающим хешом D2 схлопываются в один в рамках
одного источника; выживает первый по порядку. Между источниками дедуп не
применяется — одна и та же нода из двух подписок остаётся двумя записями, это
осознанный выбор пользователя подписаться дважды.

**D4. Выключение отдельной ноды.** Пользователь может выключить конкретный узел;
выбор привязан к хешу D2 и переживает обновление подписки, перезапуск лаунчера и
переименование узла провайдером. Отметки для узлов, исчезнувших из подписки,
подлежат сборке мусора по TTL — иначе список отметок растёт неограниченно.

## 4. Критерии приёмки

### Фаза A
1. Тело `{"type":"vless",...}` даёт одну ноду.
2. Тело `[{"type":"vless",...},{"type":"trojan",...}]` даёт две ноды.
3. Целый конфиг с `outbounds` + `route` + `dns` + `inbounds` даёт только ноды из
   `outbounds`; факт игнора трёх секций виден в превью.
4. Конфиг с `endpoints` (wireguard) даёт ноду, попадающую в секцию `endpoints`
   итогового config.json.
5. Конфиг с `urltest`, ссылающимся на три узла, даёт **четыре ноды**: три
   обычные плюс одну со схемой `group` и тремя членами. Во вкладке Outbounds
   (`ParserConfig.Outbounds` / `ProxySource.Outbounds`) не появляется ничего.
6. `urltest` со ссылками только на несуществующие теги не создаёт узел-группу.
7. Конфиг, где один outbound из пяти битый, даёт четыре ноды.
8. `sing-box check` на итоговом config.json проходит для каждого случая выше.

### Фаза B
9. Конфиг с цепочкой A→B→C даёт рабочую ноду с двумя хопами.
10. Цепочка из 12 хопов обрывается на 8-м; нода работает.
11. Конфиг с кольцом A→B→A даёт **обе** ноды; ни одна не теряется; `sing-box check` проходит.
12. Detour на несуществующий тег — нода живёт, дозванивается напрямую.
13. `state.json` со старым скалярным `Jump` читается без потери цепочки.

### Фаза C
14. Xray-элемент с vmess даёт ноду (сегодня — ноль).
15. Xray-элемент с тремя vless даёт три ноды (сегодня — одну).
16. Xray-элемент с `xhttp` в `streamSettings` даёт ноду с транспортом `xhttp`.
17. Порядок нод в итоге совпадает с порядком в подписке; узел «Авто | Лучший
    сервер», стоящий в подписке первым, остаётся первым.
18. Регрессия: существующая фикстура `testdata/xray_provider_anon.json`
    продолжает давать не меньше нод, чем сегодня, с теми же тегами.

### Фаза D
19. Подписка, где один сервер повторён трижды с разными ремарками, даёт одну ноду.
20. Хеш ноды не меняется при переименовании узла провайдером и при смене
    `tag_prefix`; меняется при смене порта.
21. Выключенный узел остаётся выключенным после обновления подписки и
    перезапуска лаунчера.
22. Отметка об узле, отсутствующем в подписке дольше TTL, удаляется.
