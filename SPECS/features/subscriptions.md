# Подписки: разбор тела

Блок описывает путь от байтов, полученных от провайдера, до состава
источника: как опознаётся формат тела, какие записи из него рождаются и
что становится метаданными подписки.

Что такое источник, как живёт его состав, теги и идентичность, merge при
обновлении, NodeLink и свобода узлов — см. features/sources.md. Схема
хранения и материализация — см. features/state.md. Что именно мы умеем
из каждого протокола (ключи URI, поля JSON, деградации) — нормативно
описано в `contract/registry/protocols/*.json`, по файлу на протокол; здесь
эти списки не дублируются.

## Что этот блок обещает пользователю

- Провайдер прислал формат, который мы понимаем, — узлы появятся, каким бы
  из четырёх диалектов он ни пользовался.
- Строка, которую написал человек для человека («ПОДХОДЯТ ДЛЯ ИГР»), не
  выглядит поломкой: это комментарий, а не ошибка.
- Запись, которую мы не поняли, не пропадает молча: она стоит на своём
  месте с причиной и исходником.
- Служебная шапка подписки (имя профиля, интервал обновления, остаток
  трафика) читается и показывается там, где ей место, а не засоряет список
  серверов.
- Одна битая запись не обнуляет подписку: остальные разбираются.

## Классификация тела

Формат опознаётся по первым байтам и по форме первого пригодного элемента,
а не по заголовку `Content-Type`: провайдеры отдают JSON под `text/plain`
и наоборот.

| Тело начинается с | Формат | Запись состава |
|---|---|---|
| `vpn://` | Amnezia-профиль | контейнер WG/AWG |
| `[` + валидный JSON | массив: sing-box outbound'ов, sing-box конфигов или Xray | элемент массива |
| `[` + невалидный JSON | INI wg-quick (`[Interface]`) | блок `[Interface]` |
| `{` | одиночный sing-box outbound или конфиг | элемент `outbounds[]` |
| прочее | URI-список (по строке на запись) | строка |

Внутри JSON-массива формат уточняется по первому элементу, о котором вообще
можно судить: поле `type` — sing-box outbound; `outbounds[]` с полем
`protocol` внутри — Xray; `outbounds[]`/`endpoints[]` без него — sing-box
конфиг. Порядок проверок именно такой: одиночный selector несёт и `type`, и
`outbounds`, и спутать его с конфигом нельзя.

Тело, которое не опознано ни как JSON, ни как INI, разбирается URI-списком.
Это не отказ, а последний рубеж: строка без известной схемы там станет
записью состава со своей диагностикой, и пользователь увидит, что именно
прислал провайдер.

## Куда попадает запись тела

Ветка «комментарий» существует только для URI-списка — в остальных
форматах она не достигается (см. §Признак комментария).

```
                    ┌──────────────────────┐
                    │  запись тела подписки │
                    └───────────┬──────────┘
                                │
                    ┌───────────▼──────────┐
                    │  это комментарий?    │
                    │  (признак формата,   │
                    │   см. таблицу ниже)  │
                    └─────┬──────────┬─────┘
                     нет  │          │  да
              ┌───────────▼──┐   ┌───▼────────────────────┐
              │ разбор       │   │ ведущая шапка тела     │
              │ как узла     │   │ и это известный ключ?  │
              └───┬──────┬───┘   └────┬──────────────┬────┘
             ok   │      │ err     да │              │ нет
        ┌─────────▼─┐ ┌──▼────────┐ ┌─▼───────────┐ ┌▼──────────────┐
        │  kind=    │ │  kind=    │ │ МЕТАДАННЫЕ  │ │  kind=        │
        │  server   │ │unsupported│ │ подписки    │ │  comment      │
        └───────────┘ └───────────┘ └──────┬──────┘ └───────────────┘
                                           │
                                  ┌────────▼────────┐
                                  │ поле источника  │
                                  │ (имя, интервал, │
                                  │  трафик, ссылки)│
                                  └─────────────────┘
                                  из состава ИСЧЕЗАЕТ
```

## Три вида записи состава

| kind | в Preview | чекбокс | в конфиг | значок |
|---|---|---|---|---|
| `server` | да | да | да | — |
| `comment` | да | нет | нет | — |
| `unsupported` | да | нет | нет | ⚠ + причина |

`comment` и `unsupported` оба минуют конфиг, но это разные вещи: первый —
рубрикатор, написанный человеком, второй — запись, которую мы не смогли
разобрать. Помечать комментарий предупреждением неверно: чинить там нечего.

Общее у обоих (правила целиком — в features/sources.md, §Unsupported):
`enabled` всегда `false` и включение запрещено; эмиссия пропускает их до
тег-машины, поэтому они не двигают финальные теги соседей; целью NodeLink
быть не могут; в экспорт, бэкап и выгрузку JSON не попадают; достоверность
ответа считается только по собравшимся узлам.

### comment

Строка-рубрикатор в теле: «Лучшие сервера», «ПОДХОДЯТ ДЛЯ ИГР», «БЕЛЫЕ
СПИСКИ В САМОМ НИЗУ», `# Количество: 150`. Стоит там, где её прислал
провайдер: она и есть заголовок следующей за ней группы узлов.

Поля `reason` у неё **нет** — она ничем не отбракована. Есть `origin.raw`
(запись как пришла) и тег, равный её тексту.

Идентичность при merge **не отслеживается**: при обновлении подписки
комментарии удаляются и создаются заново. Текст комментария — это и есть
всё, что в нём есть; считать «тот же самый комментарий с новым текстом»
не от чего, а позиционный ключ поехал бы от любой вставки выше по телу.
Пользовательских пометок на комментарии нет (включить нельзя, detour
нельзя), поэтому терять при пересоздании нечего.

### unsupported

Запись, которая заявила себя узлом, но не разобралась: `vless://` с пустым
uuid, неизвестная схема, элемент JSON без endpoint'а, протокол, которого
лаунчер не умеет. Причина у неё техническая — там нужно чинить, а не читать
«это комментарий».

`reason` хранится английским ключом, перевод применяется на показе. Полная
модель — features/sources.md, §Unsupported.

## Признак комментария — форматно-зависимый

Единого признака нет и быть не может: в каждом формате комментарий
устроен по-своему.

| Формат | Что считается комментарием | Становится записью состава |
|---|---|---|
| URI-список | строка **без** разделителя схемы `://` | да, `kind=comment` |
| INI (wg-quick) | строка на `#` или `;` | нет — живёт внутри блока |
| JSON (sing-box, Xray) | своей формы комментария нет | нет — всё неразобранное `unsupported` |
| `vpn://` | комментариев нет в формате | не возникает |

**URI-список.** Признак намеренно узкий: отсутствие `://`. Всё, что схему
заявило, но не разобралось, — сломанный узел, а не комментарий. Ведущая
решётка `#` не требуется: провайдеры пишут рубрикаторы и без неё
(«— Лучшие сервера»), и требование решётки оставило бы половину из них
помеченными как ошибки.

**INI.** Запись состава здесь — блок `[Interface]` целиком, а не строка.
Происхождением узла становится **этот блок байт в байт**
(`origin.kind = wg_ini`), а не канонический `wireguard://`-URI, в который
он конвертируется для разбора: ссылка — наш вывод, а в блоке живут
комментарии провайдера, и без них узел нельзя пересобрать из исходника
(SPEC 119). Многосекционный conf даёт каждому узлу свой блок, а не весь
файл.

Комментарии лежат *внутри* блока и относятся к нему: метка сервера
(`# US-FREE#109`), выключенная настройка (`# Endpoint = [2a02:...]:51820`),
инструкция человеку. Они не соседи узла, а его часть, и отдельными записями
состава не становятся. Разбор блока их пропускает — включая строки вида
`# Key = Value`, которые формально выглядят как поле: закомментированная
настройка не должна становиться настройкой.

Именно поэтому исходник блока хранится целиком: закомментированная строка —
не мусор, а выключенная настройка, которую пользователь может включить.
Правка исходника и пересборка узла из него — Regen, см. features/sources.md
§Происхождение.

**JSON.** Своей формы комментария формат не имеет, и `kind=comment` в
JSON-теле не возникает: всё, что не разобралось, — `unsupported`.

Провайдеры (заметно чаще в Xray-подписках) всё же вставляют
элементы-псевдокомментарии — запись без endpoint'а, со служебным именем
вместо сервера, иногда с пустым `protocol`, — рассчитывая, что клиент
покажет её как заголовок группы. Такие элементы остаются `unsupported` с
технической причиной. Признака, отличающего их от элемента, который
провайдер *хотел* сделать узлом и испортил, у нас нет: и то и другое
выглядит как запись без endpoint'а. Ошибиться в эту сторону дешевле —
пользователь увидит запись с причиной и решит сам, а не получит молча
проглоченный сломанный узел под видом рубрикатора. Если формат подобных
записей устоится и станет распознаваемым, решение можно будет пересмотреть.

## Метаданные подписки

Провайдер сообщает служебные сведения о самой подписке двумя каналами:
HTTP-заголовками и теми же ключами в теле в виде `# ключ: значение`.
Второй канал нужен статическому хостингу (Gist, GitHub Pages), который
своих заголовков поставить не может.

| Ключ | Поле | Примечание |
|---|---|---|
| `subscription-userinfo` | остаток трафика, лимит, срок | |
| `profile-title` | имя профиля | принимает `base64:` и голый base64 |
| `profile-update-interval` | интервал обновления, часы | только положительное целое |
| `support-url` | ссылка на поддержку | |
| `profile-web-page-url` | страница профиля | |
| `content-disposition` | имя файла | берётся `filename` |
| `announce` | сообщение провайдера | принимает `base64:` |
| `announce-url` | ссылка при сообщении | |

Только по HTTP, в теле сознательно не зеркалятся: `x-hwid-active`,
`x-hwid-not-supported`, `x-hwid-max-devices-reached`, `x-hwid-limit`. Они
описывают серверный подсчёт устройств, которого у статического хостинга нет.

**Приоритет.** HTTP-заголовок выигрывает; инлайновый ключ — запасной
источник для полей, которые заголовками не пришли. История fetch'а
(время, счётчик ошибок) метаданными не является и из тела не читается
никогда.

**Строка, отдавшая значение, из состава исчезает.** Она не комментарий и не
unsupported: её содержимое уже забрано в поле источника и показано там, где
ему место — в шапке источника, в Overview. Оставлять её ещё и записью
состава значило бы показать одно и то же дважды и завысить счётчик.

**Только ведущая шапка.** Ключи читаются из непрерывного блока
комментариев в начале тела — до первой строки, которая комментарием не
является. Дальше по телу `# ключ: значение` остаётся обычным комментарием.
Иначе рубрикатор в середине списка мог бы случайно совпасть с известным
ключом, молча уехать в поле источника и оставить дыру в составе.

Из INI и JSON метаданные тела не читаются: там нет ведущей шапки
комментариев как формы.

**Диагностический announce — это другое.** `announce` / `announce-url` —
сообщение о самой подписке (лимит устройств, истёкший триал, региональная
блокировка), а не запись её тела. Его дом — Overview, где живёт вся
диагностика fetch'а, плюс причина «источник не дал узлов» в отчёте сборки.
Склеенной строки «provider says: …» над списком Preview не существует: она
смешивала разные записи тела в один абзац, теряла их порядок и место в
составе и не давала ни скопировать исходник, ни понять, к какой группе
узлов относится рубрикатор.

## Счётчик состава

Строка под шапкой источника отвечает на два вопроса: сколько серверов
получено и что сломалось. Комментарии в неё не входят — они не серверы и
не поломки, и в списке видны сами.

```
147 server(s) from 1 source(s)                    ← комментарии есть, но не в счёте
38 server(s) from 1 source(s) + 4 unsupported     ← четыре записи не разобрались
```

## Диалекты, которые мы понимаем

Полные списки полей — в `contract/registry/protocols/*.json`. Здесь только
то, что касается опознания формата.

**sing-box.** Родной формат: `type` определяет протокол. Импортируется как
одиночный outbound, массив outbound'ов, конфиг целиком или массив конфигов;
секции route/dns/inbounds не читаются и перечисляются пользователю как
пропущенные.

**Xray.** Протокол определяется полем `protocol`, endpoint — формой
`settings.vnext[]` (vless, vmess) или `settings.servers[]` (trojan,
shadowsocks). Служебные протоколы (`freedom`, `blackhole`, `dns`,
`loopback`) узлами не считаются. `dialerProxy` разбирается в цепочку.

Отдельный случай — **диалект `hysteria`**: форки Xray отдают под этим
именем оба протокола семейства, различая их полем `version` (в
`streamSettings.hysteriaSettings` либо в `settings`). `version: 2` — это
Hysteria 2, `version: 1` или отсутствие поля — Hysteria v1. Адрес там лежит
плоско в `settings`, а не в `settings.servers[]`. Подробности —
`contract/registry/protocols/hysteria.json`.

**INI wg-quick.** Один файл может нести несколько секций `[Interface]` —
так провайдеры отдают набор локаций. Битый блок пропускается, остальные
разбираются; число пропущенных сообщается пользователю.

**`vpn://`** — профиль Amnezia: контейнеры WG/AWG.

## Устойчивость разбора

- Одна битая запись не обнуляет подписку: она становится `unsupported`,
  остальные разбираются.
- Тело, из которого не родилось ни одного узла, недостоверно — сколько бы
  отбракованных записей в нём ни было. Так выглядит HTML-страница,
  присланная вместо подписки; сохранённый список узлов при этом не
  трогается.
- Записи без пофрагментного исходника узлом-заглушкой не становятся:
  показывать было бы нечего, они остаются деградациями с предупреждением.
- Разбор ограничен капом записей; упёршийся в кап результат помечается
  обрезанным, и «исчезнувшие» узлы при merge не удаляются.
