# DELTAS — разрешённые изменения поведения кампании SPEC 133

Единый список. **Любое расхождение с фикстурами identity вне этого файла =
красное** (решение владельца 19.09.2026, вопрос 2 = Б).

Правила работы со списком:

1. фикстуры identity снимаются **старым путём** до первой дельты (W0.5) —
   база сравнения от решения не зависит;
2. `expected` корпуса меняется **отдельным коммитом на каждую дельту**, и
   только в полях, которые дельта называет;
3. дельта без кейса корпуса не принимается: «было→стало» обязано быть
   проверяемым;
4. статус **кандидат** = в код не едет, ждёт решения владельца.

Стороны: **Л** — лаунчер (Go), **X** — LxBox (Dart).

### D133-6 · фолбэк тега по ТИПУ ТЕЛА

**Решение владельца 19.09.2026 (вопрос 3 = Б).** Самая широкая дельта:
меняет **identity живых узлов**.

| | |
|---|---|
| Кейсы | 52 кейса корпуса, 12 написаний схем из 26 |
| Поле | `tag` (и `label`, когда метка была равна тегу) |
| Было Л | `generateDefaultTag(scheme, …)` по **написанию схемы** (`node_parser_core.go:640-642`) |
| Стало Л | `label_fallback.scheme_source: "singbox_type"` |
| Было X | уже по типу тела |
| Почему старое — ошибка | одна и та же нода получала разные теги в зависимости от написания ссылки |

Что меняется:

| Написание | → тег | кейсов |
|---|---|---|
| `naive+https` / `naive+quic` / `naive` | `naive-…` | 17 |
| `socks5` / `socks4` / `socks4a` | `socks-…` | 10 |
| `proxy-http` / `proxy-https` / `proxy+http` / `proxy+https` | `http-…` | 10 |
| `ss` | `shadowsocks-…` | 9 |
| `awg` | `wireguard-…` | 4 |
| `hy2` / `hy` | `hysteria2-…` / `hysteria-…` | 3 |

**Исключение — Xray-вход.** У X historical `tagScheme`. У Л написание уже
расходится с типом тела: `xrayTagOrDefault(ob, "ss")` при
`type: "shadowsocks"` (`xray_protocols.go:295` против `:303-304`). Правило
для `mappers.xray` фиксируется **отдельной записью реестра**, а не выводится
из общего.

**Новый риск, названный явно:** `socks4://`, `socks4a://` и `socks5://` на
одном `host:port` дают один тег `socks-host-port`. Коллизию разрешит
`MakeTagUnique` суффиксом `-2`/`-3`, но порядок суффиксов зависит от порядка
узлов в подписке — **нестабилен между обновлениями**.

**Миграция состояния — вопрос §14.5 SPEC.md, не решён.** Без неё рвутся
`detour`, цепочки, состав групп, цели правил, `Source.Skip`-фильтры;
узлы пересоздаются, теряя `Enabled` и вердикт ядра.

## Кандидаты — в код НЕ едут, ждут владельца

### D133-C1 · политика «+» в query — **ждёт прогона корпуса**

| | |
|---|---|
| Поле | любое значение query с `+` |
| Было Л | `url.ParseQuery` превращает `+` в пробел **везде**, кроме четырёх заплат: WG `publickey`/`presharedkey`/`privatekey`, AWG3 `header_protection_key`, masque `publickey` (`PRIMITIVES.md` §2) |
| Стало Л | единый декодер без замены `+` |
| Было X | `Uri.queryParameters` заменяет **везде**, заплата одна (`headerprotectionkey`) |
| Стало X | то же |

Что меняется у X по их сверке: WG-ключи и masque `publickey` с сырым `+` —
**сегодня узел молча пропадает, после — появится**; `pbk` с `+` — сегодня
пробел → реестр снимает поле → REALITY деградирует; `password` /
`obfs-password` — сегодня пробел, узел не подключается.

**Статус: кандидат.** Порядок (SPEC §10.3): прогнать корпус с флагом «не
заменять `+`» в двух режимах → выписать кейсы с изменённым телом → если
меняются только заведомо битые сегодня значения, принять как дельту с
фикстурой на каждый; если меняется тело рабочего узла — отдельное решение.
**Ничего в `expected` до этого не менять.**
