# SPEC 185 — Обновление наборов правил (.srs): общий цикл с подписками, режим remote

Issue: Leadaxe/singbox-launcher#157. Решения владельца — 22.11.2026.

## 1. Проблема

Набор `.srs` скачивается один раз (кнопка srs во вкладке Rules или тихая
докачка при открытии Конфигуратора) и больше не обновляется никем:

- сборка превращает `type: remote` в `type: local` с `path` и выбрасывает
  `url` / `download_detour` / `update_interval` (SPEC 004: `raw.githubusercontent.com`
  в РФ недоступен напрямую, ядро с remote-набором не стартовало);
- сама сборка в сеть не ходит, таймера нет — списки блокировок устаревают на
  месяцы, а у правила горит ✔️;
- если файл удалён вручную, ядро падает `FATAL initialize rule_set: open …srs`:
  старт берёт готовый `config.json`, где путь уже записан.

## 2. Решение

### 2.1 Набор — такой же обновляемый ресурс, как подписка

| | Подписка | Набор `.srs` (режим local) |
|---|---|---|
| Локальная копия | узлы в state | файл в каталоге `.srs` машины |
| Интервал | источник → общий → запасной | правило → `srs_update_interval_hours` → 168 ч |
| Проверка свежести | общий цикл, раз в час | тот же цикл |
| Неудача | повтор через 15 с, затем при подъёме VPN | то же |
| Сборка, копии нет | докачивает сама | докачивает сама |
| Сборка, копия есть | в сеть не ходит | в сеть не ходит |
| Вручную | Update | кнопка srs |

- Свежесть файла — по времени его изменения (mtime); в state ничего не пишется.
- Запрос условный (`If-Modified-Since`); ответ 304 продлевает свежесть.
- Скачанное проверяется до замены: 200, непустое, бинарный набор начинается с
  сигнатуры `SRS`, исходный (JSON) — с `{`. Иначе прежний файл не трогается.
- Замена атомарная (временный файл + rename). Работающее ядро перечитывает
  local-набор само (fswatch в sing-box) — перезапуск не нужен.
- После обновления существующего файла конфиг не пересобирается (путь тот же).
  Если файл раньше ОТСУТСТВОВАЛ — конфиг помечается устаревшим, как после
  обновления подписки (правило вернётся при ближайшей сборке).
- Параллельность — не больше 2 загрузок. Мёртвая ссылка (404) и любой сбой
  повторяются не чаще раза в час (пауза в памяти процесса).
- Интервал 0 — автообновление набора выключено.
- Один файл у нескольких правил (имя файла — от URL): действует наименьший
  ненулевой интервал.

### 2.2 Сборка и старт ядра

- `RebuildConfigIfDirty`, дойдя до настоящей сборки, докачивает ОТСУТСТВУЮЩИЕ
  файлы включённых правил (общий лимит 20 с). Истёкший интервал сборку не
  задерживает — это дело цикла.
- Пользовательское правило `kind: srs`, чей файл так и не появился, выпадает из
  конфига целиком (как правило пресета, SPEC 153), а не уезжает в конфиг с
  путём к несуществующему файлу.
- Перед стартом ядра (`rebuildConfigBeforeStart`, оба движка): если
  `config.json` ссылается на local-набор, которого нет на диске, сборка
  становится принудительной — файл докачивается либо правило выпадает; ядро
  стартует.

### 2.3 Удалённые машины

- По умолчанию режим local: файлы лежат у лаунчера в каталоге машины и
  заливаются при Deploy.
- Перед Deploy лаунчер обновляет наборы этой машины (отсутствующие и с истёкшим
  интервалом), затем заливает изменившиеся (сравнение по SHA-256 уже есть).
- Фоновой доливки на машину нет (решение владельца): без Deploy наборы на ней
  не обновляются. Кому нужно автообновление без Deploy — режим remote.

### 2.4 Режим набора: local | remote

Три настройки набора, два уровня: значение у правила → общая переменная
шаблона → встроенное умолчание.

| Поле записи правила (`kind: srs`, `kind: preset`) | Переменная шаблона | Умолчание | Смысл |
|---|---|---|---|
| `srs_mode` | `srs_mode` | `local` | кто качает набор |
| `update_interval_hours` | `srs_update_interval_hours` | `168` | период обновления, ч; 0 — не обновлять |
| `download_detour` | `srs_download_detour` | пусто | через что качает ядро (только remote) |

Режим remote: в конфиг уходит `{type: remote, tag, format, url,
update_interval: "<N>h", download_detour}`; файл лаунчер не держит и не
заливает. `update_interval` при 0 не пишется (умолчание ядра), пустой
`download_detour` не пишется (ядро качает через выход по умолчанию).

Риск remote осознанный (штатное поведение sing-box, форк не правим): если
набора нет в `cache.db` и первая загрузка не удалась, ядро не стартует. UI
предупреждает об этом рядом с переключателем.

`download_detour` — ребро графа сборки: цель проверяется по итоговому списку
тегов; недоступная цель → набор не эмитится (правило выпадает с
предупреждением, как при нескачанном файле). Переименование Направления
переписывает и это поле.

### 2.5 UI

- Settings: три переменные в разделе шаблона (рисуются автоматически).
- Окно пользовательского правила SRS и окно пресета с remote-наборами: блок
  «Rule-set updates» — Mode (Default / Local / Remote), Update interval,
  Download via; у Remote — предупреждение.
- Подсказка кнопки srs показывает дату последней загрузки.

### 2.6 Контракт

`update_interval_hours` у `rules[]` из поля стороны LxBox становится общим
(и для `kind: preset`); `srs_mode`, `download_detour` — новые поля записи
правила, поддержка — лаунчер; три переменные — `registry/vars.json`
(`in: desktop`). Бамп `contract/VERSION`, строка changelog, параграф
`TASKS_LXBOX.md`, кейс корпуса бэкапа.

## 3. Принятые ограничения

- Лаунчер выключен — наборы не обновляются (как и подписки).
- Автозамена без отката: содержимое списка не проверяется, только формат.
- Без VPN в РФ загрузка с GitHub не проходит: прежний файл остаётся, попытка
  повторится при подъёме VPN.
- Удалённая машина в режиме local обновляется только при Deploy.
- Режим remote может уронить ядро при первой загрузке.

## 4. Критерии приёмки

1. Файл старше интервала заменяется циклом без действий пользователя; ядро не
   перезапускается.
2. Битый ответ (HTML, пустой) прежний файл не портит.
3. Удалённый вручную `.srs` не даёт FATAL: при старте файл докачан или правило
   выпало.
4. Режим remote эмитит `type: remote` с `url`, `update_interval`,
   `download_detour`; недоступный detour — набор и правило выпадают.
5. Поля правила переживают save/load и экспорт/импорт бэкапа.
