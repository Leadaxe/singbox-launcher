# SPEC 160 — Debug API: правка состояния по образу Конфигуратора; импорт без ключа `rules` не трогает правила

**Контекст:** debug API (SPEC 050/053/056–058, 078, 100, 127). Контракт 1.1.116, TASKS_LXBOX §113.
**Решение владельца:** 09.10.2026 — «нужны все точки API, включая то, что я могу делать в Конфигураторе: добавить/удалить сервер, правило, DNS»; четыре предложения разбора инцидента приняты.

## Проблема

Инцидент 08.10.2026: агент добавил один узел через `POST /backup/import` файлом, нёсшим только `sources[]`, — приёмник потерял все правила маршрутизации. Разбор инцидента:

1. **Импорт обнулял `rules[]` безусловно** (`core/backup/import.go`, applyDecoded), а декодер не различал «ключа `rules` нет» и «`rules: []`». Норма BACKUP.md §9 п. 7 («единственная секция полной замены») была написана для файла, описывающего всю настройку; для частичного файла она стирала маршрутизацию молча — ответ `ok`, `applied.rules: 0`, предупреждений ноль.
2. **Единственный способ добавить узел через API — `/backup/import`.** Точек «добавить/удалить сервер», «добавить/удалить правило», «добавить/удалить DNS-сервер/правило» у API нет, хотя Конфигуратор всё это умеет. Агент вынужден собирать файл бэкапа руками и попадает в ловушку п. 1.
3. **`PATCH /state/dns` заменяет секцию целиком**, гард ловит только `{}`: тело только с `servers` молча стирает `dns.rules`, и наоборот.
4. **API не журналирует мутирующие вызовы** — инцидент нечем разобрать по логу лаунчера.

## Требования

### A. Импорт бэкапа (контракт 1.1.116) — сделано в этой же волне

- A1. Ключ `rules` в файле есть (в т. ч. `[]`) → правила приёмника замещаются файлом, как прежде; снятые считаются и называются одним предупреждением `backup_rules_replaced {count}` (`count > 0`).
- A2. Ключа `rules` нет → правила приёмника не трогаются, кода нет. Норма одна на 1.0 и 0.x.
- A3. Экспорт пишет ключ всегда (без изменений). `ImportResult` несёт `RulesReplaced`, `ReplacedRules`; ответ `POST /backup/import` — `applied.rules_replaced`, `applied.replaced_rules`.
- A4. Фраза UI для кода + перевод; `registry/backup_warnings.json`, `schema/backup.schema.json`, BACKUP.md §9 п. 7, README 1.1.116, TASKS_LXBOX §113.

### B. Точки CRUD состояния (локально и зеркалом `/remote/machines/{id}/state/*`)

Общее для всех мутаций B: гейт мажора схемы (`guardStateSchema`), мьютекс `stateAccess`, load → изменение → `state.ApplyRecordVars` → save; у локального состояния после сохранения — `RebuildConfigIfDirty` с полями `config_rebuilt` / `config_rebuild_error` в ответе (как у `/backup/import`); у машины — `config_rebuilt: false`. Идентификаторы в `DELETE` — **query-параметрами**, не `{…}` в пути: на Win7-сборке (go1.20) маршруты с подстановкой недостижимы. Ответ мутации — `{"ok": true, "diff_summary": [...], ...}`; ошибки — 400 (тело), 404 (нет цели), 409 (схема / неоднозначность), 422 (семантика, с `field`).

**B1. Серверы — `GET/POST/DELETE /state/servers`.**
- `GET` — список узлов-серверов: корневые и члены папок: `{tag, kind, type, enabled, folder_id?, folder?}`. Нужен агенту, чтобы найти тег для `DELETE`.
- `POST` тело `{"input": "<текст>", "folder": "<имя или ULID папки>"?, "tag": "<тег>"?}`. `input` — то же, что принимает поле добавления источника Конфигуратора: ссылки по строкам, `.conf` WireGuard/AWG, `vpn://`, JSON sing-box (один outbound / массив / документ с `outbounds`). Строки-подписки **не добавляются** — попадают в `skipped` с причиной `subscription_url`; битые строки — в `skipped` с текстом ошибки разбора (не молча). `tag` применяется, только если из `input` получился ровно один узел, иначе 422. Тег узла уникализируется против корневого пространства имён (`X`, `X-2`, …) — в папке против состава папки, как в Конфигураторе. Дубль по происхождению (`Origin.Raw` у `uri`) в корне пропускается с причиной `duplicate`. Папка ищется по ULID, затем по имени (`kind=folder`; подписка — 422). Ответ: `added: [{tag, folder_id?, type, warnings[]}]`, `skipped: [{line, reason}]`.
- `DELETE ?tag=…[&folder=…]` — удаляет корневой узел (без `folder`) или член папки. Вместе с узлом снимаются ссылки на него в источниках: `detour`, хопы цепочек, члены и `default` групп (форма `{folder_id, tag}` / `{tag}`), строки `include` Направлений. Ссылки **по имени** в правилах (`outbound`), `route_final`, `detour` DNS-серверов, `vars` — **не правятся**, а перечисляются в ответе `dangling: [...]` (как Конфигуратор: сообщает, не чистит). У узла `tailscale` снимается каталог состояния (`config.RemoveTailscaleStateDir`). Нет узла — 404; тег есть и в корне, и в папках, а `folder` не задан — удаляется корневой.

**B2. Правила — `POST/DELETE /state/rules`** (к существующим `GET/PATCH`).
- `POST` тело — одна запись правила в форме состояния v8 (`kind`, `name`, `body`, `refs`, `ref`, `vars`, `enabled`, `num?`). Проверки: `DecodeBody`; у inline/srs тело — объект с `outbound` или `action`; цель `outbound` — известный тег (Направления после слияния с шаблоном, системные теги, корневые узлы, цепочки, свёртки), иначе 422 `field: body.outbound`; у preset — `ref` из пресетов шаблона. `num` без значения — `NextUserRuleNum`; массив остаётся отсортированным (`SortRulesByNum`). У `kind=preset` после добавления — `SyncDNSOptionsWithActivePresets` и `build.SyncOutboundsWithTemplate` (то, что делает Конфигуратор при сохранении); то же при удалении пресета. `enabled` без значения = `true`.
- `DELETE ?num=N` | `?name=X` | `?ref=preset_id` — ровно одна запись; совпало несколько → 409 с перечнем `num`, тогда удалять по `num`. Пресет-голова (несортируемый, `traffic-processing`) — 422: загрузчик всё равно досеет.

**B3. DNS-серверы — `POST/DELETE /state/dns/servers`.**
- `POST` тело — запись `kind=user`: `{"tag", "enabled"?, "body": {...}}`. Проверки: тег непустой и свободен среди `dns.servers` и тегов шаблона; тело непустое; `body.detour`, если есть, — известная цель (иначе 422). `kind` template/preset — 422 с подсказкой (`PATCH /state/dns`, пресеты — через правила).
- `DELETE ?tag=…` — только `kind=user` (template/preset — 422). Если удалённый был `dns_final` — final переносится на первый включённый сервер; если был `dns_default_domain_resolver` — сбрасывается (как Конфигуратор).

**B4. DNS-правила — `POST/DELETE /state/dns/rules`** (к существующим `GET/PATCH` текстового вида).
- `POST` тело `{"rule": {...}}` — одно DNS-правило sing-box (объект, не массив; `server` или `action` обязательны); добавляется записью `kind=user, enabled=true` в конец.
- `DELETE ?index=N` — индекс в `dns.rules` в том виде, что отдаёт `GET /state/dns`; запись `kind=preset` — 422 (пресеты — через правила).

**B5. Хвосты существующих точек.**
- `PATCH /state/dns` требует **оба** ключа `servers` и `rules` (пустой список — явный сброс); иначе 422 с подсказкой на новые точки.
- `PATCH /state/dns/rules` получает `guardStateSchema` и `state.ApplyRecordVars` — как остальные PATCH.

### C. Журнал мутирующих вызовов

Каждый `POST/PATCH/PUT/DELETE` к API пишется в основной лог лаунчера (`debuglog.InfoLog`) одной строкой: метод, путь (без query-секретов не бывает — query пишется), код ответа и первые ~400 символов тела ответа одной строкой (`diff_summary`, `applied`, `error`). Тело запроса не пишется (ссылки несут секреты). `GET` не журналируется. `api.log` не используется — он занят трафиком Clash API.

### D. Документация

`docs/API.md` и `docs/API.ru.md`: раздел «State write» — новые точки с примерами curl (и примеры `/state/rules` в форме v8 вместо устаревших `body.name/match`); раздел «Backup / transfer» — норма ключа `rules`, поля `rules_replaced`/`replaced_rules`, рецепт «добавить узел» через `POST /state/servers`; «Source» — новые файлы. `docs/release_notes/upcoming.md` (EN + RU). `docs/ARCHITECTURE.md` — новый пакет операций над состоянием.

### E. Открытое окно Конфигуратора узнаёт о внешней правке (решение владельца 09.10.2026: «подписать окно на событие и выкидывать попап»)

- E1. Каждое сохранение состояния через debug API (все `PATCH/POST/DELETE /state/*`, `POST /backup/import`, локально и для машины) публикует `events.StateChanged` с указанием источника и адресата: `Source: "debugapi"`, `Target: local|remote`, `MachineID`. Собственное сохранение Конфигуратора и маркеры StateService публикуются как прежде (без `Source`).
- E2. Окно Конфигуратора при создании подписывается на `StateChanged` и отписывается при закрытии. Реагирует только на события с `Source == "debugapi"`, чей `Target`/`MachineID` совпадают с тем, что редактирует окно. Обработчик шины вызывается на goroutine HTTP-обработчика — переход в UI-поток через `fyne.Do`.
- E3. Попап (модальный confirm над окном Конфигуратора): заголовок «Settings changed outside the Configurator», текст: настройки изменены через debug API, пока окно открыто; «Reload» перечитывает `state.json` в окно (как «Read → state.json»: LoadCurrentState → LoadState → MarkAsSaved → SyncModelToGUI), «Keep mine» оставляет окно как есть с оговоркой, что следующий Save перепишет внешнюю правку. Пока попап открыт, повторные события не плодят новые попапы (одно окно — один попап; после закрытия попапа следующее событие покажет его снова).
- E4. Строки — через `locale.T`, перевод в `bin/locale/ru.json`.

## Вне рамок

- Подписки, папки, цепочки, Направления как сущности CRUD (добавить/удалить) — следующая волна, если понадобится.

## Критерии приёмки

- Файл 1.0 и 0.x без ключа `rules` оставляет правила приёмника; с `rules: []` — снимает их и даёт `backup_rules_replaced` с числом (тест `TestImportWithoutRulesKeyKeepsLocalRules`).
- Сценарий инцидента через API: `POST /state/servers` с одной ссылкой добавляет узел, число правил, DNS-серверов и DNS-правил не меняется, `config.json` пересобран.
- `DELETE /state/servers?tag=` снимает узел и ссылки в источниках/Направлениях, перечисляет висячие цели правил.
- `POST /state/rules` с неизвестной целью — 422; с известной — правило на оси, массив отсортирован; `DELETE` по `num` снимает ровно его.
- `POST /state/dns/servers` с занятым тегом — 422; `DELETE` финального сервера переносит `dns_final`.
- `PATCH /state/dns` без одного из ключей — 422, состояние не тронуто.
- Правка через API при открытом окне Конфигуратора показывает попап; «Reload» показывает в окне добавленный узел, «Keep mine» оставляет окно как было (проверяет владелец, UI без тестов).
- Все новые маршруты видны в `/` и `/help`, тест `TestHelpMethodsMatchHandlers` зелёный; мутация оставляет строку в `singbox-launcher.log`.
- `go build ./...`; локально — только новые именованные тесты; полный прогон — CI.
