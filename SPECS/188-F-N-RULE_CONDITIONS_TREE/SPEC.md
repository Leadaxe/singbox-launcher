# SPEC 188 — Правило из условий: дерево, наборы внутри правила, DNS по дереву

Решения владельца — 22–23.11.2026. Строится поверх SPEC 185 и 187 (наборы,
`file://`, формат по расширению). Общая задача лаунчера и LxBox: норма — в
контракте, релиз лаунчера с этой задачей выходит только после того, как LxBox
сделает то же самое (п. 8).

## 1. Проблема

- Форма правила взаимоисключающая: один тип на правило (IP, домены, процессы,
  набор, Custom JSON). «Домены И порт 443», «набор И только этот клиент LAN»,
  «торрент-протокол мимо VPN» пишутся только руками в JSON.
- Портов, протокола, транспорта, источника, входящего, Wi-Fi в форме нет
  вообще.
- Правило с двумя группами условий форма не узнаёт и открывает как JSON.
- Связки «или / и / не» между условиями задать негде.

Ядро всё это умеет; хранение (`body` — правило sing-box) тоже. Ограничение —
в форме и в том, как сборка выпускает наборы.

## 2. Модель

Правило одного понятия, двух видов:

- **простое** — набор условий;
- **составное** — `type: logical`, `mode: and | or`, `rules[]`, `invert`;
  элементы `rules[]` — снова простые или составные.

Цель (`outbound` | `action`) — только у корня. Вложенность в хранении и
сборке не ограничена.

### 2.1 Условия простого правила

Условие — рамка формы. Поля внутри условия соединены «любое из», условия
между собой — «и». Каждое условие в простом правиле — не более одного раза,
кроме группы правил.

| Условие | Ключи тела | В DNS |
|---|---|---|
| Destination / Rule sets | `refs`, `domain`, `domain_suffix`, `domain_keyword`, `domain_regex`, `ip_cidr`, `ip_is_private` | да, кроме `ip_cidr`, `ip_is_private` |
| Port | `port`, `port_range` | нет |
| Source | `source_ip_cidr`, `source_ip_is_private` | да |
| Source port | `source_port`, `source_port_range` | нет |
| Process | одно из: `process_name` \| `process_path` \| `process_path_regex` | да |
| Protocol | `protocol` | нет |
| Network | `network` | нет |
| Inbound | `inbound` | да |
| Wi-Fi | `wifi_ssid`, `wifi_bssid` | да |
| Rule group | составное правило | по содержимому |

- Protocol и Network — разные условия: ядро связывает их «и».
- В Process выбирается один способ: имя и путь вместе ядро связывает «и».
- Wi-Fi ядро читает на Windows и Linux; на macOS условие показывается с
  пометкой «на этой машине не действует» (цель сборки — машина правила, не
  хост лаунчера).
- `network_type`, `network_is_expensive`, `package_name*` форма лаунчера не
  показывает, но запись хранит и провозит без изменений.
- Тело с ключом вне реестра условий открывается как JSON, как сейчас.

Таблица «ключ → условие, вид поля, идёт ли в DNS, идёт ли в набор» живёт в
`contract/registry`; в коде формы и сборки имён ключей нет. В таблице есть и
ключи, которых форма лаунчера не показывает, — условия LxBox Apps
(`package_name`, `package_name_regex`) и Network type (`network_type`,
`network_is_expensive`): в DNS — да, в набор — нет. Сборка обеих сторон идёт
по одной таблице.

## 3. Хранение

Запись `rules[]` прежняя; меняется одно: `refs` — ключ простого правила
внутри `body`, рядом с остальными условиями, на любом уровне дерева.

```json
{ "kind": "srs", "name": "Streaming", "enabled": true,
  "body": { "refs": ["https://…/netflix.srs"], "domain_suffix": ["nflxvideo.net"],
            "port": [443], "outbound": "direct" },
  "dns": { "enabled": true, "serverTag": "cf" } }
```

- `kind` выводится: есть `refs` в дереве — `srs`, нет — `inline`.
- `dns`, `update_interval_hours`, `srs_mode`, `download_detour` — на записи,
  одни на все наборы дерева.
- Старая форма (`refs` на записи) читается обеими сторонами и при сохранении
  переписывается в тело корня. `refs` есть и на записи, и в дереве — главнее
  дерево, `refs` записи игнорируется.
- `refs` допустим только в простом правиле; у узла `logical` его нет.
- Правило с группами хранится как `logical and`: первым под-правилом —
  обычные условия, следом каждая группа. Одна группа без других условий —
  сама группа, без обёртки.
- Версия формата бэкапа поднимается (`lx_backup: 3`, читаются 2 и 3):
  приложение, не знающее новой формы, отказывает файлу целиком с сообщением
  «файл новее приложения», а не теряет правила молча. `state.json` — v9.
- Блокировки DNS (Block HTTPS, Force IPv4, Fixed IP) над деревом: ядро не
  принимает `query_type` и `ip_version` у корня `logical`, поэтому такое
  DNS-правило оборачивается в `and` из условия блокировки и дерева.

## 4. Сборка: наборы и маршрутное правило

Сборка обходит дерево. В каждом простом правиле:

1. Каждая ссылка `refs` — запись `rule_set` (local | remote, SPEC 185/187).
2. Ключи столбца «в набор» — ровно `domain`, `domain_suffix`,
   `domain_keyword`, `domain_regex`, `ip_cidr` — уходят в отдельный
   inline-набор этого правила («укрупнённый набор»). Остальное ядро либо не
   примет в наборе, либо сломает «или» со ссылками. `invert` в набор не идёт
   никогда — остаётся на правиле.
3. На правиле остаётся `rule_set: [теги ссылок в порядке refs…, тег
   inline-набора последним]` и все остальные ключи как есть.

Основание — справка ядра (`route/rule.md`): разные наборы между собой всегда
«или»; набор из нескольких правил с ключами внешнего правила — «и». Иначе
«любое из» в Destination не выполняется. Обратный случай: набор из одного
простого правила без `invert` сливается с группами внешнего правила
(`{rule_set: набор(домены, порт 80), port: 443}` ловит 80 и 443). Разбор
содержимого набора вне задачи; подсказка у поля наборов это называет.

**Теги** — одна схема на обе стороны (решение владельца 23.11.2026). B — имя
правила с обрезанными краями (пустое после обрезки — `unnamed`; контракт
1.1.180): оно читается в логах ядра, и по нему ссылаются рукописные
JSON-правила.

Развод одинаковых имён — один раз на правило, а не на каждый тег:

- сначала заняты теги наборов шаблона и наборов всех пресетов, стоящих в
  `rules[]`, включённых и нет (пресет никогда не теряет набор из-за имени
  правила пользователя);
- базу берёт каждая запись вида `inline` | `srs` (в том числе verbatim-JSON
  у LxBox) в порядке оси — с наборами
  и без, включённая и выключенная, выпускаемая и нет: тег зависит только от
  имён и порядка и совпадает у сторон. Записи-пресеты базу не берут;
- следствие: у существующих правил тег может смениться при первой сборке,
  если выше по оси стоит выключенное или невыпускаемое одноимённое правило
  (включённое занимает тег и сегодня);
- B' — первый из `B`, `B (2)`, `B (3)`, …, который не занят и не взят как
  база правилом выше; все теги правила строятся от B';
- производный тег, совпавший с занятым (правило с именем `X:inline`),
  разводится тем же суффиксом на этом теге.

- лаунчер уходит с `user:<id>`: теги всех наборов существующих правил
  меняются; ссылки `rule_set` на старые теги в телах правил состояния
  переписываются при первой загрузке; файлы копий остаются под прежними
  именами и не перекачиваются (имя файла от тега не зависит);

- ссылка: первая ссылка корневого простого правила — `B`; любая другая —
  `B:<h8>`, h8 = первые 8 hex sha256 строки ссылки (UTF-8, края обрезаны,
  нижний регистр); коллизия h8 внутри правила — 16 символов у обеих;
- одна ссылка в нескольких листах — один тег и одна запись `rule_set`;
- inline-набор: у корневого простого правила без ссылок — `B` (тег `B`
  получает первая ссылка, а если ссылок нет — inline-набор), со ссылками —
  `B:inline`; у листа дерева
  `B:inline:<путь>`, путь — индексы `rules[]` от корня через точку;
- у LxBox меняются только теги второй и следующих ссылок (`имя-2` →
  `имя:<h8>`).

- inline-набор обязателен у простого правила с `refs` и доменными или
  адресными ключами; без `refs` ключи могут остаться на правиле (выбор
  стороны, результат тот же).
- `ip_is_private` в набор ядро не принимает. В условии с `refs` галка
  недоступна, подсказка ведёт в группу правил («любое из»: набор, приватные).
  Тело с обоими ключами, написанное руками, выпускается как есть; результат
  зависит от устройства файла набора.
- Всё или ничего: не доехал хоть один набор дерева — правило целиком не
  выпускается.
- Теги наборов нормируются контрактом. Рукописный `rule_set` в теле
  сохраняется и стоит первым в списке; ссылается на невыпущенный набор —
  правило не выпускается. Копия набора привязана к ссылке, а не к номеру в списке:
  правка дерева файлов не перекачивает.

## 5. Сборка: DNS-зеркало

Зеркало повторяет дерево (DNS-правила ядра поддерживают `logical`).

| Узел | Действие |
|---|---|
| Простое правило | остаются ключи списка `rule_dns_mirror_match`; из `rule_set` исключается inline-набор без доменных ключей |
| Ничего не осталось | узел пустой |
| `and`, `or` | пустые дети выбрасываются |
| Один ребёнок | обёртка снимается |
| `invert` | переносится всегда; узел, опустевший целиком, выбрасывается и под `invert` |
| Пустой корень | зеркало не выпускается |

- Порядок DNS-правил одного правила, место на оси, Fixed IP, Force IPv4 —
  без изменений (TEMPLATE_LANG §6.11).
- Block HTTPS доступен, если доменный ключ или набор есть хоть в одном
  простом правиле дерева.
- **Предупреждение.** DNS-опция включена, а зеркало пустое — ⚠ на вкладке DNS
  и в строке правила: «DNS options have no effect: the rule has no condition
  DNS can see». Правило сохраняется, маршрут работает.
- Зеркало у́же или шире маршрута из-за выпавших ключей — принятое поведение;
  подсказка «DNS options apply on any port and protocol» остаётся.
- inline-набор исключается из зеркала по признаку «в наборе нет ни одного
  доменного ключа»: ядро проверяет каждый тег и не стартует на наборе только
  из `ip_cidr`.
- Лист `{ip_cidr, inbound}` (или `ip_cidr` + процесс) с DNS-опцией даёт
  зеркало на все запросы этого входа или процесса; с Fixed IP — подмену всех
  доменов. Принятое поведение (у лаунчера так и сегодня), кейс корпуса.
- Заодно исправляется: `invert` плоского правила сегодня в зеркало не
  переносится, зеркало действует на обратное множество.

## 6. Форма

- Радио «тип правила» убирается. Вкладки Form / JSON / DNS / Preview остаются.
- Под стопкой условий — кнопка «+ Condition» с меню условий; выбранное
  условие появляется рамкой со всеми своими полями. Уже добавленное из меню
  пропадает; «Rule group» отделена чертой и добавляется сколько угодно раз.
- Между рамками подпись «AND», в рамке — «any of». Пустые поля в тело не
  пишутся, пустое условие при сохранении отбрасывается.
- Rule group: переключатель «all of / any of», галка «Not», внутри список
  правил и «+ Rule»; каждое правило — такая же стопка условий.
- Поле наборов — как в SPEC 187 (URL или файл, «Add file…»), с подсказкой:
  набор может содержать порты и процессы; для «или» с другими условиями —
  группа правил.
- Форма открывает любое тело из ключей реестра; `logical`, не укладывающийся
  в «условия + группы», открывается одной группой верхнего уровня.

## 7. Контракт (1.1.178 → следующая)

- `rules[].body`: дерево, `refs` внутри простого правила; чтение старой формы.
- Реестр: таблица условий (п. 2.1); `rule_dns_mirror_match` выравнивается
  (добавляются `network_type`, `network_is_expensive`; `source_ip_is_private`
  кладут обе стороны — DNS-правило ядра lx.35 все три принимает).
- TEMPLATE_LANG §6.11: зеркало по дереву (п. 5). ONE_NAMESPACE §1, BACKUP.md,
  схема бэкапа, версия формата.
- Норма выпуска наборов (п. 4) и тегов.
- Корпус: плоское правило с набором и доменами; дерево `and`+`or`; `invert`
  с выпавшим портом; пустое зеркало; старая форма записи.
- `contract/VERSION`, changelog, параграф `TASKS_LXBOX.md`.

## 8. LxBox

Разведка сделана (сессия LxBox, 22.11): модель — тело-дерево с типизированным
видом простого правила; `CustomRuleInline` и `CustomRuleSrs` сливаются; из
headless-набора на правило переезжают приложение, Wi-Fi, источник, тип сети;
флаг `verbatim` для деревьев не нужен. Конфиг таких правил у LxBox меняется
(критерий 5 для него — только теги и файлы). Гейт `dnsLayerEligible` для
`ip_cidr + inbound` снимается. Под-правило группы LxBox открывает отдельным
экраном, предела глубины в форме нет. Resolve-правило матчит то же дерево. Реализация стартует после параграфа в
`TASKS_LXBOX.md`. Релиз лаунчера — после готовности LxBox.

## 9. Вне задачи

- Resolve перед маршрутом (`rules[].resolve`) — отдельная задача.
- Разбор содержимого `.srs` (что внутри — домены, порты, процессы).
- Условия `user`, `ip_version`, `clash_mode`, `network_type` в форме.
- Правила DNS-вкладки конфигуратора (свои DNS-правила) — форма та же не
  переиспользуется в этой задаче.

## 10. Критерии приёмки

1. «Домены И порт 443», «набор И источник LAN», «протокол bittorrent» собираются
   формой без JSON; ядро проходит check.
2. Набор из многих правил + свои домены в Destination: совпадение по любому из
   них (inline-набор выпущен, правило ссылается на список тегов).
3. Группа «любое из» и галка «Not» дают `logical` в `route.rules` и зеркально в
   `dns.rules`.
4. Правило «не порт 443» с DNS-опцией: сохраняется, зеркала нет, ⚠ виден.
5. Существующие правила открываются формой; файлы наборов не перекачиваются;
   теги наборов — имя правила, рукописная ссылка на старый тег `user:…` в теле
   правила после загрузки ведёт на новый; config.json плоских правил без
   набора байт-в-байт прежний.
6. Запись старой формы читается; сохранение пишет новую; экспорт/импорт
   бэкапа и кейсы корпуса проходят на обеих сторонах.
