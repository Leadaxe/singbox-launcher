# 135 · Раскладка данных: AppDir / DataDir / LogDir

Закрывает issue #85 (падение на NixOS, Guix, Flatpak, snap). Поглощает
SPEC 022 (данные macOS в `~/Library`) и SPEC 080 (XDG + portable-режим):
обе закрываются этой спекой, их папки переводятся в `…-C-…` со ссылкой сюда.
Спека #99 (Windows без `requireAdministrator`) опирается на эту и не
стартует раньше неё (§3.5).

Статус: **реализовано в ветке spec-135-impl, ждёт CI и приёмки владельцем**.
Развилки решены владельцем 24.09.2026 (§6); отступления от этого документа,
вскрывшиеся при реализации, — §11.

## 1. Проблема

Единственный корень путей сегодня — `FileService.ExecDir = filepath.Dir(os.Executable())`
(`core/services/file_service.go:82-96`). От него строятся все пути: 17
хелперов в `internal/platform/platform_common.go` (состояние, снапшоты,
remote-машины, `config.json`, шаблон, `.srs`, кэш подписок, логи) и ещё
около десятка мест россыпью (`gl-state.json`, `wintun.dll`, `settings.json`,
локали, каталог tailscale, клиентская пара демона `bin/daemon`, реестр
`remote-daemons`, ядро). Всего ~190 обращений к `ExecDir` в 62 файлах.

Следствия:

- На read-only установке `EnsureDirectories` падает на первом `MkdirAll`
  (`platform_common.go:205-215`). Это и есть #85.
- Ещё раньше, в `main.go:76-90`, `crash.log` и `native-stderr.log`
  открываются по `Dir(exe)/logs` до создания контроллера; на read-only
  каталоге они молча теряются.
- На macOS всё лежит **внутри бандла** (`Contents/MacOS/bin`, `logs`). Полная
  замена `.app` стирает данные пользователя; `build/build_darwin.sh:422-500`
  вынужден выносить `bin`/`logs` наружу ради `codesign`, а `codesign --verify`
  признан бесполезным (комментарий на :446-449).
- Литералы `"bin"` и `execDir + "/bin/rule-sets/"` живут мимо хелперов:
  `core/build/preset_merge.go:58,760`, `file_service.go:94`,
  `ui/core_dashboard_tab_status.go:254`, `core/controller.go:306`.
- Пользователь не может узнать, где лежат его данные, иначе как из
  документации: в интерфейсе путей нет, кроме двух кнопок открытия папок
  в Diagnostics.
- Удаление лаунчера оставляет данные, wintun-адаптеры и правила файрвола
  на машине: процедуры «удалить с очисткой» нет.

## 2. Что отвергнуто из #85 и SPEC 080 и почему

| Предложение | Откуда | Почему нет |
|---|---|---|
| `os.UserConfigDir()` как корень | #85, 080 | На Windows это roaming `%APPDATA%`: 70 МБ ядра и `state.json` с ключами будут ездить между машинами домена. На Linux это `~/.config`, куда не место бинарям и кэшам `.srs`. |
| Seed копированием шаблона и локалей при первом запуске | #85 | Классический баг «старый seed лёг поверх свежего». Поставляемое читается на месте, копия появляется только когда лаунчер реально скачал новое. |
| Без миграции: «state пересоздастся» | #85 | В `state.json` подписки, ключи, Направления, remote-машины. Потеря недопустима. |
| `SINGBOX_LAUNCHER_EXEC_DIR` | 080 | Подменяет и код, и данные разом. Нужны раздельные override только для данных и логов. |
| `SINGBOX_LAUNCHER_PORTABLE=1/0` | 080 | Переменная окружения не переживает переноса папки на флешку. Portable — свойство дистрибуции и папки, поэтому файл-маркер рядом с бинарём (§3.2). |
| Переименовать функции путей в `*FromExec` | #85, 080 | Строковые аргументы не защищают от подмены. Защита — именованные типы, которые ловит компилятор. |
| Каталог по `CFBundleIdentifier` с настраиваемым Bundle ID | 022 | Идентификатор подписи уже `com.singbox.launcher`, а имя каталога в `~/Library` для пользователя понятнее по имени программы. Требование снимается: каталог `singbox-launcher` на всех платформах. |

Что из 080 **взято**: переключатель Portable в настройках (§4.2) и детект
унаследованной раскладки по папке состояний (§3.2, правило 3). Курица-яйцо
из 080 («флаг portable нельзя хранить в settings.json») решается маркером
рядом с бинарём: он читается до любых настроек.

## 3. Целевая модель

Три роли вместо одного `ExecDir`:

| Роль | Права | Что лежит |
|---|---|---|
| **AppDir** | только чтение | бинарь, поставляемые шаблон и локали (`bin/wizard_template.json`, `bin/wizard_template.version`, `bin/locale/`), поставляемое ядро со спутниками (если есть), `mesa3d/`, маркер `portable.txt` |
| **DataDir** | запись | всё состояние и кэши в **прежней внутренней структуре** `bin/…` (состояние, снапшоты, remote, `config.json`, скачанные шаблон и локали, скачанное ядро, `.srs`, подписки, `settings.json`, `gl-state.json`, `wintun.dll`, `tailscale/`, `daemon/`, `remote-daemons/`) |
| **LogDir** | запись | четыре лога и их `.old`, `crash.log`, `native-stderr.log` |

Внутренняя структура `bin/…` под DataDir сохраняется намеренно: снапшоты,
каталоги remote-машин, документация и sudo-команды демона не меняются.
Переименование `bin` — отдельная косметика, не здесь.

Единственное известное исключение из «AppDir только чтение» — переключение
Mesa3D на Windows (`internal/platform/glstate.go:222`, `DisableMesa`/`EnableMesa`
переименовывают DLL рядом с exe): `opengl32.dll` обязан лежать рядом с exe,
иначе загрузчик его не найдёт. Исключение объявляется явно (§5) и в UI
недоступно, когда AppDir не пишется.

### 3.1 Пути по платформам

| Платформа | AppDir | DataDir | LogDir |
|---|---|---|---|
| Linux | каталог бинаря | `$XDG_DATA_HOME/singbox-launcher` (по умолчанию `~/.local/share/singbox-launcher`) | `$XDG_STATE_HOME/singbox-launcher/logs` (по умолчанию `~/.local/state/…`) |
| macOS из `.app` | `…app/Contents/MacOS` | `~/Library/Application Support/singbox-launcher` | `~/Library/Logs/singbox-launcher` |
| macOS голый бинарь | каталог бинаря | = AppDir (portable, как в SPEC 022) | `AppDir/logs` |
| Windows | каталог exe | `%LOCALAPPDATA%\singbox-launcher` | `%LOCALAPPDATA%\singbox-launcher\logs` |
| Любая, portable | каталог бинаря | = AppDir | `AppDir/logs` |

Каталог бинаря берётся после `filepath.EvalSymlinks(os.Executable())`:
Homebrew и `/nix/store` ставят симлинки, и AppDir должен указывать на
реальную папку с `bin/locale`.

Пустой `%LOCALAPPDATA%` → `%USERPROFILE%\AppData\Local`; пусто и там →
portable, если AppDir пишется, иначе старт останавливается с понятным
сообщением и подсказкой про `SINGBOX_LAUNCHER_DATA_DIR`.

Один корень данных, без дробления на config/data/cache: `.srs` и подписки
в `XDG_CACHE_HOME` вычищают «чистильщики», после чего `config.json` ссылается
на несуществующие файлы. Логи вынесены отдельно, потому что только они растут
и только их просят приложить к issue.

### 3.2 Порядок определения раскладки

Первое сработавшее правило выигрывает. Решение принимается один раз, **первым
действием в `main()`**, до открытия `crash.log` и до `RunGLProbeChild`, и
логируется первой строкой старта:
`layout: mode=<режим> app=<путь> data=<путь> logs=<путь>`.

1. **Переменные окружения** `SINGBOX_LAUNCHER_DATA_DIR`, `SINGBOX_LAUNCHER_LOG_DIR`
   (каждая независимо). Для Flatpak-обёрток, пакетов, CI, отладки. Режим `Env`.
2. **Маркер `portable.txt`** рядом с бинарём. Содержимое не читается,
   достаточно существования. Режим `Portable`. Маркер ставит дистрибуция
   (zip для Windows) или переключатель в настройках (§4.2).
3. **Унаследованная раскладка**: рядом с бинарём есть `bin/wizard_states/state.json`
   и AppDir проходит пробу записи → режим `Legacy`, данные там, где были,
   **без записи маркера**. Ничего не копируется, ничего не «уезжает».
4. **Платформенный дефолт** из таблицы 3.1. Режим `System`.

Правила 2 и 3 **не применяются на macOS из `.app`**: рядом с бандлом маркер
никто не положит, карантин Gatekeeper переносит бандл, а данные внутри
бандла — то, от чего эта спека уходит. Голый бинарь macOS под правила
попадает как Linux.

**Проба записи** — создать и удалить `AppDir/.write-probe-<pid>`. Биты
режима и `access()` на Windows с ACL врут; проба честна на всех платформах.

Дистрибуция решает режим по умолчанию: **все три zip для Windows (`win64`,
`win64-full`, `win7-32`) поставляются с `portable.txt`**, так что для нынешних
пользователей флешек и «папки с программой» ничего не меняется. Установщик
(если появится вместе с #99) маркер не кладёт. Tarball для Linux маркера не
содержит: там ожидают XDG.

### 3.3 Двухуровневое чтение поставляемого

Шаблон, локали и ядро читаются по цепочке **DataDir → AppDir**. Запись
(скачивание шаблона, ядра, локалей) идёт только в DataDir. Поставляемое
никогда не копируется, кроме миграции §3.4, где скачанное от поставляемого
уже неотличимо.

**Порядок по месту, а не по версии, имеет одну известную дыру**: после
обновления лаунчера в AppDir лежит свежий поставляемый шаблон с маркером
`wizard_template.version == AppVersion` (архив `win64-full` кладёт его,
чтобы первый старт не ходил в сеть), а в DataDir — скачанный шаблон от
прошлой версии. Поэтому для шаблона правило уточняется:

- в AppDir есть шаблон и его маркер равен `AppVersion`, а штамп
  `LastTemplateLauncherVersion` в `settings.json` меньше `AppVersion` →
  побеждает **AppDir**, `RefreshTemplateIfStale` ставит штамп без сети;
- иначе DataDir → AppDir.

`RefreshTemplateIfStale` (`core/template_migration.go`) переписывается под
два каталога: маркер читается из AppDir, штамп и скачивание — в DataDir.

**Ядро.** Порядок поиска: `SINGBOX_LAUNCHER_CORE` (новая переменная, явный
путь) → `DataDir/bin/sing-box` → `AppDir/bin/sing-box` → `PATH`. Здесь
DataDir побеждает **всегда**, даже если поставляемое новее: владелец кладёт
dev-сборки руками, и терять их нельзя. Когда ядро есть в обоих местах,
при старте логируются обе версии и слово `shadowed`. Системный `sing-box` из
`PATH` **последний**, а не первый (сегодня на Linux он первый,
`internal/platform/singbox_exec_path_linux.go`): лаунчер требует форк `lx`
(XHTTP, AWG), дистрибутивный бинарь почти всегда не тот. Смена порядка —
пункт заметок релиза для Linux с указанием на `SINGBOX_LAUNCHER_CORE`.

**Спутники ядра** (`wintun.dll`, `libcronet.dll`) ищутся загрузчиком ОС
рядом с самим `sing-box`, а не рядом с лаунчером. Поэтому их путь выводится
из каталога **выбранного** ядра: `WintunPath = Dir(SingboxPath)/wintun.dll`.
Проверка и скачивание wintun работают с этим каталогом; если он не пишется
(поставляемое ядро в read-only AppDir без спутника), пользователю
показывается причина и предлагается скачать ядро в DataDir, куда спутник
ляжет рядом. Архив `win64-full` кладёт ядро, wintun и libcronet в один `bin/`,
так что штатно случай не возникает.

**Локали.** `LoadExternalLocales` вызывается дважды: сначала `AppDir/bin/locale`,
затем `DataDir/bin/locale`; более поздний каталог перекрывает язык целиком.

### 3.4 Миграция

Данные копируются, когда выбран режим `System` или `Env`, в DataDir нет
`bin/wizard_states/state.json`, а рядом с бинарём он есть. Главный случай —
**macOS из `.app`** (правило 3 там отключено). Второй — Windows и Linux,
когда AppDir с унаследованными данными перестал проходить пробу записи
(§3.5). Третий — пользователь поставил `SINGBOX_LAUNCHER_DATA_DIR` на
существующей установке.

Порядок:

1. `bin/` копируется целиком во временный `DataDir/bin.migrating` с
   сохранением прав (у `bin/daemon` и `bin/remote-daemons` режим `0700`,
   внутри ключи). Ядро копируется тоже: владелец кладёт dev-сборки руками.
   Логи не копируются.
2. Нечитаемые файлы (после classic-режима на macOS в `bin/` бывают
   root-owned артефакты, см. комментарии в `build_darwin.sh`) пропускаются с
   предупреждением и считаются; итог — одной строкой в лог.
3. `bin.migrating` переименовывается в `bin`. Обрыв на любом шаге до этого
   оставляет DataDir без `state.json`, и следующий старт начинает заново.
4. В DataDir ставится маркер `.migrated_from` с путём источника,
   **последним** шагом.

Старое рядом с бинарём не трогается: откат на предыдущую версию остаётся
рабочим. Оставленная копия видна в очистке (§4.3) как «неиспользуемые
данные».

Честное ограничение: если пользователь macOS обновился, перетащив новый
`.app` поверх старого, данные уничтожены до первого запуска новой версии, и
никакой код это не спасёт. Поэтому:

- заметки релиза для macOS: **перед обновлением сделать LX Backup** (Settings →
  Backup) или обновляться через `build_darwin.sh -i`, который меняет только
  исполняемый файл;
- при первом запуске без данных и без источника миграции показывается
  одноразовое уведомление «данных предыдущей версии не найдено; если они
  были, импортируйте бэкап» со ссылкой на документацию.

### 3.5 Абсолютные пути в `config.json` и штамп корня

Сохранённый `config.json` содержит **абсолютные пути** к `.srs`
(`preset_merge.go:58`) и к каталогу tailscale (`controller.go:306`). Любая
смена DataDir делает их ложными: миграция, переключение portable,
переменная окружения, перенос `bin/` руками. Форсировать пересборку только
после миграции macOS недостаточно.

Правило общее: в `settings.json` появляется поле `config_data_root` — DataDir,
с которым `config.json` был собран в последний раз. При старте, если поле
непусто и не равно текущему DataDir, вызывается `MarkConfigStale`, как это
делает `RefreshTemplateIfStale` (`core/template_migration.go:87`), и в лог
пишется причина. Поле обновляется при каждой успешной сборке.

**Связь с #99.** Сегодня Windows-сборка требует администратора, поэтому
проба записи в `Program Files`-подобных каталогах проходит и унаследованные
установки остаются в режиме `Legacy`. После перехода на `asInvoker` проба
перевернётся, и правило 3 перестанет срабатывать. Миграция §3.4 (второй
случай) переносит такие данные в `%LOCALAPPDATA%` при первом запуске
неповышенного лаунчера. Спека #99 обязана сослаться на этот пункт и
проверить его руками; без этой спеки #99 не выполняется.

## 4. Функции для пользователя

Все строки — через `locale.T`, ключи сразу с переводом в `bin/locale/ru.json`.

### 4.1 Раздел Storage в Settings: где что лежит

Новый раздел **Storage** на вкладке Settings (по образцу разделов
`Connection`, `Language` в `ui/settings_tab.go`). Содержимое:

| Строка | Значение | Кнопка |
|---|---|---|
| Mode | `Portable` / `Legacy` / `System` / `Env` (и какой переменной) | — |
| Program | AppDir | Open |
| Data | DataDir | Open |
| Logs | LogDir | Open |
| Core | `SingboxPath`, версия, откуда взят (`data` / `app` / `PATH` / `env`) | Open |
| Template | какой уровень выбран (`data` / `app`), версия маркера | — |
| wintun (Windows) | путь, найден или нет | — |

Кнопка **Copy paths** копирует блок целиком текстом, как «Copy API info»
там же: его просят приложить к issue.

Тот же блок:

- пишется первой строкой каждого старта в главный лог (§3.2);
- отдаётся Debug API как `GET /debug/paths` (JSON), с записью в манифест;
- печатается флагом **`-paths`** в stdout до инициализации GUI и процесс
  выходит. Это единственный способ увидеть пути на машине, где окно не
  поднимается (NixOS без GL, headless CI).

Кнопки «Logs folder» и «Config folder» в Diagnostics
(`ui/diagnostics_tab.go:319-335`) переводятся на LogDir и DataDir и остаются.

### 4.2 Переключатель Portable

В разделе Storage чекбокс **«Portable mode (keep data next to the program)»**.
Показывается на Windows и Linux; на macOS из `.app` скрыт (режима нет), для
голого бинаря macOS скрыт (он и так portable).

Состояние: отмечен в режимах `Portable` и `Legacy`. Недоступен, с причиной
во всплывающей подсказке, когда:

- режим `Env` («paths are set by environment variables»);
- AppDir не проходит пробу записи («program folder is read-only»);
- ядро запущено («stop the VPN first»): живой процесс не трогаем, а раскладка
  меняется только перезапуском.

Переключение — это переезд данных с перезапуском (`Layout` считается один
раз). Диалог подтверждения показывает откуда и куда, затем:

**Включить** (`System` → `Portable`):

1. `DataDir/bin` копируется в `AppDir/bin.migrating` → переименование в
   `AppDir/bin` (тот же копировщик, что в §3.4). Если `AppDir/bin` уже есть
   (поставляемые шаблон, локали, ядро), копия сливается поверх: скачанное
   перекрывает поставляемое, как и в цепочке §3.3.
2. Записывается `AppDir/portable.txt`.
3. Перезапуск через `platform.RestartSelf()`.

4. После удачного переименования старый системный DataDir удаляется
   (решение Б). Что удалить не вышло, остаётся и попадает в очистку §4.3 как
   неиспользуемое. Старый LogDir не трогается: он занят до выхода процесса.
   Правило 2 сильнее правила 4, так что остатки на режим не влияют.

**Выключить** (`Portable`/`Legacy` → `System`):

1. `AppDir/bin` копируется в `DataDir/bin.migrating` → `DataDir/bin`.
2. Удаляется `portable.txt` (если был).
3. `AppDir/bin` удаляется (решение Б): иначе правило 3 на следующем старте
   вернёт `Legacy`. Поставляемые файлы, которые в нём лежали (шаблон, локали,
   ядро из `win64-full`), уже скопированы в DataDir и будут найдены цепочкой
   §3.3. Если часть файлов удалить не удалось, остаток переименовывается в
   `AppDir/bin.moved-<ГГГГММДД-ЧЧММСС>`, чтобы `state.json` рядом с бинарём
   гарантированно исчез; остаток видно в очистке. `AppDir/logs` остаётся.
4. Перезапуск.

В обе стороны `config.json` пересобирается сам по штампу §3.5. Отказ
копирования на любом шаге до переименования оставляет обе раскладки
нетронутыми, и чекбокс возвращается в прежнее состояние с ошибкой.

### 4.3 Удаление с очисткой

В разделе Storage кнопка **«Remove all data…»** (низ раздела, красная
иконка). Условие: ядро остановлено; иначе диалог просит остановить VPN.

Диалог перечисляет всё, что будет удалено, с чекбоксами и размерами:

- **Data** — DataDir целиком (состояние, подписки, кэши, скачанное ядро,
  клиентская пара демона, реестр remote-демонов). Всегда отмечен.
- **Logs** — LogDir. Отмечен.
- **Unused data** — что нашлось лишнего: остатки неудачного переезда
  (`bin.moved-*` рядом с бинарём, системный DataDir при активном portable,
  `AppDir/logs` в системном режиме), старый `Contents/MacOS/bin` на macOS
  при наличии `.migrated_from`. Отмечено.
- **Network cleanup** (Windows) — призрачные wintun-адаптеры и осиротевшие
  правила файрвола `sing-tun`, существующими
  `platform.CleanupGhostSingboxTunAdapters` и
  `platform.CleanupOrphanSingTunFirewallRules`. Отмечено.

Чего диалог **не делает**, и говорит об этом текстом:

- не удаляет AppDir: исполняемый файл, поставляемые шаблон и локали,
  `mesa3d/`, `portable.txt`. Папку с программой пользователь удаляет сам
  (на macOS — `.app` в корзину). Маркер остаётся, чтобы повторный запуск из
  той же папки не сменил режим молча;
- не трогает системную службу демона на macOS. Если plist установлен,
  диалог сначала показывает готовую команду
  `sudo <SingboxPath> lxd --service=uninstall --purge` (копировать / открыть
  Terminal, как остальные команды службы) и предупреждает, что после
  удаления DataDir лаунчер её собрать уже не сможет: ядра не будет.

Порядок выполнения: закрыть файлы логов → удалить DataDir → удалить
отмеченное лишнее → сетевая очистка → удалить LogDir → выход из приложения
без перезапуска. Итог печатается в stdout (лог уже закрыт).

Тот же сценарий флагом **`-purge-data`**: без GUI, печатает план (пути,
размеры) и выходит; с `-purge-data -yes` выполняет. Нужен установщику из
#99 как uninstall-хук и поддержке для машин без окна. Сетевая очистка во
флаге включена; служба демона — нет, команда печатается.

## 5. Механизм в коде

Новый пакет **`internal/paths`** (не `internal/platform`: тот тянет `os/exec`
и `syscall` в платформенных файлах, а резолвер должен импортироваться
отовсюду, включая тесты).

```go
type AppDir  string   // только чтение
type DataDir string   // запись
type LogDir  string   // запись

type Mode string      // "env", "portable", "legacy", "system"

type Layout struct {
    App  AppDir
    Data DataDir
    Logs LogDir
    Mode Mode
    // EnvSource — какие переменные сработали при Mode == "env", для §4.1.
    EnvSource []string
}

// Resolve чистая: exe уже после EvalSymlinks, env и goos подменяются в тестах.
func Resolve(exe string, env func(string) string, goos string, probe func(dir string) bool) (Layout, error)

// Describe — блок путей для лога, Settings, -paths и /debug/paths.
func Describe(l Layout, core CoreInfo, tmpl TemplateInfo) string
```

Правила:

- `Layout` вычисляется **один раз в `main()`** и передаётся значением в
  `NewAppController` → `NewFileService`. Никаких package-level глобалов и
  ленивой инициализации: они делают невозможной проверку двух раскладок в
  одном тестовом процессе. `main.go:76-90` (crash log, native stderr) и
  `RunGLProbeChild` получают `Layout` первыми.
- Каждый хелпер путей принимает **именованный тип**: пишущие только `DataDir`
  или `LogDir`, читающие поставляемое только `AppDir`. Передать `AppDir` в
  пишущий хелпер не даст компилятор. Это главная защита при правке ~190 мест.
- `EnsureDirectories(Layout)` создаёт **только** writable-каталоги.
- `FileService.ExecDir` исчезает как публичное поле; `wizard_model.ExecDir` и
  `debugapi` facade (`GetExecDir()`) разделяются на `App`/`Data`. Это два
  шва, где сейчас легче всего протащить AppDir в пишущий путь.
- Литералы из §1 переводятся на хелперы **до** рефакторинга, отдельным
  коммитом без смены поведения.
- Исключение Mesa (§3): `DisableMesa`/`EnableMesa`/`IsMesaInstalled`
  принимают `AppDir` явно, с комментарием-обоснованием; страж из §8 знает их
  поимённо. Кнопки Mesa в Diagnostics недоступны, когда AppDir не пишется.
- Копировщик каталогов один для миграции (§3.4) и переключателя (§4.2):
  временный каталог, права, пропуск нечитаемого, переименование в конце.
- `SingboxPath` и `WintunPath` считаются в одном месте: сначала ядро по
  цепочке §3.3, затем спутники от его каталога.

### 5.1 Демон (macOS, lxd)

Конфиг доставляется демону по mTLS (`prepareConfigForDaemon`), из каталога
приложения демон ничего не читает; `.srs` по абсолютным путям в
`~/Library/Application Support` root читает без ограничений. Клиентская пара
переезжает `bin/daemon` → `DataDir/bin/daemon`; уже установленное сопряжение
должно пережить переезд (пара копируется с правами).

**Путь ядра в plist.** `sudo <SingboxPath> lxd --service=install` фиксирует
путь к бинарю в `/Library/LaunchDaemons/<label>.plist`. После миграции
`SingboxPath` уедет в DataDir, а служба продолжит запускать бандловый бинарь:
обновление ядра кнопкой и `launchctl kickstart` перестанут до неё доходить.
Поэтому `DaemonStatusSnapshot` читает `ProgramArguments[0]` из plist (файл
`0644`, читается без root) и при расхождении с `SingboxPath` показывает
состояние «service runs another core binary» и команду `--service=install`
повторно. Проверить руками: sudo-команды в панели LOCAL не содержат старых
путей; сопряжение не отваливается; статус расхождения появляется и уходит
после переустановки службы.

### 5.2 Сборка macOS

`build_darwin.sh`: снять перенос `bin`/`logs` ради `codesign`, вернуть
`codesign --verify` в строй, режим `-i` сводится к замене бинаря без
сохранения `bin/`. Поставляемые шаблон, локали и ядро (если кладутся)
остаются в `Contents/MacOS/bin` как read-only seed, чтобы не менять раскладку
бандла.

## 8. Проверка

Локально только `go build ./...` и именованные `-run`. Полный прогон в CI.

- Резолвер: матрица из этапа 1.
- По одному интеграционному тесту на волну (CONSTITUTION), все в
  `t.TempDir()`:
  - **миграция**: старая раскладка → миграция → state, подписки, `.srs`
    читаются, источник на месте, права `0700` сохранены, маркер выставлен,
    `config_data_root` не совпал и конфиг помечен stale; обрыв до
    переименования → следующий старт мигрирует заново;
  - **переключатель**: `System` → `Portable` → `System` в одном каталоге,
    данные целы, маркер появляется и исчезает, старая копия после каждого
    шага удалена, правило 3 после выключения не срабатывает; неудаляемый
    файл → остаток уехал в `bin.moved-*`;
  - **очистка**: `-purge-data` без `-yes` только печатает; с `-yes` удаляет
    DataDir, LogDir, лишнее; AppDir и `portable.txt` нетронуты.
- Read-only: AppDir с правами `0555`, старт не падает, `crash.log`
  открывается в LogDir (Linux, macOS).
- Страж «AppDir не пишем»: AST-скан вызовов пишущих хелперов с аргументом
  типа `AppDir` по образцу `tools/l10n/l10n_check/scan.go:131`, с поимённым
  исключением функций Mesa.
- Legacy-режим: данные рядом с бинарём → тот же путь, ничего не скопировано.
- Шаблон: `win64-full`-раскладка (маркер в AppDir равен версии, старый штамп
  в DataDir) → выбран AppDir, сети нет.
- Ручная проверка владельцем: macOS через `-i` и статус plist в daemon-режиме,
  Windows из zip с маркером и переключение туда-обратно, очистка на Windows с
  проверкой адаптеров и правил файрвола, `-paths` на Linux.

## 10. Риски, по убыванию

1. Абсолютные пути в сохранённом `config.json` при любой смене DataDir:
   лечится штампом корня и принудительной пересборкой (§3.5).
2. `wizard_model.ExecDir` и `debugapi` facade: один недосмотр возвращает
   исходный баг на NixOS. Закрывается именованными типами и стражем.
3. Daemon-режим macOS: plist со старым путём ядра, sudo-команды, сопряжение
   (§5.1).
4. Переключатель Portable: старая копия удаляется только после
   переименования новой в окончательное имя; при отказе удаления остаток
   переименовывается в `bin.moved-*`, чтобы режим не откатился.
5. Очистка удаляет не то: закрывается списком путей в диалоге, dry-run во
   флаге и тем, что AppDir не трогается никогда.
6. macOS drag-replace: данные теряются до старта нового кода. Закрывается
   только заметками релиза и уведомлением при первом запуске.
7. Спутники ядра на Windows не рядом с ядром: закрывается выводом путей от
   каталога выбранного ядра (§3.3).

## 11. Отступления при реализации

Норма — этот документ; здесь зафиксировано, где код (ветка `spec-135-impl`)
разошёлся с текстом выше и почему. Ссылки на код/тесты — CODEMAP.md.

а) **§3.3, правило шаблона зацикливалось на штампе.** Формулировка «в AppDir
   есть шаблон и его маркер равен `AppVersion`, а штамп в DataDir меньше →
   побеждает AppDir» была неполной: если после победы AppDir штамп
   `LastTemplateLauncherVersion` всё же ставился (обычный путь после успешной
   сборки), а устаревший скачанный файл в DataDir оставался на месте,
   следующий старт с прежним (уже поднятым) штампом снова видел устаревший
   файл в DataDir и с этого момента правило порядка по месту («иначе
   DataDir → AppDir») возвращало его. Решение: когда поставляемый шаблон
   побеждает по маркеру, устаревший файл в DataDir **удаляется** —
   `core/template.ResolveTemplate` не удаляет сам (резолвер чистый), удаление
   выполняет вызывающая сторона по возвращённому `TemplateResolution`
   (`core/template_migration.go`, `RefreshTemplateIfStale`). Без этого шага
   правило 1 §3.3 срабатывало бы только один раз за версию.

б) **`CompareVersions` перенесён в `internal/constants`.** SPEC ожидал вызов
   `core.CompareVersions` из `core/template` (§3.3), но `core/template` не
   может импортировать `core` (core-domain L2 не имеет права зависеть от L3
   — было бы восходящим импортом, ARCHITECTURE.md §2–3). Функция перенесена
   в `internal/constants.CompareVersions` (лист, доступен всем слоям);
   `core.CompareVersions` (`core/core_version.go`) оставлен как тонкая
   обёртка над ней ради существующих вызывающих в `core/*`.

в) **Копировщик даёт владельцу rwx/rw, а не переносит права один в один.**
   §3.4 и §5 описывают перенос прав как есть; на практике источник `0555`
   (защита каталога от `codesign --force`/классик-режима macOS, см.
   `build_darwin.sh`) сделал бы `DataDir/bin` нечитаемым для последующей
   записи тем же копировщиком (миграция и переключатель работают одним
   кодом). `internal/paths.CopyTree` поэтому берёт исходные права и
   принудительно добавляет владельцу `rwx` на каталоги и `rw` на файлы;
   `0700` у `daemon`/`remote-daemons` и `0600` у ключей внутри сохраняются
   как есть (маска только добавляет биты, не снимает).

г) **Очистка: без `wizard_template.version` в portable-`AppDir/bin` данными
   считаются и ядро, и шаблон, а не только локали.** §4.3 предполагал, что
   `<App>/bin` при переключённом Portable содержит поставляемое (шаблон,
   локали, ядро из `win64-full`) плюс данные пользователя вперемешку.
   Различить их можно только по маркеру `wizard_template.version`: полные
   архивы и установщик его кладут, а сам лаунчер после скачивания в свежем
   portable-каталоге — нет. Поэтому правило: маркер есть → поставляемым
   (не удаляется) считается список `shippedBinNames` (шаблон+маркер,
   локали, ядро со спутниками); маркера нет → только `locale/`
   (`alwaysShippedBinNames`), всё остальное, включая скачанные лаунчером
   ядро и шаблон, — данные и попадает под удаление. `locale/` не удаляется
   **никогда**, в обоих случаях: SPEC §3.3 трактует поставляемые локали как
   App-уровень независимо от маркера шаблона (внешние переводы кладёт и
   установщик, и сам пользователь вручную, различить некому).

д) **`RestartSelf` вне Windows — настоящая реализация, а не заглушка.**
   На момент SPEC переключатель Portable (§4.2) уже требовал рабочий
   перезапуск на Linux/macOS, но `internal/platform/restart_other.go`
   возвращал «not supported» (унаследовано от SPEC 125, где перезапуск был
   нужен только на Windows из-за Mesa). Реализовано по образцу
   `restart_windows.go`: `exec.Command(exe, os.Args[1:]...)` с
   `SysProcAttr{Setsid: true}`, чтобы потомок пережил выход и не получил
   сигнал, адресованный терминалу родителя; `cmd.Process.Release()` —
   ждать его некому.

е) **Пересборка `config.json` после миграции — по флагу миграции, а не
   только по штампу `config_data_root` (§3.5).** На dev-сборках версия
   лаунчера не меняется между запусками, а `config_data_root` в перенесённом
   `settings.json` уже указывал на новый DataDir к моменту первой проверки
   в отдельных сценариях (миграция копирует `settings.json` вместе со всем
   `bin/`) — сравнение штампа с текущим DataDir иногда не отличало «конфиг
   собран для старого расположения» от «уже пересобран». Форсирующий сигнал
   — сам факт миграции (`FileService.Migration.Migrated`), который
   `RefreshTemplateIfStale`/`RebuildConfigIfDirty` учитывают отдельно от
   штампа: пересборка после миграции происходит всегда, штамп остаётся
   дополнительной, не единственной, проверкой для остальных случаев смены
   DataDir (переключатель Portable, ручной перенос `bin/`, переменная
   окружения).

ж) **wintun скачивается в каталог выбранного ядра.** `FileService.WintunPath`
   = `Dir(SingboxPath)/wintun.dll` (`core/services/file_service.go`,
   `core/wintun_downloader.go`): wintun обязан лежать рядом с `sing-box.exe`.
   При поставляемом ядре (`win64-full`) в пишущемся AppDir это запись в
   `AppDir/bin` — под защитой `paths.ProbeWritable` (каталог не пишется →
   отказ с подсказкой, без попытки записи). Осознанное исключение из «в
   AppDir не пишем» наравне с Mesa (§3, `DisableMesa`/`EnableMesa`).

з) **Данные в системном каталоге, скрытые маркером (по итогам ревью).**
   Сценарий: Portable выключен (данные уехали в `%LOCALAPPDATA%`, `AppDir/bin`
   удалён), затем поверх папки распакован новый zip с `portable.txt` —
   режим Portable с пустым `AppDir/bin`, данные не видны, а очистка удалила
   бы их как «unused system data folder». Добавлено:
   - `paths.HiddenSystemData`: Portable/Legacy, в `AppDir/bin` нет
     `state.json`, в системном `Data/bin` есть → на старте диалог
     «Existing data found» (как уведомление первого запуска, с `-tray` — при
     первом показе окна). Yes — удалить `portable.txt` и перезапуститься
     (копировать нечего); Cancel — `hidden_data_notice_shown` в settings.json,
     больше не спрашивать.
   - Очистка: системный DataDir с `state.json` при Portable/Legacy — в плане
     с пометкой «system data folder with settings — kept by default», чекбокс
     по умолчанию снят (и `-purge-data -yes` его не трогает). Исключение —
     `state.json` внутри записанного остатка переезда (`storage_leftover`).
   - `SwitchToSystem`: в системном `Data/bin` есть `state.json`, а в
     `AppDir/bin` нет → `ErrTargetHasData` без изменений; `SwitchPortable(false)`
     в этом случае удаляет `portable.txt` и перезапускается — для
     пользователя это не ошибка.

и) **Переезд переключателем: пропуски копировщика, блокировка записи,
   немедленный перезапуск (по итогам ревью).** Решение Б («старое удаляется»)
   уточнено: если копировщик пропустил хоть один файл, источник не стирается
   (включение — `Data/bin` остаётся целиком; выключение — переименование в
   `bin.moved-<метка>` без стирания), путь — `Leftover`. Пропуск
   `wizard_states/state.json` — отказ `CopyTree` (`ErrStateNotCopied`) до
   продвижения копии и до маркера: обе раскладки целы. На время копирования
   старт ядра и автообновление подписок отказывают (флаг контроллера);
   после переезда лаунчер перезапускается сразу, без диалога «Data moved»:
   сводка — в лог, остаток — в `storage_leftover` settings.json нового места
   (строка в Storage, элемент очистки «moved-away data»). В режиме `Env`
   очистка удаляет только `Data/bin`, `Data/.migrated_from` и файлы логов
   лаунчера, а не каталоги, выбранные пользователем.
