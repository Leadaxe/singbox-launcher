# SPEC 103 — LX Shared Contract: единый контракт данных launcher ↔ LxBox

## Проблема

Десктопный лаунчер (Go, `core/config/subscription/`, ~18,6 тыс. строк) и LxBox
(Flutter/Dart, `app/lib/services/parser/`, ~3,4 тыс. строк) разбирают одни и те же
подписки двумя независимыми реализациями. Паритет сегодня держится дисциплиной
(SPEC 094 — порт возможностей LxBox в лаунчер, SPEC 101 — симметрия identity-хеша,
SPEC 090 — общий `#if`-язык шаблонов), но ничем не проверяется автоматически:

- каждый приём (`?ed=N`, uTLS-allowlist, reality-мусор, hysteria2 gecko, XHTTP `extra`)
  надо вносить дважды и легко забыть во втором проекте;
- одна и та же подписка может дать разный набор нод на десктопе и телефоне,
  и это никто не заметит до жалобы пользователя;
- правила, переменные и бэкапы между устройствами не переносятся: форматы
  `state.json` (v6) и `lxbox_settings.json` близки по духу, но несовместимы по форме.

## Цель

Конечные цели программы, утверждены пользователем 2026-08-19 (формулировки его):

1. Общий язык шаблонов.
2. Общий «сохранить/восстановить» (бэкапы телефон ↔ десктоп).
3. Общий язык пресетов.
4. Общее поведение, архитектура и блок-схема парсера целиком.
5. Общая схема хранения и формата JSON нод.
6. Общая логика.
7. В лаунчер вводится логика «правила → каналы → узлы» (модель каналов LxBox;
   активирует давно запланированный SPEC 087 → оформляется как **SPEC 104**).
8. DNS-группы как в LxBox (§312/§354) в лаунчере (**SPEC 105**).
9. По ходу — ревью и оптимизация архитектуры.
10. Берутся лучшие архитектурные решения обоих проектов (направление переноса
    решается по существу, не «кто первый написал»).
11. Все решения аккуратно протоколируются (**DECISIONS.md** в этой папке;
    нормативные — дублируются в contract/docs/).
12. Документация обоих проектов по парсерам и правилам приводится в порядок
    по ходу фаз (лаунчер: `docs/ParserConfig.md`, `DATA_FLOW.md`,
    `TEMPLATE_REFERENCE.md`, `WIZARD_STATE.md`; LxBox: `docs/PROTOCOLS.md`,
    `TEMPLATE.md`, `STORAGE.md`) — актуализация входит в DoD каждой фазы.
    При неоднозначной семантике параметров подписок эталон сверки — парсер
    **Happ** (D-019).

Операционные критерии (как цели 1–6 проверяются):

- **Одинаковый разбор.** Подписка (тело или share-URI), скормленная лаунчеру и LxBox,
  даёт одинаковый набор канонических узлов — проверяется общим конформанс-корпусом
  в CI обоих репозиториев.
- **Одинаковая эмиссия.** Share-URI, сгенерированный одним проектом, парсится другим
  в тот же канонический узел (round-trip между проектами, не только внутри одного).
- **Переносимые бэкапы.** Правила, DNS-настройки, переменные, подписки и отметки
  отключённых нод экспортируются с одного устройства и импортируются на другом
  без потерь — единый формат «LX Backup v1». После SPEC 104 переносимыми становятся
  и каналы.
- **Единый язык шаблонов и пресетов.** Синтаксис `@var`/`#if`/пресетов зафиксирован
  нормативной спецификацией с конформанс-фикстурами; приём, придуманный в шаблоне
  одного проекта, работает в другом без адаптации.
- **Процесс.** Новый протокол/параметр/приём сначала попадает в контракт
  (реестр + фикстуры), потом в реализации — закреплено в принципах обоих проектов.

## Решение (выбрано пользователем)

**Контрактная унификация, не кодовая.** Реализации остаются двумя (Go и Dart),
никакого Go-моста на мобиле. Общими становятся **данные и правила**:

- канонический JSON-узел (с учётом разделения outbound / endpoint);
- машиночитаемый реестр протоколов (схемы, поля, allowlist'ы, деградация);
- нормативные блок-схемы пайплайна (классификация тела, разбор, эмиссия);
- общий корпус golden-фикстур + конформанс-раннеры в обоих проектах;
- спецификация языка шаблонов v1 (ядро + расширения по проектам);
- формат LX Backup v1 поверх выровненных схем сущностей состояния.

Отвергнутые альтернативы:
- *Общий Go-парсер через gomobile/FFI* — отвергнуто пользователем: чужая сущность
  в Dart-стеке, компилируемый мост ради парсинга не оправдан.
- *Кодогенерация парсеров из спеки* — преждевременно; реестр сначала используется
  как нормативный документ и источник сверочных тестов.

## Не-цели

- Слияние кодовых баз или общая библиотека парсинга.
- Идентичный UI/UX двух приложений (унифицируется поведение данных, не экраны).
- Перенос между устройствами: выбранной ноды (живёт в `cache.db` ядра у обоих —
  уже унифицировано самим ядром), кэша тел подписок, платформенных настроек
  (tun_apps, vpn_mode, native_prefs, remote-таргеты лаунчера).
- Редизайн алгоритма identity-хеша: контракт фиксирует **текущий** развёрнутый
  скелет алгоритма (он уже байт-идентичен в обоих проектах для большинства форм
  нод). Допускается только точечное выравнивание четырёх известных классов
  расхождений (PLAN §9.A) с миграционной оговоркой: отметки затронутых нод
  истекают по штатному TTL.

## Критерии приёмки

1. В CI обоих репозиториев есть job «contract conformance», гоняющий общий корпус;
   расхождение = красный билд.
2. Эталонный набор тел подписок (URI-list, base64, sing-box config/outbound(s),
   Xray-массив, wgconf, `vpn://`) даёт в обоих проектах идентичный список
   канонических узлов (включая warnings-коды и порядок). Исключение — явно
   задокументированные by-design различия (например, схлопывание нод с разными
   SNI по `nodeIdentityKey` в LxBox): для них корпус несёт per-app override
   ожиданий со ссылкой на пункт IDENTITY.md (PLAN §5).
3. Экспорт LX Backup на десктопе → импорт на телефоне (и обратно) переносит:
   подписки (URL, tag-политика, import-правила, отключённые ноды), правила
   маршрутизации, DNS-настройки, переносимые переменные — с предсказуемой
   деградацией непереносимого (warning, не молчаливая потеря).
4. Известные накопленные расхождения (таблица в PLAN.md) закрыты фикстурами:
   каждое либо выровнено, либо явно помечено в реестре как расширение одного проекта.
5. Правило «контракт раньше кода» закреплено в принципах обоих проектов:
   в лаунчере — поправкой в CONSTITUTION.md; в LxBox — созданием аналогичного
   документа принципов (или раздела в AGENTS.md — там его сегодня нет).
