# SPEC 098 — Вкладки Local и Remote, конфиг на каждую машину

**Тип:** Feature · **Статус:** Complete · **Платформа:** все

Вкладки `Core` и `Servers` сливаются в одну — **Local**. Рядом появляется
**Remote** той же геометрии: слева список прокси выбранной машины, справа —
список удалённых машин с управлением. У каждой машины **свой** конфиг: своё
состояние визарда, свой собранный файл, свой деплой.

**Depends on:** SPEC 097 (таргет генерации, реестр машин, транспорт),
SPEC 096 (lxd), SPEC 064 (шов ProxyTransport).

---

## 1. Проблема

**Профиль один на всех.** `bin/wizard_states/remote/state.json` — единственный
файл на все удалённые машины, `bin/remote-config.json` — единственный
собранный конфиг. Роутер и VPS требуют разных конфигов (разные платформа,
gateway-роль, интерфейсы), а места есть под один. Вторая машина затирает
первую молча. SPEC 097 §5 отложил это как «формат готов — `remote/`
расширяется до именованных папок».

**Выбор машины и таргет конфига разъехались.** Дропдаун в шапке Servers
говорит, чьи прокси показывать; шаг 0 визарда — для кого собирать конфиг. Это
два независимых переключателя, и ничто не мешает собрать конфиг для роутера,
а нажать Deploy, когда выбран VPS.

**Управление размазано по трём местам.** Start/Stop и Deploy — в шапке
Servers для «текущей» машины; добавление, правка, удаление и диагностика — в
модальном окне подключения; конфиг — в визарде. Чтобы настроить одну машину,
надо обойти три экрана, и ни на одном не видно её целиком.

## 2. Целевая модель

### 2.1 Две вкладки одной геометрии

`Local` и `Remote` устроены одинаково: **слева серверы, справа управление**.
Разница только в том, чем управляем — своим ядром или списком чужих машин.
Одинаковая геометрия — не эстетика: список прокси на обеих вкладках это один
и тот же виджет с одним и тем же поведением, и пользователь не переучивается,
переходя между ними.

### 2.2 Выбор машины — клик по строке

Активная машина отмечена `●`, остальные `○`. Клик по строке переключает
транспорт, и левая половина показывает прокси этой машины. Дропдаун
`endpoint_picker` исчезает: список строк — тот же выбор, только видно сразу
всё, включая состояние каждой машины.

Пункта `Local` в списке нет — у него своя вкладка.

Выбор остаётся эфемерным (SPEC 097 §4.3): после перезапуска вкладка Remote
открывается без активной машины, левая половина пуста до первого клика. Это
сохраняет инвариант «на старте лаунчер работает со своим ядром».

### 2.3 Конфиг на машину

Каждая машина владеет **одной директорией**, в которой лежит всё её:

```
bin/wizard_states/state.json                    # local, без изменений
bin/wizard_states/<snap>.json                   # local-снапшоты
bin/rule-sets/                                  # .srs локальной машины
bin/subscriptions/                              # тела подписок локальной машины
bin/wizard_states/remote/<id>/state.json        # состояние машины
bin/wizard_states/remote/<id>/<snap>.json       # её снапшоты
bin/wizard_states/remote/<id>/config.json       # её собранный конфиг
bin/wizard_states/remote/<id>/srs/              # её .srs
bin/wizard_states/remote/<id>/subscriptions/    # её тела подписок
bin/remote-daemons/<id>/                        # её клиентские ключи (SPEC 097)
```

`<id>` — ID записи реестра (`bin/remote-daemons.json`), тот же, что уже
именует папку клиентских ключей. Одно имя на все артефакты машины — иначе
переименование или удаление оставляет сирот в разных местах.

**Строгая изоляция вместо дедупликации.** Ни `.srs`, ни тела подписок не
разделяются между машинами, хотя одноимённые файлы будут дублироваться на
диске. Причины: удаление машины должно сводиться к удалению одной директории;
GC живых тегов и живых Source.ID считается по состояниям **этой** машины, а не
по объединению всех (сегодня `collectAllStageRuleSetTags` и
`collectAllStageSourceIDs` вынуждены обходить все уровни `wizard_states/`,
чтобы rebuild одной машины не снёс файл, которым владеет только другая); и
наборы у машин расходятся — конфиг роутера и конфиг VPS включают разные
правила и часто разные подписки.

Тела подписок (`bin/subscriptions/<source-id>.raw`) попадают под то же
правило, что `.srs`, и по той же причине: сегодня они лежат в одной общей
папке, а `collectAllStageSourceIDs` считает живой набор объединением по всем
состояниям — ровно та глобальная связность, ради устранения которой
разделяются `.srs`. Оставить подписки общими значило бы сохранить нарушение
инварианта «машины не делят файлы» (§5.7) в половине пайплайна.

Локальная машина сохраняет `bin/rule-sets/` и `bin/subscriptions/` без
изменений — переносить её файлы незачем, а любой такой перенос ломает
инвариант «local-путь не меняется».

**Сигнатуры.** `GetWizardStatesDirFor(execDir, target)` получает третий
аргумент — ID машины; для `local` он игнорируется. Добавляются
`GetRemoteMachineDir(execDir, id)`, `GetRemoteConfigPathFor(execDir, id)`,
`GetRuleSetsDirFor(execDir, target, id)`,
`GetSubscriptionsDirFor(execDir, target, id)`. `GetRemoteConfigPath`
(единственный `bin/remote-config.json`) удаляется — у файла больше нет
владельца.

**Миграция.** Существующие `bin/wizard_states/remote/state.json`, его
снапшоты (`bin/wizard_states/remote/*.json`) и `bin/remote-config.json`
принадлежат единственной машине, которая уже настроена. Если в реестре ровно
одна запись — всё это переезжает в её папку. Если записей ноль или больше
одной, файлы остаются на месте и пишется warning: угадывать, чьи они, нельзя,
а потерять настроенный конфиг недопустимо.

`.srs` и тела подписок не мигрируют: `.srs` пересобираются из состояния при
первом же rebuild, тела подписок — при первом Update (а до него старый общий
`bin/subscriptions/` остаётся читаемым фолбэком, чтобы миграция не выглядела
как «подписки пропали»).

**Первое состояние машины — пустое**, не копия local. Копирование тащит чужие
источники подписок (открытый пункт SPEC 097 §6): пользователь получает на
роутере то, чего туда не добавлял, и не понимает, откуда оно.

### 2.4 Configure — визард машины

`[Configure]` открывает тот же визард, что `[ Wizard ]` на Local, но
корневой на состоянии этой машины. Шаг 0 (выбор таргета) при этом теряет
смысл как **выбор**: таргет уже задан тем, из какой строки открыли.

Отсюда следует главное: **промах «собрал для одной, задеплоил на другую»
становится невозможен по конструкции**. Кнопка Deploy в строке машины
отправляет `bin/wizard_states/remote/<id>/config.json` — другого файла у неё
нет.

**Платформа и архитектура принадлежат записи реестра, а не состоянию
визарда.** Сейчас `GOOS`/`GOARCH` живут в состоянии (`TargetSpecFromState`), а
в `RemoteDaemon` таких полей нет — при этом строка машины обязана показывать
`linux/arm64` (§3.1.4), и демон свою платформу не сообщает. Поля переезжают в
`RemoteDaemon`: задаются при добавлении и правке машины, визард читает их
оттуда и **не редактирует**. Иначе остаётся второй способ разъехаться —
собрать под архитектуру, отличную от той, что показана в строке, — и §2.4
своего обещания не выполняет.

`TargetSpec` при генерации собирается из записи реестра
(`RemoteTarget(d.GOOS, d.GOARCH)`), а не из состояния. Для local всё
по-прежнему: `LocalTarget()` из runtime.

### 2.5 Что уходит

| Что | Куда |
|-----|------|
| Вкладка `Core` | левая часть → не меняется, правая часть Local |
| Вкладка `Servers` | левая часть Local и Remote |
| `endpoint_picker` (дропдаун) | список строк на Remote |
| `endpoint_power` (Start/Stop/Deploy в шапке) | кнопки в строке машины; Start/Stop для local — блок Core |
| Область Remote в окне подключения | правая часть Remote |
| Шаг 0 визарда как выбор таргета | таргет задаётся точкой входа |
| `GOOS`/`GOARCH` как поля состояния визарда | поля записи реестра (§2.4) |

Окно подключения (`⚙` в шапке) остаётся: там настройки Clash API и локального
демона — они не про удалённые машины.

## 3. Требования

### 3.1 Обязательные

1. Вкладки `Local` и `Remote` вместо `Core` и `Servers`; порядок в строке:
   `Local | Remote | 🔍 | ⚙ | ?`.
2. Обе вкладки — двухколоночные, слева список прокси, справа управление.
3. Список прокси — **один** виджет, используемый обеими вкладками; поведение,
   сортировка, ping, переключение узла идентичны.
4. Строка машины показывает: имя, платформу/арх, адрес, статус ядра, а при
   недоступности — причину; кнопки `Configure`, `Start`/`Stop`, `Deploy`,
   правку и удаление.
5. Клик по строке делает машину активной и перезагружает список прокси слева.
6. Состояния визарда, конфиги, `.srs` и тела подписок — на машину, пути
   по §2.3.
7. Платформа и архитектура машины — поля записи реестра; визард их читает,
   но не редактирует; `TargetSpec` генерации собирается из записи (§2.4).
8. Миграция существующих файлов по §2.3 при ровно одной записи в реестре:
   `state.json`, снапшоты `remote/*.json` и `remote-config.json`.
9. Удаление машины удаляет её директорию состояний целиком и её клиентские
   ключи; диалог предупреждает, что доступ на самой машине надо отозвать
   отдельно (инвариант SPEC 097 §4.1).
10. GC осиротевших `.srs` и тел подписок работает **в границах машины**: живые
    теги и Source.ID считаются по её состояниям, удаление — только в её
    `srs/` и `subscriptions/`. Файл одной машины не удерживает и не удаляет
    файл другой.
11. Окно 1000×700 минимум (§3.2).
12. Все подписи через `bin/locale/*.json`; в коде и шаблоне — только ключи.

### 3.2 Размер окна

Главное окно — **1000×700**, это и минимум, и стартовый размер. Растянуть
можно, сжать ниже — нет: обе колонки перестают помещаться, и вместо
деградации получается каша из обрезанных подписей.

1000 берётся из измеримого: левая колонка не ужимается ниже ~420px (иначе
имена узлов схлопываются в многоточие), правой нужно ~300px на строку версии
ядра и адрес машины, плюс поля и разделитель. 700 по высоте — блок Core
занимает ~400px, ниже должно оставаться место хотя бы на несколько строк
списка.

Адаптивная раскладка (одна колонка на узких экранах) **вне scope** этой
задачи. Пользователи с экраном 1024×768 попадают впритык; менее того — не
поддерживаются. Если такие найдутся — отдельная задача, и решаться она будет
перекладыванием колонок друг под друга, а не сжатием.

### 3.3 Границы

- Массовые операции над машинами (deploy на все) — вне scope.
- Переименование машины меняет только отображаемое имя; ID и папки неизменны.
- Дедупликация `.srs` между машинами — сознательно не делается (§2.3).

## 4. Критерии приёмки

1. Две машины настроены по-разному (разные платформа и gateway); каждая
   собирает свой конфиг, `Deploy` доставляет на неё именно её файл. Проверка —
   `active_sha256` демона совпадает с хешем файла машины.
2. Переключение между машинами меняет список прокси слева; на недоступной
   машине список пуст и видна причина, а не данные предыдущей.
3. `Local` работает без единой удалённой машины в реестре.
4. Существующие `remote/state.json`, его снапшоты и `remote-config.json`
   после обновления лаунчера доступны как конфиг настроенной машины — ничего
   не потеряно.
5. Удаление машины не оставляет её файлов в `bin/`: ни состояний, ни
   снапшотов, ни конфига, ни `.srs`, ни тел подписок, ни ключей.
6. Rebuild и Update конфига одной машины не трогают `.srs` и тела подписок
   другой и не трогают `bin/rule-sets/` / `bin/subscriptions/` локальной.
7. Архитектура, показанная в строке машины, совпадает с той, под которую
   собран её `config.json`; изменить её из визарда нельзя.
8. Окно не сжимается ниже 1000×700; на 1000×700 обе колонки читаемы, подписи
   узлов не обрезаны.
9. `go build ./...`, `go vet ./...`, `go test ./...` — чисто.

## 5. Инварианты

1. **`bin/config.json` принадлежит локальному ядру** — конфиг машины туда не
   попадает никогда (SPEC 097 §7.2).
2. **`settings.json` держит одно подключение — своего демона** (SPEC 097 §7.3).
3. **UI не подменяет данные при ошибке** — пустой список честнее чужого
   (SPEC 097 §7.4).
4. **Ключи машин раздельны** — своя пара на `bin/remote-daemons/<id>/`
   (SPEC 097 §4.1).
5. **local-путь генерации не меняется** — те же секции и значения, что до
   SPEC 097 и до этой задачи; её `.srs` остаются в `bin/rule-sets/`, тела
   подписок — в `bin/subscriptions/`.
6. **Всё имущество машины — в одной директории.** Состояние, снапшоты,
   конфиг, `.srs` и тела подписок под `bin/wizard_states/remote/<id>/`;
   ключи — под `bin/remote-daemons/<id>/` (там их держит SPEC 097). Удаление
   машины = удаление двух директорий, без обхода `bin/` в поисках следов.
7. **Машины не делят файлы.** Ни `.srs`, ни тела подписок, ни конфиг, ни
   состояние. Операция над одной машиной не может изменить или удалить файл
   другой.
8. **Платформа машины — одна на всех потребителей.** Строка списка, визард и
   генерация читают `GOOS`/`GOARCH` из записи реестра; второго источника
   правды нет.

## 6. Открытые пункты (наследуются)

- `.srs` включённых пресетов на remote указывают на пути машины-сборщика;
  следует оставлять `type: remote` (SPEC 097 §6).
- Пресеты фильтруются по платформе **хоста**, а не целевой машины
  (`filterPresetsByPlatform`).
