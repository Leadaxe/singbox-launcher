# SPEC 096 — Daemon core engine (lxd)

**Тип:** Feature · **Статус:** Complete · **Платформа:** macOS

Второй движок ядра: вместо спавна `sing-box run` лаунчер управляет ядром внутри
долгоживущего системного демона `sing-box lxd` по gRPC (протокол CommandClient,
общий с Android-линией) и admin REST. Классический движок остаётся дефолтом.

---

## 1. Проблема

Классический движок запускает ядро как дочерний процесс (`sing-box run`) и
управляет им через Clash HTTP API:

- Каждая смена конфига — kill + рестарт процесса; TUN на macOS требует
  привилегий, значит запрос пароля на каждый привилегированный старт.
- Выход из лаунчера гасит VPN.
- Наблюдаемость ограничена Clash API; удалённое управление невозможно.

Ядро форка предоставляет сабкоманду `sing-box lxd` — headless-демон, который
держит ядро внутри процесса за долгоживущим управляющим каналом (gRPC + admin
REST), переживающим смену конфига. Задача — научить лаунчер работать через этот
демон как через альтернативный движок, не ломая классический.

---

## 2. Требования

### 2.1 Движок

- **D1.** Абстракция движка ядра: единый интерфейс, за которым classic (spawn) и
  daemon (lxd) взаимозаменяемы. Весь UI/трей/шорткаты/debug-API ходят к ядру
  только через активный движок.
- **D2.** Переключатель режима в настройках. Classic — дефолт. Переключение —
  только при остановленном VPN.
- **D3.** Операции с прокси (список групп, выбор узла, пинг, пул) абстрагированы
  транспортом: classic — Clash HTTP, daemon — gRPC.

### 2.2 Daemon

- **G1.** Управление и наблюдаемость по gRPC `daemon.StartedService`: группы,
  `SelectOutbound`, `URLTestOutbound`, статус, логи, пул балансировщика,
  соединения. Clash API в конфиг демона не эмитится.
- **G2.** Доставка конфига — admin REST `POST /admin/apply` (валидация
  сабпроцессом, автооткат на last-good на стороне демона). Start/Stop — `/admin`.
- **G3.** Конфиг перед отправкой демону адаптируется: относительные пути,
  которые ядро пишет (`cache_file`), абсолютизируются в каталог демона (демон
  стартует с cwd=`/`); `experimental.clash_api` удаляется.

### 2.3 Служба и сопряжение

- **S1.** Установка/удаление системного LaunchDaemon (`--service=install`),
  включая полное удаление данных (`--purge`). Привилегии — один раз на операцию.
- **S2.** mTLS-сопряжение по одноразовому приглашению `адрес#отпечаток#код`:
  авто для локальной службы, ручное (вставка приглашения) для любой.
- **S3.** Выход из лаунчера по умолчанию оставляет ядро в демоне работать;
  опция «останавливать VPN при выходе» возвращает классическое поведение.

### 2.4 Границы

- **B1.** Classic-режим не меняется: тот же spawn, Clash API, поведение.
- **B2.** Только macOS. Win7-сборка не затрагивается (весь daemon-код и gRPC —
  под darwin build-tags, в `go.win7.mod` не попадают).
- **B3.** Требует ядра, собранного с сабкомандой `lxd` (`with_lx_command`,
  релиз форка `1.14.0-lx.23+`). До релиза — локально собранное ядро; для
  пользователей нужен бамп `constants.RequiredCoreVersion`.

---

## 3. Критерии приёмки

- Переключатель Classic/Daemon в настройках; classic работает как прежде.
- В daemon-режиме: установка службы (один пароль), сопряжение mTLS, Start/Stop и
  смена конфига без пароля; список нод, переключение, пинги, пул и логи — по
  gRPC; трафик-график — по gRPC; выход из лаунчера оставляет VPN работать.
- Win7-сборка компилируется без gRPC/daemon-кода.

---

## 4. Ревизия модели владения (2026-08-09)

Синхронно с ревизией SPEC 057 форка: секрет демона больше не живёт в каталоге
лаунчера. Дом демона — его state-dir, лаунчер — просто mTLS-клиент.

- **S2 уточнено.** Bootstrap сопряжения: `--service=install --tls` сам пишет
  `daemon.json` (listen/tls/секрет) в state-dir демона и после старта службы
  печатает одноразовое приглашение — лаунчер извлекает его из вывода
  привилегированного вызова (`extractInvite`) и энроллится. В лог лаунчера
  вывод пишется с вырезанным приглашением (`redactInvites`). Пере-сопряжение
  («Pair local») — привилегированный `sing-box lxd client add` (CLI сам
  находит state-dir службы и секрет в её daemon.json), один запрос пароля.
- **Секрет.** `bin/daemon/secret` больше не создаётся (легаси-файл подчищает
  `UnpairDaemon`); `settings.json.daemon_secret` для локальной службы пуст и
  нужен только для сопряжения с plain-h2c демоном (dev). Доверенный
  клиентский сертификат — полный мандат admin/gRPC-плоскостей
  (bearer-or-cert на стороне демона); `AllowUnpinnedTLS` и `MintInvite`
  удалены из lxdclient — пин обязателен всегда.
- **G3 уточнено.** Каталог для `cache_file` берётся из паспорта демона
  `GET /admin/info` (`state_dir`) перед каждым apply; историческая константа
  `/Library/Application Support/sing-box-lxd` — только fallback для демона
  старой сборки. Паспорт (версия, каталог) показывается в статусе секции
  настроек.

## 5. Ревизия UX (2026-08-09): терминальная модель + окно подключения

- **AEWP выпилен полностью.** `AuthorizationExecuteWithPrivileges`-путь
  (кнопки Install/Uninstall/Remove all/Pair local, priv-exec хелпер
  `--priv-exec` c setuid(0), `RunPrivilegedProgramAndWait`, done-маркеры)
  удалён. Все привилегированные операции — готовые sudo-команды, которые
  пользователь выполняет сам: панель показывает их с кнопками «копировать» и
  «открыть в терминале». Приглашение сопряжения печатается командой установки
  (или `lxd client add`) и вставляется в поле руками. Kickstart после
  обновления ядра — диалог с командой вместо фонового привилегированного
  вызова. Классический TUN-запуск (`RunWithPrivileges`) не затронут.
- **Окно «Настройки подключения»** (⚙ на Servers, `Application.NewWindow`,
  не попап) с вкладками: **REMOTE** — прежний remote-override Clash
  (SPEC 064, перенос из модального диалога), **LOCAL** — движок ядра.
  Радио Process/Daemon: радио — намерение (выбор Daemon показывает панель
  с командами даже до сопряжения; фактический движок включается, когда
  сопряжение готово, и отражается в статусе). Секция демона из общих
  настроек удалена.
