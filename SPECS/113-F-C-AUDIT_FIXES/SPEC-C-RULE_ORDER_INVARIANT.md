# SPEC 113-C — Инвариант оси порядка правил

Закрывает находки аудита: C6 (перекос безымянных правил), M7 (дроп у
системного правила уводит выше якорей), минор movedPos==0 (равные номера).

## Принцип (решение пользователя 27.08)

**Массив правил в файле всегда отсортирован по оси.** Двойной порядок —
файловый порядок слайса vs ось order_num — упраздняется как источник багов.
Ни один потребитель не имеет права полагаться на файловый порядок как на
самостоятельную информацию.

## 1. Инвариант на записи

- Всякая перенумерация оси завершается пересортировкой массива:
  `renumberImportedRules` (core/backup/import.go:451) после раздачи номеров
  сортирует слайс; `NormalizeRuleOrder` / `MarkRuleOrder` — так же.
- Сохранение (`SyncRulesByOrderToStateRulesV6` и смежные) эмитит правила
  в порядке оси. Если модель подаёт иначе — сортировать на выходе,
  стабильно.
- Тест-инвариант: load → save → массив в файле отсортирован по order_num
  (стабильно, при равных номерах исходный порядок).

## 2. Очередь безымянных — в порядке оси

`RuleOrderFromStateRulesV6` (ui/configurator/models/preset_ref_sync.go:121):
`crQueue` строится обходом customRules В ПОРЯДКЕ ОСИ (та же стабильная
сортировка, что у потребления через `SortRulesByNum`), а не в файловом.
После п.1 порядки совпадают всегда, но очередь обязана быть корректной и
на кривом входе (файл, собранный чужой рукой): построение и потребление —
один комparator по построению.

Тест (падает на старом коде): два безымянных inline-правила, файловый
порядок обратен оси → load → save → номера НЕ перекрестились, порядок оси
сохранён.

## 3. M7: клэмп пользовательской зоны

`applyAxisAfterMove` / `PlaceRuleAfter` (ui/configurator/models/rule_order_axis.go:107):
дроп вплотную под правило с номером ниже `UserRuleNumStart` (системное 0,
якоря 950–990) даёт `want = сосед+1` → правило покидает пользовательскую
зону 1000–1100 навсегда (`NextUserRuleNum` его не видит). Фикс: want
клэмпится к `UserRuleNumStart` снизу. Зоны 1–949 не существует.
Тест: система(0), якоря 950/960, юзерское 1000 → дроп под систему →
номер ≥ UserRuleNumStart, якоря не тронуты.

## 4. movedPos == 0: без равных номеров

Ветка rule_order_axis.go:99–103 отдаёт перетащенному номер соседа снизу,
оставляя дубль номера и полагаясь на стабильность сортировки. Заменить на
честный сдвиг (тот же ленивый механизм PlaceRuleAfter, D-053а: до первой
дырки, якоря не трогаются). Исчерпанная зона (все номера заняты до
UserRuleNumEnd) — допустимо ужать шаг, но не выдавать равные номера двум
правилам, пока в зоне есть свободные значения.

## Рефакторинг попутно

- Имена: функции, говорящие «V6»/«legacy» без нужды, привести к модели
  «ось порядка» (RuleOrderAxis) — но только в затрагиваемых файлах
  (preset_ref_sync.go, rule_order_axis.go, rule_slot.go), без расползания.
- Комментарий-закон об инварианте «файл = ось» — в одном месте
  (rule_order_axis.go, package comment), остальные ссылаются.

## Запреты

- Массовая перенумерация при d&d по-прежнему запрещена (D-053а) — ленивый
  сдвиг, якоря не двигаются.
- Системные правила (order 0) не двигаются и над ними ничего не встаёт.
