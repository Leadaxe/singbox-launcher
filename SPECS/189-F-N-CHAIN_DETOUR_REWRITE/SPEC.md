# SPEC 189 — Лаунчер под ядро с SPEC 165: цепочка как перезапись `detour`, `lx.detour`, итоговый конфиг узла

Пара к SPEC 165 ядра sing-box-lx (ветка `lx-spec165-chain-detour`, войдёт в
`v1.14.4-lx.37-rc.2`). Ветка лаунчера `spec189-chain-detour-rewrite`; в `develop`
вливается после выхода rc2 и слова владельца.

## 1. Проблема

Ядро с SPEC 165 перестаёт создавать копии узлов цепочки: узлу на позиции ≥ 1 при
загрузке ставится `detour` на внутренний хоп `<цепочка>#<i>`. Для лаунчера это
ломающее изменение:

- **ошибки загрузки** в том, что лаунчер пишет сейчас: `idle_timeout`,
  `strip_evasion`, `strip` в теле цепочки; корневой `lx.mtu_align` (переехал в
  `lx.detour.mtu_align`); фиксированный локальный порт у
  узлов на позициях ≥ 1 (WireGuard `listen_port`, Tailscale `listen_port` /
  `relay_server_port`, OpenConnect `dtls_local_port` — ALGORITHM К5 ядра);
- **удалённые RPC**: `GetChains`, `GetChainCloneConfig`; у `SetChainPositionEnabled`
  нет `warmupError`; в статусе позиции нет полей звеньев (`clone`,
  `clonesCreated`, `clonesEvicted`, `liveClones`);
- **конфликты и кольца** — ошибка загрузки всего конфига: узел или группа в двух
  местах цепочек, кольцо через хоп, локальный порт узла внутри цепочки, занятый тег
  хопа, rewrite с detour (§2.1);
- **новые исходящие** типа `chain-hop` в списках ядра.

Отдельно (решение владельца 26.11): JSON узла в окне Info сейчас печатается из
конфига лаунчера (`prettyNodeJSON(node.Raw)`) и не показывает, что ядро сделало с
узлом. С rc2 у ядра есть `GetOutboundConfig(tag)` — `original`, `effective`,
`changes`.

## 2. Решение

### 2.1 Эмиссия цепочки

- Тело цепочки в конфиг: `outbounds`, `rewrite`, `interrupt_exist_connections`.
  `idle_timeout`, `strip_evasion`, `strip` не пишутся.
- Редактор цепочки (`ui/configurator/tabs/source_chain_tab.go`,
  `source_edit_window.go`): поля «Idle timeout», «Strip evasion», каталог `strip`
  убираются.
- State и бэкап: ключи снимаются при загрузке и импорте с кодом предупреждения
  (Р1). Это изменение контракта: тело цепочки в бэкапе общее с LxBox
  (`contract/registry/protocols/chain.json`, `schema/source_chain.schema.json`,
  `backup.schema.json`, корпус `direction/chain_strip_and_timeout`,
  `backup/chains_roundtrip`, `backup/v10_*`). Из `chain.json` уходит и `__dialer`:
  у `ChainOutboundOptions` ядра (rc.1 и SPEC 165) полей дозвона нет.
- **Решение владельца 26.11: клиент не допускает колец и конфликтов цепочек** —
  ядро понятных сообщений не даёт. Одна проверка `config.ChainDetourProblems`
  (сверена с ядром d9fc75468) для сборки и редактора:
  - одно место на тег: узел или группа, достижимые с позиций цепочек (все члены
    групп любой вложенности, кроме direct/block), не нужны двум местам, из которых
    хотя бы одно — позиция ≥ 1 (`chain_detour_conflict`); общий вход двух цепочек
    допустим;
  - кольцо: узел входа внутри группы позиции выше (`chain_detour_ring`) или свой
    detour нижней позиции в узел выше (`chain_detour_ring_detour`);
  - фиксированный локальный порт у узла позиции ≥ 1 (`chain_hop_local_port`);
  - тег хопа `<цепочка>#<i>` занят (`chain_hop_tag_taken`);
  - rewrite меняет detour (`chain_rewrite_detour`; редактор rewrite отмечает строку
    `detour` сразу).
  Сборка снимает цепочку (из пары — позднюю) с кодом в отчёт; редактор цепочки
  показывает те же тексты и не даёт сохранить, по графу последней сборки модели.
  Тексты подсказывают, что скопировать. Поля
  привязки сокета — не ошибка (ядро показывает их в `GetOutboundConfig` записями
  `lx.detour`), сборка их не трогает.
- Копии узлов и групп лаунчер сам не собирает (решение владельца 26.11): ошибка в
  редакторе с подсказкой, что скопировать.
- Правила действуют, только когда ядро цели переписывает цепочку: версия не ниже
  `min_core` блока `lx.detour` реестра или неизвестна. Ядру старше rc2 (удалённая
  машина) конфиг уходит как раньше.

### 2.2 `lx.mtu_align` → `lx.detour.mtu_align`

Переменная шаблона `mtu_align` остаётся. Шаблон пишет и `lx.mtu_align`, и
`lx.detour.mtu_align`; гейт ядра оставляет один (Р2).
Фильтры `lx.detour.strip` лаунчер не пишет: без ключа ядро включает весь каталог,
это и есть нужное поведение. `except_outbounds` — тоже не пишется (UI нет).

### 2.3 gRPC

- `internal/daemonpb` — по тегу rc2 (`SYNC_REV`); до тега — по ветке ядра.
- Состояние цепочки — `GetChainStatus(tag)` вместо `GetChains`. Теги цепочек
  лаунчер знает сам (окно Info открывается по тегу; список — из своего конфига или
  у удалённой машины из `GetRunningConfig`).
- `SetChainPositionEnabled` — только ошибка.
- Debug API `…/chains`: поля звеньев уходят из ответа.
- Ядро старше rc2 (удалённая машина): `GetChainStatus` нет, а клиентского `GetChains`
  в сгенерированном коде больше нет — секция цепочки в окне Info у такой машины не
  рисуется (видимая потеря до обновления ядра машины; Deploy ставит ядро пина).

### 2.4 JSON узла из ядра

Вкладка JSON окна Info берёт узел у работающего ядра через `GetOutboundConfig(tag)`
по gRPC демона — тот же канал, что у `GetPool`, одинаково для своего демона и
удалённой машины. CLI `sing-box api` не подходит: нужен локальный бинарь, до
удалённой машины не дотягивается, а в classic-режиме ядра-демона нет вовсе.

- По умолчанию — `effective`; переключатель на `original`; ниже — список `changes`.
- У хопа (`chain-hop`) — только `effective`, без переключателя и списка.
- Ядро не отвечает (classic, ядро старше rc2, узла нет в работающем конфиге) — прежний
  вид из конфига лаунчера с подписью источника.
- Весь итоговый конфиг — `GetEffectiveConfig`: кнопка в окне рантайма ядра рядом с
  текущим `GetRunningConfig` (если он там показывается) — уточняется в PLAN.

Макет — Р3.

### 2.5 `chain-hop` в UI

Исходящие типа `chain-hop` не показываются в списках узлов и групп (по типу, не по
форме тега).

### 2.6 Под `impair` ничего

Решение владельца 26.11: ни UI, ни генератора. Теги сборки ядра лаунчер читает из
`sing-box version`, не пинит.

### 2.7 Пин

`constants.RequiredCoreVersion = "1.14.4-lx.37-rc.2"` — когда выйдет тег.

## 3. Развилки владельца

**Р1. Сохранённые `idle_timeout` / `strip_evasion` / `strip` в state. Решено по умолчанию (26.11): снимаются.**
Предложение: снимать при загрузке state и импорте бэкапа (код предупреждения в
журнале), не писать. Удалённая машина со старым ядром получит дефолты ядра
(простой 5 мин, каталог `strip` по умолчанию) — разница незаметна.
Альтернатива — хранить и писать только старым ядрам (тот же `max_core` для полей
тела узла).

**Р2. Ключ, который новое ядро запрещает, а старое знает. Решено по умолчанию.**
В реестре есть только `min_core` (ключ появился) и `forbidden` (запрещён всегда).
Предложение: новый примитив `max_core` — первая версия ядра, где ключа уже нет;
гейт снимает ключ, когда версия исполнителя ≥ `max_core`. Шаблон пишет и
`lx.mtu_align`, и `lx.detour.mtu_align`; `lx.mtu_align` получает
`max_core: 1.14.4-lx.37-rc.2`, `lx.detour` — `min_core: 1.14.4-lx.37-rc.2`.
Версия неизвестна — ключ с `max_core` снимается (как `forbidden`): иначе конфиг
несёт оба ключа и негоден ни для какого ядра; лаунчер ставит машинам ядро своего
пина. У своей машины версия известна всегда, у удалённой — из паспорта демона.
Локальная проверка конфига удалённой машины своим ядром (issue #161,
`ui/configurator/presentation/draft_reject.go`) проходит через тот же гейт под
версию **своего** ядра — иначе конфиг для старого ядра машины не прошёл бы `check`
у нового локального.
Изменение контракта: `contract/VERSION`, changelog, `TASKS_LXBOX.md` (LxBox таблицу
не исполняет — ядро всегда равно пину, параграф информационный).
Альтернатива без нового примитива: писать только `lx.detour` с `min_core` rc2 —
ядро старше rc2 тогда теряет недефолтный режим (`fill`/`off`) и работает на `clamp`.

**Р3. Макет вкладки JSON. Сделано по макету (26.11), смотрит владелец.**

```
[ Details ] [ Network ] [ Diagnostics ] [ JSON ]
 (●) Effective  ( ) Original                    [ Copy JSON ]
 ┌───────────────────────────────────────────────────────────┐
 │ {                                                         │
 │   "type": "wireguard",                                    │
 │   "tag": "NL-FREE#114",                                   │
 │   "detour": "c-proton#0",                                 │
 │   "mtu": 1380, …                                          │
 │ }                                                         │
 └───────────────────────────────────────────────────────────┘
 Changes by the core (2)
   detour   o-ru → c-proton#0      chain c-proton, position 1
   mtu      — → 1380               MTU alignment
 From the running core
```

Без ответа ядра — только JSON из конфига и строка «From the launcher config: the
core does not report this node» (без переключателя и списка).

## 4. Что сделано иначе, чем в первом черновике

- JSON узла: источник подписан внизу вкладки; переключатель Effective / Original
  появляется только когда ядро ответило и у узла есть `original`.
- Весь итоговый конфиг — вкладка **Effective config** в окне Core runtime (отдельного
  показа `GetRunningConfig` в UI не было).
- Список цепочек для debug API `/chains` берётся из `GetRunningConfig` (исходящие типа
  `chain`), состояние каждой — `GetChainStatus`.

## 5. Критерии приёмки

1. Конфиг цепочки, собранный лаунчером, проходит `sing-box check` ядра ветки SPEC 165
   (и rc2, когда выйдет) и ядра rc.1 для удалённой машины со старым ядром; конфиг
   удалённой машины на rc.1 проходит локальную проверку ядром rc2.
2. Ни одного ключа из §1 «ошибки загрузки» в конфиге для ядра rc2; конфликт
   перехвата снимает одну цепочку с кодом, а не валит конфиг.
3. Сборка `go build ./...`; один интеграционный тест сборки цепочки под rc2 (гейт по
   версии ядра); полный прогон — CI.
4. Окно Info: секция цепочки и вкладка JSON на ядре rc2 — смотрит владелец.
5. Контракт: изменения реестра с бампом версии, changelog, параграф
   `TASKS_LXBOX.md`; release notes.
